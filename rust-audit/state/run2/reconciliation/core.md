### 1.2 The fee-cap sub-claim (F-CORE-060 vs F2-CORE-060) — settled

Run 1 measured "the cap bypassed ~28,700×"; run 2's R3 and Critic say the cap is applied once to the fresh estimate and the _ratio_ is preserved through bumps. **Both are correct, about different quantities; the report should say so rather than pick one.**

- `cap_priority_fee` (`crates/core/src/tx/fees.rs:12-31`) computes `base_fee = max_fee − tip` **of the fresh estimate** and caps the tip at `base_fee · c / (1 − c)`; it is called exactly once per block, inside `fees()` (`tx/mod.rs:326-340`), never after `bump` (`tx/types.rs:64-66` calls `fees::bump(estimate, self.fees())` afterwards). Run 2's algebra — if `p_f ≤ c·mf_f` and `p_prev ≤ c·mf_prev` then `max(p_f, 1.1·p_prev) ≤ c·max(mf_f, 1.1·mf_prev)` — holds, so **tip / maxFeePerGas stays ≤ c** through any number of bumps. Checked against run 1's measurement: 201,207 / 4,238,607,810,118 = 4.7 × 10⁻⁸ ≪ 1 %.
- What the bump does _not_ preserve is the relation to the **chain's base fee**, which is the only economically meaningful reading and the one the handbooks sell ("protecting against runaway estimates", `docs/validator-handbook.md:65`). At Anvil's real base fee of 772 wei and `c = 1 %` the cap admits `772 · 10,000 / 990,000 = 7` wei; run 1 observed 201,207 wei, i.e. **28,744×** the cap (re-derived this pass). After bumping, `mf − p` is no longer the base fee, so the ratio bound is a bound on nothing.
- Executed anchor at `fe9e84c`: `cargo test -p safenet-core --lib -- tx::fees tx::tests::failed_replacements` — 4 passed (`state/run2/logs/rec-core-fees-test.txt`), pinning the ×1.1 step (210/10 → 231/11) and the cap arithmetic run 2 cites.
- Two bump cadences, both real: the **underpriced-rejection arm** records `Submission { block: None, .. }` (`tx/mod.rs:277-282`), so `stale_submissions`' `submitted_at IS NULL` predicate (`tx/storage.rs:296-297`) makes the row stale on **every** block (run 1's per-block rate, measured 1 bump/nonce/block over 80 blocks); the **accepted arm** records the block, so the row is stale every `blocks_before_resubmit` = 2 blocks (run 2's rate, ×311.9 after 60 bumps in 120 blocks).

Resulting wording for the canonical F-CORE-060: "`priority_fee_cap_percentage` is a ratio of the transaction's own `maxFeePerGas` and is preserved through bumps; it never bounds the tip against the chain's base fee once the ratchet runs (measured 28,744× the base-fee-derived cap), and no absolute ceiling exists." Severity **High 98** stays: the underpriced arm needs only one underpriced rejection to start (a foreign transaction at the nonce, a stricter node, a floor behind the pool — run 1 Phase 8; the restored-backup starter is out of scope under A17, Section 3) and thereafter is unbounded except by balance, which is §8's "unbounded fund drain through gas"; run 2's accepted arm alone would be Medium (it needs an independent blocking condition) and is carried as the second trigger.

## 4. Team questions in this crate

### 4.1 F-CORE-033 (@nlordell): "I would expect the transaction deadline to prevent this fan-out."

**Answer: it does not. The transaction deadline bounds the transactions, not the engine-check effects that precede them.** Evidence from run 2 at `fe9e84c`:

1. The effect is emitted unconditionally on `TransactionProposed`: `crates/sentinel/src/service.rs:137-144` (`F2-SEN-005` row 1, `F2-CORE-035` row 4) — no comparison against any deadline, and the effect carries `block` but not the request's deadline (`crates/sentinel/src/effect.rs:21-25`, F2-SEN-005 Critic-after-QA note).
2. Deadlines are consulted only in `handle_block_advance` on `Message::NewBlock`; a warp page delivers `Message::Event` only — no `NewBlock` (`crates/core/src/state/mod.rs:173-181`, `200-239`; `F2-CORE-035` row 7). So during a catch-up over a busy range every proposal in the page (up to `block_page_size` = 100 blocks) is checked, including those whose `commit_deadline` already passed during the downtime. R2's Critic adds that a single live `Logs{n}` with M proposals spawns M tasks through the same path.
3. The only per-effect bound is `engine_timeout` ≈ ¾ · (`voting_window` − 1) · block time (`crates/sentinel/src/main.rs:50-62`; ≈ 371 s with the sample config on Gnosis). It bounds each check's duration, not the number in flight.
4. Where the deadline _does_ act: the follow-up `ApproveToken`/`Commit` rows carry `expires_at = commit_deadline` (`service.rs:226-242`) and `next_transaction` skips expired rows at allocation (`crates/core/src/tx/storage.rs:150-155`). An expired check's verdict is therefore discarded at the queue — after the engine work was done — and only while the row is still unallocated (F-CORE-064 / F2-CORE-064).
5. Nothing in the `3ec8bc5` → `fe9e84c` merge (#914) adds a gate before the effect: R7Δ's re-validation of F2-SEN-005 reads "one `EngineCheck` per proposal (`service.rs:137-144`, unchanged)".
6. Executed evidence for the downstream cost: `poc/F2-SEN-005` drives the real `TransactionQueue` (16 in flight, FIFO) — reveals starve behind commits from ≥ 8 proposals per block, 124 of 300 commitments slashable at 10/block; re-run at `fe9e84c` "narrowed, not fixed" (F2-SEN-005 QA-Δ). Branch (i), engine saturation, is unexecuted in both runs (engine out of scope).

Remediation both runs converge on: a concurrency cap in `EffectManager` (F-CORE-033 option 1 = F2-CORE-035 option 1 = F-SEN-004 option 1), plus either passing the request deadline into the effect so expired checks resolve `Unknown` immediately (F2-SEN-005 option 1 with QA's correction) or delivering a synthetic `NewBlock(to)` at the end of each warp page so deadline pruning runs before the next page's effects spawn (F2-CORE-035 option 3 — which is also the answer to the F-SEN-003 design question). Note run 1 QA's caveat: a queued-but-unspawned effect is lost on shutdown exactly like an in-flight one, so the cap's pending queue should be the same structure as any durable pending-effect set (F-CORE-031 option 1 / F2-CORE-030 option 1).

### 4.2 F-CORE-067 (@rmeissner): "they will have different nonces and one of them will revert, right?"

**Yes — confirmed against the merged contract.** At `fe9e84c` `contracts/src/libraries/SentinelOracleCommitments.sol:92-96` reads `require(commitHash != bytes32(0), InvalidCommitHash()); require(self.commitments[requestId][sentinel].vote == SentinelOracleCommitment.Vote.NONE, AlreadyCommitted());` and the first commit writes `vote = PENDING` (`:96`); a reveal moves it to `APPROVED`/`DENIED` (`:120`). A duplicate `commit` therefore reverts `AlreadyCommitted()` at every later stage — the `checkNotCommitted`/`commitHash == 0` form run 1 cited is superseded with an identical outcome (F2-SEN-007 R7Δ and C2-SEN-Δ, F2-CORE-032 row 8). The new `InvalidCommitHash` path is unreachable from the sentinel (its hash is a `keccak256` output). Run 1's Phase 8 observed exactly this on the real binary: nonces 2 and 3 in the same block, the duplicate `commit` reverting with `0xbfec5558`.

Five qualifications the team should carry with the "yes":

1. **The paired duplicate `approve` succeeds** (a redundant allowance write, full gas), so per replayed request the cost is one successful and one reverted transaction, two nonces, two of the 16 in-flight slots for a block.
2. **The revert is invisible to the service.** Execution is inferred from the account nonce alone (`tx/mod.rs:185-197`, `tx/storage.rs:224-231`), so the reverted duplicate is marked executed and nothing is logged or metered (F-CORE-063 / F2-CORE-061; F2-CORE-067).
3. **It is not always just gas.** Run 2's F2-CORE-030 ordering extension (executed) shows the replayed duplicate `Commit` is what leaves the rebuilt entry at `self_committed = false` when the resume is discarded — the duplicate sits on the bond-loss path of F-SEN-001 / F2-CORE-030. And for the validator, F-VAL-065's replayed `Sign` is not a revert: it burns a nonce sequence for the whole group (REC-VAL's row). That is why the core finding stays Medium.
4. **The surface grew with the merge.** At `fe9e84c` the sentinel emits `Claim` from four log-keyed handlers with `expires_at: None` — the one row class the queue never prunes (F-CORE-067 RV-SEN; F2-CORE-063 row 8), so a restart replays more duplicates than at `2893917`.
5. **The fix must be keyed on identity, not calldata.** A `request`-keyed dedup would drop a legitimately repeated `approve(oracle, bond)` and fail the following `Commit`; key on `(block hash, log index, action kind)` with `INSERT OR IGNORE` on a `UNIQUE` column (F2-CORE-063 Critic and QA), and retain the key beyond the row's lifetime or fix F-CORE-063 first (F-CORE-067 QA).
