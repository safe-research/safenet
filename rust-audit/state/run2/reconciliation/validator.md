## 4. Team question — `F-VAL-005` "this should be fixed with the prune refactor" (@rmeissner)

**Answer: fixed for the trigger the audit reproduced; not fixed for two residual paths, one of which is by design and documented, the other a new ordering defect run 2 executed.**

What the refactor changed (`#909 8b88f4a`, `#910 c87c054`; all at `fe9e84c`):

1. **Deletion is no longer immediate.** `ReconcileGroupSecrets` now carries the block it was computed for (`service/effect.rs:60-63`) and calls `schedule_group_secrets_deletion(block, &retained)` (`:241-244`), which only _schedules_: `UPDATE <table> SET delete_at_block = CASE WHEN group_id IN (…) THEN NULL ELSE COALESCE(delete_at_block, <block>) END` (`secrets/store.rs:381-411`). Rows are collected later by `prune_scheduled_secrets(safe)`: `DELETE FROM keygen_secrets WHERE delete_at_block <= ?` (`store.rs:356-375`), invoked from `housekeeping` (`effect.rs:278-308`) once per `BlockUpdate::New` with the driver's `safe` block (`core/driver.rs:257-264, 292-294`).
2. **Reconciliations are ordered by a stored marker.** `INSERT INTO group_secret_reconciliation … ON CONFLICT (id) DO UPDATE SET block = excluded.block WHERE excluded.block >= group_secret_reconciliation.block RETURNING block` (`store.rs:323-328`); a request below the marker returns `false` and the effect handler returns `Resume::Noop` without touching schedules or generators (`effect.rs:245-251`). Executed at `fe9e84c`: `reconciliation_below_the_last_accepted_block_is_ignored`, `schedules_absent_groups_and_unschedules_retained_ones`, `collects_only_secrets_scheduled_at_or_before_the_safe_block` all pass (`state/run2/logs/REC-VAL-store-tests.txt`).

Why that closes the reproduced trigger. `F-VAL-005`'s live reproduction was a reorg of ≤ `max_reorg_depth` blocks back past the epoch-1 `KeyGen` block with no restart: the state rolled back to a snapshot in which `state.rollover` no longer named the group, `NewBlock` for the re-indexed block was applied before that block's logs (`core/state/mod.rs:190-200`, unchanged), and the old `retain_keygen_secrets` deleted the row before the `KeyGen` log was replayed. At `fe9e84c` the replayed `NewBlock`s carry block numbers **below or equal to** the stored marker: those below are ignored outright; the one equal to the marker recomputes the set from replayed state — and even where a group is scheduled, its row is not collected until `safe >= schedule block`, by which time the re-included `KeyGen` log has been replayed and the group's next reconciliation sets `delete_at_block = NULL`. Run 1's own AS-PRUNE re-run on the branch observed exactly this: reconciliations at blocks 8–10 ignored on both validators, epoch-1 commitments identical before and after the reorg, no `IncorrectCommitment` (`F-VAL-005` § In-flight impact). The `store_keygen_secrets` insert-or-return contract that the fix relies on is unchanged (`store.rs:176-212`; test `store_keygen_secrets_does_not_overwrite` passes).

What is **not** fixed:

- **Absence longer than `max_reorg_depth`** (`F-VAL-068` D2). If the group's `KeyGen` log is re-included more than `max_reorg_depth` blocks after it was scheduled, `safe` passes the schedule block first, the row is collected, the replayed `KeyGenSetup` samples fresh secrets, and the own commitment fails `IncorrectCommitment` exactly as before. The module doc concedes this: "Block numbers order reconciliations but do not identify chain branches, so a deep rollback or a restart replaying past where a group was dropped can still collect material a ceremony needs" (`store.rs:38-41`). This is a design decision — deletion bounded by the same `safe` boundary snapshots are pruned to — and is recorded as `known`, Informational.
- **The restart-window ordering race** (`F2-VAL-035`, Medium 78, E1). The driver spawns the block's `ReconcileGroupSecrets` (`driver.rs:278`) and then awaits the prune inline (`driver.rs:292-294`) with no join between them. No housekeeping runs during a catch-up warp, so the first live block after a restart arrives with `safe = latest - max_reorg_depth` already past any schedule the previous process wrote more than `max_reorg_depth` blocks before the new head; if the replayed branch still needs that group, the reconciliation would cancel the schedule but the inline prune usually wins. QA2-XC executed the driver's exact construction on the real `Handler`/`SecretStore`: **secret lost in 19 of 20 rounds** under the precondition (`state/run2/coverage.md` §8 item 3, `poc/F2-XC-050/coverage-7.3`). `F-VAL-068` D3 (`max_reorg_depth` 0 or 1: `housekeeping(B+1)` runs inline before `Reconcile{B+1}` can cancel a same-block schedule) is the small-depth instance of the same ordering. The enabling condition from run 1 — retention set computed inside `NewBlock`, before the block's logs — is untouched (`state/preprocess.rs:108-121`; `core/state/mod.rs:190-200`).
- **Two adjacent defects the refactor introduced or left**, distinct from `F-VAL-005` but on the same path: the below-marker early return now happens **before** `generator.retain`/`generator.start` (`effect.rs:245-256`), so after a short-outage restart no nonce stream exists until the reconciliation for the marker block, and every `NonceTree` in that window fails (`F2-VAL-031`, Medium 80, `F-VAL-068` D1); and the failed `NonceTree` still leaves the phantom reservation that is counted as capacity (`F2-VAL-030` / `F-VAL-030`, unchanged, `state/preprocess.rs:85-103, 231-252`).

**Suggested reply to the thread:** "Confirmed fixed at `fe9e84c` for the case the audit reproduced (reorg within `max_reorg_depth`, no restart): reconciliations are ordered by the stored marker and collection waits for `safe`, and the store tests pin it. Two residuals remain: (1) absence beyond `max_reorg_depth` still loses the ceremony — documented in `store.rs:38-41`, we record it as known; (2) the driver spawns the reconciliation and prunes inline (`driver.rs:278` vs `:292-294`), so on the first live block after a restart a schedule the old branch wrote is collected before the replayed branch's reconciliation can cancel it — executed, 19/20 rounds (`F2-VAL-035`). A synchronous first reconciliation on resume, or awaiting the reconciliation before `housekeeping`, closes (2); the same ordering fix also covers `F2-VAL-031`'s cold-generator window."

`F-VAL-005` ledger status: **Fixed by merge (#909/#910) for the in-scope trigger; residual (1) Informational `known`, residual (2) carried under `F-VAL-066` / `F2-VAL-035` Medium 78.**
