## Hypotheses considered and rejected (with the refuting citation)

1. `Error::UnexpectedBlockUpdate` reachable through `Watcher` — rejected: `on_block_update` is called only after `next_logs()` returned `Ok(None)`, i.e. the event watcher is `Idle` (`crates/core/src/index/mod.rs:86-95`, `events.rs:281-283`).
2. `Error::UnexpectedBlockInvalidation` reachable — rejected: `revalidate_last_block` returns `Some` only when the queue front is `New { k+1 }` or the queue is empty, and `rposition` then selects the block the event watcher is fetching (`blocks.rs:486-502`); with a `Warp`/`Uncle` at the front it returns `Ok(None)` (`blocks.rs:488`); in the warp-at-startup case `recent` starts above the warp range so no candidate exists (`blocks.rs:271-278`, `297-313`).
3. `expect` at `blocks.rs:336` reachable — rejected: the scan loop runs at least once because `safe = latest.saturating_sub(depth) <= latest_number` (`blocks.rs:246`, `298`).
4. `expect` at `blocks.rs:457` — rejected: guarded by `blocks.rs:453`.
5. `expect` at `events.rs:342` — rejected: `div_ceil(2)` of a value >= 1 is >= 1.
6. Overflow at `events.rs:332` (`query_to_block + 1`) — rejected: reached only when `query_to_block != to_block`, and `query_to_block <= to_block` by construction (`events.rs:310`, `326`).
7. A queued block update lost to cancellation of the `next_input` select — rejected: `BlockWatcher::next` mutates state only after its last `.await` (`blocks.rs:418-469`), `Watcher::next` calls `on_block_update` synchronously after the await (`index/mod.rs:93-94`), `revalidate_last_block` mutates after its await (`blocks.rs:504-533`), and `EventWatcher` sets `step` only after `fetch_logs` completes (`events.rs:324-325`, `382-383`). The only pre-await mutation is `self.pending.timestamp_ms += self.block_time` (`blocks.rs:414`), whose loss or persistence only shifts the next poll.
8. Prune deleting the anchor a watcher uncle needs — rejected: the watcher never uncles at or below `safe` (it errors instead, `blocks.rs:435-439`), and `prune` keeps `>= safe` plus the newest row (`state/storage.rs:152-156`). Driver call site not re-read (R2).
9. Same event signature shared by two contracts watched by one service (mis-attribution even with an address check) — rejected: the `event` declarations in `crates/validator/src/bindings.rs` and `crates/sentinel/src/bindings.rs` share no name across contracts within a service (grep output recorded this session).
10. Out-of-order or duplicate logs from a node corrupting state — rejected: `decode_and_sort` sorts by `(block, index)` (`events.rs:517`) and the state machine rejects non-strict order or out-of-range logs with `BadUpdate` (`state/mod.rs:207-211`) — fail-stop, not corruption (exit code is R2's).
11. `may_contain_log` address/topic independence being a false-negative bug — rejected: documented as conservative (`bloom.rs:19-22`), and the function is unused in production.
12. `compute_logs_bloom` disagreeing with header blooms — rejected: alloy's `logs_bloom` accrues each log's address and topics (registry `alloy-primitives-1.6.0/src/log/mod.rs:8-14`) and the Gnosis block vector test passes (E1).
13. Header-timestamp arithmetic overflow (`timestamp * 1000` at `blocks.rs:427`, `525`, `541`; `+= block_time` at `414`) reachable by a chain participant — rejected: PoS slot timestamps are not participant-chosen; an RPC returning a timestamp > 1.8e16 is malicious (out of scope, A4); wraps in release, mis-times polling only.
14. `ExceededMaxReorgDepth` swallowed by the driver's retry loop — rejected: returned un-retried (`driver.rs:213-217`).
15. Revalidation selecting the wrong block when startup `New`s are queued — rejected: `rposition(number < front)` picks the block immediately before the queue front, which is the one being fetched (`blocks.rs:494-497`).
16. A reorg within `max_reorg_depth` during downtime going undetected — rejected: the unconditional `Uncle { safe + 1 }` rollback plus replay of everything above the anchor (`blocks.rs:261-266`, `345-358`) re-derives it from the node's current chain. Only the anchor itself is unverified (F2-CORE-001).
17. A reorg exactly at `safe` while running being absorbed silently — rejected: `safe.hash != parent_hash` errors (`blocks.rs:435-439`); `evicting_from_recent_promotes_the_block_to_safe` passes (E1).
18. `MultipleQueries` delivering logs out of order — rejected: sorted after concatenation (`events.rs:439`, `517`).
19. `ClientFiltered` accepting logs of the wrong block — rejected: bloom equality (`events.rs:450`) plus the state machine's range check (`state/mod.rs:208`).
20. The sentinel being affected by address-agnostic decoding — rejected: its event set is two protocol contracts (`crates/sentinel/src/bindings.rs:165-171`); its address list in `main.rs` was not re-read (R7).
21. `Provider::call` cloning the inner transport without `poll_ready` — not a finding: `BoxTransport` readiness could not be verified offline; standard tower pattern; no observed consequence.
22. `initialize` mis-handling the persisted range being ahead of the node within the window — rejected by trace: with node latest N in `[S, L)` the `New` updates for `recent` blocks `>= S+1` (or the first live poll at `S+1` when `N == S`) line up with `BlockPending { S+1 }` (`blocks.rs:345-365`, `538-543`); only `N < S` fails (F2-CORE-007).
23. Prune/rollback races across warp page commits and a crash — rejected by trace: every warp page is at or below the node's `safe`, and a crash between commit and prune leaves `{anchor, page_end}` which restarts as `Uncle { anchor+1 }` and a re-warp (correct, wasteful; observation O12).

## Observations (plausible, unproven; not filed)

- O1 (I, ~35%): warp range queries (`events.rs:303-354`) have no completeness verification; a lagging backend answering a `toBlock` above its own head may return a silently truncated set (node-dependent). `max_logs_per_query` does not cover this.
- O2 (I, ~40%): the uncled-block recovery is keyed on exactly `-32001`; provider-specific codes for the same condition (`-32000 "unknown block"` etc.) fall into the F2-CORE-005 stall. Included there as case (c).
- O3 (I, ~40%, Low): the polling schedule anchors header timestamps to the host wall clock (`clock.rs:33-38`, `blocks.rs:538-551`). Host clock behind chain time by d delays every block by d silently; ahead by d costs four extra polls per cycle. Not participant-controlled; NTP mitigates. (Map lead CORE-H13.)
- O4 (E2 by trace, Informational): `block_time = 0` together with `block_retry_delays = []` is a tight poll loop (`blocks.rs:404-415`: index `retry_count % 1 == 0`, `get(0)` is `None`, `+= 0`, `sleep_until` returns immediately). No range validation on `block_time`, `block_propagation_delay`, `max_reorg_depth` (checklist 8). Doubly misconfigured file required.
- O5 (trivial): `start_block` above the head is not honoured; it only filters the initial `recent` (`blocks.rs:345-351`).
- O6 (I): `log.removed` and `log.block_hash` are never checked against the request; out-of-range block numbers are a `BadUpdate` fail-stop; `removed` logs should not appear for by-hash or final-range queries.
- O7 (I, ~25%): `TooManyLogs` as a participant-triggered stall needs a configured cap reachable within one block's gas (`Consensus.proposeTransaction` is `public`, `contracts/src/Consensus.sol:253`); with realistic caps (>= 1000) it is not reachable. Folded into F2-CORE-005 (b).
- O8 (seams): `Provider::connect` configures no timeout or retry layer (`provider/mod.rs:129-137`, R2 / CORE-H12); chain id is cached once and never re-checked (`provider/mod.rs:135`, `163-165`, R8 / CORE-H17); full JSON-RPC payloads are logged at `trace` (`provider/mod.rs:86-94`) — no key material observed in them.
- O9 (seam R2/R3): every restart and every spurious uncle (F2-CORE-006) re-emits the actions of the replayed blocks; the transaction queue does not deduplicate (map lead CORE-H5).
- O10 (seam R2): during the stalls in F2-CORE-005/008/009 the process stays up and `/health` presumably answers OK; not read.
- O11 (seam R3): at startup `status().latest` is the node's latest before the queued updates are consumed (`blocks.rs:376-381`), so the transaction queue reconciles at the node tip while the state is at the anchor; looks benign since the nonce is chain truth.
- O12 (Informational): a crash between a warp page commit and the following prune leaves two snapshots and causes a full re-warp from the older one on restart (correct, wasteful).
- O13 (seam R4/R5/R6): `Consensus.proposeTransaction` is permissionless and each call triggers a coordinator `Sign` (`contracts/src/Consensus.sol:253-265`) — a spam vector for validator signing sessions, outside my files.
- O14 (Informational): `fallible_events` (`events.rs:426-436`) drops a failed topic's logs and commits the block as complete; no service sets it (grep); enabling it is accepting permanent event loss.
