## 11. Observations (plausible, unproven, or outside my remit)

- **O1** Secret hygiene in logs structurally depends on upstream `Debug` impls (`frost-core`, `alloy-signer-local`, `ecdsa`); a manual `Debug` for `Effect`/`Resume` that prints only ids would remove the dependency (Info; no finding, as the current versions redact).
- **O2** (SEN-H14) reqwest defaults for the engine client: redirects followed (10); environment proxies are _not_ honoured in this build (`system-proxy` feature off, see Section 9); no client-level timeout beyond the per-request one; `Client::new()` would panic at startup only if the TLS backend failed to initialise. Under A3 no finding. If the engine URL ever becomes `https://` to a remote host, revisit (a redirect to a third party would hand the verdict decision to that party).
- **O3 (out of scope for findings — CI trust boundary, route to repository owners)** `post_pr_comment.yml:24-54` runs with `pull-requests: write` on `workflow_run` and posts, verbatim, `*.md` content and an `issue-number.txt` produced by the unprivileged `coverage.yml`/`sentinel_engine_integration.yml` runs (`coverage.yml:41,49-66`), which execute fork code (`scripts/generate_coverage_report.sh`); a fork PR can therefore choose the target issue number and the markdown body posted by the bot. Not a Rust-crate finding.
- **O4** `voting_window = 0` is accepted (`sentinel/config.rs:56`) → 1-second engine timeout floor (`main.rs:60`) and immediate cleanup; consequences are R7's (SEN-H12); listed in F2-XC-008 as a validation gap.
- **O5** `SharingState` (round-2 secret share + peers' shares) is written into every per-block snapshot until pruned (F2-XC-005); R4 may want to weigh the reorg/rollback interplay with `keygen_secrets` retention.
- **O6** The unauthenticated metrics/health listener, when bound to `0.0.0.0:3555` as the handbooks suggest, exposes `safenet_validator_secrets_total`, bond/fee histograms and effect failure counts, and enables the h2 server path (F2-XC-004); recommend a private interface or a scraping sidecar.
- **O7** Both `main`s connect to the RPC before opening the database (`validator/main.rs:45-46`, `sentinel/main.rs:41-42`), so database misconfiguration surfaces only after a successful network handshake; harmless ordering nit that made the F2-XC-002 E1 need an RPC stub.
- **O8** `Justfile:44` `cargo test --workspace` lacks `--locked`; the preceding clippy `--locked` step (`Justfile:29`) catches lockfile drift, so no gate gap in practice.
- **O9** The sentinel's reveal salt (`hashing.rs:43-52`) is derived per request from the signer key. `Commit { id, hash }` carries only the blind hash; the salt first appears in `SentinelActionKind::Reveal { id, approve, salt, reason }` (`action.rs:15-20`), i.e. it is persisted (as the queued reveal transaction's request JSON in the `transactions` table) only once the sentinel is revealing, at which point it is destined for the chain by design. `SentinelActionKind` derives `Debug` (`action.rs:8`) but no sentinel tracing site formats an action with `?` (grep: none), and the driver traces only `?update`/`?resume` (`driver.rs:240,267`). No concern found during the blind window; noted because it is the one secret in scope that is not a key.
- **O10** `docs/validator-handbook.md:17` states only x86-64 images are distributed while `docker.yml` builds arm64 too; documentation drift only.
- **O11** proc-macro-error2 2.0.1 triggers future-incompat lint E0365 (`08-future-incompat.log`); a future stable rustc will fail the build until alloy-sol-macro moves off it (in F2-XC-004).
