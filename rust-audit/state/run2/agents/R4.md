## Questions from the assignment, answered from the code

- **What binds `q` to its owner?** Nothing. `frost/keygen.rs:86-93` verifies the PoK over `c[0]` only; `ecdh.rs:70-75` rejects identity only; `FROSTCoordinator.sol:383` `requireNonZero(q)`. Republishing a peer's `q` is accepted everywhere → F2-VAL-001.
- **Pad derivation.** `ecdh.rs:115-119`: raw affine x of `q_peer·sk_me`, XOR; symmetric (test `ecdh_is_commutative`), unhashed, unbound → F2-VAL-002.
- **Complaint protocol.** Plaintiff learns `f_accused(plaintiff)` in plaintext (`state/keygen.rs:737-744`, `frost/keygen.rs:420-427`); one complaint per (plaintiff, accused) pair onchain, `n-1` per plaintiff (`FROSTParticipantMap.sol:183`); the Rust round closes at `count` shares with valid `y` (`state/keygen.rs:351`) and at `count` confirmations (`449`); the local confirmation waits for a verified share from everyone (`385`, `879`); a false plaintiff is never penalised (no plaintiff state, `state/mod.rs:225-232`) → F2-VAL-006.
- **Finalise with an unvalidated share?** An honest node confirms only with `shares.len() == count` (`state/keygen.rs:383-386, 875-880`); each share is verified against the summed commitments before insertion (`frost/keygen.rs:316-324`); a missing/invalid share is resolved by complaint or exclusion at `deadlines.response` (`1083-1086`). No path found where an honest node confirms without every peer's share verified for itself. A malicious peer's inconsistent shares to _others_ only harm those recipients' own shares (Feldman VSS), not the group.
- **Encoding parity.** Group id `consensus/group.rs:352-364` == `FROSTGroupId.create/mask` (word layout and 64-bit mask); participant leaf `p.into_word()` == `bytes32(uint256(uint160(p)))` (`FROSTParticipantMap.sol:149`); context `encodePacked(u32 0, address, u64)` pinned against the onchain group in test `actual_group`; commitment `(q, c[0..t), r, mu)` == `KeyGenCommitment`; `c.len() == threshold` matches `dkg::part1`'s `min_signers` coefficients; identifier `HID(address)` with DST `FROST-secp256k1-SHA256-v1id` on both sides (`frost-secp256k1/lib.rs:226-228`, `FROST.sol:342-347`), same `hash_to_field` reduction (`FROST.sol:355-370`); callback context `(u64, u64)` == `Consensus.onKeyGenCompleted` decode. No mismatch found.
- **Identifier collisions.** `Identifier::derive` = uniform hash to `Z_n` of the 20-byte address; collision or zero is negligible (`participants.rs:16-19` `expect`). Consistent keying: `BTreeMap<Address>` for commitments/shares, `BTreeMap<Identifier>` for frost packages; ordering of `f` by ascending address on both sides (`frost/keygen.rs:196-204, 365-374`).
- **Reorg across a key-generation block.** Secrets live in the reorg-immune store keyed by `(gid, me)` and are reused, never overwritten (`secrets/store.rs:176-212`, R5's file — boundary); the snapshot rolls back and the replay re-derives identical `SharingState`; a replayed own commitment suppresses a second publish (`state/keygen.rs:94-96`); a secrets/commitment mismatch fails safe via `IncorrectCommitment` → `rollover_failure` (`frost/keygen.rs:181-183`, `state/keygen.rs:1270-1275`). Residual issues are the late-setup race (F2-VAL-004) and the restart warp (F2-VAL-003).

## Hypotheses considered and rejected (with the citation that refutes them)

1. **M1 — pad reuse across two keygens with the same gid.** A gid is created onchain once (`FROSTParticipantMap.sol:126-128` `AlreadyInitialized`); the Rust never repeats a gid within one epoch because exclusions only accumulate (`consensus/group.rs:186-208`) and the context changes per epoch (`368-377`); the store reuses the same polynomial for the same gid (`secrets/store.rs:196-197`), so the same pad only re-encrypts the same `f_me(peer)`. Two different plaintexts under one pad occur only as the two directions of a pair (F2-VAL-002).
2. **H9 — late complaint excludes the plaintiff and wastes a round.** True (`state/keygen.rs:692-695`, `1087-1090` excludes non-confirmers, and the plaintiff cannot confirm per `FROSTParticipantMap.sol:222`), but the excluded party is the late plaintiff itself and a member can waste a round equally by not confirming; no added capability. Folded into F2-VAL-006 as context.
3. **H7 — `ReconcileGroupSecrets` races same-block store writes.** The scheduled-deletion design closes it: reconciliation only _schedules_ (`secrets/store.rs:311-345`, `381-411` `COALESCE(delete_at_block, block)`), retained groups get `NULL` again next block, `store_keygen_secrets` clears the schedule on reuse (`176-194`), deletion happens only at `safe` (`356-372`), and the rollover-started keygen is retained in the same block because `handle_rollover_new_block` runs before `handle_group_reconciliation` (`state/mod.rs:465-470`; retention set `state/preprocess.rs:149-163`). Residual: a crash before the next reconcile plus ≥`max_reorg_depth` downtime plus the startup prune winning against the first reconcile — observation for R5/R6 below.
4. **H10 — secrets printed via `Debug`.** All secret-bearing types redact: `EncryptionKey` (`ecdh.rs:50-54`), `round1::SecretPackage` (`frost-core dkg.rs:191-204`, coefficients redacted), `round2::SecretPackage` (`337-350`), `SigningShare` (`frost-core keys.rs:126-133`, used by `round2::Package` and `KeyPackage`). `Secrets`, `SharingState`, `VerifiedShare`, `KeyShare` derive `Debug` but contain only these plus public data. Not a finding from the DKG side (R8 owns the sweep).
5. **PoK missing onchain lets a bad commitment through.** The contract indeed does not verify the PoK (`FROSTCoordinator.sol:371-389`), but every Rust node verifies it (`frost/keygen.rs:89-93`) deterministically, so an invalid committer never reaches `count` locally and is excluded at the deadline (`1027-1046`). Genesis (no deadline) would stall — A16, known.
6. **Identity coefficient commitments.** `frost_point((0,0))` → identity accepted for `c[k]` (`marshal.rs:136-138`); contract `Secp256k1.add` accepts zero. A zero `a_0` is a legal (if useless) contribution in Pedersen DKG; the PoK still verifies. Key _bias_ by the last committer is inherent to this DKG and accepted by FROST. Not a finding.
7. **`c.len()` and `f.len()` not checked locally.** Relies on `FROSTCoordinator.sol:384, 436`; a mismatch would surface as `IncorrectNumberOfCommitments`/`IncorrectNumberOfShares` → `rollover_failure`/complaint rather than a panic. Only reachable with event injection (VAL-H2, R6). Observation.
8. **Membership not checked for `KeyGenCommitted`/`KeyGenConfirmed`.** `state/keygen.rs:173-175, 448` accept any address; the contract's `register`/`confirm` (`FROSTParticipantMap.sol:146-153, 219-225`) restrict emission to members. Only reachable with VAL-H2 (R6). Observation.
9. **Non-canonical scalars/points.** `marshal.rs:125-129` (`from_repr`), `133-148` (k256 decode) reject `≥ n`, off-curve and `≥ p`; parity with `Secp256k1._satisfiesCurveEquation` (`239-246`). A non-canonical reveal is treated as invalid and excludes the accused (`state/keygen.rs:842-859`) — only a malicious accused harms itself.
10. **Complaint threshold parity.** Rust `total >= threshold` (`714-722`) vs contract unresolved `accusations >= threshold` (`FROSTParticipantMap.sol:191`, `208`): Rust is stricter and deterministic across honest nodes; contract-compromised implies Rust-restarted. Consistency note in F2-VAL-006, not a divergence.
11. **`u16` arithmetic.** `complaint.total/unresponded` bounded by one complaint per plaintiff (`FROSTParticipantMap.sol:183`); `len() as u16` comparisons bounded by contract membership; `unresponded -= 1` guarded by the `> 0` filter (`821-826`).
12. **`participants::identifier` panic.** `expect` on `HID(address) == 0` (`participants.rs:16-19`): probability `2^-256`.
13. **`handle_key_gen_committed` after a reorg republishes our commitment.** Guarded by `commitments.contains_key(&self.account)` (`94-96`).
14. **Reorg replays a stale `Resume::Setup` into a different group.** Guarded by `group_id == group.id()` (`82`) and `secrets: None` (`78`).
15. **Genesis stuck states.** Invalid PoK, unanswered complaint, lost setup, or late-setup race all stall genesis forever (`deadline: None`, `1204-1210` halt). A16: Informational/known; recorded inside F2-VAL-004/005 rather than as separate findings.

## Observations (plausible, unproven, or out of my files)

- **O1 (R5/R6 boundary, residual of H7).** After a reconcile that scheduled a freshly inserted group's secrets (race in block `N`), a crash before block `N+1`, downtime ≥ `max_reorg_depth`, and the startup `housekeeping` prune (`service/effect.rs:278-307`, `driver.rs:292-293`) running before the first reconcile's `NULL` reset would delete DKG secrets. Consequence would only bite on a later reorg replay of the round start (resample → `IncorrectCommitment` → skip/halt). Very narrow; not filed.
- **O2 (design, R2/R6).** `Secrets`, `SharingState.peer_packages` (every plaintext share this validator sent) and `KeyShare` are serialised into the core `snapshots` table in plaintext (`state/mod.rs:113-126, 129-146`, `frost/keygen.rs:144-150`), in addition to the secret store. Documented in the handbook per the analysis; noted for the report's secret-at-rest inventory.
- **O3 (off-by-one windows).** Event gates are inclusive (`block <= deadlines.complain` at `692-695`, `<= deadlines.response` at `798-800`) while timeouts fire at `block >= deadline` on `NewBlock`, which the driver applies before the block's logs (`core/state/mod.rs:190-199` then `200-239`). A response or confirmation included in the deadline block itself is processed after the restart and dropped, although the action's `expires_at` equals that block (`743`, `1347`). Deterministic across honest nodes; Informational.
- **O4 (config trust, checklist 8).** The participant list, `genesis_salt` and per-epoch activity windows are purely local (`consensus/group.rs:277-317`, `service/mod.rs:51-57`); nothing onchain pins them, so a config mismatch makes a validator compute a different gid and silently sit out. Operational; no finding.
- **O5 (test gaps).** `frost/mod.rs::ceremony` covers only the happy path; there is no test for duplicate/related `q`, invalid PoK, wrong `y`, undecryptable ciphertext, invalid reveal, or any `state/keygen.rs` transition (0 tests in 1459 lines). The finding files list the specific tests to add.
- **O6 (R6).** `Action::KeyGenAndCommit` uses a fixed 250k gas (`service/action.rs:145`) for a call that may also execute `keyGen` (group creation) plus a Merkle verification and `t` point-encodings in the event; worth a Foundry gas report for the largest planned `t`.
- **O7 (docs).** `docs/overview.md:48` describes `C[0]` as the ECDH key and a one-value-per-pad argument; the code publishes a separate `q` and uses each pad twice. Recorded inside F2-VAL-002 (docs are outside the filing scope).
- **O8 (R6/VAL-H2).** With unauthenticated event sources, `handle_key_gen_complained` would reveal a share for any plaintiff address that is a peer (`reveal_secret_share` fails for non-peers, `frost/keygen.rs:422-427`), so injected complaints are bounded to real peers; still a reason to bind events to the coordinator address.
- **O9 (R5).** `handle_key_gen_confirmed` picks `responsible = event.participant` (the last confirmer) even when that party is not a signer of the active epoch (`535`, and the doc comment at `state/mod.rs:288-292`); R5 should check the timeout path handles a non-signer responsible party without penalising signers.
