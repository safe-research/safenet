## 4. Hypotheses considered and rejected (with the refuting citation)

- **R1 - nonce reuse across reorg rollback or crash (M5, checklist 4).** `take_nonce` is a single `DELETE ... RETURNING` (secrets/store.rs:281-294); the secret `Nonces` value exists only in the `Resume::Nonce` message and is consumed by value in `frost::sign::signature_share` (state/sign.rs:377; frost/sign.rs:60-82); snapshot state stores only `NonceIndex { root, offset }` (state/mod.rs:78-85), never the nonce, so a rollback can at most re-issue `UseNonce` for the same coordinates, which returns `None` -> `Resume::Noop` (service/effect.rs:191-203). A reorg that re-issues the same sequence for a different message re-reveals the same `(D, E)` (non-consuming `nonces_reveal`, store.rs:253-272) but a second share is impossible because the row is gone; the queued share for the old message reverts under the new message because the challenge binds `m` (FROSTCoordinator.sol:590-592). Upstream: `round2::sign` rejects a package whose own commitment differs from the nonces (`frost-core-3.0.0/src/round2.rs:136-143`, `IncorrectCommitment`); `SigningNonces` is `ZeroizeOnDrop` with a redacting `Debug` (`round1.rs:212`, `271-280`); `SigningShare` `Debug` is redacted (`keys.rs:126-134`). Only a database restore can resurrect a nonce - A17 (O7).
- **R2 - stale `Resume::Nonce` applied to a restarted session.** `handle_nonces` requires `CollectSigningShares` for the message (state/sign.rs:365-375) and computes exactly one share per resume; frost-core's own-commitment check (above) rejects a package whose self commitment does not match.
- **R3 - `MerkleTree::proof(index)` out of bounds (M4).** Callers: `NonceChunk::with_size` with `i in 0..size` (frost/preprocess.rs:134-141) and `signature_share` with `index = signers.range(..own).count()` after `signers.get(own)` succeeded (frost/sign.rs:129-136). Second preimage / padding confusion: nonce leaves hash 160 bytes (frost/preprocess.rs:164-172 = FROSTNonceCommitmentSet.sol:147-159), signer leaves 192 bytes (frost/sign.rs:165-179 = FROSTSignatureShares.sol:118-133, E1 by `cast`), internal nodes 64 bytes (merkle.rs:87-93); the contract requires exactly 10 proof elements for a 1024-leaf tree (FROSTNonceCommitmentSet.sol:131) and `build` on 1024 leaves has height 11 (merkle.rs:13-29, 49-59).
- **R4 - Merkle padding mismatch with the contract.** The contracts only verify proofs (OpenZeppelin commutative hashing), never rebuild trees; every validator runs the same `build`, so the selection root is consistent across honest nodes. Noted that per-level `B256::ZERO` padding differs from power-of-two padding (O8) - only relevant if a second implementation must reproduce roots; none found in scope (explorer `signing.ts` has no Merkle code).
- **R5 - `ON DELETE CASCADE` without `foreign_keys` (M6).** sqlx-sqlite 0.9.0 sets `PRAGMA foreign_keys = ON` by default (`sqlx-sqlite-0.9.0/src/options/mod.rs:185-187`), applied per connection in `establish.rs`; `connect_sqlite` (core/utils.rs:56-62) only disables recycling. Refuted.
- **R6 - EIP-712 / leaf encoding mismatch with Solidity.** E1 by `cast` (section 2): all four type hashes, domain, `SafeTx` struct hash, proposal message (with `bytes oracleData` hashed), rollover message and signer leaf match byte for byte; `transaction_proposal_hash` hand-encoding is additionally pinned against alloy's `SolStruct` by `proposal_hash_matches_solstruct` (hashing.rs:217-236, passes).
- **R7 - `sequence` -> `(chunk, offset)` mismatch.** `decode_sequence` = `(seq / 1024, seq % 1024)` (frost/preprocess.rs:28-33) = `_sequence` `(seq >> 10, seq & 0x3ff)` (FROSTNonceCommitmentSet.sol:167-170); `sid.sequence()` is used onchain for the reveal (FROSTCoordinator.sol:560-563). Offsets below the contract's `startOffset` are never attempted because those sequences were observed while the local chunk was still `None` (state/preprocess.rs:185-199).
- **R8 - selection-root ambiguity at `CollectSigningShares` timeout.** Two selections with >= threshold shares would need > n distinct honest signers; ties resolved deterministically by `max_by_key` over a `BTreeMap` (state/sign.rs:677-683).
- **R9 - nonce RNG weakness (M7).** One `ChaCha12Rng` seed per chunk from the OS-seeded thread RNG, distinct streams per offset (frost/preprocess.rs:112-121); frost-core mixes the signing share into each nonce (`round1.rs:77`); the seed is a local, `Nonces`/`NonceChunk` `Debug` redact (frost/preprocess.rs:64-71, 150-159); nothing persists it (store.rs writes `Nonces` JSON only). Informational.
- **R10 - duplicate `NonceTree` via the per-group semaphore creates phantoms.** A duplicate returns `Ok(None)` -> `Resume::Noop` (secrets/nonces.rs:194-218; service/effect.rs:161-164) but the reorg-replayed reservation recomputes the same index and the in-flight request links it; only a _failed_ request (030) leaves a phantom.
- **R11 - reorg replay creates phantoms by itself.** Same index (deterministic `expected_chunk`), durable `Preprocess` in the transaction queue, `link(event.chunk, ..)` (state/preprocess.rs:79). Rejected; failure, not replay, is the defect.
- **R12 - reveal replay / lost reveal effect leads to inconsistency.** Lost reveal -> self missing from `revealed` -> timeout -> `signers.retain(revealed)` excludes self -> `!signers.contains(self)` -> dropped (state/sign.rs:643, 538-541). Graceful.
- **R13 - `signature_id_to_message` leaks.** Cleaned on rejection, oracle timeout, restart, attestation timeout and attestation (state/sign.rs:235, 533, 628, 718, 490-493); `WaitingForRequest` has no sid. Bounded.
- **R14 - `selections` map unbounded growth from forged shares under many roots.** A member can submit valid shares for arbitrary `selection.r` (it knows its nonce), each creating an entry (state/sign.rs:419-432), but the entries live only for the session and are gas-bounded per block. Not a finding.
- **R15 - re-reveal changes `revealed[M]` to different commitments (binding-factor manipulation).** The leaf binds the offset, so a second valid reveal at the same `sid` is the same `(D, E)`; after `revealed.len() == signers.len()` reveals are ignored (state/sign.rs:304-320, 346-349). Only the `last_signer` effect remains (033).
- **R16 - `handle_oracle_result` accepts a result from the wrong oracle.** `expected == oracle` where `oracle` is the emitting address (state/sign.rs:189, 226; state/mod.rs:458-460). Rejected.
- **R17 - `store_keygen_secrets` overwrites / resamples after a reorg.** `UPDATE ... RETURNING secrets` then insert only when absent, in one transaction (store.rs:182-208); test `store_keygen_secrets_does_not_overwrite` passes.
- **R18 - keygen secrets scheduled while still needed.** Rows are scheduled only when the group has a key share or left the retained set; a rollback that could re-run `KeyGenSetup` with `secrets: None` must land on a snapshot >= safe, and on the same branch every such snapshot already has the key share (retention decided on pre-log state, groups leave `epochs`/`rollover` monotonically); across a reorg the equal-height reconciliation is accepted and cancels (store.rs:299-303). Rejected for in-window reorgs; see O1/O2 for the restart cases.
- **R19 - `schedule_absent_groups` SQL injection / bind limits.** Table name is a `&'static str` from two call sites; retained set is a handful of `push_bind`s (store.rs:381-411).
- **R20 - `prune_scheduled_secrets` deletes rows a rollback can still need (steady state).** Deletes `delete_at_block <= safe`; a rollback cannot go below `safe` (core/state/storage.rs:145-160; core/index/blocks.rs:435-439 exits on deeper reorgs); scheduling at block N happens on the state after N-1's logs plus N's `NewBlock` transitions, and snapshot N-1 (the earliest a rollback can restore when `safe = N-1`) is replayed through the same deterministic `NewBlock(N)`. `max_reorg_depth = 0` and `1` traced: at 0 the same-block housekeeping may delete rows the same block's reconciliation scheduled - correct since no rollback is possible; at 1 there is one block between scheduling and collection.
- **R21 - `ReconcileGroupSecrets` computed pre-log races the same block's store writes (VAL-H7).** A group introduced by block N's logs may be scheduled at N if its insert commits before the reconciliation's `UPDATE`; the reconciliation for N+1 (accepted, higher) cancels it, D >= 1 blocks before collection. Benign in steady state (O3 for the restart interaction).
- **R22 - worker thread panics leave a dead stream.** No panic path found in `NonceChunk::with_size` (only an unreachable `expect` at frost/preprocess.rs:117); `thread_rng` fill cannot fail. Robustness note O5 (a dead stream is never restarted because `start` is a no-op for an existing entry, secrets/nonces.rs:36-39).
- **R23 - SQLite locking under the validator's write pattern.** `busy_timeout` 5 s default (`options/mod.rs:203`), pool `max_connections` 10 (`sqlx-core-0.9.0/src/pool/options.rs:151`), journal mode left at SQLite's default (`options/mod.rs:179-183`; the sample config sets none), `synchronous` FULL. Longest transaction is the 1025-row chunk insert; far below 5 s. Not a finding (O6).
- **R24 - `observe` arithmetic.** `saturating_add`, `checked_add` in `expected_chunk` (state/preprocess.rs:194, 234); `u64` sequences are unreachable in practice.
- **R25 - `handle_sign` with a tracked group but a session of a different group.** Falls to the `(_, Some(other))` arm and is re-inserted (state/sign.rs:36-45 guard, 115-122). Only the `None` arm drops (032).

## 5. Observations (plausible, unproven; not filed)

- **O1 (35%, `known`)** Long-outage restart: the first housekeeping after the warp prunes every row scheduled at `<= safe'` inline, racing the same block's reconciliation that would cancel a schedule the replay no longer agrees with. Harmful only if the replayed branch differs from the one that scheduled (a reorg during the outage inside `max_reorg_depth`): a needed keygen row or nonce chunk can be deleted; the outcome is "secret missing" (`IncorrectCommitment` -> rollover failure, or missed reveals for one chunk). The module doc acknowledges exactly this (`store.rs:38-41`). Citations: service/effect.rs:278-283 and core/driver.rs:292-294 (inline housekeeping after spawning), core/index/blocks.rs:246 (watcher safe from the live head), store.rs:356-370.
- **O2 (40%)** Warp-deferred `NewBlock` transitions (timeouts, rollover, top-up) make the replayed state diverge from the pre-restart state for the blocks covered by the warp (late commitments accepted, sessions kept alive) even without a reorg; the nonce-relevant consequences are covered by 031; the general determinism question belongs to `core/state` (R2, CORE-H5).
- **O3 (25%)** VAL-H7's transient mis-schedule (R21) combined with 031's below-marker window: the correcting reconciliation is ignored for up to `max_reorg_depth` blocks after a restart; the replayed `KeyGenSetup` cancels the schedule via `store_keygen_secrets` (store.rs:186-194) unless collection happens first (needs the long-outage inline prune, O1).
- **O4 (30%)** Reorg-induced stream stop: `generator.retain` stops a group's stream when a reconciliation drops it (e.g. a confirmation timeout at block N on the old branch); a rollback that restores the group cannot restart the stream until the equal-height reconciliation at N because the intermediate ones are below the marker (service/effect.rs:240-256). An `EpochStaged` for that group replayed in `(U, N)` would hit 030/031's failure. Needs a reorg of depth close to `max_reorg_depth`.
- **O5 (20%)** A nonce worker thread that dies is never restarted (`start` no-op on an existing entry, secrets/nonces.rs:36-39, 100-121); no realistic death path found.
- **O6 (Informational)** SQLite runs in the default rollback-journal mode with `synchronous=FULL`, `busy_timeout` 5 s and a 10-connection pool; WAL would remove reader/writer blocking but nothing here exceeds the timeout.
- **O7 (out of scope, A17)** Restoring `storage.db` from a backup (recommended by `docs/validator-handbook.md:19,75`) after any `take_nonce` resurrects consumed nonces; the handbook does not warn about this. Recorded for the operator documentation, not filed.
- **O8 (Informational)** `MerkleTree::build` pads odd levels with `B256::ZERO` per level, which differs from padding the leaf list to a power of two (the `generates_the_expected_merkle_root` test feeds an already padded 8-leaf list). Consensus-relevant only if a second implementation must reproduce selection roots.
- **O9 (Informational)** The `String` read from SQLite holding serialized `Nonces`/`Secrets` is not zeroized (store.rs:258-271, 282-291, 186-197); the decoded frost-core types are.
- **O10 (Informational)** `Action::Preprocess` is submitted with no expiry (service/action.rs:237-255 by grep); this is what lets a pre-restart request self-heal (031), so keep it when changing expiries.
