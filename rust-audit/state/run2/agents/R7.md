## Hypotheses considered and rejected (with the refuting citation)

1. **Invalid UTF-8 in `Revealed.reason` / `DisputeResolved.context` / `DisputeOutOfScope.context` stalls every sentinel's indexer.** Refuted. `watcher_events!` decodes with `SolEventInterface::decode_raw_log` (`crates/core/src/index/events.rs:550-553`, `583-586`), the non-validating path (`alloy-sol-types-1.6.0/src/types/event/mod.rs:186-200` → `abi_decode_data` → `abi_decode_sequence`); `<String as SolType>::detokenize` is `RustString::from_utf8_lossy(...)` (`data_type.rs:381-388`); `valid_token` (`data_type.rs:377-379`) is only reached through the `_validate` variants (`event/mod.rs:179-182`, `202-211`). A decode failure would indeed loop the driver (`events.rs:498-510`, `driver.rs:218-224`), but no watched field can produce one from chain data: the `RequestState` ordinal is emitted only from the contract's own enum (`SentinelOracleRequests.sol:327`).
2. **Commit-hash / request-id divergence from Solidity.** Parity vectors on both sides pass (`hashing.rs:149-166`, `177-192`; E1 in `R7-sentinel-tests.log`). Encodings re-read: `commit_hash` = `keccak(approve‖salt‖sentinel‖requestId‖reason)` (`hashing.rs:31-37`) vs `abi.encodePacked(approve, salt, sentinel, requestId, reason)` (`SentinelOracleCommitments.sol:55`).
3. **Engine binds a verdict to the wrong request / answers twice.** The resume carries the effect's own `request_id` (`effect.rs:57-68`); one HTTP request → one resume; a second resume for an advanced entry is ignored (`service.rs:158-166`, test `2141-2157`).
4. **Engine inflates `reason` to exceed the 250k reveal gas.** `reason` is `RuleId(u32,u32).to_string()` (`engine.rs:45-49`, `service.rs:175`), ≤ 23 bytes.
5. **Vote alterable after commit within one process.** `approve`/`reason` are carried in state and taken at reveal (`state.rs:38-55`; `service.rs:214-225`, `418-433`). Only a rollback re-derives them → F2-SEN-001 (c).
6. **Unlimited or third-party ERC-20 approval.** `approve(oracle, bondTarget)` exactly (`service.rs:823-833`).
7. **Deadline off-by-one against the contract.** Reveal emitted at `block > commit_deadline` (`service.rs:410`) ↔ `block.number > commitDeadline` (`Requests.sol:126`); finalize at `block > reveal_deadline` (`453`) ↔ `174`; `Commit` expiry `commit_deadline` with `expires_at > latest` (`tx/storage.rs:152`) → last submission at `commit_deadline − 1` for inclusion at `commit_deadline` ↔ `block.number <= commitDeadline` (`117`). Consistent.
8. **Salt predictability / loss.** HKDF-SHA256 keyed by the private key, domain-separated, request-bound (`hashing.rs:14`, `49-53`; `tx/signer.rs:59-64`; `kdf.rs:19-27`); never persisted so never lost.
9. **Duplicate `TransactionProposed` resets progress.** Guarded (`service.rs:119-126`; test `1370-1384`).
10. **Stale resume creates state after a reorg.** Guarded (`service.rs:167-170`; test `1928-1938`).
11. **Late resume commits after the deadline.** Entry gone at `commit_deadline + 1` (`394-399`) and the `Commit` row expires (`231`, `tx/storage.rs:152`); test `2097-2136`.
12. **Panics reachable from chain input.** None in non-test transition code (grep; `hashing.rs:68-69` is `cfg(test)`-only via `expect(dead_code)` gate at `57`).
13. **Event spoofing between the two watched addresses.** Distinct topic0 sets; only the oracle emits `NewRequest`/`Committed`/…; `postRequest` restricted to `PROPOSER` (`SentinelOracle.sol:207-208`); request ids derive from Consensus's own event fields (`service.rs:108-115`).
14. **SEN-H3's "warp makes `finalize` claim on a frozen request and drop the entry".** Partly refuted on the current code: the terminal events (`DisputeTriggered`/`RequestTimedOut`/`OracleResult`) are now handled from `CollectingCommitments{self_committed}`, `CollectingVotes`, `WaitingForOutcome` via `approve_and_slash_amount` (`state.rs:118-141`; `service.rs:669-817`), and `handle_arbitration_timeout` claims from any tracked state (`545-557`), so a frozen request seen in a warp is recovered as long as the entry exists. What remains is the `finalize()` drop when reveals are observed but ours is not (→ F2-SEN-003) and the discarded own `Committed` (→ F2-SEN-001).
15. **`bondTarget − slashAmount` underflow making the "remainder" claim moot.** `BondConfig.sol:58` enforces `slashingMultiplier ≤ bondMultiplier`.
16. **Resume applied during a warp is lost.** `handle_resume` updates live state regardless of `Status` (`state/mod.rs:250-258`).
17. **`handle_block_advance` iteration order affects correctness.** Entries are independent; only the order of emitted actions (queue FIFO) varies.
18. **Reorg of our own `Committed` block loses the bond.** The queue un-marks and resubmits (`tx/mod.rs:166-179`); the FSM is rolled back to before the count and re-counts the re-mined event when in `CollectingCommitments`. (Fails only in the F2-SEN-001 window.)
19. **`RequestState` decoding of `DisputeResolved.outcome` by position.** Declaration order matches `SentinelOracleRequests.sol:15-22` (`bindings.rs:14-21`).

## Observations (plausible, unproven, not filed)

- O1. `x-request-timeout` equals the client timeout (`engine.rs:155-161`): the engine has no margin to answer before the client aborts — folded into F2-SEN-008.
- O2. `reqwest` `%err` may echo credentials embedded in the engine URL (`engine.rs:182-185`) — in F2-SEN-008 as class I.
- O3. `.json()` buffers an unbounded engine response (`engine.rs:168`); trusted engine (A3).
- O4. Fresh or in-memory database (`sqlite::memory:` as used by `scripts/run_sentinel_integration_test.sh`) forgets all in-flight requests on restart → non-reveal slashes. A17 territory; noted for operators.
- O5. `handle_block_advance` re-emits `Reveal` at the first post-warp block even when both deadlines have passed; the row expires unsubmitted (`storage.rs:152`) so no gas is burnt, but the next block's `finalize()` takes the `timed_out` branch and labels the metric `Timeout` although others revealed (`service.rs:631`, `695`). Cosmetic.
- O6. USDT-style tokens (non-zero → non-zero `approve` reverts): a reverted `commit` leaves `allowance = bondTarget`, after which every later `approve(bondTarget)` reverts and the sentinel never commits again until a manual reset. Deployment-dependent (class I).
- O7. `approve` gas 55 000 (`service.rs:832`) is adequate for OZ ERC-20 (~46k cold) but not for hooked/upgradeable tokens with extra storage writes. Deployment-dependent (class I).
- O8. Metrics `to::<u128>() as f64` casts (`service.rs:328`, `517`, `591`) are lossy above 2^53; metrics only.
- O9. `voting_window ∈ {0,1}` → `deadline = block` and a 1 s engine timeout: the sentinel silently never votes — in F2-SEN-006.
- O10. `Config` derives `Debug` (`config.rs:17`); `Signer`'s `Debug` prints only the address (`tx/signer.rs:96-100`); `Config` is never logged (`main.rs:39` logs the path). No leak found.
- O11. The tx queue resubmits an already-submitted `Reveal` with bumped fees past `reveal_deadline` (`tx/mod.rs:224-237`, no expiry check in `stale_submissions`), so a late-mined reveal reverts `RevealWindowClosed` and pays gas; inherent to the game, but a bounded number of bumps would cap it. Core-owned (R3).
- O12. The engine has unbounded authority over bond exposure (every `Approved`/`Denied` → bond; no loss budget or kill switch). Under A3 this is a design property, not a defect; noted because a compromised engine converts directly into `slashAmount` per lost dispute with no local circuit breaker.
- O13. `Consensus.proposeTransaction` emits `TransactionProposed` before `postRequest` (`Consensus.sol:264-266`), so `WaitingForRequest` is effectively unreachable with this proposer; its `deadline` (`voting_window`) only matters if a different proposer contract ever separates the two calls.
- O14. Two `Approve`+`Commit` rows per request with distinct nonces: a stuck `approve` (underpriced, RPC rejects) blocks the `commit` behind it by nonce order; the queue's bump logic covers it but the commit window is short. Core-owned (R3).
