## 3. Checklist answers

- Q33 (nonces for one signature id meeting another id's commitments). Yes, `handle_nonces` does not compare the resume's signature id with the state's (`state/sign.rs:339-357`; `Resume::Nonces` carries only `message`, `service/effect.rs:82-86`). The result is only a failed share: frost-core `round2::sign` rejects nonces whose commitments differ from the signer's entry in the signing package (`frost-core-3.0.0/src/round2.rs:134-143`, `Error::IncorrectCommitment`), and `handle_nonces` logs and returns no action (`state/sign.rs:357-368`). The stale pair is burned; the correct `UseNonces` for the new id is a separate effect and is unaffected. Reaching this needs the old effect to outlive a 6-block share round or a reorg; liveness only. No finding.
- Q34 (one nonce pair for two messages). No path found. A pair is generated per call (`service/effect.rs:128-131`), stored first-wins under `signature_id` (`secrets/store.rs:228-239`), read back only by `take_signing_nonces`, which selects and clears it inside `BEGIN IMMEDIATE` (`secrets/store.rs:273-288`), and is consumed by value in `frost::sign::signature_share` (`frost/sign.rs:92-114`, `state/sign.rs:357`). The secret never enters the snapshot (`Resume::Nonces` changes no state, `state/sign.rs:339-384`), never reaches logs (`frost/sign.rs:49-53`, `frost-core-3.0.0/src/round1.rs:271-281`), and the wrapper is not `Clone` outside tests (`frost/sign.rs:26-31`). Durability: sqlx leaves `journal_mode` and `synchronous` unset (`sqlx-sqlite-0.9.0/src/options/mod.rs:180-191`), so SQLite's rollback journal with `synchronous=FULL` applies and the clearing commit is durable before the share exists. Reorgs, restarts and pruning can at worst regenerate a fresh pair for an old signature id (see observation O3), never return a used one. The signature id is `gid | (sequence + 1)` (`contracts/src/libraries/FROSTSignatureId.sol:38-40`), so one id can name different messages on different branches; the per-id single take still allows only one share per pair. Verified correct.
- Q35 (commitment timeout set). All honest validators compute the same set: `NewBlock(deadline)` is applied before the deadline block's logs, live, optimistically after the previous block's snapshot, and per block during warps (`crates/core/src/state/mod.rs:228-268`), and only `CollectNonceCommitments` accepts commitments (`state/sign.rs:243-331`). Caveat: the optimistic `NewBlock(deadline)` makes validators burn nonces on block `deadline - 1` before it is final; see `F3-VAL-031`.
- Q36 (share-round restart). Deterministic for all honest validators: `selections` is a `BTreeMap` by root and `max_by_key` is deterministic (`state/sign.rs:623-629`). The comment's uniqueness claim (`state/sign.rs:618-622`) is not strictly true: a member that submits shares to two roots can make two selections reach the threshold if the honest validators are split across roots, which only happens after a reorg (`F3-VAL-031`). Without a reorg a misbehaving signer cannot split honest shares: every honest validator derives the same `committed` set (first valid commitment per signer, `state/sign.rs:253-285`) and so the same root (`frost/sign.rs:101-157`); fake roots carry only the attacker's shares, fewer than the threshold for f < n/3.
- Q37 (oracle approval and restarts). On the current branch the machine never reaches `CollectSigningShares` or a restart without an approving `OracleResult`: state is a function of the branch's events (resumes do not touch oracle state), and an `Uncle` restores `WaitingForOracle` (`crates/core/src/state/mod.rs:187-195`). However shares broadcast on an orphaned branch survive the reorg and can complete the attestation on a branch whose oracle did not approve: `F3-VAL-030`.
- Q38 (permissionless `sign`). An outsider's `Sign` is accepted only in `WaitingForRequest` with a matching group (`state/sign.rs:29-37`); every honest validator accepts the same first `Sign`, so they all proceed under the same id. For transaction packets the consensus `Sign` is in the same transaction as `TransactionProposed` (`contracts/src/Consensus.sol:253-267`), so no outsider can interleave; an earlier outsider `Sign` meets no session (`state/sign.rs:102-108`). In a restart, front-running the responsible party only supplies the `Sign` early. A later `Sign` is ignored (`state/sign.rs:94-101`). Verified correct within the accepted group-mismatch risk.
- Q39 (hash agreement and callback). `transaction_packet_hash` reduces to `transaction_proposal_hash` (`consensus/hashing.rs:142-150`), whose hand-rolled encoding matches `ConsensusMessages.transactionProposal` (`contracts/src/libraries/ConsensusMessages.sol:95-114`, typehash string identical) and is pinned against the `SolStruct` reference by `proposal_hash_matches_solstruct` (passed in command 3). `safe_tx_hash` uses the two-field domain like `SafeTransaction.partialHash`. The callback context encodes `attestTransaction` with seven arguments (`state/sign.rs:785-799`); `Consensus.onSignCompleted` decodes the first six and ignores the trailing zero signature id (`contracts/src/Consensus.sol:329-349`). Field order of the `sol!` bindings matches `IConsensus` and `FROSTCoordinator` (`crates/validator/src/bindings.rs:80-243`). Verified correct.
- Q40 (key share disappearing). Signing states carry their own `Arc<KeyShare>` (`state/mod.rs:260-345`), so reaping `epochs` (`state/secrets.rs:19-24`) only affects later `TransactionProposed` lookups (`state/transactions.rs:23-31`), which cannot target an epoch older than the contract's active one. Signing nonces of a group stay retained while any session references its epoch (`state/secrets.rs:26-30`). Verified correct; see observation O4 for a reorg-near-depth pruning caveat with liveness-only impact.
- INV-V8: holds. The signed message is always the state key the validator computed (`state/transactions.rs:42-47`, `state/keygen.rs:516-524`), carried through `Effect::UseNonces { message }` (`state/sign.rs:320-323`).
- INV-V9: holds per branch, broken across a reorg of 3 to 5 blocks (`F3-VAL-030`).
- INV-V10: holds for single use. Its clause "a used signature id never gets fresh nonces" does not hold once the row is collected (observation O3, documentation part of `F3-VAL-032`).
- INV-V11: holds (`state/sign.rs:253-285`, `frost/marshal.rs:168-181`).

## 6. Observations (plausible, not proven or below finding level)

- O1. A taken pair is burned when the process stops, or the effect task is aborted, between the clearing commit and the resume being applied (`secrets/store.rs:282-288`; `crates/core/src/effects.rs:35-43`; `crates/core/src/driver.rs:172-181` breaks on shutdown before collecting finished resumes). That validator then has no share for the ceremony, the share round times out and the ceremony restarts without it (one extra round, about 60 s). Safe by design (burning is preferred to reuse); liveness only. Overlaps R2's Q15.
- O2. `GenerateNonces` and `UseNonces` are not retried after a transient failure (`service/effect.rs:171-183` turns every error into `Resume::Noop`); a `SQLITE_BUSY` past the 5 s busy timeout or an I/O error silently drops this validator from that ceremony while the pair stays unused. Low; no concrete trigger at Aegis load.
- O3. After a group's rows are collected, a replay (restart from the oldest retained snapshot, or a reorg near the depth limit) re-running `GenerateNonces` for an old signature id stores a fresh pair (`secrets/store.rs:228-239`). Not a reuse: the old commitment stays first onchain, so a share from the fresh pair fails frost's commitment check (`frost-core-3.0.0/src/round2.rs:140-143`), and replayed actions past their deadline are not sent (`crates/core/src/tx/storage.rs:172-175`). The module documentation says the opposite; filed as part of `F3-VAL-032`.
- O4. The reconciliation marker orders by block number only. After a reorg of depth close to 5 where the new branch is longer, housekeeping can collect rows scheduled on the old branch before the new branch's reconciliation catches up with the marker (`secrets/store.rs:330-343`, `crates/core/src/driver.rs:256-263, 292-294`). Consequence: liveness only (a missing pair, regenerated fresh, commitment mismatch). Documented trade-off at `secrets/store.rs:38-41`.
- O5. A malicious member can be the last signer of a selection and finish the ceremony with plain `signShare` (no callback), forcing the 6-block `WaitingForAttestation` fallback where every validator submits `attestTransaction` and all but one revert (`state/sign.rs:670-688`). Bounded delay and gas; by design.
- O6. In the `WaitingForRequest` timeout with no responsible party left, every remaining signer sends `Sign` (`state/sign.rs:544-550`); all but the first create unused signature ids. Gas only.
- O7. Plaintext nonce JSON is built in a `String` that is not zeroized (`secrets/store.rs:236`, `:251`, `:291`). Memory hygiene under A1; Informational at most, not filed.
