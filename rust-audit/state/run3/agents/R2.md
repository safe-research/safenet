## Checklist answers

- Q9 (resumes not snapshotted, actions persisted): no validator or sentinel transition queues a second, different action after an uncle. Validator: `store_keygen_secrets` reuses stored secrets (`crates/validator/src/secrets/store.rs:172-208`), so a replayed `KeyGenSetup` yields the same commitment; `store_signing_nonces` is first-stored-wins; `take_signing_nonces` is take-once (`store.rs:266-294`), so a replayed `UseNonces` resumes `Noop`; `handle_key_gen_setup` only fills `secrets: None` (`state/keygen.rs:65-149`); `handle_nonce_commitments` checks the signature id (`state/sign.rs:117-145`). Sentinel: the verdict store is first-wins (`crates/sentinel/src/effect.rs:72-119`). Duplicates of the same action are queued (Q16). The related gap is that an uncle can also lose an effect for good: F3-CORE-032 (generalizes #973).
- Q10 (resumes that never arrive): effect failures resume `Noop` (validator `service/effect.rs:171-183`) and panics are skipped (`effects.rs:93`); nothing retries. States left waiting: validator `CollectingCommitments { secrets: None }` (genesis: no deadline, stalls, A16; rollover: abandoned at the deadline, `state/keygen.rs:1012-1039`, the validator sits out the epoch); `CollectNonceCommitments` and `CollectSigningShares` end at the signing timeout. Sentinel engine errors resolve to `Unknown` so a resume always arrives (`effect.rs:72-119`); a request whose effect is lost is dropped after its commit deadline (`service.rs:402-407`). A rollback can also strand a waiting state: F3-CORE-032. Observation O3.
- Q11 (inputs that make `handle_update` fail): within A4, a restart against a node whose head is below the oldest retained snapshot gives `BadUpdate` and the driver exits: F3-CORE-030 (E1). Duplicate logs would also be `BadUpdate` (`state/mod.rs:219-223`, `decode_and_sort` does not deduplicate, `index/events.rs:675-711`), but no reachable source was found (H6). Storage errors need more than 5 s of lock contention or a broken disk (H9). A2 chain data cannot reach `BadUpdate`: ordering comes from the watcher; transitions are infallible (panics would be owned by the service reviewers, H21).
- Q12 (optimistic `NewBlock(pending)`): semantics unchanged by #1015. `NewBlock(N + 1)` is applied after block `N`'s logs, so block `N` is mined and actions land at `N + 1` at the earliest (H10). The decision at `NewBlock(n)` never knew block `n`'s events, before or after #1015, and every honest node applies it at the same logical point. No core-level divergence; per-service deadline boundaries belong to R5 and R7.
- Q13 (`deny_unknown_fields` with `flatten`): a misspelled key fails startup at every level tried (E1, `logs/R2-startup-config-checks.txt`). Mechanism: serde's flattened structs claim only their own field names (`serde-1.0.228/src/private/de.rs` `flat_map_take_entry`) and the outer `deny_unknown_fields` rejects the rest. Minor: the reported position is line 1, column 1 with no key path (O8).
- Q14 (`from_str_with_env` errors): `url::ParseError` and `InvalidPrivateKey` carry no input; sqlx's SQLite parser echoes `mode`/`cache`/`immutable` values and unknown query keys (`sqlx-sqlite-0.9.0/src/options/parse.rs:62-109`), not the path; the variable value is never formatted (`serialization.rs:99-109`). The RPC URL does leak at startup, through alloy's connection-string parser rather than the `url` crate: F3-CORE-031 (E1).
- Q15 (SIGTERM): the shutdown branch is `biased` and checked first (`driver.rs:177-184`), so a resume that is ready when the signal arrives is dropped with the `EffectManager`. `UseNonces` is the costly case: the nonces are cleared before the resume (`store.rs:266-294`), so after the restart the replayed `UseNonces` resumes `Noop` and this validator gives no share for that ceremony. Liveness only, one ceremony; no nonce reuse. Observation O2.
- Q16 (actions without expiry, duplicates): the queue never deduplicates (`tx/storage.rs:112-127`). Each restart replays about `max_reorg_depth + 1` blocks (from the oldest snapshot) and re-queues their actions; a reorg of depth `d` re-queues `d` blocks. Expired duplicates are filtered before allocation (`tx/storage.rs:172-178`); no-expiry ones (validator genesis `deadline: None`, `SetValidatorStaker`; sentinel `Finalize`, `Claim`, `TimeoutArbitration`) are always sent and revert. Duplicate `Sign` events are ignored (`state/sign.rs:94-100`). Batches are best-effort, so a reverting duplicate does not sink a batch (`contracts/src/Safenet7702Executor.sol:96-111`). Gas only; observation O9.
- INV-C1: holds (`state/mod.rs:257-268`); a restart replays `NewBlock(N + 1)` (`state/mod.rs:196-208`). The part about effects is weaker than the docs claim: F3-CORE-032.
- INV-C2: holds in code; F3-CORE-030 is a reachable out-of-order sequence produced by the watcher.
- INV-C4: holds for the validator nonces and DKG secrets and the sentinel verdicts (see Q9); the replay that should re-run effects does not cover the restore point (F3-CORE-032).
- INV-C11: holds for TOML errors (`config.rs:33-48`), substitution errors, the signer (`tx/signer.rs:152-163`), and transport errors through `ObservabilityTransport` (`provider/mod.rs:124-134`). Broken by alloy's connection-string parser at startup (F3-CORE-031) and, with a debug filter, by alloy's `ReqwestTransport` span (O7, already listed in #1046).

## Hypotheses considered and rejected

- H1 misspelled keys vanish under `flatten` + `deny_unknown_fields`: refuted, E1 (`logs/R2-startup-config-checks.txt`).
- H2 a TOML error span starts inside a multi-byte character, so `contents[..span.start]` (`config.rs:39`) panics and the panic message quotes the document head (signer key): refuted for 200,000 mutated documents (`logs/R2-toml-span-fuzz.txt`); toml_parser keeps tokens on UTF-8 boundaries (`toml_parser-1.1.2/src/lexer/mod.rs`, boundary comments at 161, 203, 292, 628).
- H3 the `url` crate quotes a malformed URL: refuted, `url::ParseError` messages are fixed; the quote comes from alloy (F3-CORE-031).
- H4 the database URL leaks through sqlx errors: only query values and keys are echoed (parse.rs:62-109); not a secret in practice.
- H5 substitution errors leak a variable's value: refuted (`serialization.rs:99-109`, test `does_not_leak_variable_values_in_errors`).
- H6 duplicate topics make `Fetch::MultipleQueries` return each log twice and `handle_update` fail: refuted for the current bindings; `topics()` does not deduplicate (`index/events.rs:728-785`) but no event signature is shared (validator `Consensus`, `Coordinator`, `Oracle` events, `crates/validator/src/bindings.rs:112-243`; sentinel `SentinelOracle` and `Consensus`, `crates/sentinel/src/bindings.rs:25-50, 112-113`).
- H7 `revalidate_last_block` during an in-progress warp mutates the block queue, then `on_block_invalidated` fails and a later uncle is `BadUpdate`: refuted; during a warp every recent block is queued as `New`, so `rposition` finds no emitted block and it returns `Ok(None)` (`index/blocks.rs:540-556`, queue built at :396-420).
- H8 per-block `ReconcileGroupSecrets` effects during a long warp starve the driver's snapshot commit until `PoolTimedOut` (30 s) makes it fatal: refuted; the sqlx 0.9 pool is fair (`sqlx-core-0.9.0/src/pool/options.rs:151, 160, 163`), so each page's commit waits behind at most one page of effects, which throttles the page rate. The per-block write stays the known performance item.
- H9 driver writes fail with an immediate `SQLITE_BUSY` (read-then-write deadlock avoidance): refuted for driver paths; every driver transaction starts with a write (`state/storage.rs:107-114, 129-133`, `tx/storage.rs:112-127`), so the 5 s busy handler applies. Effect transactions also start with writes (`secrets/store.rs:172-256, 266-294, 321-352`).
- H10 optimistic `NewBlock(N + 1)` lets an action land in block `N`: refuted (applied after `Logs { N }`, `state/mod.rs:257-268`).
- H11 a resume after an uncle produces a second, different action: refuted (Q9).
- H12 the h2 advisory is reachable through the metrics listener: refuted; the listener uses `hyper::server::conn::http1` only (`metrics-exporter-prometheus-0.18.3/src/exporter/http_listener.rs:9, 77`).
- H13 the signal handlers panic on input: `unix::signal(...).unwrap()` (`utils.rs:17-36`) only fails if the runtime cannot install handlers; not input-driven.
- H14 `kdf::derive_key` treats multi-part messages as their concatenation (test at `kdf.rs:67-74`), so two callers could collide: refuted; the only caller passes one 32-byte part (`tx/signer.rs:127-131`, `crates/sentinel/src/hashing.rs:49-52`). `assert!` on the domain (`kdf.rs:20`) only sees a constant.
- H15 snapshot pruning drops an anchor a live reorg needs: refuted; the driver prunes below the watcher's anchor and uncles start above it (`driver.rs:263`, `index/blocks.rs:476-494`; test `restart_can_reorg_after_observing_an_uncommitted_block`).
- H16 housekeeping prunes verdicts or secrets the replay still needs: refuted for live operation; housekeeping uses the same `block_status.safe` as the snapshot prune in the same update (`driver.rs:242, 263, 292-294`). The restart case is the known replay-pruning item.
- H17 chain data can make a transaction queue error fatal: refuted; only non-RPC errors are fatal (`tx/mod.rs:65-72`), and `NonceNotFound` or `SigningError` need a missing row or chain id 0.
- H19 transient watcher errors end the driver: refuted (`driver.rs:211-225`); only `ExceededMaxReorgDepth` does (A5).
- H20 an effect panic ends the process: refuted (`effects.rs:93`, test `skips_panicked_tasks_without_losing_successful_resumes`).

## Observations (plausible, not proven, or below finding level)

- O1 RPC amplification during warps. Every warped block emits `ReconcileGroupSecrets` (`crates/validator/src/state/secrets.rs:78-84`), which resumes `Noop`. `next_input` races the watcher against resumes without bias (`driver.rs:229-232`); when the watcher branch is polled first it sends the page's `eth_getLogs`, and a ready resume then wins and drops it. With about 100 ready resumes per 100-block page, roughly half the iterations abandon a request, so a page can cost tens of `eth_getLogs` calls. Combines two known items (cancel safety of `next_input`, the per-block reconcile write); E2 only, not executed (the mock transport resolves on first poll).
- O2 SIGTERM drops ready resumes (`driver.rs:177-184`); a lost `UseNonces` resume costs this validator's share in one ceremony (Q15).
- O3 effect failures are never retried; a failed `KeyGenSetup` (SQLite error) skips the rollover epoch for this validator, or stalls genesis (Q10).
- O4 `/health` always answers `OK` (`metrics-exporter-prometheus-0.18.3/src/exporter/http_listener.rs:141-145`), also while the driver is stuck on a hung RPC call or in its retry loop. Monitoring gap, Informational.
- O5 the RPC client has no request timeout: alloy's `Http::new` uses `reqwest::Client::default()` (`alloy-transport-http-2.0.5/src/reqwest_transport.rs:34-36`), whose `timeout` and `read_timeout` are `None` (`reqwest-0.13.4/src/async_impl/client.rs:313-314`); TCP keepalive and the 30 s user timeout only catch dead peers. A server that holds a request open stalls the driver (watcher and queue calls are awaited inline). A4 trusts the RPC for liveness, so hardening.
- O6 the watcher retry logs `warn` every 100 ms with no backoff (`driver.rs:218-224`): about 860,000 lines a day during an outage and 10 requests a second against a rate-limited endpoint (seen in `logs/R2-stale-rpc-restart.txt`).
- O7 alloy's `debug_span!("ReqwestTransport", url = %this.url)` (`alloy-transport-http-2.0.5/src/reqwest_transport.rs:92`) records the RPC URL; #1046 lists it as needing `alloy_transport_http=debug`, but `log_filter = "debug"` or `"trace"` (written by `scripts/run_devnet.sh:377`) enables it too. Known per #1046.
- O8 unknown keys under flattened tables report "line 1, column 1" and no key path (`logs/R2-startup-config-checks.txt`); the field name is still shown. UX, Informational.
- O9 restart and reorg duplicates (Q16): gas only.
- O10 no `PRAGMA secure_delete` or `journal_mode` in scope (grep), so pruned snapshots (DKG `Secrets`, `SharingState`, retired `KeyShare`s in the snapshot JSON) and rollback-journal pages stay in free disk pages. Plaintext at rest is A1; hardening note.
- O11 `connect_sqlite` (`utils.rs:56-62`) keeps sqlx's `create_if_missing: false` (`sqlx-sqlite-0.9.0/src/options/mod.rs:200`), and the samples use `sqlite:/var/lib/...` without `?mode=rwc` (`crates/validator/validator.sample.toml:26`). Whether a fresh node starts is Q42 (R6); not run here (needs an RPC before the pool is opened).
- O12 no `[profile.release]` in `Cargo.toml`, so release builds (`crates/validator/Dockerfile:18`) wrap on integer overflow instead of panicking; core uses checked or saturating arithmetic where it matters (`state/mod.rs:144, 311-320`).
- O13 `MissingSnapshot` paths: a fresh start without `start_block` followed by a reorg of exactly `max_reorg_depth` before the first new block (`Uncle` of the first processed block needs the absent anchor snapshot), and a restart against a slightly stale node followed by a deep reorg. Both theoretical.
- O14 the metrics listener spawns one task per connection with no cap and retries `accept` errors in a tight loop (`http_listener.rs:56-66`); only matters if `metrics_address = "0.0.0.0:3555"` (handbook) is reachable by an attacker. Hardening.
- O15 warps apply resumes only between pages. #1017 makes warped blocks run `NewBlock` "at exactly the same blocks" (`state/mod.rs:231-239`), but every effect emitted inside a page resumes after the page, while live processing applies it before the next block. Example for R4 and the Critics: a validator whose restart replay warps over a key generation start and all its commitments takes the late-setup path, whose share-round deadline is `commitment deadline + key_gen_timeout` (`state/keygen.rs:130-133`) instead of `last commitment block + key_gen_timeout` (`state/keygen.rs:247-252`), so for up to `key_gen_timeout` blocks it can time out shares later than its peers. Not traced to a lasting divergence; liveness only.
