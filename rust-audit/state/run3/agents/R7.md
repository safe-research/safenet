## Checklist answers

- Q47. Commits processed while the request is in `WaitingForEngineCheck` are dropped and `commit_vote` restarts the tally at zero. The undercount fires the early finalize too soon: the request is dropped at the first foreign reveal (no claim) or a rejected `Finalize` parks it in `WaitingForOutcome` with no retry. Filed as F3-SEN-002 (executed). `WaitingForRequest` is unreachable on the live path because `NewRequest` and `TransactionProposed` share a transaction (`contracts/src/Consensus.sol:253-267`).
- Q48. Bond-holding paths without a claim: (a) undercounted tally, F3-SEN-002; (b) own reveal missed, dropped at `revealDeadline + 1`, F3-SEN-003 (known; the outcome-handler recovery is unreachable); (c) own commit ignored during a restart replay or after a live reorg, F3-SEN-004 (known, #961/#973; also the case #973 lists as recovered). `service.rs:423-427` drops only when the own `Committed` was not seen, which with a real bond happens only in (c). Every other path ends in `Claim`: `WaitingForOutcome` on any outcome event, `WaitingForDisputeResolution` on ruling, out of scope, arbitration timeout, and its own timeout branch (`service.rs:477-507`).
- Q49. The allowance cannot run short through ordering: `commit_vote` emits `ApproveToken` then `Commit` in one batch of commands, the queue preserves insertion order (`tx/storage.rs:172-175`, `ORDER BY id ASC`), Direct-mode nonces execute in order, and a Batched prefix keeps each approve before its commit, so `approve(X), commit(X), approve(Y), commit(Y)` holds in all modes. Duplicate pairs from replays leave a dangling allowance that the next approve overwrites. The real shortfall is gas: F3-SEN-001.
- Q50. `Consensus.proposeTransaction` computes `safeTxHash = transaction.hash()` and emits it with the same `transaction` (`Consensus.sol:258-264`), so id and engine input match. The id equals `ConsensusMessages.transactionProposal(epochs.active, oracle, keccak256(oracleData), safeTxHash)` in domain `(block.chainid, consensus)`: the sentinel's `TransactionProposal` struct hashes `bytes oracleData` as its keccak (EIP-712), the type string equals `TRANSACTION_PROPOSAL_TYPEHASH`, and the parity test `hashing.rs:148-166` pins it. The chain id comes from the provider (`main.rs:46, 72`). A misconfigured `consensus` silently ignores every request (observation O6).
- Q51. A late check (restart catch-up) still has the commit expiry at `commitDeadline`: the queue allocates only while `latest < expires_at` (`tx/storage.rs:172-175`), and an allocated commit resubmitted after the deadline reverts with `CommitWindowClosed`, so no bond is posted; cost is gas. Not a finding. The engine timeout is three quarters of `(voting_window - 1)` blocks from the start of the check (18.75 s with 6); in live operation the check starts about 1.6 s after block P and the commit can still land in P + 5 or P + 6.
- Q52. Revealed vote equals the commitment: `approve` and `reason` are stored in `CollectingCommitments` and moved into the `Reveal` (`service.rs:428-447`); the salt is re-derived deterministically; replays reuse the first recorded verdict (`verdicts.rs:99-121`, executed by `effect::tests::replayed_check_resumes_with_the_first_verdict`). Pruning: verdicts and snapshots are pruned against the same watcher `safe` (`driver.rs:242, 257-263`, `effect.rs:139-163`); retained snapshots are all at or above that block, and a replay only re-runs proposals above the oldest retained snapshot, so a needed verdict is never pruned. Verified correct.
- Q53. Unknown verdict, missing `rule`, malformed rule, non-2xx, transport error, timeout: all `Unknown`, no vote (`engine.rs:174-204`, tests at `engine.rs:344-429`). Extra fields are ignored (internally tagged enum without `deny_unknown_fields`). The rule string is re-rendered from the parsed `RuleId` (`service.rs:184`, `verdicts.rs:107`), so the onchain `reason` is canonical (`R-{u32}.{u32}`, at most 23 bytes) and identical in commit and reveal. A very large body is read unbounded (observation O2).
- Q54. alloy-sol-types 1.6.0 `decode_raw_log` does not validate, and `sol!` enums map out-of-range values to a hidden invalid variant, so a bad `outcome` cannot fail the page. The `outcome` is set by the oracle itself (`SentinelOracleRequests.sol:331`), and every fetch mode filters by contract address (`events.rs:497-555`), so no third party can emit it. Not reachable.
- Q55. Each action has a block to land in: `Commit` expires at `commitDeadline`, queued while the head is below it; `Reveal` is queued at `NewBlock(commitDeadline + 1)` (applied right after block `commitDeadline`'s logs) and expires at `revealDeadline`; `Finalize` at `revealDeadline + 1` and `TimeoutArbitration` at `arbitrationDeadline + 1` never expire and satisfy the oracle's strict `>` checks (`SentinelOracleRequests.sol:174, 225`). The known stranded bond at `revealDeadline + 1` is extended in F3-SEN-003.

## Observations (plausible, not filed)

- O1. The early `Finalize` in `handle_revealed` is always rejected onchain when the count is right, because the oracle finalizes inside the last `reveal` (`SentinelOracle.sol:256-258`). One wasted transaction per request (about 30,000 gas, negligible on Gnosis). Folded into F3-SEN-002's remediation.
- O2. `engine.rs:178` reads the engine response with no size limit. A3 (co-deployed engine): Informational.
- O3. `engine.rs:192-195` logs `%err`; reqwest's `Error` display appends the full URL (`reqwest-0.13.4/src/error.rs:279-281`). If an operator put credentials in `engine` (userinfo or a query token), every failed check would log them. The design does not expect secrets there (`engine` is not an `${NAME}` field, `config.rs:11-19`), and open issue #113 is the umbrella. Informational.
- O4. No concurrency limit on engine checks: a burst of proposals spawns one HTTP request each (`effects.rs` `JoinSet`). Each proposal costs the sponsor 0.40 USDC.e, refunded on timeout (known #549), so a burst can briefly overload a co-deployed engine and make the sentinel miss votes (no bond risk). Low at most.
- O5. `handle_arbitration_timeout` claims for any tracked entry without the `approve_and_slash_amount` guard the other outcome handlers use (`service.rs:586-606`); the states it would wrongly claim from are unreachable by then. Informational.
- O6. No startup check that the oracle's `PROPOSER` is the configured `consensus`; a wrong `consensus` makes every request id mismatch and the sentinel silently never votes (`NewRequest` for an untracked proposal logs at debug, `service.rs:295-298`). Operator error (A1).
- O7. `main.rs:48-52` says the timeout uses "the configured time until the block before the reveal deadline", while the sample says to set `voting_window` to the commit window (`sentinel.sample.toml:38-41`). An operator following the comment (12 on Aegis) would get a 41.25 s timeout, longer than the 30 s commit window: late commits revert, votes are missed, no bond is lost. Known TODO; Informational.
- O8. A storage error on `VerdictStore::get` during a replay resolves to `Unknown` and drops a request that may already have a commit onchain (`effect.rs:85-92`); needs SQLite busy for 5 s or a disk fault. Same outcome class as F3-SEN-004; not filed separately.
- O9. `WaitingForOutcome` entries that never see an outcome (F3-SEN-002 case 2) stay in the snapshot forever, growing the per-block snapshot by one entry per affected request.
- O10. `requests_proposed_total` is incremented again when a reorg or restart replays a proposal (metric only).
- O11. Dockerfile runs as root and builds from floating `rust:1-slim` and `debian:trixie-slim` tags (R8 owns Q61); `Dockerfile.dockerignore` admits all of `crates/**`, so any local config or database placed under `crates/` enters the builder stage (not the final image). Hardening.
