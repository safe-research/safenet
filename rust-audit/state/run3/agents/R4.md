## Findings written

- F3-VAL-001 (High, LEAD/E2): a cancelled identity verifying share excludes an honest validator; Rust `verify_secret_share` accepts `y = identity` (#1025) but the contract rejects it in `set` -> `requireNonZero`, so the honest victim's share reverts and it is excluded on timeout. One Byzantine participant causes two exclusions, dropping a 5/4 group below `min_participants`, freezing rollover.

## Checklist (Q25 to Q32)

- Q25 (commitments/confirmations counted by address, no local membership check): safe for safety. The contract gatekeeps: `keyGenCommit` requires a valid PoAP (`register` -> MerkleProof) and `--pending`, `keyGenConfirm` requires REGISTERED status, so events only fire for genuine participants. Rust can only lag the contract's `pending`, never lead it, because it inserts on verified events and the set is capped at `count`. The one real divergence (contract accepts, Rust rejects) is a liveness grief, see observation O1; the safety-relevant divergence is F3-VAL-001.
- Q26 (PoP of q vs PoK of c[0], same scheme/domain): cannot cross-substitute. Both use HDKG `H(identifier, phi, R)` bound to the identifier, with phi = q or c[0] respectively, so a proof is valid only for its own phi. `q == c[0]` is only a self-foot-gun (ties the ECDH key to a0), no leak for peers; a copied q is blocked by the PoP (must know the dlog). Matches the #1027 design. Not a finding.
- Q27 (share index ordering across group sizes/exclusions): consistent. Sender `generate_secret_shares` orders by ascending address excluding self (filter by identifier); receiver `verify_encrypted_secret_share` computes its index as `position` among ascending addresses excluding the sender. Both index the same ascending-address sequence with one element removed. Holds for lowest/highest addresses. keygen.rs:204-222, 361-377; marshal.rs:45-48. Not a finding.
- Q28 (identity in group key / verifying share / y): group key cannot be forced to identity (sum of c[0], each bound by PoK so an attacker cannot know the dlog of the cancelling sum). A verifying share CAN be forced to identity via unconstrained non-constant coefficients -> F3-VAL-001. frost-core rejects identity on element deserialize but `from_commitment` returns the computed point without a non-zero check, and Safenet's identity-tolerant serde (serialization.rs) preserves it.
- Q29 (keyGenConfirmWithCallback reverts on a late rollover): a keygen that finishes after `rolloverBlock = N * blocks_per_epoch` makes `proposeEpoch` revert (`_requireValidRollover`: `rolloverBlock > block.number`), so the last confirm reverts and the honest last-confirmer is excluded on the confirm timeout, then the stale epoch is skipped. Recoverable (the machine advances to the next due epoch). With Aegis params (120-block keygen inside a 1440-block epoch, max 1 exclusion in a 5/4 group) it cannot repeat enough to persist. Observation O2, not a finding.
- Q30 (late complaints count but need no response): matches the contract. `keyGenComplain` accepts complaints in SHARING/CONFIRMING and counts every (plaintiff, accused) toward `accusations`, never decrementing on response (#1019). Rust `complaint.total` mirrors this and `requires_response` is false past the local complain deadline; responses only resolve complaints still in `unresponded`, so a late complaint cannot resolve a different one. keygen.rs:725-729, 835-842; FROSTParticipantMap.sol:181-210. Not a finding.
- Q31 (resume KeyGenSetup after the state moved on; secrets reused per group+address): double-publish is guarded (`commitments.contains_key(&self.account)` -> skip; keygen.rs:94-107). A setup that resumes after the state left CollectingCommitments is dropped (`_ => (state, Vec::new())`); the state cannot reach CollectingShares with `secrets: None` (the all-committed arm returns early while secrets are None, keygen.rs:225-244). The deep-replay prune of keygen secrets is the settled/known item. Not a new finding.
- Q32 (different participants lists / active windows): each validator independently derives a group id from its own config; a mismatch yields a different id so the node never joins (observes) or fails to form a genesis set at startup (`InvalidValidators`). By design (INV-V1), tested against real on-chain values (`genesis_group_matches_the_parity_vector`, `actual_group`). Not a finding.

## Hypotheses considered and rejected

- H1: group key can be forced to the identity by a cancelling last committer. Rejected: c[0] is bound by a PoK forcing the attacker to know the dlog of its contribution, and the dlog of the negated sum of others' c[0] is unknown (sum of others' secrets). FROSTCoordinator.sol:374; frost-core keys/dkg.rs:445-470.
- H2: a copied/reused encryption key q lets an attacker decrypt a peer's shares. Rejected: the PoP of q binds it to the attacker's identifier and requires the dlog, so q cannot be copied (#1027). ecdh.rs:41-57, 113-126; test proof_of_possession_is_bound_to_identifier.
- H3: share index desync between sender and receiver for some exclusion set. Rejected: both sides walk ascending addresses with exactly the sender removed (Q27). keygen.rs:204-222, 361-377.
- H4: a non-participant can inflate the local commitment/confirmation count. Rejected: the contract only emits those events for registered participants with a valid PoAP; the Rust set is keyed by address and capped at count. FROSTParticipantMap.sol:146-153, 220-226.
- H5: the genesis or epoch group id or context diverges from the contract. Rejected: pinned by `actual_group` (real Gnosis tx) and `genesis_group_matches_the_parity_vector`; byte layout matches FROSTGroupId.create and group_context encodePacked. group.rs:249-297.
- H6: identifier derivation (`Identifier::derive(address)`) can panic or collide. Rejected: documented to never fail for this ciphersuite (participants.rs:16-19), injective over addresses, matches FROST.identifier and the TS port.
- H7: Secrets/SharingState/KeyShare leak through Debug. Rejected for the frost-core members (SecretPackage redacts coefficients/secret_share; SigningShare/EncryptionKey redact), but `Secrets`/`SharingState`/`KeyShare` derive `Debug` and `Serialize` and are held in snapshot JSON at rest; that is A1 (plaintext at rest, accepted) and the L-rust/R8 secret-in-logs census, not an R4 DKG defect. Noted as O3 for the Debug-in-logs reviewers.

## Observations (plausible, not proven to finding grade)

- O1: Rust `verify_commitment` rejects non-constant coefficient points that are off-curve or malformed, which the contract never validates (it checks only `c.length`, `c[0]` PoK, `q` PoP). A malicious last committer can post a commitment the contract accepts but every honest validator rejects, stalling the commitment round until timeout, then the attacker is excluded and keygen restarts. Bounded liveness grief (one round, self-harm), same class as issue #69. keygen.rs:85-107 vs FROSTCoordinator.sol:361-380.
- O2: a keygen that finishes after its `rolloverBlock` makes the confirm callback (`proposeEpoch`) revert, excluding the honest last-confirmer on the confirm timeout and skipping the stale epoch (Q29). Bounded under Aegis params. keygen.rs:1328-1370 (callback), Consensus.sol:217-224, 395-397.
- O3: a participant can submit a bogus but on-curve non-zero `y` that the contract's `set` accepts (it does not check y against the committed polynomial) while every honest Rust validator rejects it (recomputed-share mismatch). The bogus submitter is excluded on timeout and the abandoned group never finalizes, so no bad y reaches signing. Liveness grief, self-harm. FROSTParticipantMap.sol:161-168 vs keygen.rs:276-288.
- O4: `Secrets`, `SharingState`, `KeyShare` derive `Debug` + `Serialize` and live in the snapshot JSON (state/mod.rs:161-201). Covered by A1 and the cross-cutting secret-in-logs census; flagged here for L-rust/R8.
