## Checklist

- **Q1 (reorg while down, below the oldest snapshot).** Not detected; replayed as canonical. Snapshots have no hash (`crates/core/src/state/storage.rs:51-54`) and resume trusts the snapshot at `indexed.safe` (`crates/core/src/index/blocks.rs:315-320`). The same holds after a live `ExceededMaxReorgDepth` exit followed by a restart. Filed as `F3-CORE-004`.
- **Q2 (warp completeness).** Nothing limits it. Warp pages use a node-filtered range query with no bloom or count check (`events.rs:369-394`; the bloom check exists only for client-filtered new blocks, `events.rs:533-548`; `max_logs_per_query` defaults to none, `events.rs:111`). A page that silently misses logs is committed and never re-queried. Recorded as observation O1 (not filed: the documented failure mode concerns blocks queried right after they appear, and warps stop at least `max_reorg_depth` blocks below the head).
- **Q3 (undecodable watched log).** The stall is real: any decode failure fails the page (`events.rs:682-708`), warp pages shrink to one block and keep failing (`events.rs:416-431, 656-660`), new blocks keep failing in per-event mode (`events.rs:474-484`), and the driver retries forever (`driver.rs:218-223`). No reachable trigger found: every watched event in both bindings matches its contract declaration in types and `indexed` flags; decoding uses alloy's non-validating `decode_raw_log` (`alloy-sol-types-1.6.0/src/types/event/mod.rs:186-196`), which decodes strings lossily (`data_type.rs:382-388`), maps out-of-range enum values to `__Invalid` (`alloy-sol-macro-expander-1.6.0/src/expand/enum.rs:62-66, 166-170`) and ignores extra topics (`topic_list.rs:47-55`). `Consensus.proposeTransaction` takes the transaction as a memory struct, so its enum is validated by the ABI decoder (`contracts/src/Consensus.sol:253`). No contract in scope emits logs from assembly. Observation O7.
- **Q4 (shared event signatures).** None. Validator set: Consensus 5, Coordinator 10, Oracle 1, all distinct names (`crates/validator/src/bindings.rs:112-146, 171-208, 242-243`); sentinel set: SentinelOracle 10, Consensus 1 (`crates/sentinel/src/bindings.rs:25-50, 112-121`). So per-event queries cannot return a log twice (which `crates/core/src/state/mod.rs:219-223` would reject as `BadUpdate`). Dispatch ignores `log.address` for Consensus and Coordinator events, so this relies on configured oracles never emitting a colliding signature; the oracle contracts emit only `OracleResult` and SentinelOracle's own events.
- **Q5 (timestamps).** A log cannot carry another block's timestamp at the default depth: new-block logs are fetched by hash and fall back to the same block's header (`events.rs:466-472`); warp logs fall back to headers fetched by number inside the reorg-safe range (`events.rs:598-634`). Consumers: only the sentinel's engine header `x-proposal-timestamp` (`crates/sentinel/src/service.rs:954-963`, `crates/sentinel/src/engine.rs:157-160`); the validator state does not read timestamps. With `max_reorg_depth = 0` the warp reaches the head, where a header fetched by number could belong to a replacement block (O3).
- **Q6 (revalidation loop and `UnexpectedBlockInvalidation`).** `UnexpectedBlockInvalidation` is unreachable in the normal flow: revalidation picks the last emitted block (`blocks.rs:551-559`), which is the block the event watcher is fetching, and returns `None` while warping (the next queued update is then `New { safe + 1 }` and no block in `recent` is below it, `blocks.rs:543-558`). Loops: a warp page answered with `-32001` is retried forever (by design, `blocks.rs:541-547`); with `max_reorg_depth = 0`, `recent` is always empty, so revalidation never invalidates and a Reth-style uncled block is retried forever (O3); recovery only covers code `-32001` (`index/mod.rs:135-142`), so a node that answers logs of an uncled hash with another code stalls the watcher (O9).
- **Q7 (warp versus live transitions).** Same order: warped blocks get `NewBlock(b)` before their logs (`state/mod.rs:230-244`), intermediate pages get no optimistic block, the last page applies `NewBlock(to + 1)` optimistically (`:246-268`) and the queued `New { to + 1 }` skips it (`:203-205`). Differences are only snapshot granularity (page ends) and where resumes interleave, which the design leaves unordered.
- **Q8 (discovery after outages and skipped slots).** RPC errors are retried every 100 ms; `None` answers walk the retry list and then advance the expected time by one block (`blocks.rs:459-470`), so discovery does not stop and recovers within one retry after the node answers. It can fall behind permanently when the host clock is behind the chain: filed as `F3-CORE-005`. It also stops completely whenever the event watcher is stuck, because the block watcher is only polled after the event watcher drains (`index/mod.rs:85-97`), which is what makes `F3-CORE-001` a full stall.
- **INV-C3.** Holds for reorgs within `max_reorg_depth`: the driver prunes below the watcher's safe block (`driver.rs:242, 263`), the watcher's oldest uncle is `safe + 1` (`blocks.rs:476-494`), and after a warp the last page's snapshot is the safe block (`events.rs:369`, `state/mod.rs:257`). Exception: on a fresh start the first indexed block has no parent snapshot (O4).
- **INV-C5.** Holds while running (`blocks.rs:490-494`, `driver.rs:213-217`), including `max_reorg_depth = 0` for reorgs seen through new blocks. It does not hold across a restart (`F3-CORE-004`), and with depth 0 a reorg seen only through unavailable logs is retried forever instead of failing (O3).
- **INV-C6.** Holds at the default depth: warps end at `latest - max_reorg_depth` (`blocks.rs:300, 325-343`) and header-by-number lookups happen only in `warp` (`events.rs:397-399`); `decode_and_sort` refuses a log without a timestamp (`events.rs:687-690`).

## Hypotheses considered and rejected

1. Per-event queries return duplicates that the state machine rejects as `BadUpdate`: rejected, no duplicate topic0 in either event set (Q4).
2. `DisputeResolved.outcome` out of range fails the page: rejected, non-validating enum decoding yields `__Invalid` (`alloy-sol-macro-expander-1.6.0/src/expand/enum.rs:62-66, 166-170`); its meaning is R7's.
3. Invalid UTF-8 in `Revealed.reason` (sentinel-chosen) fails the page for every sentinel: rejected, strings decode lossily (`alloy-sol-types-1.6.0/src/types/data_type.rs:382-388`).
4. A `TransactionProposed` with `operation = 2` fails the validator's decoding: rejected, the contract's memory-struct parameter validates the enum on entry (`contracts/src/Consensus.sol:253`).
5. `on_block_update` fails after the block watcher already advanced, losing a block: rejected, `Watcher::next` calls it only after `next_logs` returned `None`, which means the event watcher is idle (`index/mod.rs:86-95`, `events.rs:264-267`).
6. `on_block_invalidated` mismatch (`UnexpectedBlockInvalidation`): rejected (Q6).
7. A live uncle for the optimistically applied block hits `BlockApplied` with `number == pending` and fails: rejected, uncles are only emitted for blocks already emitted as `New` (`blocks.rs:476-488, 566-589`), so `number < pending`.
8. Pruning drops a snapshot a reorg within depth needs: rejected (INV-C3), apart from O4.
9. Warp and live paths apply different transitions (Q7): rejected.
10. Mixed-up timestamps across blocks (Q5): rejected at the default depth.
11. Block discovery stops after an RPC outage (Q8): rejected; errors are retried every 100 ms and `None` advances one block time per cycle.
12. `timestamp * 1000` overflow in `blocks.rs:482, 582, 598`: rejected, needs absurd header timestamps (A4 excludes a malicious RPC).
13. Empty watched-address list turning the filter into "all addresses": rejected, both services always pass at least two addresses (`crates/validator/src/main.rs:56-57`, `crates/sentinel/src/main.rs:84`).
14. `may_contain_log` returning `false` for empty inputs and skipping logs: rejected, the function is not called in production.
15. A mid-init reorg to a shorter chain: `require_block(latest_number)` fails with `MissingBlock` and startup errors (`blocks.rs:360-363, 376-380`); transient, a retry starts normally. Not filed.

## Observations (plausible, not proven)

- **O1, warp completeness (Q2).** Warp pages are trusted as complete. A load-balanced endpoint whose serving backend lags behind the page's upper block, or any node that returns partial ranges, loses events permanently. The bloom check could be applied per block of a page, at the cost of header requests. Evidence: `events.rs:369-394`, `:533-548`.
- **O2, bloom equality is not completeness.** The client-filtered check recomputes the bloom over the returned logs (`events.rs:542`). A partial answer that drops a log whose address and topics are also set by another log in the same block (for example two `KeyGenCommitted` from the Coordinator for the same group: same address, topic0 and `gid`) leaves the bloom unchanged and passes. Also, a block stuffed with cheap junk logs from any contract (`LOG0` costs 375 gas, so tens of thousands fit in one 17M-gas block) makes the all-logs query exceed provider result caps, which pushes client-filtering nodes onto the unchecked fallback for that block (see `F3-CORE-002`).
- **O3, `max_reorg_depth = 0`.** `recent` stays empty, so `revalidate_last_block` never invalidates (`blocks.rs:551-558`) and a block whose logs the node can no longer serve is retried forever instead of failing loudly; the warp also reaches the head (`blocks.rs:300`), where the empty-array behaviour from the handbooks applies and timestamps by number may belong to a replacement block. Non-default configuration.
- **O4, fresh start, reorg of the first indexed block.** Without `start_block` (or with one inside the reorg window) the first indexed block has no parent snapshot; a reorg that reaches it (5 deep, within one block time of startup) makes `reorg` fail with `MissingSnapshot` (`state/storage.rs:134-139`), poisoning the machine; on restart the uncled first block is kept as the anchor. Very narrow window.
- **O5, spurious uncle from a lagging backend.** `revalidate_last_block` treats `None` at the last block's height as uncled (`blocks.rs:561-564`), so a load-balanced backend that has not seen the block yet triggers a one-block rollback and replay, with the re-applied `NewBlock` re-emitting its actions. Consequences for duplicate actions belong to R2 and R3 (Q9, Q16).
- **O6, `max_logs_per_query` (opt-in, undocumented).** When set to `M`, a block with at least `M` logs of one watched event fails every attempt, including per-event and one-block pages (`events.rs:639-651`). `sign` and `keyGen` on the Coordinator are permissionless, so a cheap spammer can fill a block with one event type and stall every node using a small `M`.
- **O7, one undecodable log stalls the watcher forever (Q3).** No reachable trigger with the current bindings, but there is no skip, quarantine or exit path; a future binding drift on a rare event would halt every node at that block.
- **O8, no bloom skip.** `may_contain_log` is dead code (`index/mod.rs:5-6`, `bloom.rs:23-35`), so every new block costs one `eth_getLogs` even when its bloom excludes every watched address or topic; the TypeScript watcher skipped such blocks. Performance and RPC budget only.
- **O9, uncled-block recovery depends on error code `-32001`.** `next_logs` revalidates only for `ResourceNotFound` (`index/mod.rs:109-126`, `:135-142`). A node that answers logs of an uncled hash it never saw with another code (geth-style clients return `-32000` "unknown block") keeps the event watcher retrying that hash, and the block watcher, which would detect the reorg, is not polled meanwhile. Needs data on Gnosis clients (Nethermind, Erigon) behind load-balanced endpoints.
- **O10, unbounded header fan-out on warps.** `fetch_missing_block_timestamps` fetches up to one header per block of the page concurrently (`events.rs:610-620`), up to 100 at once for nodes that omit `blockTimestamp`, which adds to the rate-limit pressure behind `F3-CORE-001`.
- **O11, RPC calls have no timeout.** The provider is built with `ClientBuilder::default()` and no timeout layer (`provider/mod.rs:146-149`); a request that never gets an answer blocks the watcher for as long as the connection stays open. Provider construction is R2's file; noted here because it stalls indexing.
- **O12, zero timings.** `block_time = 0` with `block_retry_delays = []` makes the pending-block loop poll with no sleep at all (`blocks.rs:459-470`); no validation of the timings. Configuration only.
- **Cross-reference.** Warps replay old blocks through the same transitions, so actions without an expiry (validator genesis actions, sentinel `Claim`, `Finalize`, `TimeoutArbitration`) can be queued for long-past history during a `start_block` back-fill; the queue's expiry filter does not drop them. Belongs to R2 (Q16).
