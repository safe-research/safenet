## Claim

Known item (`settled.md` section 2: "A bond can be stranded at `revealDeadline + 1` in the sentinel's deadline handling"). This finding adds three things.

At `NewBlock(revealDeadline + 1)` the reveal-deadline branch calls `finalize()`. If this sentinel committed but its own reveal did not land in time and at least one other sentinel revealed, `finalize()` returns no state and the request is removed. The oracle then slashes only the governed `slashAmount` from a non-revealer (0.40 USDC.e on Aegis) and owes the rest of the bond (799.60 USDC.e) back through `claim`, which only the sentinel itself can call. Nothing in the state machine ever claims it.

Addition 1: the recovery code written for exactly this case is unreachable in live operation. `handle_oracle_result` records `ResolvedOutcome::RevealMissed` and claims when the outcome event finds the request in `CollectingVotes` with `self_revealed == false`, and `approve_and_slash_amount` documents recovery from `CollectingCommitments`/`CollectingVotes`. But the oracle cannot emit an outcome for a request with an unrevealed commitment before `revealDeadline + 1` (its `finalize` guard), and the core applies `NewBlock(revealDeadline + 1)` before any log of that block, live and in warps. So `finalize()` always removes the request first; the `RevealMissed` metric can never be recorded, and the unit test that covers this recovery drives an ordering the oracle cannot produce (an `OracleResult` at block 22 with `revealDeadline` 40).

Addition 2: the amount. A missed reveal costs 0.40 USDC.e by protocol design; the state machine turns it into 800 USDC.e locked until manual action, because the claim is never sent.

Addition 3: the triggers are ordinary. The reveal has six blocks (30 s) to land: a reveal priced too low is only resubmitted after `blocks_before_resubmit` (2) blocks, in Batched mode one stuck batch blocks every later action, and a restart or outage across the reveal window replays `NewBlock(revealDeadline + 1)` with the reveal expired. F3-SEN-002 reaches the same drop earlier through an undercounted commit tally.

## Trigger

Aegis request opened in block P (`commitDeadline` P + 6, `revealDeadline` P + 12), this sentinel and one other committed:

1. At `NewBlock(P + 7)` this sentinel queues its `Reveal` (expiry P + 12). It is not mined by block P + 12: for example, its fee estimate was too low and it was only resubmitted after two blocks, or a Batched-mode batch ahead of it was stuck, or the node was down from P + 7 to P + 13.
2. The other sentinel's reveal lands within the window.
3. `NewBlock(P + 13)` runs `finalize()`: `self_revealed` false, `revealed_count` 1, so the request is removed with no action.
4. The other sentinel's `finalize()` lands in P + 13, emitting `OracleResult`; this sentinel finds no entry. Its commitment is `PENDING`, slashed by 0.40 USDC.e; 799.60 USDC.e stay claimable by it alone, with no claim ever queued.

## Considered and rejected

- The outcome handlers' recovery: unreachable, as shown (rows 3 to 5, 7, 8). The same reasoning applies to `handle_dispute_triggered`, and to the `CollectingCommitments` branch of `approve_and_slash_amount`: with this sentinel's own commitment onchain, no outcome can precede `NewBlock(commitDeadline + 1)` either.
- Nobody revealed: then `revealed_count == 0`, `finalize()` sends `Finalize`, and the `RequestTimedOut` path claims the full bond. Not affected.
- Already known: yes, tagged `known`; the additions are the unreachable recovery path and its misleading test, the amount, and the routine triggers.
- Code age: pre-existing; the drop rule is at `fe9e84c` `crates/sentinel/src/service.rs:653`.

## Remediation options

1. In `finalize()`, keep a request this sentinel committed to even when it did not reveal: send `Finalize` (harmless if someone else's lands first) and move to `WaitingForOutcome`, so the existing outcome handlers claim and record `RevealMissed`.
2. Alternatively, queue `Claim` directly at `revealDeadline + 1` behind a `Finalize`, as the arbitration-timeout branch already does with `TimeoutArbitration` plus `Claim` (`service.rs:494-505`).
3. Replace the unit test's block 22 with an `OracleResult` after `NewBlock(revealDeadline + 1)`, so the test exercises an ordering the oracle can produce.
