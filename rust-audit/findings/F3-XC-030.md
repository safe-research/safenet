## Claim

`Driver::update` passes a log update to `StateMachine::handle_update`, which commits the snapshot for the update's last block before it returns the commands. The driver then prunes snapshots below the watcher's safe block, and only afterwards encodes the actions and stores them in the transaction queue. In steady state this order is safe: about `max_reorg_depth + 1` snapshots remain, and a restart rolls back to the oldest one and replays the rest, so actions lost in a crash are emitted again. During a warp it is not. Every warp page ends at or below the watcher's safe block, so the prune leaves the page's own snapshot as the only one, and a restart that finds a single snapshot emits no synthetic uncle and resumes after it. A process kill, OOM kill, host failure or fatal storage error after the prune and before the queue insert commits loses every action that page produced, and nothing emits them again.

R8 rejected this family as R-12 ("a crash after the snapshot commit replays from the safe snapshot"). That holds in steady state only: during a warp the safe snapshot is the page's own snapshot.

The actions at stake are those that event and block transitions emit during a catch-up. For the validator the clearest is `KeyGenSecretShare`, emitted on the last `KeyGenCommitted` of a round with an expiry of that block plus `key_gen_timeout` (120 blocks), so it is still live when a restart warp replays it up to five blocks behind the head. If it is lost, the validator's shares are never published, the share timeout excludes it, and it sits out that epoch. The same holds for `KeyGenConfirm` and complaint responses. For the sentinel the comparable actions are `Claim` and `Finalize`, which can be sent by hand later; its reveal is already too late by the time a restart warp reaches it under the Aegis windows of 6 and 6 blocks.

## Trigger

1. A validator restarts after some downtime (or starts fresh with a `start_block`). `BlockWatcher::initialize` sets its safe anchor to `latest - 5` and queues `Warp { from: S + 1, to: latest - 5 }` (blocks.rs:300, 325-331; for a fresh start, :333-343), paged at up to 100 blocks.
2. A page contains the last `KeyGenCommitted` of a key generation round whose share deadline (that block plus 120) is still ahead, so `handle_update` returns a `KeyGenSecretShare` action for it.
3. The page's snapshot is committed (state/mod.rs:257), and the prune at the warp's end leaves it as the only snapshot (driver.rs:263). Before `enqueue` commits (tx/storage.rs:112-126) the process dies: `kill -9`, an OOM kill, a host failure, or `enqueue` returns a SQLite error, which is fatal (Basis 8).
4. On restart the store reports `{ safe: W, latest: W }`; no uncle is queued and the watcher warps from `W + 1` (Basis 5 and 6). The share is never queued; at the share deadline the other validators exclude this one (Basis 10) and it sits out the epoch.

The exposed window is the encode plus one SQLite write transaction per warp page (milliseconds; sqlx leaves `synchronous` at SQLite's default, so the commit waits for fsync), and only warp pages, plus the first block of a fresh start without `start_block`, have it. A graceful stop is safe: the run loop finishes the current input before it looks at the shutdown signal (driver.rs:186-187).

## Considered and rejected

- Steady state: the prune keeps `safe..=latest`, and the restart's uncle at `safe + 1` replays the lost block (blocks.rs:315-320); the replay duplicates actions, which R2 (Q16) found to cost gas only.
- A crash before the prune: two snapshots remain, the restart's uncle restores the earlier one and replays the page. Only the window from the prune to the queue commit loses actions.
- Intermittent RPC errors in `queue`: rows are stored before `submit_pending` (tx/mod.rs:153-161), so R-12's main point stands.
- Does a later transition emit the lost action again? No. The transition already moved the round to `CollectingShares` with this validator's share computed (keygen.rs:1262-1273); nothing re-sends an action that never reached the queue, and the queue persists only what was inserted.
- F3-CORE-032 (an effect emitted in the restore-point block is never performed again after any rollback) shares the root cause, commands that are not durable together with the snapshot that records their emission, but needs no crash and concerns effects. This item concerns actions and needs a crash in the window. Kept separate; the head may fold it into F3-CORE-032 as a second consequence.
- Severity: the PROMPT.md scale lists crash-consistency gaps with recoverable impact under Medium, but the window is milliseconds per warp page, needs an independent hard failure, and the worst live consequence found is one validator sitting out one epoch. Low, in line with F3-CORE-032.
- Introduced since run 2? No. `driver.rs` and `state/storage.rs` are unchanged since `fe9e84c` (baseline section 5) and the single-snapshot resume without an uncle came with #685 (`dcc6fcf`, 2026-08-07). #1017 since run 2 made warped blocks run `NewBlock` too, which adds block-driven actions to warp pages.

## Remediation options

1. Prune after queuing: move `self.state.prune(block_status.safe)` (driver.rs:263) below the queue call (after :290). A crash before the queue commit then leaves the previous snapshot, the restart's uncle replays the page and its actions are queued again; a crash after it gives the replay duplicates that already happen on every restart (expired ones are filtered before allocation, tx/storage.rs:172-178). One moved line, no schema change.
2. Or store the snapshot and the page's actions in one SQLite transaction; the snapshot store and the queue already share one pool and one file. Exact, but it couples the state machine and the queue across a module boundary.

Tests to add: a restart test that applies a warp page whose event returns an action, runs the driver's prune, stops before queuing (the crash), restarts on the same pool and asserts the action is queued exactly once. It fails today (the existing `warps_and_prunes_intermediate_snapshots` already shows the page is not replayed) and passes with option 1. No code is committed.

The test service returns an action for each watched event, and the queue keeps rows in its `transactions` table so they can be counted. A test-only hook panics the driver task right before `self.transactions.queue(...)` (`crates/core/src/driver.rs:283`), so nothing more reaches SQLite, as with kill -9. Run 0 follows the chain live up to 993 (snapshots 988 to 993). Run 2 resumes after 1004 and the action for 997 is never queued (0 rows). Controls: the same warp without the crash queues it once; a crash on a live block (event at 996) leaves snapshots 991 to 996, and run 2's uncle replays the block and queues the action once.

Command and output: `poc/F3-XC-030/` (`warp-crash-test-at-361aaf3.txt`).

Bite check: remediation 1 (prune after the queue insert): the same crash leaves snapshots 988 and 1004, run 2 replays the page and queues the action once; the controls are unchanged and the other 151 core tests pass. Sound; a crash after the insert gives a duplicate on replay, which already happens on every restart.
