## Claim

`handle_revealed` calls `finalize` as soon as its local reveal tally reaches its local commit tally, and `finalize` queues a `Finalize` transaction. In `SentinelOracle`, the `reveal` call that brings `revealedCount` up to `committedCount` already calls `finalize(requestId)` itself, in the same transaction. So whenever the sentinel's tally is accurate, the request is no longer `PENDING` by the time its own `Finalize` lands, and the call reverts with `RequestNotPending`. When the tally is low (F3-XC-001), the call reverts with `FinalizeTooEarly` instead. The early `Finalize` therefore never succeeds: every request that resolves by unanimous or split reveal costs each revealing sentinel one reverted transaction, and in Direct mode it also takes a nonce and a slot of the in-flight window. The outcome event is emitted by the last reveal, so the sentinel still claims; only gas and queue capacity are lost. The existing flow test asserts this `Finalize` as expected behaviour.

## Trigger

Any request where every committed sentinel reveals: the last `Revealed` log is processed, the local tallies meet, `Finalize` is queued, and the same transaction's `OracleResult` or `DisputeTriggered` follows in the same block. The `Finalize` lands one block or more later and reverts. Each revealing sentinel pays for one reverted `finalize` call per request resolved this way (gas limit 250,000, service.rs:912-919; the gas used is that of the revert path only).

## Considered and rejected

- Could the early `Finalize` ever be the call that resolves the request? Only if onchain `committedCount == revealedCount` without the last `reveal` having finalized, which Basis 3 rules out; or with a high local tally, which cannot happen because every counted `Committed` log is a real onchain commitment.
- Does the revert break claiming? No: `handle_oracle_result` and `handle_dispute_triggered` act on the event emitted by the reveal (service.rs:819-861, 766-796).
- In Batched mode the failing call is swallowed by the executor (`contracts/src/Safenet7702Executor.sol:106-109`), so the batch is not lost; the gas is.
- Introduced since run 2? No. The same early-finalize path is at `fe9e84c` (line 372 of that version).

## Remediation options

1. Drop the early `Finalize`: when the local tallies meet, move to `WaitingForOutcome` without an action and rely on the oracle's own finalize in the last `reveal`. Keep `Finalize` for the reveal-deadline path, where it is needed.
2. If an explicit call is wanted as a fallback, schedule it for `revealDeadline + 1` only, which also covers F3-XC-001 variant B.

Tests to add: update the flow test at service.rs:1564-1587 to expect no action after the last reveal and a `Claim` after the outcome event. No code is committed.

Whenever the local tallies are right, the `Revealed` log that makes them meet comes from the transaction whose `reveal` already ran `finalize` (`SentinelOracle.sol:256-258`), and its `OracleResult` or `DisputeTriggered` follows in the same block, so the queued `Finalize` reverts with `RequestNotPending`. The gas actually burned is only the revert path, so Informational stays right.
