## Claim

`state.active_epoch` is advanced in exactly one place: `handle_rollover_new_block`, and only when the local rollover state is `EpochStaged`, i.e. when this validator itself generated the group that was staged. An `EpochStaged` event for any other group is ignored by the `_` branch of `handle_epoch_staged`. A validator that was excluded from epoch `k+1` (F2-VAL-003/004/005, a missed share, a timeout) therefore keeps `active_epoch = k` while the chain's active epoch is `k+1`.

When it then takes part in the key generation for `k+2` and the last confirmation lands, `handle_key_gen_confirmed` computes the rollover message as `epoch_rollover_hash(active_epoch = k, k+2, ...)` - not the message the coordinator will be asked to sign, which uses the contract's active epoch `k+1` - and, because `state.epochs` still holds epoch `k` (retained down to `active_epoch` by the reconciliation), inserts a `WaitingForRequest` session keyed by the wrong hash, with epoch `k`'s key share and epoch `k`'s participants as signers. The real `Sign` for the `k+2` rollover never matches it. On the session's timeout the generic recovery removes the responsible party and, since this validator is among epoch `k`'s signers, broadcasts `Coordinator.sign(gid_k, wrong_message)` (150k gas), which opens a real onchain session on the finalised epoch-`k` group; every epoch-`k` member observes the junk sequence number and this validator additionally reveals a nonce for it. The outcome is a wasted sequence number and nonce for the stale group and two wasted transactions per rollover until the validator is next inside a staged epoch, at which point `active_epoch` catches up. The signing of the actual rollover is unaffected (this validator is not one of its signers), so the impact is bounded to griefing the validator itself and, if epoch `k` is still the active group onchain, one junk ceremony on the live group.

## Trigger

1. Validator `V` is in epoch `k` and misses epoch `k+1`'s key generation (any of F2-VAL-003/004/005 or a share timeout): its rollover state ends in `EpochSkipped{k+1}`; the peers stage `k+1` with a group `V` is not in; `V` ignores that `EpochStaged` (row 2). At block `(k+1)·bpe`, row 1 leaves `active_epoch = k`.
2. `V` joins the `k+2` key generation normally. At the final `KeyGenConfirmed`, row 3 computes `epoch_rollover_hash(k, k+2, ...)` and inserts a `WaitingForRequest` with epoch `k`'s key share (row 4) and `responsible = last confirmer`.
3. The responsible party submits `sign(gid_{k+1}, hash(k+1, k+2, ...))`; `V` has no session for that message. After `signing_timeout` (6 blocks) row 5 fires: `V` broadcasts `sign(gid_k, hash(k, k+2, ...))`, the coordinator emits `Sign` for the finalised group `gid_k`, all epoch-`k` members advance their sequence bookkeeping for it (`state/sign.rs`, R5), `V` reveals a nonce for its own phantom session and nobody else joins; the session is dropped on the next timeout.

## Considered and rejected

- _`V` is not a signer of the real rollover, so nothing is lost._ Correct for the attestation; what is lost is `V`'s nonce and gas and one sequence number of group `k` for everyone, which is why the severity is Low.
- _`handle_transaction_proposed` uses `epochs`, not `active_epoch`._ Not checked in this assignment (R5); the finding is limited to the rollover path.

## Remediation options

1. Track the chain's active epoch from every `EpochStaged` event (`event.activeEpoch`/`proposedEpoch` are in the event, `bindings.rs:120-128`) and roll `active_epoch` forward at the rollover block regardless of who generated the group. Tradeoff: none of substance; `EpochSkipped` becomes informational.
2. In `handle_key_gen_confirmed`, only open the rollover signing session when `state.epochs.get(&active_epoch)` is the group that is actually active onchain (e.g. compare against the last observed `EpochStaged.groupId`). Tradeoff: needs that group id kept in state.

Tests to add: a state test staging epoch `k+1` for a foreign group, then confirming `k+2`, asserting the rollover hash uses `k+1` and no session is opened with epoch `k`'s key share.

## Critic (C2-VAL-A)

**Finding verdict: Confirmed (mechanism). Severity Low (unchanged). Certainty 65%.**

Mechanism verified end to end:

- **[E2] `active_epoch` advances only from `EpochStaged`** (keygen.rs:930-938; the `else` arm just warns), and a staged epoch for a foreign group is ignored (keygen.rs:636-645). So a validator excluded from epoch `k+1` keeps `active_epoch = k` while the chain is at `k+1`. Supported.
- **[E2] The stale hash and phantom session.** `handle_key_gen_confirmed` for `k+2` builds the rollover message from `state.active_epoch` (keygen.rs:516-526) and inserts a `WaitingForRequest` keyed by that (wrong) hash with epoch `k`'s key share, group id and signer set (keygen.rs:529-547). Epochs are retained down to `active_epoch` (preprocess.rs:116-121), so `k`'s key share is still present. The `SigningState::WaitingForRequest` doc (state/mod.rs:288-292) itself notes the responsible party need not be a signer. Supported.
- **[E2] The junk `Sign`.** On timeout, since `responsible` is `Some`, `retain` removes it, and because `k`'s signer set is full (`>= threshold`) and contains this validator, it sets `responsible = None` and broadcasts `Action::Sign { group_id: gid_k, message: stale_hash }` (sign.rs:577-616). That opens a real ceremony on the finalised `gid_k` (contract `sign` needs only `FINALIZED`), wasting one sequence number on the old group plus this validator's nonce and gas. Supported.

**Why Confirmed-mechanism at Low/65:** the outcome is self-griefing plus one wasted sequence/nonce on the (still-finalised) epoch-`k` group; the _real_ `k+1→k+2` rollover is unaffected because this validator is not one of its signers. The trigger is conditional on the validator first missing an epoch (via F2-VAL-003/004/005 or a share timeout), so it is a downstream consequence rather than an independent primary; that conditionality, not any doubt about the code, is why certainty is 65. Remediation 1 (advance `active_epoch` from every `EpochStaged` regardless of who generated the group; the fields are in the event, bindings.rs) is clean and also neutralises the exclusion's after-effects. No promotion from the rejected list.

- QA2-VAL-A: Not attempted (downstream, Low); certainty unchanged at 65.

## QA (QA2-VAL-A)

**Not attempted. Certainty unchanged at 65 (Confirmed mechanism).**

- **Reason:** Low severity and conditional on the validator first missing an epoch (F2-VAL-003/004/005 or a share timeout); the stale-hash / phantom-session mechanism is already E2-Confirmed by the Critic. A pure test could confirm the wrong hash and the opened session, but the decisive onchain harm (the junk `Sign` on the finalized epoch-k group) runs through R5's signing-timeout path, so a single-node PoC would not add the missing half. Given the priority order I spent the budget on the Critical (F2-VAL-001) and the two Low/Medium reproductions instead.
- **Unexecuted PoC:** `rust-audit/poc/F2-VAL-007/SKETCH_unexecuted.rs` — command `cargo test -p validator --bins poc_f2_val_007_stale_active_epoch`; expected: confirming k+2 while `active_epoch == k` inserts a `WaitingForRequest` session keyed by `epoch_rollover_hash(k, ...)` (not `k+1`) with epoch k's key share.

**Remediation check.** Option 1 (advance `active_epoch` from every `EpochStaged` event regardless of who generated the group; the `activeEpoch`/`proposedEpoch` fields are in the event, `bindings.rs:120-128`) is **sound**, of no adverse tradeoff, and also neutralises the after-effects of an exclusion — it keeps `active_epoch` in step with the chain. It does not violate the core runtime contract or the Solidity. At least one option is sound.
