## Claim

Regular-epoch key generation is started exclusively from the block clock: `handle_rollover_new_block` runs only on `Message::NewBlock` and it is the only place that creates the local `CollectingCommitments` state for epoch `k+1`. Every `KeyGenCommitted` (and later `KeyGenSecretShared`) event is matched against that local state and silently dropped when the validator is not yet in the matching phase. On a process restart, safenet-core rolls the state back to the earliest retained snapshot (the reorg-safe block) and replays everything up to the new safe block as a `Warp`, which delivers _logs only_ - no `NewBlock` transition is applied for warped blocks. If the epoch-boundary block `B` lies inside that warped range, the rollover clock never ticks for it: the validator stays in `EpochStaged{k}` / `EpochSkipped{k}` while the peers' commitments for `gid(k+1)` stream past and are ignored, then starts its own key generation at the first live block, with an empty commitment map, and republishes a commitment the contract rejects (`InvalidParticipant`, already registered) or accepts late. It never reaches `count` commitments, times out `key_gen_timeout` blocks later, excludes every peer as a "non-committer", cannot form a viable set and lands in `EpochSkipped{k+1}`; the peers, missing its share, exclude it and form the epoch without it.

Because snapshots are pruned to the reorg-safe block, the rollback anchor can predate a boundary the validator had already processed before shutting down: a restart that begins less than `max_reorg_depth` (default 5) blocks after a boundary, or that spans a boundary, is enough. The same missing `NewBlock` delivery also postpones `handle_key_gen_timeouts` to the first live block, so a validator restarted across a keygen deadline restarts the round with `deadline = first_live_block + key_gen_timeout`, which differs from every peer's deadline and, by the same event-dropping mechanism, makes it miss the restarted group's commitments as well. Impact: an honest validator forfeits one epoch (about two hours at 1440 blocks) after a routine restart; a coordinated restart of more than one third of the set around a boundary skips the epoch for everyone (the old group keeps signing, so this is rollover liveness, not safety).

## Trigger

Defaults: `blocks_per_epoch = 1440`, `key_gen_timeout = 120`, `max_reorg_depth = 5`; `n = 6` participants; boundary block `B = 1440·k`.

1. Every peer processes `NewBlock(B)`, enters `CollectingCommitments{gid(k+1)}` (rows 3-5) and its `keyGenAndCommit` lands in blocks `B+1..B+2`.
2. The validator under test is stopped at block `S` and restarted at head `H` such that `B` is in the replayed warp range `(S − 5, H − 5]`; e.g. `S = B + 3`, `H = B + 6` (a ~15 s restart three blocks after the boundary), or any downtime that spans `B` by more than five blocks.
3. On start the watcher queues `Uncle{S−4}` and `Warp{S−4 .. H−5}` (row 1). The state rolls back to the snapshot at `S−5 < B`, i.e. `EpochStaged{k}`. The warp delivers the `KeyGenCommitted` logs of `B+1..B+2` as `Logs` only (row 2); in `EpochStaged` they are dropped (row 6). No `NewBlock(B)` is ever applied.
4. The first live block `H−4` yields `NewBlock(H−4)`: `handle_rollover_new_block` now starts `gid(k+1)` with an empty map (rows 4-5) and re-emits `KeyGenAndCommit` (its earlier one, sent before shutdown from the durable queue, is already onchain; the second reverts with `InvalidParticipant`).
5. `commitments.len()` stays at 1 (only its own replayed event would ever arrive, and it already passed), so at `H − 4 + 120` row 8 excludes all five peers; `min_participants(6) = 5 > 1` (row 9) gives `EpochSkipped{k+1}`. Onchain the group moved to `SHARING` with its commitment; the peers wait for its share, time out, and continue with a group of five that excludes it; the `EpochStaged` for that group is ignored (row 10). The validator is out of epoch `k+1`.

Variant (timeouts): the same restart geometry around a keygen deadline defers the timeout to the first live block, so the validator restarts the round at a different block than its peers and misses the peers' commitments for the restarted group in exactly the same way.

## Considered and rejected

- _A reorg replay behaves the same._ No: after a real `Uncle`, the next block arrives as `BlockUpdate::New` and the state machine applies `NewBlock` for it (`crates/core/src/state/mod.rs:190-199`), so the clock ticks again. Only the restart warp skips `NewBlock`.
- _The persisted snapshot already contains the group._ Only if the rollback anchor is at or after `B` (i.e. the validator kept running for at least `max_reorg_depth` blocks after `B` and shut down cleanly); the pruning to the safe block (row 1) makes the anchor `S − 5`.
- _`WaitingForGenesis → EpochStaged` recovery covers it._ That branch (`state/keygen.rs:613-635`) exists only before genesis; the `_` branch (row 10) applies afterwards.
- _This is purely a core bug (CORE-H5)._ The warp semantics are core's, but the validator's key-generation machine is what depends on `NewBlock` for phase entry and drops phase-mismatched events; the validator can be made robust without changing core (remediation 1-2). The cross-crate root cause is recorded for R2.
- _A16._ Genesis is unaffected (row 11); regular epochs carry full severity.

## Remediation options

1. Drive the rollover clock and the keygen timeouts from log block numbers as well: in `apply_transition`, before handling a `Message::Event(log)`, apply `handle_rollover_new_block`/`handle_key_gen_timeouts` for every block boundary crossed since the last processed block (the state can track `last_block`). Tradeoff: a small amount of bookkeeping in the snapshot; makes warps equivalent to live blocks for the validator regardless of core.
2. Make phase entry lazy: when a `KeyGenCommitted` arrives for the group id the validator _would_ compute for the next epoch (`participants_set(config, Epoch::Number{next_number(log.block)})`), start that key generation on the spot (setup effect included) and accept the commitment. Tradeoff: derives the group id per event; also covers the timeout variant if applied to restarted groups.
3. Core-side: synthesise `NewBlock` transitions for warped blocks (R2's call; changes semantics for all services).

Tests to add: a `state` unit test applying `Event(KeyGenCommitted{gid(k+1)})` in `EpochStaged{k}` followed by `NewBlock(B+3)` and asserting the commitment is retained; a restart flow test (epic P0) that stops a validator three blocks after a boundary and asserts it still shares.

## Critic (C2-VAL-A)

**Finding verdict: Confirmed. Severity Medium (unchanged). Certainty 75%.**

I verified the cross-crate mechanism against core before reading the Claim:

- **[E2] Restart warp delivers logs only, no `NewBlock`.** On resume the watcher pushes `Uncle{indexed.safe+1}` then `Warp{indexed.safe+1 .. new_safe}` (index/blocks.rs:255-289 — re-anchored; the reviewer's 261-278 quote matches). A `Warp` sets `Status::WarpEvents` and returns **no commands** (state/mod.rs:173-181); the warped range then arrives as `Update::Logs`, each log applied via `apply_transition(Message::Event(log))` with a commit after (state/mod.rs:200-239). No `Message::NewBlock` is produced for warped blocks. By contrast `BlockUpdate::New` does apply `NewBlock` (state/mod.rs:190-199), which is why the considered-and-rejected "a reorg behaves the same" is correctly refuted: only the restart warp skips the clock.
- **[E2] The rollover clock/timeouts run only on `NewBlock`** (validator state/mod.rs:464-466), and `KeyGenCommitted` is consumed only in `CollectingCommitments` for the matching gid, dropped by the `_` arm otherwise (keygen.rs:161-168, 263). `start_key_gen` opens with `commitments: BTreeMap::new()` (keygen.rs:1137-1146); the round closes only at exactly `count` (keygen.rs:196); the deadline path excludes all non-committers and, if the surviving set is unviable, yields `EpochSkipped` (keygen.rs:1027-1045; group.rs:227-232). Genesis is started from the `KeyGen` **log** event (validator state/mod.rs:416-418), which a warp _does_ deliver, so genesis is unaffected (row 11).

So if an epoch boundary `B` falls inside a restart's warp range (rollback anchor `indexed.safe < B`, i.e. the validator restarts within `max_reorg_depth` blocks after `B` or is down across `B`), the clock never ticks at `B`, the peers' commitments for `gid(k+1)` stream past in a stale rollover state and are dropped, and the validator enters the round late with an empty map, times out, and lands in `EpochSkipped{k+1}`. All Basis rows Supported.

**Severity: Medium, confirmed against A16 and the High bar.** The trigger is a routine restart/crash near a boundary — **operator-caused, not attacker-controlled, and not a plain reorg** (the finding's own rejected note shows a reorg re-ticks via `New`). It therefore does **not** meet the High criterion ("attacker-controlled input or reorgs within `max_reorg_depth`"); it is a crash-consistency/liveness gap with recoverable impact (the validator rejoins at `k+2`, modulo F2-VAL-007) → Medium. A16 does not reduce it: it reaches regular rollover epochs, genesis is exempt. Remediations 1-2 (drive the clock/timeouts from log block numbers, or lazy phase entry) are validator-local and sound; remediation 3 is the core-side root cause (R2's territory). Not raised to E1 (would need a crate test edit); QA can reproduce with the suggested state-machine test.

**Remediation check.** Option 1 (drive the rollover clock and keygen timeouts from log block numbers too, tracking `last_block`) and Option 2 (lazy phase entry: start the keygen for the epoch a `KeyGenCommitted` implies) are **both sound and validator-local** — they make a warp equivalent to live blocks without touching core, and they do not violate the core runtime contract in `crates/core/src/state/mod.rs` (transitions stay pure and non-failing; the extra bookkeeping is a `u64` in the snapshot). Option 3 (core synthesises `NewBlock` for warped blocks) is the root-cause fix but changes semantics for every service (R2's territory) and would need its own review. At least one option is sound; none contradicts the Solidity under A7 (rollover timing is a client concern).
