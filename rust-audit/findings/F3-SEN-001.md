## Claim

The sentinel sends `ApproveToken` with a fixed gas limit of 55,000. In Direct mode, the default submission mode, that number is the whole transaction's gas limit, intrinsic gas included. On the Aegis fee token, USDC.e on Gnosis (Circle `FiatTokenProxy` in front of `FiatTokenV2_2`), an approval from a zero allowance needs a gas limit of at least 55,819. With 55,000 the call runs out of gas and the allowance stays zero. The `Commit` queued right behind it then reverts in `SentinelOracle.commit`, whose `safeTransferFrom` pulls the bond against a zero allowance.

The allowance is zero before every approval in normal operation: it starts at zero, and each successful commit spends the exact approval. So a Direct-mode sentinel on Aegis never gets a commit onchain. It votes on nothing, earns nothing, and pays gas for two failed transactions per request. If every sentinel runs the default configuration, no request on the Aegis `SentinelOracle` ever receives a vote, every request ends `TIMED_OUT`, no `OracleResult` is emitted, and validators attest no transaction that names this oracle. Batched mode is not affected, because there the 55,000 is the callee's budget and the intrinsic gas is paid by the batch.

## Trigger

Any proposal on the Aegis `SentinelOracle` (chain 100, fee token USDC.e) seen by a sentinel running the default `[transactions]` configuration (no `executor`):

1. `TransactionProposed` and `NewRequest` arrive in block P; the engine check returns `secure` or `insecure`.
2. `commit_vote` queues `ApproveToken { bond: 800_000_000 }` and `Commit`, both with 55,000 and 250,000 gas.
3. The approval transaction is mined with gas limit 55,000. Intrinsic gas for `approve(0x4F61…1d03, 800000000)` is 21,596, so the token code runs with 33,404 gas. The proxy's `DELEGATECALL` into `FiatTokenV2_2.approve` (paused check, two blacklist checks, a zero-to-nonzero `SSTORE`, the `Approval` log) needs 34,223 forwarded gas, so it runs out of gas and reverts. The allowance stays 0.
4. The commit transaction reverts inside `safeTransferFrom`. No `Committed` event.
5. At `NewBlock(commitDeadline + 1)` the request is dropped (`self_committed` is false). The next request repeats steps 2 to 5, again from a zero allowance.

Measured offline with Foundry 1.5.1 against the real runtime code of the proxy (`0x2a22…76F0`) and implementation (`0x107C…EC7`) and the proxy's storage, taken from Foundry's RPC cache at Gnosis block 48635154 (code hashes checked). Command and full output: `rust-audit/state/run3/logs/R7-usdc-approve-gas.txt`.

## Considered and rejected

- The allowance might already be nonzero. It only is after a manual approval by the operator; the measured nonzero-to-nonzero approval fits in 55,000, but it sets the allowance to exactly one bond, the next commit spends it, and every later approval starts from zero again.
- An attached EIP-7702 authorization adds 25,000 gas (`crates/core/src/tx/bundle.rs:174-177`), but only on the one transaction that removes a leftover delegation.
- Batched mode: the executor forwards 55,000 to the token call and the batch pays intrinsic gas separately; the measurement shows the approval succeeds there. Batched mode is opt-in (`sentinel.sample.toml:67-78`, `docs/sentinel-handbook.md:69` presents it as a gas tip).
- The other fixed limits are not affected. Measured the same way against the deployed `SentinelOracle` build (optimizer 1,000,000 runs, via IR) with the USDC.e bytecode and worst-case cold balances, as Direct-mode transactions with gas limit 250,000: first commit 112,789 gas, last reveal with auto-finalize 95,553, finalize with a non-revealer slash and dust transfer 87,908, finalize on timeout 80,042, winner claim 76,741, `timeoutArbitration` 74,300 (same log, part 2). Only the approval is too tight.
- A pause or blacklisting by the token's operators would also stop approvals; that is a trust assumption on Circle's roles, not this defect.
- The gas figure is not an estimate: it is measured on the deployed implementation's bytecode with cold accounts and slots (each case runs in its own transaction after `setUp`, and the binary search cools both accounts before every attempt). The binary search and `lastCallGas` agree up to the 1/64 the proxy must keep back at its `DELEGATECALL`.
- Code age: the 55,000 is pre-existing (present at `fe9e84c`, `crates/sentinel/src/service.rs:850` there, introduced by #504/#540). It became reachable in production when #1062 (`fcc7028`, 2026-10-07) set USDC.e as the Aegis fee token; the integration test and the testnets use the mock `MyToken`.

## Remediation options

1. Raise the `ApproveToken` gas limit to cover FiatToken approvals with margin (for example 80,000). Simple; any unused gas is not charged. Keep the per-call figure in Batched mode in mind: `call_gas` adds it to the batch estimate.
2. Approve once for a large allowance (or `type(uint256).max`) and skip the per-request approval while the allowance covers the bond, reading `allowance` at startup or tracking it. Removes one transaction per vote; widens what a compromised oracle could pull, so weigh it against the oracle's trust model.
3. Estimate gas for the approval (`eth_estimateGas`) instead of a constant. Adds an RPC call per action and a failure mode of its own.

Tests to add: an integration run against a FiatToken-style fee token (proxy plus blacklist and pause checks), or a Foundry test in `contracts/test` that replays the sentinel's encoded `approve` with the encoder's gas limit against FiatToken bytecode.

Finding verdict: Confirmed. Severity: High to High. Certainty: 90, band 90 to 100 (E1 for the gas threshold by two independent methods; the commit revert and the drop are direct code reads). Duplicate: canonical, no other file covers it.

Direct mode is the default path for Aegis sentinels. The code default is Direct (`crates/core/src/tx/config.rs:27-37`), a config without `executor` is Direct (`:110-113`), the sample leaves `executor` commented out (`crates/sentinel/sentinel.sample.toml:74-78`), the handbook offers the executor as an optional gas saving (`docs/sentinel-handbook.md:69`), and the published Aegis sentinel configuration has no `[transactions]` table at all (`docs/configuration.md:106-121`). An operator who copies the documented Aegis config runs Direct mode.

Measurement method. R7 etches the cached FiatTokenProxy and FiatTokenV2_2 code and the 14 cached proxy slots, then calls `approve` with a callee budget of 55,000 minus a hand-computed intrinsic gas. I checked its two weak points with my own forge project in the local run folder's `scratch/C3-SEN/usdc-gas/` (same cache file, `~/.foundry/cache/rpc/xdai/48635154`):

- Warm state carried over from `setUp`: the first call in a test function is fully cold. It uses 33,841 callee gas, the sum of three cold SLOADs (6,300), a cold DELEGATECALL (2,600), a zero-to-nonzero SSTORE (22,100), the `Approval` LOG3 (1,756) and 1,085 of overhead. `vm.cool` alone leaves the implementation account warm (31,341), but R7's binary search reverts to a snapshot before each attempt, so its attempts are cold too.
- Hand-computed intrinsic gas: with `forge test --isolate` each top-level call runs as its own transaction and revm charges intrinsic gas itself (calibrated: a no-op call forwarded 100 gas succeeds, so the isolated gas limit is the forwarded gas plus 21,000). A transaction with gas limit 55,000 does not set the allowance; the smallest limit that does is 55,819; a callee budget of exactly 55,000 (Batched mode, through a forwarding contract) succeeds. Same numbers as R7.
- Storage coverage: `vm.accesses` shows the approval reads only the proxy admin, implementation and paused slots and writes the allowance slot. All three read slots are in the cache, so the partial cache does not change the result.

Two corrections that do not touch a Basis row. The deployed FiatTokenV2_2 `approve` does no blacklist reads (Trigger step 3 says "two blacklist checks"); the numbers stand. And with no commits a request does not end `TIMED_OUT` by itself: it stays `PENDING` until someone calls `finalize`, which `nothingToReveal` allows after `commitDeadline` (`contracts/src/libraries/SentinelOracleRequests.sol:173-174`). There is no `OracleResult` either way.

Escalation the Claim leaves out. If every honest sentinel follows the documented config, only Batched-mode sentinels can vote. One approving reveal with no deny resolves `RESOLVED_APPROVED` (`SentinelOracleRequests.sol:176-188`), so a malicious or compromised Batched-mode sentinel would approve unopposed: the Critical outcome "malicious Safe transaction rated `secure`", once the Safe owners have signed it. That needs a governance-registered sentinel (`SentinelOracle.sol:246`) to misbehave, so it is a condition for the practicality check, not the base severity.

Seam with the other sentinel findings: F3-SEN-002, F3-SEN-003 and F3-SEN-004 all need this sentinel's commit to land. On Aegis with the documented config they are reachable today only in Batched mode, and for every sentinel once this is fixed.

QA recipe: (1) copy the local run folder's `scratch/C3-SEN/usdc-gas/` into `poc/F3-SEN-001/` and run `python3 -I scripts/extract.py && forge test -vv --offline --root . --isolate --match-test "test_c|test_d|test_e"`; expected: forwarded 34,000 fails, minimum forwarded 34,819 (gas limit 55,819), a 55,000 callee budget succeeds. (2) End to end on Anvil (QA ports only): `anvil_setCode` the cached proxy and implementation at their Gnosis addresses, `anvil_setStorageAt` the 14 cached proxy slots, fund the sentinels by impersonating the master minter or writing their balance slots, deploy `SentinelOracle` with that fee token, and run one sentinel request flow twice, without and with `executor`. Expected without: the approve receipt has status 0 and gas used 55,000, the commit reverts, no `Committed` log, and the request is dropped at `commitDeadline + 1`. Expected with: a `Committed` log from the sentinel.

## QA (QA3-SEN, 2026-10-08)

Result: Reproduced, end to end.

Route: the real `sentinel` binary in Direct mode (no `executor`), against a local Anvil carrying the real Gnosis USDC.e proxy+implementation code and its 14 cached storage slots (`~/.foundry/cache/rpc/xdai/48635154`, code hashes proxy `ad30d8...`, impl `aada1fd...`) and a `SentinelOracle` deployed with the Aegis production parameters (fee 400000, bond 2000x, slash 1x, commit 6, reveal 6, USDC.e fee token). One proposal is driven through a stub engine returning `secure`. The sentinel's own `approve` (gasLimit 55000) runs out of gas: receipt status 0, gasUsed 54629, allowance stays 0. The `commit` queued behind it reverts in `safeTransferFrom` (status 0, gasUsed 100202). Zero `Committed` events, `getCommitment` vote NONE, no bond in the oracle, and no reveal (a block scan of the sentinel's account found only nonce 0 `approve` and nonce 1 `commit`). A token-level probe (`probe_etch.sh`) confirms the same on the bare token: 55000 fails, 80000 succeeds with gasUsed 55437.

Command and output: `poc/F3-SEN-001/` (`e2e.sh buggy`, `out-buggy-run.txt`, `out-buggy/`; probe in `probe_approve_55000.json`/`probe_approve_80000.json`).

The approve now succeeds (gasUsed 55437, the finding's exact figure), the commit lands (`Committed` count 1, vote recorded), and the sentinel reveals and claims its bond plus fee. Remediation option 1 is sound. Reverted with `git checkout`. (Incidental: the fixed run's nonce 3 `finalize` reverts `RequestNotPending`, an end-to-end sighting of F3-XC-006.)

Certainty: 98 (Reproduced end to end plus Critic Confirmed; gasUsed 55437 matches the finding exactly).

Reason. The Aegis validators honour exactly one oracle, the `SentinelOracle` (`docs/configuration.md:87`), and a request with no commit can only end `TIMED_OUT`, which emits `RequestTimedOut`, never `OracleResult` (`contracts/src/libraries/SentinelOracleRequests.sol:176-208`, `contracts/src/SentinelOracle.sol:290-292`). If every sentinel follows the documented configuration, no Aegis request gets a vote and no oracle-gated Safe transaction is attested; Safes fall back to the guard's delayed escape hatch. That is a network-wide liveness failure at launch, under Section 8's High row (an honest sentinel loses liveness), with no attacker and no special state. Not Critical: no invalid attestation and no fund loss, and the failure shows at the first request after launch. Operator workaround today: set `executor` (Batched mode), where the 55,000 is the call's own budget. C3-SEN's escalation (a malicious Batched-mode sentinel then approves unopposed) needs a governance-registered sentinel to misbehave (`SentinelOracle.sol:246`, `:368`), so it is a condition on top, not the base rating. The same defect is filed in run 1 as `F-SEN-008`; the two rows should carry one rating.
