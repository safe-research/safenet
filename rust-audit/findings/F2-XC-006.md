## Claim

None of the three persistent stores records what it belongs to. `snapshots` holds `(block_number, state)`, `transactions` holds serialized requests plus nonces and block numbers, and the validator's secret tables are keyed by group id and address. The chain id is read from the RPC at connect time and never persisted; the watched contract addresses and the signer address come from the config file on every start and are never compared with anything on disk.

Consequently a configuration-only change — a new `rpc` pointing at a node on another chain, a new `consensus`/`oracle` address after a redeployment, or a different `signer` — reuses the existing database as if nothing had changed. The block watcher resumes from the persisted block **numbers** (`indexed.safe + 1` as the synthetic uncle, then a warp to the new head), applies the new chain's or new deployment's events on top of state derived from the old one, resubmits queued transaction requests built for the old deployment under the new chain id, and keeps the old groups' secrets. No error, warning or refusal is produced. A17 rules out out-of-band database access, but this trigger is an ordinary edit of the configuration file that operators are expected to make (new deployments, RPC migrations), and the outcome is silent state corruption rather than a loud failure; with a trusted operator (A1) the severity is Low.

## Trigger

Operator edits `rpc` to a node on a different chain (or a provider load-balancer starts serving a different chain), or edits `consensus`/`oracle`/`signer` after a redeployment or key rotation, and restarts with the same `database`. No database access is involved.

## Considered and rejected

- "Transactions signed for the wrong chain are rejected anyway": true for already-signed payloads, but the queue stores unsigned `request`s and signs at submission with the live chain id (`crates/core/src/tx/mod.rs`, R3's scope), so old requests are validly re-signed for the new chain.
- "The deep-reorg check catches a chain switch": the anchor is a block number, so the watcher happily treats the new chain's block `safe+1` as the uncle of the old one and warps forward (claim 6); `ExceededMaxReorgDepth` is only raised when the _new_ chain reorgs deeper than configured.
- "This is A17 territory": A17 excludes triggers that need database access; this one needs only a config edit.

## Remediation options

1. Add a `meta` table written on first start with `chain_id`, the watched addresses, the signer address and a schema version; on later starts compare and refuse to run on mismatch, with an explicit operator override (`--accept-new-deployment`) that wipes or migrates state. Small, contained change in `Driver::new`.
2. Additionally persist the block hash with each snapshot and verify it against the node on resume (also closes the "reorg during downtime" gap noted in the map's cross-crate themes; R1/R2 scope).
3. At minimum, log the persisted-vs-configured values at startup so a mismatch is visible.

Tests to add: start the driver against a store created with a different chain id and assert a startup error.
