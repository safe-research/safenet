## Claim

`SecretStore::new` creates its tables with `CREATE TABLE IF NOT EXISTS` and never inspects an existing schema. The pruning series added the `delete_at_block` column to `keygen_secrets` and `nonces_chunks` and the `group_secret_reconciliation` table (commit `545c890`, #908); the accompanying migration script was deleted again in `80951a0` (#913) "on the understanding that the devnet database has been upgraded manually". A validator started on a database written by any earlier release opens it without error and then fails at first use: every `ReconcileGroupSecrets` (`no such table: group_secret_reconciliation`), every `KeyGenSetup` (`no such column: delete_at_block` in the `UPDATE`), and every housekeeping pass. Because the reconciliation fails before `generator.start`, no nonce stream is ever started (F2-VAL-031) and every `NonceTree` produces a phantom reservation (F2-VAL-030); because `KeyGenSetup` fails, the validator can never commit to a new DKG. The process stays up, `/health` keeps answering, and the only symptoms are `warn` lines and the `housekeeping_total{result="failure"}` counter the handbook mentions. Tagged `known` because the removal was a recorded decision; recorded because the failure mode is silent and total, and a one-line `PRAGMA user_version` check would turn it into a start-up error.

## Trigger

Start the current binary against a `storage.db` produced by a build at or before `7f9394c` (the previous store layout). `SecretStore::new` succeeds; the first `NewBlock` logs `failed to perform effect ... no such table: group_secret_reconciliation` and `failed to prune scheduled secrets`; the first top-up logs `nonce generator is unavailable`. A17 is not violated: no one touched the database; it simply predates the release.

## Considered and rejected

- `reopening_preserves_stored_secrets` (store.rs:946-968) recreates the _new_ schema twice; it does not exercise an old file.
- SQLite `ALTER TABLE ... ADD COLUMN` is cheap and idempotent when guarded, so the fix does not need a migration framework.

## Remediation options

1. Store a schema version with `PRAGMA user_version`; on open, either apply the additive `ALTER TABLE`/`CREATE TABLE` steps or fail start-up with a clear error when the version is older than expected. Tradeoff: one more start-up query.
2. At minimum, probe the columns (`PRAGMA table_info`) in `SecretStore::new` and refuse to start on a mismatch.

Tests to add: open a store created with the `49d7e39` schema and assert `SecretStore::new` either migrates it or returns an error. No code is committed.
