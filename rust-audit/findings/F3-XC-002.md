## Claim

When this sentinel committed a bond but its own `Reveal` did not land by `revealDeadline`, while at least one other sentinel revealed, `handle_block_advance` calls `finalize` at the first block past the reveal deadline and the guard in `finalize` drops the request (`!self_revealed && !timed_out`). The guard's comment calls this "did not participate", but the sentinel did participate: its bond is in the oracle. Onchain, the request is finalized by someone else at `revealDeadline + 1` or later, and `claim` then returns this sentinel's bond minus `slashAmount` (799.60 USDC.e of the 800 USDC.e bond at the Aegis production parameters). Because `NewBlock(revealDeadline + 1)` is always applied before that block's logs, the drop always happens before any `OracleResult`, `DisputeTriggered` or `RequestTimedOut` can arrive, so `Claim` is never sent and the remainder stays in the oracle until the operator claims by hand.

The code already intends to reclaim such a bond: `handle_oracle_result` documents the "reveal missed" recovery and records `ResolvedOutcome::RevealMissed`, and a unit test asserts the `Claim`. That test feeds `OracleResult` at block 22 with a reveal deadline of 40, which the contract cannot emit (`finalize()` before the deadline needs every commitment revealed, including ours). On the path the contract allows, the recovery is unreachable.

## Trigger

Aegis production parameters: reveal window 6 blocks (30 s on Gnosis), bond 800 USDC.e, slash 0.40 USDC.e.

1. This sentinel and another commit; `CollectingCommitments` sees both, `self_committed` is true.
2. At `commitDeadline + 1` the sentinel queues `Reveal` (`expires_at: revealDeadline`) and moves to `CollectingVotes`.
3. The reveal does not land within the six reveal blocks. Realistic causes within the assumptions: the process is down for 30 s (upgrade, restart, or the known exit-status-0 stop that an on-failure policy never restarts), the RPC is unavailable or rate limited (A4), or fees rise faster than the queue's 10 % bump every 2 blocks. The other sentinel reveals.
4. `NewBlock(revealDeadline + 1)`: `finalize` sees `self_revealed == false`, `revealed_count == 1`, and drops the request.
5. The other sentinel's `finalize()` lands in `revealDeadline + 1` or later; `OracleResult` (or `DisputeTriggered` then `DisputeResolved`) hits an untracked id. No `Claim`. 799.60 USDC.e stays claimable onchain by this sentinel's key only.

A sentinel restarted after the reveal deadline replays to the same result: the replay applies `NewBlock` for each warped block before its logs (`crates/core/src/state/mod.rs:236-238`).

## Considered and rejected

- Is the drop deliberate? The comment at service.rs:642-647 says the request is dropped to avoid paying for a `finalize()` that does not benefit this sentinel. That reasoning covers the `Finalize` call, not the `Claim`: the sentinel still benefits from claiming 799.60 USDC.e, and the code elsewhere (Basis 7) says the bond must be reclaimed.
- Can `OracleResult` arrive while the request is still in `CollectingVotes` with our reveal missing? Only before the reveal deadline, which needs every commitment revealed (Basis 4), a contradiction. So the `RevealMissed` branch of `handle_oracle_result` is reachable only from states the contract does not produce on this path.
- `DisputeTriggered` path: when both sides were revealed by others, the same drop happens; `handle_dispute_triggered` returns early on the untracked id, so even the arbitration-timeout claim never runs.
- Genuine timeout (nobody revealed): handled correctly, `timed_out` is true and the sentinel finalizes and claims (existing test at service.rs:1819-1905).
- Related to F3-XC-001, which reaches the same guard through an undercounted tally while our reveal does land; the trigger and the stranded amount differ, so they are filed separately.
- Introduced since run 2? No. The guard and the deadline branch are identical at `fe9e84c` (`git show fe9e84c:crates/sentinel/src/service.rs`, lines 651-655).

## Remediation options

1. In `finalize`, when `!self_revealed && !timed_out` (the request reached `CollectingVotes`, so this sentinel committed), keep the request in an outcome-waiting state without sending `Finalize`; the existing `OracleResult`, `DisputeTriggered` and `RequestTimedOut` handlers then claim, and `RevealMissed` becomes reachable. Add a bound on how long such entries live.
2. Or send `Finalize` in that case as well and move to `WaitingForOutcome`: one `finalize()` call on Gnosis is cheap compared with 799.60 USDC.e, and a duplicate reverts harmlessly.

Tests to add: rewrite the existing test at service.rs:1915-1979 to the order the contract allows (another sentinel's `Revealed`, then `NewBlock(revealDeadline + 1)`, then `OracleResult`), as the R8 test in the PoC log does. That test asserts today's behaviour (no command after `OracleResult`); with the assertion changed to expect `Claim` it fails on the audit commit and should pass after the fix. No code is committed.
