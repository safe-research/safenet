## Claim

When an engine request fails (connection error, timeout, non-success status, undecodable body), `SecurityCheck::execute` logs the `reqwest::Error` at ERROR level with its `Display` form. reqwest appends ` for url (<url>)` to that text, so the engine endpoint is written to the log with its full path and query on every failed or timed-out check. The core RPC provider removes the URL from reqwest errors for exactly this reason (its comment: the URL "commonly includes an API key in its path or query"); the engine client has no equivalent. An operator who follows `docs/sentinel-engine.md` and puts the engine behind access control at the deployment boundary using a token in the URL (path segment or query parameter) gets that token in the sentinel's ERROR log, which is often shipped to a third-party log service. Userinfo credentials are not affected: reqwest moves them into the `Authorization` header before sending.

## Trigger

1. The operator configures `sentinel.engine = "https://engine.example/<token>/"` or `".../?apikey=<token>"` (a gateway in front of a remote engine).
2. Any engine check fails: the engine is down, a check exceeds the derived timeout (18.75 s with the sample `voting_window` 6), or the gateway returns an error status.
3. The sentinel logs `error sending request for url (https://engine.example/<token>/v1/security-check...)` at ERROR, which the default `log_filter = "info"` keeps.

## Considered and rejected

- Is the engine URL meant to be secret? Not by design: `engine` does not accept `${NAME}` substitution (crates/sentinel/src/config.rs:50-51, unlike `rpc`, `signer`, `database` at :11-19), and A3 expects a co-deployed engine without credentials. The default and sample URL (`http://localhost:5473`) carries none. Hence Informational.
- Userinfo (`user:password@host`): reqwest's `extract_authority` (reqwest-0.13.4/src/async_impl/request.rs:582-602) clears it from the URL, confirmed by Basis 4.
- Other sentinel log sites: the verdict store and effect errors log SQLite errors, not URLs (crates/sentinel/src/effect.rs:86-89, 111-114, 155-159).
- Introduced since run 2? The logging is unchanged since `fe9e84c` (`git show fe9e84c:crates/sentinel/src/engine.rs`, lines 181-185). The RPC-side fix (`without_url`, #1046) came after run 2 and was not extended to the engine client.

## Remediation options

1. Log `err.without_url()` (or the error kind plus status) in `SecurityCheck::execute`, matching the provider.
2. Optionally accept `${NAME}` substitution for `engine` as for `rpc`, and document that a token-bearing engine URL is treated as a secret.

Tests to add: a unit test that the logged error text does not contain the configured path or query (the R8 test in the PoC log, inverted). No code is committed.

Finding verdict: Confirmed, and `known`. Severity: Informational to Informational. Certainty: 90, top band (E1 for the logged text, Confirmed). Duplicate: canonical. F3-CORE-031 and F3-XC-130 (RPC URL printed at startup) are the same bug class in a different function with a different secret, so they stay separate.

Counter-evidence that changes the framing, not the verdict: the maintainers made this call on purpose. The squash commit of #1046 (`55d811e`, the change that added `without_url`) lists under "Not covered": "Errors calling the sentinel engine still include the engine's URL, which is normally a local endpoint and useful for debugging." The file's "was not extended to the engine client" reads as an oversight; it was a stated trade-off, so the item is `known` and adds only the token-in-URL case, the E1 text and the remediation. The documented deployment carries no credential in the URL: the engine is co-deployed on the same host, pod or private network (`docs/sentinel-engine.md:37`, `docs/sentinel-handbook.md:9`) and the handbook's example is `engine = "http://safenet-sentinel-engine:5473"` (`docs/sentinel-handbook.md:82`). The trigger therefore needs an operator who departs from that deployment and puts a token in the path or query; userinfo is moved to the `Authorization` header before sending (`reqwest-0.13.4/src/async_impl/request.rs:171-184, 582-602`). Remediation 1 costs one line and could keep the debugging value by logging the URL without its query at debug level; whether to take it is remedcu's decision.

Other engine-URL sinks checked, none leaks: `EngineClient::new` fails with a fixed message (`engine.rs:96-99`); the config is never logged (`crates/sentinel/src/main.rs:40-42`); the `security_check` span records only `safe` and `request_id` (`engine.rs:129-133`).

QA recipe: in a scratch copy of `crates/sentinel/src/engine.rs`, keep R8's closed-port case and add two with the existing helper `respond_once_ex`: status `"500 Internal Server Error"` (the `error_for_status` path) and a `delay` longer than `.timeout(...)` (the reqwest timeout path). Base URL `http://127.0.0.1:<port>/engine-token-abc/?apikey=query-token-xyz`; expect both tokens in the formatted error in all three cases. To capture the emitted record itself, run `execute()` under `tracing::subscriber::with_default` with a `tracing_subscriber::fmt` writer into a buffer (`tracing-subscriber` is already locked through `safenet-core`; add it as a dev-dependency of the scratch copy only) and expect the ERROR line to contain both tokens.
