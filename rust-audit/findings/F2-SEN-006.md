Audited commit: `3ec8bc5`.

## Claim

`main.rs` wires the service without reading anything from the oracle. Nothing verifies that the signer is an active sentinel (`sentinelActiveAt`), that `sentinel.fee_token == oracle.FEE_TOKEN()`, that `oracle.PROPOSER() == consensus`, that the account holds fee tokens or gas, or that `voting_window` is sane. At runtime the FSM emits `ApproveToken` + `Commit` blind. With an inactive signer, an empty fee-token balance or the wrong token, the `approve` succeeds (~46k gas) and the `commit` reverts (`SentinelNotActive` / `safeTransferFrom`) on **every** request, indefinitely; the queue records the reverted transaction as executed and moves on, and the FSM drops the entry at `commit_deadline + 1` without an error-level log. A wrong `consensus` address makes every request id mismatch, so `NewRequest` is ignored at `debug` level and the sentinel silently never participates. A wrong `voting_window` (0 or 1) collapses the engine timeout to one second, turning every check into `Unknown`.

## Trigger

Governance has not yet activated the signer (or removed it), or the fee-token balance runs out mid-day. Every proposal → engine verdict → `approve` (mined) + `commit` (reverted). At `commit_deadline + 1` the entry is dropped (`service.rs:415-417`). Repeat per request until an operator notices the gas drain; no metric distinguishes "not registered" from "no proposals".

## Considered and rejected

- "Configuration is the operator's responsibility (A1)": the trusted-operator assumption covers malicious configuration, not the absence of any feedback loop for honest mistakes that cost money per request.
- "The queue would surface the revert": `submit_transaction` only logs RPC-level failures (crates/core/src/tx/mod.rs:271-293); an on-chain revert is an executed transaction to the queue.

## Remediation options

1. At startup: read `FEE_TOKEN()`, `PROPOSER()`, `sentinelActiveAt(signer)`, `COMMIT_WINDOW()`/`REVEAL_WINDOW()`, the fee-token balance and the gas balance; refuse to start (or log at `error` and expose a metric) on mismatch. Derive `engine_timeout` from the onchain commit window.
2. Per request: skip `commit_vote` (log + metric) when `balance < bondTarget` or the sentinel is inactive, checked through an effect; skip the `approve` when `allowance ≥ bondTarget` already.
3. Validate `voting_window ≥ 2` and fix its documentation.

Tests to add: config test rejecting `voting_window = 0`; a `Provider::mocked` test asserting startup fails when `sentinelActiveAt` returns 0.

## Critic (C2-SEN)

**Per-claim verdicts.** Claims 1–8 all **Supported**: `main.rs:37-86` (no oracle read before `Driver::new`), `service.rs:226-242,823-833`, `SentinelOracle.sol:232-238`, `402-404`, `service.rs:286-289` (`debug!`), `config.rs:54-56` + `main.rs:50-60`, `docs/sentinel-handbook.md:96` (bullet present), `bindings.rs:66` with no call site (`grep allowance crates/sentinel/src` → the binding and a comment at `service.rs:836` only).

**Independent check.** The FSM has no feedback channel for a mined-but-reverted transaction: the queue marks executions by nonce (`tx/mod.rs:188-194`) and `retain` at `415-417` drops the entry with no log at all at that site. Per request the cost is one successful `approve` (~46k gas) plus a `commit` that reverts early (`SentinelNotActive` is the first `require`, so far below the 250k cap) — bounded, repeated per request, invisible in metrics (`requests_participated_total` is only incremented on `Committed(self)`). A wrong `consensus` means the address filter never returns its logs, so the sentinel idles silently, as claimed. The A1 rebuttal is fair: this is missing feedback for honest misconfiguration, not a trust question.

**Verdict: Confirmed.** Certainty **75%** (E2). **Severity Low / Low**: robustness/configuration weakness with limited, gas-only impact. Overlaps F2-XC-008 on the unvalidated `voting_window`; this file is canonical for the missing onchain pre-flight (registration, token, proposer, balance).
