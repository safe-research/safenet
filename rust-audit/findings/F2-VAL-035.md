## Claim

Scheduled secret pruning is two-phase by design: a reconciliation at block `N` _schedules_ every non-retained group's rows (`delete_at_block = N`) and a later housekeeping pass _collects_ rows with `delete_at_block <= safe`; the `max_reorg_depth` blocks in between are what let a group that comes back cancel its schedule. The driver breaks that spacing on the one block where it matters most. For every `BlockUpdate::New` it applies the block, **spawns** the resulting `Effect::ReconcileGroupSecrets` as a detached task, and then awaits `housekeeping(status)` **inline** on the driver task. Nothing orders the reconciliation's cancelling `UPDATE ... THEN NULL` before the prune's `DELETE ... WHERE delete_at_block <= ?`; both are independent SQLite writes on the same pool.

In steady state this is harmless (a schedule written at `N` is not due until `safe >= N`, `D` blocks later, and `D` reconciliations get to cancel it). After a **restart** it is not: the schedules on disk were written by the _previous_ process on the _previous_ branch, no housekeeping runs during the catch-up warp (only `BlockUpdate::New` triggers it), and the first live block arrives with `safe = latest - D`, which is already past any schedule the old branch wrote more than `D` blocks before the new head. If the replayed branch still needs such a group (R5 O1: a reorg inside `max_reorg_depth` during the outage undid the drop; or the warp replay, which applies logs only, arrives at a different retained set than the old branch's `NewBlock`-driven decisions did), the first live block's reconciliation would cancel the schedule — but the prune usually gets there first. QA2-XC executed the driver's exact construction (`EffectManager::spawn` then `housekeeping`) on the real `Handler`/`SecretStore` under that precondition: **the secret was lost in 19 of 20 rounds**. A collected row is never recreated: `schedule_absent_groups` only updates existing rows, `store_keygen_secrets` on a missing row inserts _fresh_ secrets that no longer match a commitment already onchain, and nonces cannot be regenerated at all. The outcome is the one the store's module doc and the handbook already concede for branch-agnostic deadlines ("can come due before the validator re-registers the group") — except that the driver ordering turns that concession from an edge case into the common outcome whenever the precondition holds: a lost DKG secret (the validator cannot answer complaints or, after a further rollback re-issuing `KeyGenSetup`, commits mismatched shares) or a lost nonce chunk (missed reveals for the chunk's remaining offsets, each costing the group a `signing_timeout` restart).

## Trigger

Mechanism (executed, rows 10-11): a `keygen_secrets` row for `GROUP` scheduled at block 100 by the previous run; first live block `{ latest: 110, safe: 105 }` (`D = 5`); the replayed reconciliation `ReconcileGroupSecrets { block: 105, groups: {GROUP: None} }` is spawned, then `housekeeping` runs inline. Outcome: row gone in 19/20 rounds.

Precondition (not executed; the concrete branch shape, `D = 5`): on branch A the validator's node observed at block 100 a `NewBlock`-driven drop of `GROUP` (a DKG timeout restarting the key generation without a straggler, or the last signing session of a retired epoch completing so `handle_group_reconciliation` reaps it) and scheduled its rows at 100; the node stopped at 102 (snapshots `[97, 102]`, marker 102). During the outage a reorg of depth `<= 5` replaced blocks 98..102 with branch B on which the straggler's commitment (or the retired epoch's pending signature) is still live. Restart at head 110: `Uncle { 98 }`, `Warp { 98..=105 }` (logs only, no housekeeping), then `New { 106 }` with `safe = 101`: the replayed state still holds `GROUP` (`CollectingShares { Participating }`, or the epoch with its pending session), so the reconciliation retains it — but the prune at `safe = 101` collects `delete_at_block = 100` first (rows 1, 3, 5, 11). Consequence: for a DKG secret, the validator can no longer answer a complaint for `GROUP` and any later rollback that re-issues `KeyGenSetup` stores fresh, mismatched secrets (row 8); for a nonce chunk, `nonces_reveal`/`take_nonce` return `None` for every remaining offset, each affected ceremony times out at the group and restarts without this validator.

## Considered and rejected

- _Steady state is safe._ Yes: R5's R20/R21 analysis holds on one branch, because scheduling and collection are `D` blocks apart and every intermediate reconciliation can cancel. The defect is confined to the first live block after a resume (and to `max_reorg_depth = 0`, R2 O13, where the spacing is zero by configuration).
- _`prune_scheduled_secrets` uses `safe`, so nothing the state machine can roll back to is deleted (effect.rs:279-281)._ True for _state_ rollbacks; the schedules themselves were written by a different branch, which `safe` says nothing about — exactly the module doc's caveat (row 9).
- _The handbook already documents this (`known`)._ It documents branch-agnostic deadlines as an accepted limitation. It does not document that the driver's own ordering makes the loss the default outcome even when the replayed reconciliation arrives in time to cancel; fixing the ordering removes the restart instance of the documented limitation entirely. Tagged `known` for the design caveat, filed for the ordering.
- _Is this F2-VAL-030/031?_ No. Those concern the process-local nonce generator (cold after restart) and the in-state chunk accounting (phantom reservation); the persisted rows are intact there. Here the generator and accounting are fine and the _persisted secret rows_ are deleted. They share a root ("a restart re-establishes invariants only after effects/housekeeping have already run") and a remediation shape.
- _PoC fidelity._ The PoC stamps the reconciliation with `block: safe` (105) where the driver stamps it with the `NewBlock` number (`latest`, 110); both are `>=` the old marker and accepted, so the race is unchanged. The multi-thread runtime matches `#[tokio::main]`.

## Remediation options

1. Order collection after the block's reconciliation: run `prune_scheduled_secrets` from inside the `ReconcileGroupSecrets` handler after its schedule transaction commits (same task, same order every time), and drop the driver-level `housekeeping` for the validator — or have the `EffectManager` run `housekeeping` only once the block's spawned effects have resumed. Smallest change; removes the race for every block, not just the first.
2. Make collection branch-aware: skip rows whose `delete_at_block` is older than the last _accepted_ reconciliation minus `max_reorg_depth` until a reconciliation at or above the current `safe` has been applied since start-up (a per-process "first reconciliation done" latch). Keeps the driver wiring; adds state.
3. On resume, run one reconciliation synchronously before the first housekeeping (e.g. from `Driver::new` or on the first `Uncle`/`Warp`), so schedules that the replayed state disagrees with are cancelled before anything can be collected. Also helps F2-VAL-031 (warm generator before the first replayed log).

Tests to add: the executed PoC's second test with an assertion (`row == Some(None)` after the driver's sequence) once remediation 1 or 3 lands; an Anvil restart flow with a depth-`<= D` reorg during the outage that reverts a DKG timeout, asserting the validator still answers a complaint / reveals nonces afterwards. No code is committed.
