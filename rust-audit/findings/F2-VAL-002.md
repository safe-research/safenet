## Claim

Secret shares are "encrypted" by XORing the 32-byte big-endian scalar with the affine x-coordinate of `sk_sender · q_receiver`. Because scalar multiplication commutes, the pad for the ordered pair `(A→B)` equals the pad for `(B→A)`, so every pairwise pad protects two independent plaintexts in every honest ceremony: `c_{A→B} ⊕ c_{B→A} = f_A(B) ⊕ f_B(A)` is a public relation for every pair. The pad is not passed through a KDF and carries no binding to the group id, the sender or the receiver; it is also not uniform (only about half of all field elements are valid abscissae, roughly one bit of bias per ciphertext). The project's own security argument (docs/overview.md:48: "each ECDH shared secret is used to encrypt exactly one value with exactly the same length as the shared secret itself") does not hold for the code as written, and the overview still describes `C[0]` (which is PoK-covered) as the ECDH key, whereas the code publishes a separate uncovered `q`.

On its own the two-time pad does not reveal either share (the XOR of two independent near-uniform scalars is independent of each), so no key recovery follows from this finding alone. It is, however, the property that turns the missing proof of possession on `q` into full share recovery (F2-VAL-001), and it is the reason a leaked or revealed plaintext under one pad compromises the opposite direction of the same pair. A cryptographic construction on the consensus-critical path should not rely on that argument being unexploitable.

## Trigger

Every honest ceremony: for each unordered pair `{A, B}` the two ciphertexts published in `KeyGenSecretShared` satisfy `c_{A→B} ⊕ c_{B→A} = f_A(B) ⊕ f_B(A)`. Exploitation of the relation requires one plaintext per pad, which F2-VAL-001 obtains through the complaint flow; this finding records the construction weakness independently of that trigger.

## Considered and rejected

- _The XOR relation alone leaks a share._ Rejected: for honest `A`, `B` the values `f_A(B)`, `f_B(A)` are independent and near-uniform in `Z_n` (`n ≈ 2^256 − 2^128.4`), so their XOR is statistically independent of each; no attack from the relation alone is known to me. This is why the severity is Medium rather than Critical.
- _The one-bit abscissa bias matters._ Negligible on its own (M2 in the codebase map); listed because it disappears with the KDF fix.
- _Reorg replays reuse the pad on different plaintexts._ Rejected: `store_keygen_secrets` reuses the stored secrets for the same `(group_id, me)` (`crates/validator/src/secrets/store.rs:176-212`), the group id fixes the participant set and context (`consensus/group.rs:352-364`), and a gid can be created onchain only once (`contracts/src/libraries/FROSTParticipantMap.sol:125-129`), so the same pad only ever sees the same `f_me(peer)` again (lead M1, refuted).

## Remediation options

1. Replace the pad with `HKDF-SHA256(ikm = x(sk_sender · q_receiver), info = "safenet-dkg-share" ‖ gid ‖ sender ‖ receiver)` (safenet-core `kdf::derive_key` exists), keeping the 32-byte XOR format. Tradeoff: wire-format change for `f`; fixes direction reuse, binding and bias at once and, combined with the F2-VAL-001 fix, is the standard construction.
2. Use an AEAD (e.g. ChaCha20-Poly1305 keyed from the KDF output) so that a wrong pad is detected before verification. Tradeoff: larger `f` entries onchain (`uint256[]` would have to become `bytes[]`).
3. Update docs/overview.md to describe the implemented scheme accurately in either case.

Tests to add: assert `ecdh(a, B, m)` and a direction-bound variant differ for `(A→B)` vs `(B→A)`; a vector test pinning the KDF output against the TypeScript client.

## Critic (C2-VAL-A)

**Finding verdict: Confirmed property; Refuted as a standalone confidentiality break. Severity Medium → Low. Certainty 70%.**

The brief's two questions, answered from the code:

- **Is the pad the same value in both directions?** Yes, exactly. pad(A→B) = `x(q_B·sk_A) = x(sk_A·sk_B·G)` = pad(B→A) (ecdh.rs:110-121). This is E1-proven by `ecdh_is_commutative` (`logs/R4-targeted-tests.txt`) and holds for the third direction too (a copied `q`, F2-VAL-001). Basis rows 1-6 Supported; quotes match.
- **What does it give an attacker on its own?** Nothing. The only public relation is `c_{A→B} ⊕ c_{B→A} = f_A(B) ⊕ f_B(A)`, the XOR of two independent near-uniform scalars in `Z_n`, which is statistically independent of either operand. No share, and no confidentiality of either direction, follows from the relation alone. The reviewer states this correctly (Claim ¶2, self-estimate "15% exploitable without F2-VAL-001").

Because the standalone attacker gain is nil, I re-judge severity **Medium → Low**: this is a real cryptographic-hygiene defect (a pad reused for two plaintexts, unhashed, unbound to sender/receiver/gid, ~1 bit of abscissa bias), but its impact is latent. Its significance is entirely as the **mechanism enabler of the Critical F2-VAL-001** — a copied `q` turns the symmetric pad into full share recovery, and any single revealed plaintext (e.g. via the complaint flow) compromises the opposite direction. Both mitigations (KDF/AEAD binding to gid‖sender‖receiver, `kdf::derive_key` confirmed unused via grep) are sound and close both this and F2-VAL-001's amplifier. The doc mismatch (`docs/overview.md:48`) is reference-only, correctly out of filing scope.

Considered-and-rejected list re-checked: the M1 reorg-replay rebuttal is well-cited and correct (same gid → same stored polynomial → same `f_me(peer)` under the same pad). No promotion.

- QA2-VAL-A: Reproduced (E1) the two-time-pad property; certainty 70 -> 90.

## QA (QA2-VAL-A)

**Reproduced (E1). Certainty 70 -> 90 (the property is now executed; severity Low unchanged — the PoC confirms the construction defect, not standalone exploitability).**

- **Command:** `cargo test -p validator --bins poc_f2_val_002_pad_reused_in_both_directions`
- **PoC:** `rust-audit/poc/F2-VAL-002/` (`poc_test.rs`, `output.txt`). Pasted into the existing `frost::ecdh::tests` module, run, then reverted.
- **Decisive output:** `test frost::ecdh::tests::poc_f2_val_002_pad_reused_in_both_directions ... ok` / `1 passed`.

The PoC computes `c_ab = alice.ecdh(&bob.public_key(), m1)` and `c_ba = bob.ecdh(&alice.public_key(), m2)` with distinct plaintexts and asserts `c_ab XOR c_ba == m1 XOR m2` — the pad cancels exactly, so the two ciphertexts of a pair form a two-time pad independent of the shared secret (Basis 1-4). This is the property the finding states, and it is precisely the amplifier the Critical F2-VAL-001 exploits (my F2-VAL-001 PoC recovers a full share by turning one revealed plaintext under such a pad into the opposite-direction plaintext). Severity stays **Low**: the relation alone leaks only `m1 XOR m2`, no share.

**Remediation check.** Option 1 (`HKDF-SHA256(x(shared), info = gid||sender||receiver)`, keeping the 32-byte XOR format) is **sound** — it binds the pad to direction, pair and group, killing the two-time pad and, combined with F2-VAL-001's proof-of-possession, is the standard construction. It is a wire-format change for `f` shared by the validator and the TS client only; the coordinator treats `f` as opaque `uint256[]`, so no `contracts/src` change is forced and the core runtime contract is untouched. `kdf::derive_key` already exists in safenet-core (Basis 5 grep confirms it is currently unused in the validator). Option 3 (doc fix) is reference-only. At least one option is sound.
