## Claim

The chain a service belongs to is never stated by the operator and never recorded. It is read once from the RPC at connect time (`eth_chainId`) and held only in memory. No configuration schema has a `chain_id` field, and none of the four persistent tables — `snapshots`, `transactions`, `keygen_secrets`, `nonces_chunks` — carries a chain id, a contract address, or any other deployment discriminator.

The consequence is that the pairing of `rpc` to `database` is unchecked. Editing the `rpc` line of an existing config, or restoring a database into a differently-configured host, resumes the indexer cursor, the transaction queue (with its nonce assignments) and, for the validator, the secret store against a chain those records do not describe. Nothing at startup compares the database's provenance with the connected chain, so the failure is silent by construction rather than loud.

This is a regression against the deployment it replaces: `docs/configuration.md` documents the legacy TypeScript validator's configuration with an explicit `CHAIN_ID=100`, cross-checkable against the node. The Rust rewrite dropped that field without replacing it with a check.

The blast radius is bounded by an accidental guard rather than a deliberate one: `BlockTime::Auto` knows only chain 100 and chain 11155111 and errors out on anything else, so most chain swaps fail at startup. The exposed cases are Gnosis↔Sepolia and any deployment that sets an explicit `block_time`, which turns the guard off entirely.

## Trigger

Concretely, and staying inside the block-time guard so the swap actually succeeds: a validator runs on Gnosis (chain 100) with `database = "sqlite:/var/lib/safenet/validator/data/storage.db"`. An operator repoints `rpc` at a Sepolia endpoint — a testing step, a copy-pasted config, a DNS or load-balancer change at a multi-chain provider — and restarts. `BlockTime::Auto` resolves 12,000 ms for 11155111 and the service starts. The snapshot store then returns the tip snapshot for a block number that means something entirely different on the new chain (`state/storage.rs:68-70`, `ORDER BY block_number DESC LIMIT 1`), and the transaction queue holds rows whose `nonce` values were allocated against the old chain's account state.

The engine variant needs no restart at all: the checkers compare `transaction.chain_id` against `self.provider.chain_id` individually (`address_poisoning.rs:312-322`), so a mismatch abstains rather than misjudging — but `AGENTS.md`'s own convention notes that each RPC-backed checker must do this itself and nothing enforces it centrally (`codebase-map.md:189`).

## Considered and rejected

- **"A wrong chain fails at startup."** Only sometimes, and only by accident. Basis row 7 is the reason: an unknown chain id errors out of `BlockTime::resolve`, which is why this is Low and not Medium. But the guard is a block-time lookup table, not a deployment check; it does not fire for Gnosis↔Sepolia, and setting `block_time` explicitly (a documented option, `core/index/blocks.rs:16-26`) disables it entirely.
- **"The consensus address check would catch it."** For the validator, `main.rs:49-53` calls `Consensus::getCoordinator` on the configured address, so a chain where that address holds no contract fails the `eth_call` and `main` returns `Err` (exit code 1). That is a real partial guard and it narrows the window further — but it only compares the _contract_ to the chain, not the _database_ to either, so a database from another deployment on the same chain still resumes. The sentinel's startup performs no equivalent call.
- **"Under A1 the operator is trusted, so misconfiguration is out of scope."** A1 makes the operator honest, not infallible; the audit checklist asks specifically about "defaults, validation, dangerous combinations" (`codebase-map.md:211`). And this is the class of mistake that is cheap to make and expensive to detect: the service starts, `/health` answers, and the damage is in the nonce and snapshot records.
- **Tagged `known`** because `analysis-core.md:487` already records it as CORE-H17 at Informational. It is filed here at Low rather than Informational because the analysis scoped it to `core`'s two tables, and the sweep shows it is a workspace-wide property: no config schema offers the field, the validator's _secret_ store shares it, and the legacy configuration the system replaced did have an explicit chain id (basis row 6).

## Remediation options

1. Record provenance on first use. Add a one-row `deployment` table written when a database is created (`chain_id`, and for the validator/sentinel the `consensus`/`oracle` addresses), and compare it at startup against `provider.chain_id` and the configured addresses; refuse to start on a mismatch with a message naming both values. Small, self-contained, and it converts the whole class into a boot error. Tradeoff: existing databases have no row, so the first upgrade must adopt rather than reject.
2. Add an optional `chain_id` field to each config schema and reject a mismatch with the RPC's answer at connect time. Weaker than (1) — it catches the wrong _node_, not the wrong _database_ — but it restores parity with the legacy `CHAIN_ID` and is a two-line change.
3. At minimum, log the resolved chain id at `info!` rather than `debug!` on every service. The validator logs it at `debug!` (`crates/validator/src/main.rs:54`) and the sentinel does not log it at all, so at the shipped `log_filter = "info"` there is no record of which chain a running service believes it is on.

Tests to add: a test that opens a store stamped with one chain id and asserts that startup against another is rejected — which only becomes possible once option (1) or (2) exists.

### Corrections

- **Five tables, not four.** The Claim says "none of the four persistent tables — `snapshots`, `transactions`, `keygen_secrets`, `nonces_chunks`". `validator/src/secrets/store.rs:66-91` creates a fifth, `nonces`, in the same statement. The claim itself holds for all five (none carries a chain id, contract address or schema version), so this strengthens rather than weakens the finding — but the count should be corrected before the report quotes it.
- **The legacy-config comparison needs its own caveat.** `docs/configuration.md:33` — the note immediately above the environment block R10 quotes — says those variables configure "the legacy TypeScript Beta validator ... **not** the current Rust validator", that the Beta validator's onchain state "has diverged from the current repo" and "is not compatible with it", and that the section is "left as a historical record". Calling the missing field "a regression against the deployment it replaces" is therefore fair in substance (the earlier system did bind a chain id and the current one does not) but should not be read as a like-for-like comparison of two configuration surfaces. Worth softening in the report; it does not affect the verdict, because claims 1-5 stand entirely on their own.
- **Corroboration R10 missed in the same document.** The same block contains `GENESIS_SALT=0x5afe0000…` (`docs/configuration.md:49`) and the network-parameters list above it gives `Chain ID / 100` (`:24-25`) and `Genesis Salt / 0x5afe0000…` (`:32-33`). So the legacy deployment pinned _both_ discriminators the Rust services now leave implicit, which is a stronger version of claim 6 and is the same fact `F-XC-009` item 3 relies on.

### What I checked independently

- `Provider` does not merely cache the chain id, it **overrides the RPC method**: `chain_id` is a `const fn` returning the stored field (`provider/mod.rs:153`), and `fn get_chain_id(&self)` (`:163`) is reimplemented to return the cached value without issuing a request. So no code path in any of the three services can observe that the endpoint's chain changed mid-process, which is a fact about the _provider_ rather than about the tables and is worth keeping.
- The engine's per-checker guard is real and does what R10 says: `address_poisoning.rs:312-320` compares `transaction.chain_id` against `self.provider.chain_id` and abstains on a mismatch. It is also the _only_ such guard — `grep` finds no equivalent in any other checker, which is consistent with the finding's point that nothing enforces it centrally.
- The `Consensus::getCoordinator` partial guard is at `validator/src/main.rs:48-52` (the finding says `:49-53`, off by one on the range but the call is there), followed by `tracing::debug!(chain_id, %consensus, %coordinator, ...)` at `:54` — confirming remediation 3's premise that the resolved chain id is logged only at `debug`, i.e. not at the shipped `info`. The sentinel's `main.rs` performs no equivalent call, as claimed.

## QA (QA-XC)

**Not attempted (no toolchain).** Nothing was executed (A9 FALSE).

**No PoC written, and I judge one would be padding.** The finding is that a fact is _absent_ — no config field, no persisted column binds a deployment to a chain — and the Critic verified every structural claim by direct read and reproduced the decisive grep. A test can only demonstrate the absence by asserting the schema does not contain a column, which is a tautology restated in Rust. What the finding needs is a decision about remediation 1, not evidence.

The one thing worth running, once a toolchain exists, is the trigger end to end: point `rpc` at Sepolia with an existing Gnosis database, restart, and observe that startup succeeds (because `BlockTime::Auto` resolves on Sepolia rather than erroring) and that the resume picks up the stale snapshot via `ORDER BY block_number DESC LIMIT 1`. That is an integration exercise against two live endpoints, not a unit test, and it needs network — out of scope for this run under the PROMPT's boundaries.

**Remediation check — option 1 is sound and is the only one that closes the real gap; its stated tradeoff is the important one and must not be skipped.** A one-row `deployment` table stamped on creation and compared at startup catches the _database_/chain mismatch, whereas option 2 catches only the _node_/config mismatch — and it is the database that carries the stale snapshot and the foreign nonces. The tradeoff the finding names is correct and is a release-blocking detail: existing databases have no such row, so the first release must **adopt on absence** (write the current chain id and continue) rather than refuse, or every current operator is locked out on upgrade. I would add that the adopt-on-absence path should log at `warn` exactly once, so the adoption is visible in the operator's log rather than silent.

Option 3 (log the resolved chain id at `info` on startup) is free, catches nothing on its own, and should ship regardless of whether 1 or 2 does — it is also the same gap `F-ENG-009` and `F-XC-003`'s remediation independently ask to close: none of the three services echoes its resolved configuration at boot.

**Certainty: unchanged at 78%.** No new evidence of my own; the impact narrative remains reasoning over the schema rather than an observed failure, which is exactly why the Critic held it there.
