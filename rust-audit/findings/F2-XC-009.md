## Claim

The workspace manifest has no `[profile.release]`, and the images build with `cargo build --release`, so shipped binaries run with `overflow-checks = false` and `debug-assertions = false`. The repo-wide census (method and full table in `state/run2/agents/R8.md`) found no `panic!`/`unwrap`/`expect`/index/slice site reachable from chain logs or RPC responses in any profile. The only arithmetic on untrusted numeric input is the block watcher's wall-clock scheduling: header `timestamp * 1000`, `+ block_time`, `+ block_propagation_delay`, `+= block_time`, and `number + 1`, all on `u64`. With the default profile these wrap silently on an absurd header timestamp (≥ 2^64/1000 seconds) from a malicious or buggy RPC node (A4); with `overflow-checks = true` they would panic the watcher task. No site is _correct_ only because of wrapping; these five are _crash-free_ only because of it. A wrapped `timestamp_ms` either makes `sleep_until` return immediately (busy polling until the next header) or sleep far into the future (a liveness stall until restart). Neither exceeds what a malicious RPC can already do by withholding responses, hence Informational — but a loud crash is the better failure for a node that is supposed to be re-deployed on abnormal behaviour, and the two `debug_assert!`s in the validator are inert in production (both are provably safe, so no defect).

## Trigger

An RPC node returning a block header with `timestamp >= 18_446_744_073_709_551` (2^64 / 1000). Not observed on any real chain; reachable only from a malicious or corrupted node.

## Considered and rejected

- "Wrapping is relied upon for correctness somewhere": no. Every other arithmetic site in the census is bounded by construction (u16 counts from contracts, constant divisors, `saturating_*`/`checked_*` where inputs are chain-derived, SQL `MAX(nonce) + 1`), see the census table in `state/run2/agents/R8.md`.
- "Panicking is worse than wrapping": for a watcher whose garbage schedule can stall the node silently, a crash that the operator's restart policy surfaces is preferable; either way the impact is bounded by A4.

## Remediation options

1. Add to `Cargo.toml`: `[profile.release] overflow-checks = true` (negligible cost for this workload) so any future unchecked arithmetic fails loudly; optionally `[workspace.lints.rust] unsafe_code = "forbid"` to lock in the current no-`unsafe` state.
2. Use `checked_mul`/`saturating_mul` and `saturating_add` at the five block-watcher sites and clamp implausible timestamps (e.g. reject headers more than a day in the future) before scheduling.

Tests to add: a `BlockWatcher` test with a header timestamp of `u64::MAX` asserting no wrap (error or clamp).

**Remediation check.** Option 1 (`[profile.release] overflow-checks = true`) is sound: the test above is the proof it changes behaviour (it would start failing), the cost is negligible here, and it applies to every crate in the graph — dependencies are routinely tested with checks on, so that is a feature, not a risk; the resulting panic unwinds the driver task and `#[tokio::main]` exits non-zero, the loud failure R8 prefers, and it does not touch the `state/mod.rs` contract. `unsafe_code = "forbid"` matches the baseline's no-`unsafe` observation. Option 2 (`saturating_mul(1000)`/`saturating_add` at the five sites) is sound and targeted; its "reject headers more than a day in the future" clamp is the one part to handle with care — a node with a skewed clock would then be rejected outright, trading a garbage schedule for a liveness stall, so saturate first and make any plausibility bound a warning, not a rejection.
