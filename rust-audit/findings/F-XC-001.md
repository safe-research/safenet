## Claim

The workspace manifest defines no `[profile.release]`, so the shipped binaries are built with Cargo's stock release profile: `overflow-checks = false` and `debug-assertions = false`. Two consequences follow, and both are invisible in CI because CI tests run in the dev profile where both flags are on:

1. Every `debug_assert!` in the workspace is compiled out of the artefact that actually runs. The two that exist document real invariants (a `u16` group-size bound and a fresh-`NonceState` chunk index) and therefore assert nothing in production.
2. Every unchecked `+`, `-` and `*` on integers wraps silently instead of panicking. The arithmetic performed on RPC-supplied block timestamps (`blocks.rs:414`, `:427`, `:525`) is the reachable case: under A4 a stale or malformed timestamp is in scope, and in a debug build it would abort loudly while in the release build it wraps and mis-times block polling.

Neither flag is a defect on its own; the finding is that the choice was never made. The workspace ships whatever Cargo's defaults happen to be, and the release/debug divergence means the binary the team tests is not the binary the team runs.

## Trigger

No attacker trigger is needed for the `debug_assert` half: it is unconditional in every release build. For the arithmetic half, the concrete sequence is the A4 one — the configured RPC returns a block whose `timestamp` exceeds `u64::MAX / 1000` (a malformed or garbage header field, which A4 admits as "stale, rate limited, or incomplete" provider behaviour is not required to exclude); `blocks.rs:427` then wraps to a small `timestamp_ms` instead of panicking, and the watcher's poll scheduling is computed from the wrapped value. Impact is confined to polling cadence, which is why this is Low and not higher.

## Considered and rejected

- **"A `[profile]` might live in a `.cargo/config.toml` or a `rust-toolchain.toml`."** Checked: `ls -la rust-toolchain* .cargo` returns "No such file or directory" for both, and a `find . -maxdepth 3 -name 'config.toml' -path '*cargo*'` returns nothing. There is no profile override anywhere in the checkout.
- **"CI would catch a wrapping bug."** CI runs `cargo test --workspace` (`Justfile:44`), i.e. the dev profile, where `overflow-checks` defaults to on. That is precisely why the divergence is invisible: the tested profile panics on overflow and the shipped profile does not.
- **"The arithmetic sites are all provably safe."** Most are — `analysis-core.md:226-270` and `analysis-validator.md:159-193` argue several of them convincingly and I re-checked `fees.rs:16-29` and `state/preprocess.rs:189-246`, which use `checked_*`/`saturating_*` correctly. The three timestamp sites are the exception the analysis itself flags as "not provably safe (untrusted input)" (`analysis-core.md:239`).
- **Not claimed:** that a specific overflow is exploitable, or that enabling `overflow-checks` would find a live bug. The claim is only that the release/debug divergence exists and is unintentional-looking.

## Remediation options

1. Add an explicit `[profile.release]` to the workspace `Cargo.toml` with `overflow-checks = true`. On this workload (chain indexing, occasional signing) the cost is small and it converts a silent wrap on untrusted input into a loud crash that the supervisor restarts. Tradeoff: a genuine benign overflow anywhere becomes a crash, so it should land together with a pass over the sites the analyses list.
2. Alternatively keep `overflow-checks = false` but replace every unchecked operation on RPC-supplied or chain-supplied values with `checked_*`/`saturating_*`, and record the decision in the manifest as a comment so the absence of a profile is visibly deliberate.
3. Independently: promote the two `debug_assert`s to real `assert`s or to `if`-guarded error paths, since as written they are dead code in production.

Tests to add: a unit test that feeds `BlockWatcher` a header with `timestamp = u64::MAX` and asserts a defined outcome rather than a wrapped one — that test passes today in dev only by panicking, which is itself the point.

### Counter-evidence on the arithmetic half

The assignment asked whether any "safe" arithmetic site is safe _only_ because of release wrapping, or unsafe _because_ of it. I ran an exhaustive non-test sweep (lexer-based, strings / raw strings / comments / `#[cfg(test)]` items excluded; script and output in the session scratchpad) over all 83 `.rs` files. The entire unchecked-integer surface in non-test code is:

- **3 binary `-`**, all guarded: `index/clock.rs:55` is inside `if target > now` (`:54`); `index/events.rs:310` is `page_size.get - 1` on a `NonZeroU64`; `tx/fees.rs:24` is `PRECISION - scaled_percent` behind `if scaled_percent >= PRECISION { return fees; }` (`fees.rs:17-19`) — which also removes the divide-by-zero I went looking for, including for `cap_percentage` values of NaN (`f64::max` returns `0.0`) and `+inf` (the `as u128` cast saturates above `PRECISION`).
- **1 `-=`**: `state/keygen.rs:840` `complaint.unresponded -= 1`, guarded eight lines earlier by `.filter(|complaint| complaint.unresponded > 0)` (`:821-826`). This was the single best candidate for a release-only wrap on chain-driven input (A2) and it is explicitly guarded.
- **9 `+=` and the `*`/`+` sites**, all requiring inputs at or near `u64::MAX` to wrap.

So there is no site in this workspace that is safe only because overflow checks are off, and none that becomes unsafe because they are. The practical consequence of the missing profile today is zero; the finding is a hardening/consistency observation, not a latent bug.

The Trigger as written also over-reaches on A4. It needs "a block whose `timestamp` exceeds `u64::MAX / 1000`", i.e. roughly 5.8e8 years of Unix time, and argues A4 admits it because A4's list of in-scope RPC misbehaviours "is not required to exclude" a malformed header. A4 enumerates **stale, rate limited, or incomplete** and then says "An actively malicious RPC is out of scope." A header field fabricated at ~`u64::MAX` is neither stale, nor rate limited, nor incomplete; it is fabrication, which is the excluded case. The trigger is therefore unproven within the confirmed assumptions.

### Interaction with the panic/cast census (checked, as instructed)

I re-derived the census independently rather than accepting R10's. Method: a Rust-aware lexer that blanks comments, string, raw-string and char literals, tracks brace depth, and excludes every line of every `#[cfg(test)]`-annotated item (8,740 of 24,286 lines). Over all 83 files, non-test code: **`panic!` 0, `unreachable!` 0, `todo!` 0, `unimplemented!` 0, `unsafe` 0, `unwrap` 6, `unwrap_err` 0, `expect(` 15, `expect_err(` 0, `assert!` 1, `debug_assert*` 2, numeric `as` casts 25.** These are R10's numbers exactly, site for site. The negative is earned; see the Critic section of F-XC-002 for the per-site reachability re-check.

None of the 21 `unwrap`/`expect` sites depends on overflow-check behaviour in either direction. The two `debug_assert`s do disappear in release, but both assert invariants that are independently enforced by the types: `group.rs:236`'s `min <= u16::MAX as u32` follows from `count: u16` widened to `u32` at `:231` (`count * 2 / 3 + 1 <= 65535` for any `u16`), and `keygen.rs:1310`'s is a state-machine sanity check on a freshly created chunk. Removing them loses a diagnostic, not a guard.

### Finding verdict

**Plausible.** Mechanism verified as far as it can be without a toolchain (no profile section anywhere in the checkout; the shipped artefact is `--release`); the consequence step is `I` by construction; and the one concrete trigger offered is outside A4.

**Certainty: 66%** — top of the Plausible band, because the mechanism is about as solid as an `I` can be, and the countervailing sweep shows the impact is nil rather than merely unproven.

**Severity: Low → Informational.** PROMPT.md §8 reserves Low for "robustness, error handling, or configuration weaknesses with limited impact" and Informational for "hardening, documentation, test gaps". After the sweep above, the entire demonstrated content of this finding is (a) two diagnostics that do not run in release and are redundant with the type system, and (b) a divergence between the tested and shipped profiles with no reachable consequence in the current code. That is hardening. The remediation (option 1) remains worth doing precisely because it is cheap and keeps the property true as arithmetic is added — but it should not compete for attention with the Low-band findings that have real triggers.

### Notes for the team

Remediation option 3 ("promote the two `debug_assert`s to real `assert`s") should be taken with care: `group.rs:236` sits on the epoch-rollover path, so converting it to `assert!` would convert a theoretically-impossible condition into a validator crash. An `if`-guarded `tracing::error!` is the safer form of that option.

## QA (QA-XC)

**Not attempted (no toolchain).** Nothing was executed (A9 FALSE).

**No PoC written, deliberately.** The finding's remaining `I` leg is a property of the build, not of the code: what Cargo's stock `release` profile sets when the manifest overrides nothing. A Rust test cannot answer that; a build can. It is question 7 of `rust-audit/poc/UNRESOLVED-DEPENDENCY-QUESTIONS.md`, and it takes two minutes:

```sh
cargo build --release --workspace -v 2>&1 \
  | grep -o "\-C debug-assertions=[a-z]*\|\-C overflow-checks=[a-z]*" | sort -u
```

Confirming `overflow-checks = false` and `debug-assertions = false` leaves the finding **Informational**, which is where C-XC correctly moved it after the sweep found no reachable arithmetic consequence. Showing either enabled voids the finding outright.

The finding's own suggested test — feed `BlockWatcher` a header with `timestamp = u64::MAX` and assert a defined outcome — is worth writing on its own merits, but note what it actually proves: run under `cargo test` (a dev profile) it exercises the _checked_ arithmetic, which is the opposite of the shipped configuration. Under the release profile it would silently wrap. So the test documents the intended behaviour rather than reproducing the finding, and the README of any future PoC should say so.

**Remediation check — option 1 is sound; option 3 needs the amendment C-XC gives.** Adding an explicit `[profile.release]` with `overflow-checks = true` is cheap insurance on this workload (chain indexing and occasional signing) and keeps the property true as arithmetic is added; its stated tradeoff — that a genuine benign overflow becomes a crash — is real and argues for landing it alongside a pass over the sites the analyses list. Option 2 (keep it off and use `checked_*`/`saturating_*` at every RPC- or chain-supplied value, recording the decision in the manifest) is also sound and is the more honest of the two if the team does not want the runtime cost. **Option 3 as written is unsafe:** promoting the `debug_assert!` at `crates/validator/src/consensus/group.rs:236` to `assert!` puts a theoretically-impossible condition on the epoch-rollover path behind a validator crash. The safe form is an `if`-guarded `tracing::error!` (with a metric, per `F-XC-010`'s argument), which preserves the diagnostic without adding a liveness failure mode.

**Certainty: unchanged at 66%.** No new evidence of my own.

## Verification (V-XC, Phase 5)

**Outcome: Confirmed. `overflow-checks = false` and `debug-assertions = false` in every shipped binary, established from the actual rustc invocations rather than from Cargo's documented defaults.**

### What I ran

```
$ cargo build --release --workspace --locked -v      # exit 0
  (full log: rust-audit/state/logs/cargo-build-release-v.txt)
```

Then, over the verbose log, the codegen flags Cargo actually passed:

```
$ grep -o "\-C debug-assertions=[a-z]*\|\-C overflow-checks=[a-z]*" ... | sort -u
-C debug-assertions=off

$ grep -o "\-C opt-level=[0-9a-z]*\|\-C debuginfo=[0-9]*\|\-C strip=[a-z]*\|\-C lto[= a-z]*\|\-C panic=[a-z]*\|\-C codegen-units=[0-9]*" ... | sort -u
-C opt-level=3
-C strip=debuginfo
```

`-C debug-assertions=off` is passed explicitly. `-C overflow-checks=` is **never passed at all**, which is Cargo declining to emit a flag whose value equals the profile default — and for the stock `release` profile that default is `overflow-checks = debug-assertions = false`. Both are off. The answer to question 7 of `rust-audit/poc/UNRESOLVED-DEPENDENCY-QUESTIONS.md` is the first of its two bullets: the finding stands.

The verbose log also settles the rest of the stock profile, which the finding did not enumerate and which is worth having on record: `opt-level=3`, `strip=debuginfo`, and **no** `-C lto`, **no** `-C codegen-units`, **no** `-C panic` — i.e. `lto = false`, `codegen-units = 16`, `panic = "unwind"`. Panics unwind rather than abort in production.

The manifest premise is re-confirmed on this checkout:

```
$ grep -rn "profile" Cargo.toml crates/*/Cargo.toml
(no output)
$ ls -a | grep -i "cargo\|rust-toolchain"
Cargo.lock
Cargo.toml
```

No `[profile.*]` section anywhere, no `.cargo/` directory, no `rust-toolchain` file. Nothing overrides the stock profile, and the three Dockerfiles build `--release`.

### Verdict

**Basis class: the remaining `I` leg moves to `E1`.** The profile values are read off the compiler invocations Cargo issued for this workspace on the pinned toolchain, not inferred from documentation.

**Severity: Low / Informational — unchanged.** Execution confirms the premise; it does not supply the reachable arithmetic consequence the finding's Critic sweep looked for and did not find. The two `debug_assert!`s are dead in production, which is the finding as filed.

**Certainty: 66% → 93%.** Executed. The 7% is that "no reachable arithmetic consequence" remains a negative established by review rather than by fuzzing — **A8** is still FALSE, there is no test-vector corpus, and `overflow-checks = true` is precisely the switch that would turn a silent wrap into a loud panic if such a site existed.

**Remediation 1 (add `[profile.release] overflow-checks = true`) remains worth doing as cheap insurance**, and the Critic's caution on remediation 3 stands unchanged and unweakened: `crates/validator/src/consensus/group.rs:236` sits on the epoch-rollover path, so promoting that `debug_assert!` to `assert!` would convert a theoretically-impossible condition into a validator crash. An `if`-guarded `tracing::error!` is the safe form. Note also, from the flags above, that `panic = "unwind"` is in force: a panic in a worker task aborts that task, not the process, which is the behaviour the `if`-guarded form is chosen to avoid relying on.
