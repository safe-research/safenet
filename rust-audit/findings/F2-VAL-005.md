## Claim

`start_key_gen` emits `Effect::KeyGenSetup` exactly once, from the transition that opens the round, and `handle_key_gen_setup` is the only place that fills `secrets`. Effects are not durable and a resume is only persisted with the next committed log range, so a restart between the commit of the round-opening block and the commit of the block that carries the resume reloads `CollectingCommitments { secrets: None }` with nothing that will ever re-issue the effect. The same state is reached when the restart's rollback anchor (`safe + 1`, see F2-VAL-003) happens to be the round-opening block itself. The validator then never publishes `keyGenAndCommit`.

For a regular epoch the round either times out with the validator missing from `commitments` (peers exclude it, and locally `exclude_all_others` excludes itself too, so it follows the restarted group as an observer) or, if its earlier commitment had already landed and was replayed, hits the PR #851 "stuck setup" branch and skips the epoch. Either way the validator forfeits one epoch. For genesis there is no deadline, so the network's genesis never completes (A16: the operator redeploys; Informational, `known`).

Re-issuing the effect is safe by construction: `store_keygen_secrets` returns the already stored secrets for the same `(group_id, me)` instead of resampling, so a repeated `KeyGenSetup` produces the same commitment.

## Trigger

1. Regular epoch: `NewBlock(B)` opens the round, `B`'s log range commits `CollectingCommitments{secrets: None}`, the effect completes and resumes into live state. The process is killed before `B+1`'s log range commits (≈ one block, 5 s on Gnosis), or is later restarted with rollback anchor `B` (F2-VAL-003, row 7). On start the state is `secrets: None`; no effect is in flight (row 1-4). Peers commit; the validator does not. At `B+120` peers exclude it; locally `handle_key_gen_timeouts` excludes itself as a non-committer and it observes the restarted group. If its `keyGenAndCommit` from the durable queue had already landed before the crash, the replay puts it into `commitments`, all `count` are present, and row 4 skips the epoch at `B+120` while the peers wait for its share and then exclude it.
2. Genesis: `KeyGen` log at `B` (delivered on warps as well); the same crash window leaves `secrets: None` with `deadline: None` (row 5): no commitment is ever published, the contract needs all `count`, genesis never completes for anyone. Recovery needs the operator to redeploy (A16).

## Considered and rejected

- _The durable transaction queue saves it._ The queue only holds actions emitted after the resume; a lost resume emits nothing.
- _The reconciliation effect re-creates it._ `ReconcileGroupSecrets` retains the group's secrets (`state/preprocess.rs:149-153`) but never resumes `Setup`.
- _The store makes it unsafe to re-issue._ The opposite (row 6): the store is precisely designed for repeated setup effects.
- _A17._ No out-of-band database access is required; a plain restart suffices.

## Remediation options

1. In `handle_key_gen_timeouts` (or a new per-block routine), re-emit `Effect::KeyGenSetup` whenever the state is `CollectingCommitments { secrets: KeyGenCommitment::Participating { secrets: None, .. } }` and no resume has arrived for `k` blocks (e.g. every block; the store makes it idempotent and cheap). Tradeoff: occasional duplicate effect while the first is still in flight; `handle_key_gen_setup` already ignores a second resume once `secrets` is `Some`.
2. On startup, have the service scan the reloaded state for outstanding setups and emit the effect once. Tradeoff: needs a hook in `Driver::run`/`Service`; simpler semantics.

Tests to add: a state test that starts a round, drops the resume, applies `NewBlock`s and asserts a `KeyGenSetup` command is emitted again.

## Critic (C2-VAL-A)

**Finding verdict: Confirmed (mechanism). Duplicate of F2-VAL-063 (R6) — F2-VAL-063 is canonical. Severity Low → Medium (to match the canonical). Certainty 65%.**

The mechanism is solid and code-verified: `start_key_gen` emits `Effect::KeyGenSetup` exactly once (keygen.rs:1149-1153); `handle_key_gen_setup` is the only filler of `secrets`, and only from `secrets: None` (keygen.rs:71-82); resumes mutate live state and persist only with the next committed log range (core state/mod.rs:246-250, 236); no `NewBlock` routine or replayed log re-emits the effect (keygen.rs:1003-1024 only _skips_, and only with a deadline); re-issuing is idempotent because the store reuses existing secrets (store.rs:171-197). Genesis has no deadline and cannot restart (keygen.rs:52-53, 1204-1210) → permanent halt, Informational/`known` under A16. All Basis rows Supported.

**Duplicate resolution (as directed; F2-VAL-063 not edited).** F2-VAL-005 and **F2-VAL-063** (R6, owned by C2-VAL-B) describe the same defect: a lost/failed `KeyGenSetup` that is never re-issued, stranding the validator in `CollectingCommitments { secrets: None }`. **F2-VAL-063 should be canonical:** it is strictly broader — it additionally covers the _transient-failure_ trigger (`store_keygen_secrets` DB error → `Resume::Noop`, service/effect.rs), which needs **no restart at all** and no narrow crash window, and it cites the effect handler where the failure is swallowed. That failure path is the stronger argument and justifies **Medium**, so I align F2-VAL-005's final severity to Medium and mark it the duplicate; F2-VAL-005 contributes the restart-loss angle and the explicit genesis permanent-halt note. The report should carry one Medium finding (F2-VAL-063) and cross-link F2-VAL-005, not double-count. Remediation 1 (re-emit on `NewBlock` while `secrets: None`, idempotent via the store) is the same in both and is sound.
