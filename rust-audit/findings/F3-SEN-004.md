## Claim

Known area (`settled.md` section 2: in-flight engine checks lost on restart, #973; a commit seen while the request waits for its engine check is ignored and no reveal follows, #961). This finding adds that the case #973 lists as recovered is not.

On restart the block watcher rolls back to the oldest retained snapshot (about `max_reorg_depth` blocks behind) and, when the node was down for about five blocks or more, replays the missed range as a warp. A warp page is applied in one update, with each block's `NewBlock` before its logs, and effects are spawned only after the update. #973 says that when the proposal block P is newer than the rollback anchor, replaying `TransactionProposed` re-emits the engine check and the request recovers. It does not, for a request this sentinel already committed to: the same page replays the sentinel's own `Committed` while the request is back in `WaitingForEngineCheck`, so `handle_committed` ignores it. The recorded verdict then resumes, `commit_vote` starts over with `self_committed: false` and queues a second `Commit` (it expires unsent once the head is past the commit deadline, or reverts with `AlreadyCommitted`), and at `NewBlock(commitDeadline + 1)` the request is dropped. No reveal is sent for a bond that is onchain. If the page reaches past the commit deadline, the request is dropped inside the page, before the resume.

Result per affected request: if any other sentinel reveals, this sentinel's commitment is slashed by 0.40 USDC.e and 799.60 USDC.e stay claimable by it alone, with no claim queued; if nobody reveals, the full 800 USDC.e wait until someone finalizes and the sentinel claims by hand. Every request whose own commit landed in the last ~5 blocks before the shutdown is affected, which, with a 6-block commit window, is any request in its commit phase at the time of an ordinary restart (container restart, upgrade, crash with restart policy).

## Trigger

Aegis request opened in block P (`commitDeadline` P + 6), defaults (`max_reorg_depth` 5):

1. This sentinel's engine check resumes and its commit lands in P + 2; the state machine is in `CollectingCommitments { self_committed: true }`.
2. The process stops at block L = P + 3 (upgrade, crash and restart, host reboot). The oldest retained snapshot is about L - 5 = P - 2, older than P.
3. It comes back about 30 s later; the chain head is about P + 9, its reorg-safe block about P + 4. The watcher queues `Uncle(P - 1)` and `Warp { from: P - 1, to: P + 4 }`.
4. The warp page replays `TransactionProposed` and `NewRequest` (P) and this sentinel's `Committed` (P + 2) in one update; the commit is ignored. After the page, the engine check resumes from the verdict store; a second `Commit` is queued, and expires unsent because the head (P + 9) is past its expiry (P + 6).
5. `NewBlock(P + 7)` drops the request. No reveal; outcome as in the claim.

With a shorter downtime the replay runs as live blocks and the resume usually, but not reliably, wins the race against the next block's log fetch (`crates/core/src/driver.rs:229-232`, an unbiased `select!`).

## Considered and rejected

- #973 (open issue) covers the case where P is at or below the rollback anchor and says the case above recovers ("the restored snapshot is older than the proposal, and replaying `TransactionProposed` emits a new `EngineCheck`. ✅"). The test shows that the re-emitted check is not enough once the own commit is part of the replay. #961 reports the symptom from a suspected reorg. The fix #973 proposes (re-emitting checks for `WaitingForEngineCheck` entries) would not repair this case either, because the own commit is still ignored during the replay.
- The verdict store works as intended here: the resume carries the first verdict, so the second commit hash equals the first; the problem is the lost `self_committed`, not the vote.
- A17 (out-of-band database access) does not apply: the trigger is an ordinary restart of the service with its own database.
- Code age: pre-existing; at `fe9e84c` the ignore path is at `crates/sentinel/src/service.rs:316` and the restart replay predates run 2.

## Remediation options

1. Treat the sentinel's own `Committed` as authoritative in any state that can precede `CollectingCommitments`: record `self_committed` (and the count) in `WaitingForEngineCheck`, and let `commit_vote` keep it and skip re-sending `ApproveToken`/`Commit`.
2. Read the commitment onchain (`getCommitment(requestId, self)`) when the verdict resumes for a request whose proposal block is in the past, before queuing a commit; the oracle is the source of truth for whether a bond exists.
3. At minimum, never drop a request at `commitDeadline + 1` without checking the oracle for an existing commitment.

Tests to add: a `StateMachine`-level test (snapshots, uncle, warp) that restarts between this sentinel's commit and its reveal, for P newer and older than the rollback anchor; both must reveal.

Restart mechanics, which the executed test does not cover. Retained snapshots are those at or above the watcher's `safe` (`latest` minus `max_reorg_depth`) plus the latest (`crates/core/src/state/storage.rs`, `prune`, called from `driver.rs:263`), so after a stop at block L the oldest retained snapshot is about L - 5. `BlockWatcher::initialize` queues `Uncle(safe + 1)` and, for any downtime of at least one block, `Warp { from: safe + 1, to: head - 5 }` (`blocks.rs:315-331`). A warp page is applied in one `handle_update` (`state/mod.rs:212-244`) and its effects spawn after it (`driver.rs:261-279`). The proposal block P and the own commit block C fall in the same page when P is at or above L - 4 and C is at or below head - 5: about four blocks (20 s) of downtime when C is the last block before the stop. The Claim's "about five blocks or more" is close enough. A queued second `Commit` past its expiry is never given a nonce (`crates/core/src/tx/storage.rs:170-176`), as the Trigger says.

Known-item check. #961 is the symptom (own commit ignored in `waiting_for_engine_check`, no reveal), with a suspected reorg as the cause. #973's "✅" bullet for P above the rollback anchor does not separate an in-flight check, which recovers, from a finished check whose commit already landed, which does not. Result: Reproduced, through the real core `StateMachine` (not hand-sequenced).

Route: a `StateMachine<State, SentinelTransition>` over an in-memory sqlite pool. Phase 1 runs live to block 12 with the proposal at P=10 and our own commit at P+2=12, pruning so the oldest retained snapshot is safe=7 (< P). Phase 2 drops the machine and recreates it (restart), then feeds `Uncle(8)` (rolls back to 7, below the proposal) and `Warp{8..=14}` with one logs page replaying the proposal (P) and our own `Committed` (P+2). The real warp ordering applies `NewBlock` before each block's logs and defers the engine-check resume to after the page, so the replayed own `Committed` lands in `WaitingForEngineCheck` and is ignored (not counted as participation). The deferred resume then re-commits with `self_committed` false and queues a second `Commit` (reverts `AlreadyCommitted` onchain). Crossing the commit deadline with live blocks, no `Reveal` is ever queued for the bond that is onchain. Test `f3_sen_004_restart_replay_ignores_own_commit_and_drops_without_reveal`.

Command and output: `poc/F3-SEN-004/` (`cargo test -p sentinel --bins qa3_sen_004 -- --nocapture`; `statemachine-audit-commit.txt`, module `statemachine_poc_module.rs`).

The test then FAILS ("any Reveal queued = true"), confirming it is coupled to the drop. That raw not-drop is unsound in general (it would reveal when no bond exists); the sound fix is remediation option 1 (record `self_committed` in `WaitingForEngineCheck`) or option 2/3 (read the oracle before re-committing/dropping).
