## Claim

Lead SEN-H15, confirmed as a mechanism and rated Informational. `Config::load` reads the whole TOML file into an ordinary `String` and hands it to `toml::from_str`. The `Signer` deserializer zeroizes the 32-byte `B256` it decodes, and the `k256::ecdsa::SigningKey` it builds zeroizes its scalar on drop, so the _parsed_ key is handled correctly. The _textual_ key is not: the file `String` is freed unwiped at the end of `load`; any owned copies the TOML deserializer makes of the string value are freed unwiped; and on a parse failure the complete file text is additionally retained in the error's `input: Arc<str>` until the error is dropped (and printed, see F2-XC-001). Under A1 process memory is trusted, so the exposure is limited to core dumps, swap and post-compromise memory reads of a container that runs as root (F2-XC-003); hence Informational.

## Trigger

Normal startup; the residue exists from `load` until the allocator reuses the pages. A core dump, swap-out, or a memory read by a co-located process makes it observable.

## Considered and rejected

- "The `SigningKey`/`PrivateKeySigner` itself leaks": no; claims 3-4 show the parsed material is zeroized, and `LocalSigner`'s `Debug` prints only address and chain id (alloy-signer-local `lib.rs:166-174`).
- Rating above Informational: process memory is inside the trust boundary (A1); the actionable leak of the same text is F2-XC-001.

## Remediation options

1. Read the file into `zeroize::Zeroizing<String>` (or `Zeroizing<Vec<u8>>` + `toml::from_slice`) so the buffer is wiped on drop; cheap and local.
2. Move the key out of the TOML document (environment variable, `signer_file`, or the planned KMS path), read it into a `Zeroizing` buffer, and keep the config file free of secrets; this also removes F2-XC-001's payload.

Tests to add: none practical; a review rule that secret-bearing buffers are `Zeroizing`.
