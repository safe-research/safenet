## Claim

`cargo audit` at the audit commit exits 1 with five vulnerabilities and eleven warnings (`rust-audit/state/run3/logs/05-audit.log`). Judged by call path rather than by the advisories' scores, none gives an attacker anything against the validator or sentinel:

- `h2` 0.4.14 (RUSTSEC-2026-0258) is compiled but never used: hyper's `http2` feature is enabled only through hyper-util's `server-auto`, pulled in by metrics-exporter-prometheus; its listener serves connections with hyper's HTTP/1 builder, and reqwest is resolved without its `http2` feature, so no HTTP/2 connection is ever made or accepted. Run against the real binaries, the metrics listener rejects an HTTP/2 prior-knowledge connection (`hyper::Error(Parse(VersionH2))`) and answers an h2c upgrade over HTTP/1.1, and the RPC client's TLS ClientHello offers only `http/1.1`.
- `ruint` 1.18.0 (RUSTSEC-2026-0220) is compiled, but no code in scope shifts a `U256` or uses a signed integer type; inside alloy the affected functions serve `I256` arithmetic and constant `nybbles` masks; the infinite loop the advisory mentions needs a no-alloc build. Neither binary contains `overflowing_shl` or `overflowing_shr`, which every affected function calls, and 1.18.0 carries only the overflow-flag half of the advisory (the shift-amount truncation arrived in 1.19.0).
- `crossbeam-epoch` 0.9.18 (RUSTSEC-2026-0204): its only user, metrics-util, never formats an `Atomic` or `Shared` with `Pointer` or `Display`.
- `rustls` 0.23.40 (RUSTSEC-2026-0285) runs on every TLS connection to the RPC or an HTTPS engine, but the advisory states the handshake transcript stays authenticated; only handshake messages that should have been encrypted are tolerated in plaintext. Nothing Safenet protects is exposed.
- `quinn-proto` 0.11.14 is not compiled.

The unsound and yanked warnings are likewise unreachable or not compiled (Considered and rejected). The defect is process: CI runs format, clippy and tests (`just check`, `just test`) but no `cargo audit` or `cargo deny`, so a reachable advisory would go unnoticed, and the current output cannot be used as a gate without an explicit ignore list.

## Considered and rejected

- `event-listener` 5.4.1 (RUSTSEC-2026-0221, unsound): sqlx-core creates untagged `event_listener::Event` values (sqlx-core-0.9.0/src/pool/inner.rs:32, 61); the issue needs a `!Send` tag.
- `lru` 0.16.4 (RUSTSEC-2026-0253, unsound): alloy-provider's caches use `BlockNumber` and `B256` keys (alloy-provider-2.0.5/src/blocks.rs:69, layers/cache.rs:512), whose `Drop` cannot panic; the issue also needs `catch_unwind`.
- `anyhow`, `derivative`, `bitcoin-io`, `bitcoin_hashes`, `chacha20`: not compiled for any workspace package (baseline section 3); `atomic-polyfill`: not compiled on the host target.
- `paste`, `proc-macro-error2` (unmaintained): build-time proc macros; `proc-macro-error2` also triggers the clippy 1.99 future-incompatibility notice (baseline section 2), which matters for future toolchains, not for the binaries.
- `spin` 0.9.8 (yanked): compiled through flume into sqlx-sqlite; the only spin advisory for that line (RUSTSEC-2023-0031) is fixed in 0.9.8.
- Severity is not taken from the advisories' CVSS (7.5 for quinn-proto, 5.3 for rustls), per the brief.
- Introduced since run 2? No. Every flagged crate has the same version at `fe9e84c` (baseline section 3).

## Remediation options

1. Refresh the lock for the patched versions: `h2` 0.4.20 (fix in 0.4.16; hyper needs `^0.4.14`), `ruint` 1.20.1 (alloy-primitives needs `^1.16.0`; do not stop at 1.19.x, which introduces the shift-amount truncation that 1.20.0 fixes), `rustls` >= 0.23.45, `crossbeam-epoch` >= 0.9.20, and `lru` >= 0.18.2 once alloy allows it; then re-run the test and integration suites.
2. Add `cargo audit` (or `cargo deny check advisories`) to `just check` with an ignore list that records each accepted advisory and its reachability verdict, so a new reachable advisory fails CI.

Tests to add: none beyond the CI step. No code is committed.
