## Claim

The scheduled-pruning feature (handbook "Secret Retention") removes DKG secrets and nonce chunks with plain `DELETE` statements, and the state machine's per-block snapshots are likewise discarded with `DELETE` on rollback and prune. `connect_sqlite` sets no pragmas. Whether SQLite overwrites freed cells therefore depends entirely on the `SQLITE_SECURE_DELETE` compile-time flag of the **system** `libsqlite3` the image happens to link (the workspace deliberately does not use sqlx's `bundled` feature), and even where that flag is on, the rollback journal (the default journal mode; sqlx sets none) receives page pre-images containing the secret and is unlinked, not wiped. "Deleted" secrets remain recoverable from the database file, its journal, and the block device for an unbounded time.

Independently of erasure, the round-2 DKG state — `SharingState`, which holds this validator's encryption key, its round-2 `SecretPackage` (its own secret share) and every peer's decrypted `round2::Package` (their shares to us, i.e. everything needed to compute the final signing share) — is serialized into every per-block snapshot of the state machine while `KeyGenParticipation::Participating`. That material is thus duplicated once per block until `prune`, is not in `keygen_secrets`, is not covered by the scheduled-deletion logic, and is not counted by the `safenet_validator_secrets_total` gauge the handbook tells operators to watch.

An attacker who can read the database file is outside the threat model (A17, and the handbook already says to treat the file as containing secret keys), so this is a hardening gap in an advertised property rather than an exploitable defect: Informational.

## Trigger

None identified within the threat model; requires read access to the database file, its `-journal`, or the underlying storage after a prune, reorg or snapshot rotation.

## Considered and rejected

- "SQLite always zeroes deleted content": only with `SQLITE_SECURE_DELETE` (compile flag) or `PRAGMA secure_delete = ON`; the project sets neither and links whatever `libsqlite3-0` the runtime image resolves.
- "Foreign-key cascade might leave nonces behind": sqlx enables `PRAGMA foreign_keys = ON` by default (`sqlx-sqlite-0.9.0/src/options/mod.rs:187`), so `nonces` rows cascade from `nonces_chunks`; the deletion is logically complete, which is exactly the point — logical, not physical.
- "`SharingState` in snapshots is a leak": it is the same file and the same trust domain; the concern is retention accounting and duplication per block, not disclosure.

## Remediation options

1. In `connect_sqlite`, execute `PRAGMA secure_delete = ON` (or `fast_secure_delete`) on every connection via `SqliteConnectOptions::pragma`, and choose an explicit `journal_mode` (WAL with periodic `wal_checkpoint(TRUNCATE)`, or `DELETE` with `secure_delete`), so erasure no longer depends on the distribution's build flags. Cost: slightly more I/O on deletes.
2. Keep `SharingState` out of snapshots: store it in the `SecretStore` keyed by group (it is generated from `Secrets` plus onchain data, so it can share the keygen row's scheduled deletion) and reference it from the state machine; this also stops per-block duplication and makes the `secrets_total` gauge honest.
3. Document in the handbook that deletion is best-effort at the storage level and that disposing of a database file requires secure wiping.

Tests to add: a store test asserting `PRAGMA secure_delete` reads back `1` on a pooled connection.
