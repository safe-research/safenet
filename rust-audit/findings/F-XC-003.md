## Claim

Three configuration structs put `#[serde(deny_unknown_fields)]` on a container that also has a `#[serde(flatten)]` field. Serde documents that combination as unsupported. The observable consequence, if `deny_unknown_fields` is inert there, is that a mistyped key in a validator or sentinel TOML is silently accepted and the intended setting never applies — including the two settings whose absence is a security-relevant degradation rather than a cosmetic one:

- `[index] use_client_filtering` — the switch that makes the event watcher verify `eth_getLogs` results client-side instead of trusting the node's filtering (A4, CORE-H2). A typo here leaves the validator running with node-filtered, unverified results while the operator believes the protection is on.
- `[index] max_reorg_depth` — a typo leaves the built-in default in place instead of the operator's chosen depth (A5).

Both live inside `index::Config`, which is itself a `deny_unknown_fields`-plus-two-`flatten` container (`core/index/mod.rs:20-29`), so the same question applies one level down.

What is _not_ in doubt, and is the load-bearing half of this finding: **the engine, which is the only one of the three configs with no flattened field, is also the only one with a test proving unknown keys are rejected.** The two configs that use `flatten` have `parses_sample_config` and missing-field tests but no unknown-field test, so nothing in the suite would notice if the attribute were inert.

## Trigger

An operator copies `validator.sample.toml`, uncomments the `[index]` block and writes `use_client_filtering = ture` (or `use_client_filter`, or puts it under `[indexer]`). If `deny_unknown_fields` is inert on this container the file loads without complaint, the validator starts, `/health` answers OK, and the client-side `eth_getLogs` verification is off. Nothing in the logs distinguishes this from a correct configuration: the setting has no startup log line and no metric. The same shape applies to `max_reorg_depth` and to every key under `[transactions]`.

## Considered and rejected

- **"It is a compile error, so the code would not build."** I could not resolve this without a toolchain, and the honest reading of the available evidence is that it is not: the workspace builds in CI (`Justfile:29`, `:44`) with the attribute pair present in three structs, and a coverage report was posted on PR #896 (`codebase-map.md:59`). So the combination is accepted by the locked `serde_derive`; what it _does_ at runtime is the open question. This is stated as class `I` rather than asserted either way.
- **"The samples do not parse, so this is moot."** They do parse — each crate has a `parses_sample_config` test reading the real file from `CARGO_MANIFEST_DIR` (`crates/validator/src/config.rs:282-289`, `crates/sentinel/src/config.rs:136-143`, `crates/sentinel-engine/src/config.rs:146-153`). Sample-vs-schema drift is genuinely covered. That is exactly why the _unknown_-key case stands out as the one gap.
- **"Unknown fields would be caught by the inner struct's own `deny_unknown_fields`."** For the `[index]` and `[transactions]` tables the inner structs do deny (`core/index/mod.rs:21`, `core/tx/mod.rs:70`, `core/index/blocks.rs:48`, `core/index/events.rs:72`), but they are only reached if the flattened routing delivers the key there in the first place; and `driver::Config` in between denies nothing (basis row 4), so a stray _top-level_ key or a stray `[table]` has no denier on its path at all.
- **"`observability` is affected too."** It is not: it is a named field, not flattened, and `observability::Config` denies unknown fields itself (`core/observability/mod.rs:17`).
- **Severity.** Low, not higher: under A1 the operator is trusted and this is a misconfiguration-detection gap, not an attacker-reachable path. It is filed because the degradation is silent and because the fix is one test.

## Remediation options

1. Add the missing test to both configs — the engine's `rejects_unknown_field` copied verbatim with a validator/sentinel body, plus one that plants a typo _inside_ `[index]`. If the tests pass, the concern is closed by evidence and the tests keep it closed; if they fail, the bug is real and was found for the price of ten lines.
2. If they fail: drop `flatten` and make `driver` a named `[driver]` table (a breaking config change, but it restores the denial and removes the ambiguity), or move `deny_unknown_fields` down to every non-flattened leaf and accept that top-level typos are not caught.
3. Independently of the above, log the resolved configuration at startup (with secrets redacted, see F-XC-002) so an operator can see that `use_client_filtering` is off. Today the only startup line is `config_file = %options.config_file.display` (`crates/validator/src/main.rs:43`), which says the file was read but nothing about what it contained.

### Being precise about `E2`-from-this-repo versus `I`-about-serde, as instructed

**`E2` from this checkout, no serde knowledge required:**

1. The attribute pair exists in three structs (rows 1-3).
2. `driver::Config` — the container everything flattened is routed _into_ — has **no** `deny_unknown_fields` (row 4). Whatever serde does with the outer attribute, an unknown key that reaches this struct is dropped in silence. That is a repo-internal fact and it is the half of the finding that does not depend on upstream semantics at all.
3. No test anywhere asserts that a validator or sentinel config rejects an unknown key (row 6).
4. **The combination compiles and the flatten routing works.** `validator/src/config.rs:235-275` (`deserializes_with_optional_service_fields`) deserializes a TOML document containing `[index] max_reorg_depth = 12` and `[transactions] max_in_flight_transactions = 4` and asserts `config.driver.index.blocks.max_reorg_depth == 12` and `config.driver.transactions.max_in_flight_transactions == 4`. That is a doubly-flattened path (outer `Config` → `driver::Config` → `index::Config` → `blocks::Config`) exercised by a test in the tree. This is stronger evidence for R10's "it is not a compile error" than the CI-and-coverage-report argument the Considered-and-rejected section actually uses, and it comes from the repository rather than from a document about it.

**`I`, and unresolvable this run:** whether `serde_derive` at the locked version honours, silently drops, or partially applies `deny_unknown_fields` on a container that also has a `flatten` field — and correspondingly whether a stray _top-level_ key in `validator.toml` is rejected or ignored. Nothing in this checkout answers that, and I decline to answer it from recollection of upstream documentation.

### What this means for the finding's shape

The finding is really two claims of different strength, and the file presents them as one:

- **A test gap (`E2`, certain).** Two of the three service configs have no unknown-field test, and the third — the one that _has_ the test — has no flattened field, so its test proves nothing about the interaction. R10 states this accurately ("the only one of the three configs with no flattened field"), but a reader skimming the Claim could take the engine as the crate that "got it right" on this specific question. It is simply a different shape.
- **A possible silent-acceptance bug (`I`).** Conditional on serde's behaviour.

Both point at the same one-line remediation, so the finding stands as filed.

### Finding verdict

**Plausible.** The mechanism is verified — the attribute pair, the un-denying intermediate container, the missing tests — but the consequence the Claim leads with ("a mistyped key is silently accepted") rests on an upstream behaviour that is class `I` here, and the trigger is an operator typo rather than an observed failure.

**Certainty: 58%.** Mid-band: everything checkable is checked and correct; the one link that decides whether this is a bug or a non-issue is unreadable this run.

**Severity: Low (unchanged).** Under A1 the operator is honest but not infallible, and the two settings named — `use_client_filtering` (an A4 integrity switch) and `max_reorg_depth` (A5) — degrade silently if a typo is swallowed. That is "configuration weakness with limited impact", which is Low. Not Informational, because the failure is undetectable at runtime: there is no startup log of the resolved configuration (`validator/src/main.rs:43` logs only the file path) and no metric.

### What that settles

Question 3 of `rust-audit/poc/UNRESOLVED-DEPENDENCY-QUESTIONS.md` is answered: **yes**, `#[serde(deny_unknown_fields)]` does something on a container that also carries `#[serde(flatten)]`. Serde routes the unknown key into the flattened container's map, and the outer container's deny still fires. Concretely, and in the terms the question asked:

- **A stray top-level key is rejected**, on both crates. `not_a_real_field = "typo"` errors.
- **A typo inside `[index]` is rejected** — `use_client_filterring` on the validator (the **A4** client-side-filtering switch) and `max_reorg_dept` on the sentinel (the **A5** knob). These are the sharp cases the question named by name, and both fail loudly rather than degrading in silence.
- **A mistyped table name is rejected**: `[observabilty]` errors.
- **The two crates do not disagree.** The validator's `#[serde(default, flatten)]` and the sentinel's bare `#[serde(flatten)]` behave identically here, so no fix has to straddle both forms.
- The control passes: a typo inside `[sentinel]`, whose container has no flattened field, errors as it must.

**The one fact that survives regardless is untouched and still true**, and it is worth keeping in the finding: `core::driver::Config` is `#[serde(default)]` with **no** `deny_unknown_fields` (`crates/core/src/driver.rs:29-37`), unlike all five of its siblings in `core`. The six tests show that the _outer_ deny catches keys before they get there, so today nothing reaches it — but the asymmetry is real, it is one line to fix, and it is what would break if any of these containers ever lost its own `deny_unknown_fields`.
