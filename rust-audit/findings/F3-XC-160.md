## Claim

When the logs query for the newest block fails with JSON-RPC code -32001 ("resource not found"), the watcher asks the node for the block at that height again and treats every answer other than the same hash as proof that the block was uncled, including no block at all (`current` is `None`). The doc comment says so on purpose ("or cannot find the block at all"). A backend that has not imported the block yet can give exactly these two answers: -32001 for logs of a block hash it does not know (the code this recovery listens for; the comment attributes it to Reth around uncled blocks) and `null` for a block number above its head. Behind a load-balanced endpoint, where consecutive requests can reach backends one block apart, the watcher therefore reports an uncle for a block that is still canonical. The block watcher drops the block and queues `Uncle`, and the state machine restores the snapshot of the previous block, exactly as for a real one-block reorg.

That rollback opens the live-reorg hole issue #973 describes ("Same hole without a restart: live reorgs", which "hasn't been reproduced yet"), here without any reorg. Resumes are not snapshotted, so every effect result applied since the previous block's snapshot is lost, and the replay does not emit the effect again. For the sentinel this is the common case: the engine check for a proposal in block P starts after P's snapshot and normally answers within the 5 s before P + 1's logs are fetched, and its resume has already queued `ApproveToken` and `Commit` in the persistent transaction queue. A spurious `Uncle { P + 1 }` puts the request back into `WaitingForEngineCheck` with no check running. The `Commit` still lands, the sentinel logs "ignoring unexpected commitment" for its own commit, drops the request after the commit deadline, and never reveals. On Aegis that leaves the 800 USDC.e bond in the oracle: if another sentinel reveals, 0.40 USDC.e is slashed and the remaining 799.60 USDC.e waits for a manual `claim`; if nobody reveals, the whole bond waits for a manual `finalize` and `claim` (the end state of issue #961).

Known consequence (#973, #961, and the core mechanism in F3-CORE-032), new trigger: no reorg and no restart are needed, only two consecutive requests that reach a backend one block behind. The fix for the trigger is local and cheap (Remediation option 1), independent of the larger #973 work.

## Trigger

Aegis parameters (`settled.md` section 3, `baseline.md` section 6): Gnosis 5 s blocks, `max_reorg_depth` 5, the samples' shared public endpoint as `rpc`, SentinelOracle commit and reveal windows of 6 blocks, bond 800 USDC.e, slash 0.40 USDC.e, engine timeout 18.75 s.

1. Block P carries a `TransactionProposed` for the configured oracle and its `NewRequest`. The sentinel applies P, commits snapshot P with the request in `WaitingForEngineCheck`, and spawns the engine check.
2. The engine answers within a few seconds. The resume moves the request to `CollectingCommitments` in memory and queues `ApproveToken` and `Commit`, which the queue broadcasts at once (in #961 the commit landed in the next block).
3. The block watcher fetches block P + 1 by number from a backend that has it. The event watcher asks for P + 1's logs by block hash (also with `use_client_filtering`, whose query is by hash too) and reaches a backend that has not imported P + 1: -32001. The revalidation's `eth_getBlockByNumber(P + 1)` reaches a backend that is still behind: `null`.
4. The watcher emits `Uncle { P + 1 }` and counts it in `uncled_blocks_total`; the state machine restores snapshot P. Nothing runs the engine check again.
5. P + 1 is fetched again with the same hash and replayed (its `NewBlock` actions are queued a second time, gas only). The sentinel's own `Committed` in P + 1 or P + 2 is "ignoring unexpected commitment". At `NewBlock(P + 7)` the request is dropped. No reveal; the bond ends as described in the Claim.

The vulnerable window is one block per request (the first block whose logs are fetched after the verdict resumed). How often a load-balanced Gnosis endpoint serves two consecutive requests from a backend one block behind, and whether the Gnosis clients behind it (Nethermind, Erigon) answer -32001 rather than -32000 or an empty result for an unknown block hash, was not measured: both decide practicality.

## Considered and rejected

- Real reorgs: the same rollback after a real one-block reorg is #973's live case (known). This file adds that the watcher fabricates the rollback when a backend lags, and names the deciding code (`blocks.rs:561-564`).
- A single, non-load-balanced node: it served the header, so it also knows the hash; it can only "forget" the block through a real reorg. The trigger needs backends at different heights behind one URL.
- `use_client_filtering` does not avoid it: the client-filtered query is also by block hash (`crates/core/src/index/events.rs:453-460`, `:533-538`).
- No crash: after the restore the status is `BlockPending { pending: P + 1 }`, and the re-fetched `New { P + 1 }` matches it (`crates/core/src/state/mod.rs:196-199`); the queue unmarks executions above P on the lower `latest` (`crates/core/src/tx/mod.rs:188-199`). Duplicated actions cost gas only.
- Validators in live operation: the results of their event-emitted effects either reach the persistent queue (nonce commitments, shares) or replay from chain data, and effects emitted by the optimistic `NewBlock` are replayed (F3-CORE-032, Considered and rejected). The genesis `KeyGen` case is A16 (Informational).
- Not offered as issue #961's root cause: its nonce read at block 48382227 returned a nonce the canonical block had already passed, which suggests the answering node held a different block 48382227 (a real fork). #961 shows the end state this path also produces.
- Related, not filed: the opposite direction (R1 observation O9). A client that answers logs of an orphaned hash with another code (geth-family clients use -32000 "unknown block") never triggers the revalidation, and the block watcher, which would detect the reorg through the parent hash, is not polled while the event watcher fails (`crates/core/src/index/mod.rs:85-97`). That needs client data before it can be a finding; Remediation option 1 should keep it in mind.
- Pre-existing: the same comparison is at `fe9e84c` (`git show fe9e84c:crates/core/src/index/blocks.rs`, lines 504-505) and was ported from the TypeScript watcher, which also turned a missing block into an uncle (`git show e69fdc8^:validator/src/watcher/blocks.ts`, lines 307-318) but backed off when the block was still canonical.
- Not A17 (no out-of-band database access) and not settled. Tagged `known` because the consequence is #973 and #961 (A12).

## Remediation options

1. Treat "no block at that height" as "not available yet": in `revalidate_last_block`, return `Ok(None)` when `current` is `None`, so the logs query is retried, and report an uncle only when the node returns a different hash at that height. A real reorg to a shorter chain then resolves at the next slot, when the replacement block appears with a different hash. Trade-off: departs from the doc comment and the TypeScript behaviour; a node that permanently loses a block keeps the watcher retrying, which is already the behaviour for every other error code.
2. Require positive evidence before invalidating: confirm a missing block with a second query, or check the parent hash of the next block, before queuing `Uncle`.
3. Independently, the #973 and F3-CORE-032 fix (re-emit outstanding effects after any rollback) removes the bond consequence for real and spurious uncles alike.

Tests to add: a copy of `recovers_from_an_uncled_block_with_unavailable_logs` (`crates/core/src/index/mod.rs:355-402`) whose revalidation answers `null` (`asserter.push_success(&Option::<Block>::None)`) instead of a different hash: today `watcher.next()` returns `Update::Block(BlockUpdate::Uncle { number: 1000 })`; after option 1 it should return the retried logs query's error. For the consequence, #973's planned test "a reorg that uncles the block after an engine check resolved" covers both triggers. No code is committed.

## QA (QA3-CORE, 2026-10-08)

Result: Reproduced, with a modelled backend.

Route: (1) A copy of `recovers_from_an_uncled_block_with_unavailable_logs` whose revalidation answers `null`: the watcher emits `Uncle { 1000 }`, then the same block 1000, same hash, as new. (2) End to end: two real sentinels with real sentinel-engines vote on one request against the real `SentinelOracle` on a local Anvil (1 s blocks; fee 400000, bond multiplier 2000, slashing 1x, commit and reveal windows 6, arbitration timeout 483,840; amounts in 6-decimal base units, so 0.40 and 800). Sentinel A reads through a loopback proxy that, after serving the logs of block P = 18 holding `NewRequest`, answers the logs query for P + 1 by hash with -32001 and `eth_getBlockByNumber(19)` with `null`, once each; sentinel B reads Anvil directly. Sentinel A logs `last block no longer canonical, invalidating` and `logs unavailable for uncled block, skipping` for block 19, then `ignoring unexpected commitment` (state `waiting_for_engine_check`) for its own commit and for B's, then `ignoring reveal for an untracked request`; it never reveals. Onchain the request resolves approved with 2 commits and 1 reveal. A's commitment is unrevealed and unclaimed, A's token balance is down 800,000,000, B's is up 400,000, and the oracle still holds 799,600,000, A's bond less the 400,000 slash, waiting for a manual `claim`. The control without injection: both sentinels reveal and claim, 200,000 each.

Command and output: `poc/F3-XC-160/` (`watcher-test-at-361aaf3.txt`, `e2e-injection-at-361aaf3.txt`, `e2e-control-no-injection.txt`).

Bite check: remediation 1 (no block at that height means not available yet): the watcher test now returns the -32001 error instead of an uncle, and with the rebuilt sentinel the same injection is retried and absorbed: A reveals, finalizes and claims, 200,000 each, as in the control. It changes intended behaviour: the existing unit test `revalidate_invalidates_a_block_missing_from_rpc` (`crates/core/src/index/blocks.rs:1218-1229`) pins a missing block as uncled and fails with the remediation, so it has to change too; the rest of the core suite passes. Correction to Basis row 11: the missing-block case is tested, by that unit test.

Unverified offline: whether Gnosis clients (Nethermind, Erigon) answer -32001 for logs of a block hash they lack, and how often a load-balanced Gnosis endpoint sends two consecutive requests to a lagging backend. Anvil 1.5.1 itself answers `[]` for logs of an unknown block hash, not -32001 (`anvil-client-answers.txt`); a backend like that never takes this path and instead hands the watcher an empty log set, the situation of F3-CORE-002.
