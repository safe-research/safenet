## Claim

`Provider::connect` hands the configured RPC URL to alloy's `ClientBuilder::connect` and returns its error unchanged. The URL scrubbing added by #1046 (`without_url`) only runs inside the transport layer, so it never sees this error. alloy 2.0.5 parses the connection string by trying HTTP, then WebSocket, then IPC; when the scheme is neither `http(s)` nor `ws(s)`, the last fallback (`try_as_ipc`) formats the whole string into its error: `failed to read IPC path <url>: No such file or directory`. Both services return that error from `main`, and Rust prints it with `Debug` to stderr. So a mistyped scheme, for example `htps://`, writes the full RPC URL, including the API key in its path or query, to the service logs. This happens for a literal URL and for one supplied through `${NAME}` substitution, the path #1007 added for keeping that key out of the file.

This adds to known issue #113 and to #1046's "Not covered" list. That list says a malformed RPC URL is still quoted and attributes the quote to the `url` crate. The run below shows that `url` crate errors never quote the URL: the only quoting path is alloy's IPC fallback for a well-formed URL with an unsupported scheme.

## Trigger

An operator sets `rpc` (directly or through `${RPC_URL}`) to a URL that parses but whose scheme is not `http`, `https`, `ws` or `wss`, for example `htps://gnosis-mainnet.g.alchemy.com/v2/<key>` or `wws://...`. The service exits at startup with status 1 and prints the full URL to stderr, which container runtimes collect into the log pipeline. No network access is needed for the leak; the IPC fallback only calls `metadata()` on the string as a local path.

## Considered and rejected

- `url` crate errors: `Url::from_str` messages are fixed strings; the run in Basis row 8 confirms the URL is not quoted for a bad port, a missing scheme, or a bad host. Config parse errors also drop the document (`crates/core/src/config.rs:32-49`).
- WebSocket URLs: a `ws(s)` URL with a reachable or unreachable host goes through `WsConnect`, whose errors I did not see quoting the URL; not executed (needs a network target).
- Runtime RPC errors: covered by `without_url` (Basis row 2) and confirmed scrubbed by the control run.
- The `known` tag: issue #113 ("Prevent sensitive information from being logged", RPC keys) is open and #1046 lists a startup quote of a malformed RPC URL as not covered. This file adds the actual mechanism and shows the stated one does not occur, so it is filed tagged `known` rather than dropped.
- Severity: needs an operator typo, and the leak goes to the operator's own logs (A1). Low at most; Informational if the team counts it under #1046's accepted gap.

## Remediation options

1. In `Provider::connect`, reject any scheme other than `http`, `https`, `ws`, `wss` before calling alloy, with an error that names only the scheme (one `match url.scheme()`), or build the transport explicitly (`Http::new(url.clone())` / `WsConnect`) instead of parsing a connection string. Tradeoff: IPC support, which no sample or doc uses, would need an explicit opt-in.
2. Map the `connect` error through a scrubber that replaces any occurrence of the URL string (and its path and query) with `<redacted>`. Tradeoff: string matching on error text is brittle across alloy versions.

Tests to add: a unit test that `Provider::connect(&"htps://host/v2/SECRET".parse().unwrap())` returns an error whose `Display` and `Debug` do not contain `SECRET`, next to the existing secret-leak test in `crates/core/src/config.rs:112-156`.
