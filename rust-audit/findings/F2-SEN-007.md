## Claim

The transaction queue is durable and is never rolled back, while the FSM is rewound on every uncle and on every restart (which always replays at least `max_reorg_depth` blocks). Every replayed transition re-emits its actions and the driver enqueues them as new rows: there is no idempotency key, no `eth_call` simulation, and no check against already-queued calldata. The duplicates always revert onchain (`AlreadyCommitted`, `AlreadyRevealed`, `RequestNotPending`, `AlreadyClaimed`) but each consumes a nonce and the gas for a revert. Separately, every sentinel that participated submits `Finalize` although only one can succeed, and `handle_arbitration_timeout` emits `Claim` for a tracked entry in _any_ state — including `WaitingForEngineCheck`/`WaitingForRequest`, where no bond exists — so that claim reverts `NothingToClaim`, unlike the sibling handlers that consult `approve_and_slash_amount`.

## Trigger

A one-block reorg uncles block `commit_deadline + 1` after `NewBlock(commit_deadline + 1)` emitted `Reveal`. The FSM is restored to `CollectingCommitments`; the replacement block's `NewBlock` emits `Reveal` again; two rows now exist; the second reverts `AlreadyRevealed`. The same happens for `Claim` after a reorg of the `DisputeResolved` block, for `Finalize` after a reorg of the last `Revealed` block, and for `ApproveToken`+`Commit` after any rollback that re-runs the engine check. On restart the replayed window is `max_reorg_depth` blocks wide, so every in-flight request in that window re-emits whatever block- or event-driven actions fall inside it.

## Considered and rejected

- "Contract guards make duplicates safe": safe for funds, yes; the finding is gas and nonce consumption plus inconsistent handler behaviour, hence Low.
- "The queue's `expires_at` drops them": only for unsubmitted `Commit`/`Reveal` past their deadline; `Finalize`/`Claim` never expire.

## Remediation options

1. Add a deterministic idempotency key column (e.g. `keccak(to ‖ data)`) with a unique index over unexecuted rows, and ignore duplicates at enqueue time; alternatively have the sentinel encoder attach a key.
2. Simulate (`eth_call`) before first submission and drop transactions that would revert with a known guard error.
3. In `handle_arbitration_timeout`, use `approve_and_slash_amount()` like the other terminal handlers.

Tests to add: a queue test asserting a duplicate `(to, data)` is not inserted while the original is unexecuted; a flow test for `ArbitrationTimedOut` from `WaitingForRequest` asserting no `Claim`.
