## Claim

`handle_committed` counts a `Committed` event only while the request is in `CollectingCommitments`. While the request still waits for this sentinel's engine verdict (`WaitingForEngineCheck`), every other sentinel's commit is logged as "ignoring unexpected commitment" and lost, and `commit_vote` later starts the tally at zero. A sentinel whose engine answers later than another sentinel's commit lands therefore holds a `committed_count` below the onchain `committedCount`.

`handle_revealed` uses that count to decide when everyone has revealed. With an undercount it calls `finalize()` too early, which does one of two things:

1. If the reveal that reaches the count is another sentinel's, `finalize()` sees `self_revealed == false` with reveals present and drops the request. This sentinel's own reveal is already queued and still valid; it lands, the oracle finalizes inside that `reveal()` call, and the `OracleResult` arrives for an untracked request. No `Claim` is ever queued. The 800 USDC.e bond and the fee share stay in the oracle until someone claims by hand from the sentinel's account.
2. If this sentinel's own reveal reaches the count first, it queues a `Finalize` that the oracle rejects (`FinalizeTooEarly`, a committed sentinel has not revealed yet) and parks the request in `WaitingForOutcome`, which never acts on blocks. If the uncounted sentinel never reveals, nobody's state machine calls `finalize` after the reveal deadline: the request stays `PENDING`, no `OracleResult` is emitted, and every committed bond stays locked until someone finalizes and claims by hand.

Case 1 needs no attacker: it happens whenever two honest sentinels' engines differ in speed by about a block and the faster one reveals first. Case 2 can be forced by an active sentinel that commits in the proposal's own block (or before the honest engines answer) and never reveals: no honest state machine counts that commit, so after the honest reveals none of them finalizes. With correct counts, the reveal-deadline branch (`service.rs:460-475`) would finalize and claim in both cases.

## Trigger

Honest sentinels, Aegis parameters (request opened in block P: `commitDeadline` P + 6, `revealDeadline` P + 12; engine timeout 18.75 s):

1. Block P carries `TransactionProposed` and `NewRequest`. Sentinels A and S both start their engine checks after processing P (about 1.6 s after its slot at p90).
2. A's engine answers within about 3 s, so A's approval and commit land in P + 1. S's engine takes longer than about one block (still well inside its 18.75 s budget), so S processes block P + 1, and A's `Committed`, while in `WaitingForEngineCheck`. The commit is ignored.
3. S's verdict arrives; S commits in P + 3. S now has `committed_count: 1`; onchain `committedCount` is 2.
4. At `NewBlock(P + 7)` both reveal. If A's reveal is processed first (earlier block, or earlier in the same block), S drops the request. S's reveal lands, the oracle finalizes inside it and emits `OracleResult`, and S never claims: 800 USDC.e stranded per occurrence, plus the missed fee share.
5. If S's reveal is processed first instead, S sends a `Finalize` that reverts and waits in `WaitingForOutcome`. A's reveal then finalizes onchain and S claims, unless A never reveals, in which case nothing finalizes after the deadline.

Adversarial variant: an active sentinel M backruns `proposeTransaction` in block P (or commits in P + 1 against slower engines) with any nonzero hash and never reveals. Every honest sentinel undercounts by one; after the honest reveals, each honest state machine has either dropped the request or parked it in `WaitingForOutcome` after a rejected `Finalize`. No one calls `finalize` after P + 12, the request stays `PENDING`, and all honest bonds stay locked until manual action. M's own slash (0.40 USDC.e) only applies once someone finalizes.

## Considered and rejected

- Known items. #961 and #973 (`settled.md` section 2) cover this sentinel's own commit being ignored after a restart or a live reorg, so that no reveal follows. Here the ignored commits are other sentinels', on the normal live path with no restart or reorg, this sentinel's reveal does go out, and the loss is the claim (case 1) or the finalization (case 2). The known "bond stranded at `revealDeadline + 1`" is about this sentinel's reveal missing the window, which is not the case here.
- `WaitingForRequest` would also drop commits, but it is unreachable on the live path because `NewRequest` is emitted in the same transaction as `TransactionProposed` (`contracts/src/Consensus.sol:253-267`), so only `WaitingForEngineCheck` matters.
- Other sentinels' state machines may still finalize. Only a sentinel whose engine answered before every other commit has a correct count; in the adversarial variant (commit in block P) no honest sentinel does, and in case 1 the stranded claim is this sentinel's own, which nobody else can claim (row 8).
- Onchain recovery. `claim` has no deadline, so the funds are not lost; they need a manual `claim` (case 1) or a manual `finalize` plus claims (case 2). Each stranded bond removes 800 USDC.e from the sentinel's working balance; once the balance cannot cover a bond, its commits revert and it stops voting.
- Side note, same code path: with a correct count the early `Finalize` is always redundant, because the last reveal already finalized onchain (row 7); the queued `Finalize` reverts with `RequestNotPending`. Wasted gas only.
- Code age: pre-existing. At `fe9e84c` the same logic is at `crates/sentinel/src/service.rs:316` ("ignoring unexpected commitment"), `:222` (`committed_count: 0`), `:372` (early finalize) and `:653` (drop).

## Remediation options

1. Remove the early finalize from `handle_revealed`. The oracle already finalizes when the last committer reveals, and the outcome event (`OracleResult`, `DisputeTriggered`, `RequestTimedOut`) drives the claim. Keep the reveal-deadline branch, and never drop a request this sentinel committed to: at `revealDeadline + 1` send `Finalize` whenever the request may still be pending, and claim on the outcome. Fixes both cases and the redundant transaction.
2. Count commits from `NewRequest` onwards: keep a `committed_count` in `WaitingForEngineCheck { request: Some(..) }` and carry it into `CollectingCommitments`. Smaller change, but keeps the redundant early `Finalize` and the drop-on-not-revealed rule.
3. Make `WaitingForOutcome` retry `Finalize` after `revealDeadline` until an outcome event arrives, so a rejected early `Finalize` cannot strand the request.

Tests to add: flow tests (as in `service.rs` `mod tests`) for a foreign commit processed before the verdict, followed by a foreign reveal first (must still claim) and by a missing reveal (must finalize after the deadline).
