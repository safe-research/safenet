## Claim

Both samples set `database = "sqlite:/var/lib/safenet/<service>/data/storage.db"` with no `mode` parameter. sqlx-sqlite 0.9.0 defaults to `create_if_missing: false`, and `connect_sqlite`, the only pool constructor both services use, does not change it. On a fresh node (the data directory exists, the database file does not yet) the pool fails to open with SQLite error 14, "unable to open database file", and the service exits during startup. Every Aegis node starts fresh, so every operator who copies a sample hits this on the first run. The repository's own scripts avoid it by appending `?mode=rwc`, and the tests that load the samples only parse them; neither the samples, the handbooks nor `docs/configuration.md` mention the parameter. The failure is loud and recoverable (pre-create the file or add `?mode=rwc`), hence Low.

## Trigger

1. A new operator copies `validator.sample.toml` or `sentinel.sample.toml`, fills in the addresses and key, and mounts an empty volume at `/var/lib/safenet/<service>/data` as the handbooks describe (docs/sentinel-handbook.md:82 for the sentinel).
2. First start: `Provider::connect` succeeds, then `connect_sqlite` fails with "unable to open database file"; `main` returns the error, so the process prints it and exits with status 1. An on-failure restart policy retries and fails the same way until the operator intervenes.

## Considered and rejected

- Do the existing sample tests catch it? No. `crates/validator/src/config.rs:277` and `crates/sentinel/src/config.rs:131` deserialize the samples, which succeeds; no test opens the configured database.
- Does some other code path set `create_if_missing`? `connect_sqlite` is the only constructor in scope (`git grep create_if_missing 361aaf3 -- crates/` is empty); `SecretStore` and `VerdictStore` take the already-open pool.
- Is it only the missing directory? No: the PoC creates the directory first; the file alone is what `mode=rw` refuses to create.
- Introduced since run 2? No. The `database` lines and `connect_sqlite` are identical at `fe9e84c`.

## Remediation options

1. Call `.create_if_missing(true)` on the options inside `connect_sqlite` (a fresh file is the expected first-run case; the risk of silently creating an empty database at a mistyped path remains and can be logged at INFO with the path).
2. Or change both samples (and the handbook examples) to `sqlite:/var/lib/safenet/<service>/data/storage.db?mode=rwc` and explain the parameter.

Tests to add: a startup test that opens the sample's database URL rewritten to a temporary directory. No code is committed.

Finding verdict: Confirmed. Severity: Low to Low: every operator who follows a sample and its handbook (`docs/validator-handbook.md:116-129`, `docs/sentinel-handbook.md:77-91`) gets a failed first start, and the SQLite text ("unable to open database file") points at paths or permissions rather than at the missing parameter; the failure is loud, comes before any chain write, and one config edit fixes it, so not Medium. Certainty: 95, top band (E1 here and in both duplicates, Confirmed). Duplicate: canonical for F3-XC-005, F3-VAL-060 and F3-SEN-005. One root cause (`connect_sqlite` keeps sqlx's default and both samples omit `mode=rwc`); this is the only file that covers both services and the shared constructor, and its E1 exercises the function both services call. F3-VAL-060 holds the strongest single reproduction, the `361aaf3` validator binary exiting 1 on an empty data directory and getting past the pool with `?mode=rwc` (`logs/R6-sample-db-startup.txt`), which QA should carry into this file; F3-SEN-005 adds the sentinel-side E1 through the sentinel's own `Config` (`logs/R7-sample-database.txt`) and the risk note on remediation 1.

What the remediation options do not weigh. `create_if_missing: false` is sqlx's default, not a Safenet choice, but it protects every later start: if the container is recreated with a mistyped named volume (`--volume validator-dta:...`), Docker creates a new empty volume and the service refuses to start, instead of starting from an empty database. A validator started that way loses its key share and DKG secrets for the running epoch (`docs/validator-handbook.md:87`: loss "would prevent the validator from participating in consensus until new ones are computed"); a sentinel forgets its open commitments. Option 1 and option 2 both drop that guard. Variants that keep it: leave the default and make the first start explicit (document a one-time `?mode=rwc` start, or an `--init` flag), or name `?mode=rwc` in the startup error (F3-VAL-060 option 3).

QA recipe: rerun R6's `run_sample_db.sh` (source in `logs/R6-sample-db-startup.txt`) against the local run folder's `target-base/debug/validator`, then the same script with `crates/sentinel/sentinel.sample.toml` and the matching `target-base/debug/sentinel` (the sentinel opens the pool right after `Provider::connect`, `crates/sentinel/src/main.rs:44-45`, so the `eth_chainId` stub is enough). Expect exit status 1 and `SqliteError { code: 14, ... }` without `mode`; with `?mode=rwc`, the file is created and the next RPC call is reached. Remediation check: rerun `config::tests::parses_sample_config` in both crates against scratch samples ending in `?mode=rwc` (they must still parse).
