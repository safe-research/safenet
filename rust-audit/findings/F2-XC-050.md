## Claim

`Driver::update` processes a log range in this order: `StateMachine::handle_update` applies the transitions and **commits the snapshot** for the range; the driver prunes older snapshots down to the watcher's `safe`; then it encodes the transition's actions, **spawns** its effects, and only then **enqueues** the actions into the transaction queue, in a second, separate SQLite transaction. The recovery story for this ordering is the restart replay: on start the watcher emits `Uncle { safe + 1 }` and replays everything above the oldest retained snapshot, so a range whose actions never reached the queue is re-applied and its actions re-emitted (that replay is also what F2-CORE-032 and F2-CORE-063 complain about). The story silently depends on more than one snapshot being retained.

Whenever exactly one snapshot is retained, `initialize` emits no `Uncle` (`uncle > indexed.latest`) and resumes _after_ it (`Warp { from: latest + 1 }` or the next `New`), so the committed range is never replayed. Exactly one snapshot is retained (a) after **every page of a catch-up warp** — the watcher's `safe` during a warp is the node's `latest - max_reorg_depth` (the warp's `to`), every page ends at or below it, and `prune` keeps only rows `>= safe` plus the newest row, i.e. the page just committed — and (b) at **every block when `max_reorg_depth = 0`**. In those states a process death (SIGKILL, OOM, power loss) or a fatal error between the commit and the end of the enqueue — the enqueue's own SQLite error is fatal by design (`is_intermittent` is true only for `Rpc`) — permanently loses every action and effect the committed range produced. Nothing re-issues them: the snapshot records the events as handled, the queue has no row, and no effect is in flight.

Consequences per service, traced to the seam: the sentinel emits `Claim` and `Finalize` **directly from event handlers** with `expires_at: None` (the dispute, timeout and outcome terminal events, and the early-finalize path) — exactly the kind of event a catch-up warp delivers for a request the sentinel bonded on before its outage. Losing that `Claim` forfeits the bond remainder and the fee reward, because no later path re-emits it (F2-SEN-002 and F2-SEN-003 already establish that `Finalize`/`Claim` have no retry). The validator emits `KeyGenSecretShare`, `KeyGenConfirm`, `KeyGenComplain` and `KeyGenComplaintResponse` directly from event handlers; losing one inside a warp page that covers a rollover key generation excludes the validator from that epoch's group (the end state of F2-VAL-003/005). Effects lost in the same window generalise F2-CORE-030 to a whole page: during a warp the "anchor block" whose effects are never re-issued is every page, not one block.

Severity is Low: the window is short (the time between two SQLite statements on the driver task), it needs a hard kill or a storage fault rather than an orderly shutdown (the `biased` select completes the current input before stopping), and case (b) is a non-default configuration. A17 keeps it in scope: the loss is caused by the service's own write ordering, not by out-of-band database access.

## Trigger

Sentinel, catch-up variant. (1) The sentinel is down for longer than `max_reorg_depth` blocks (an outage, an image upgrade, the handbook's restore flow) while a request it bonded on reaches a terminal event (`ArbitrationTimedOut`, `DisputeOutOfScope`, `DisputeResolved`, `RequestTimedOut`, `OracleResult`). (2) On start the watcher queues `Uncle { safe+1 }` and `Warp { safe+1 .. node_safe }`; the first page is applied and committed; `prune(node_safe)` leaves exactly one row (rows 3–5). (3) The page contained the terminal event; `handle_arbitration_timeout` (or the outcome handler) removed the entry and returned `Claim { id }` with `expires_at: None` (row 9). (4) Between `commit` and the end of `queue` the process is killed, or `enqueue` fails with a SQLite error (`SQLITE_BUSY` after the 5 s `busy_timeout`, an I/O error); in the error case the driver logs "unrecoverable driver error; exiting" and `main` returns (with status 0, F2-CORE-031). (5) Restart: `snapshots = {page_end}`, no `Uncle` (row 6), `Warp { page_end+1 .. }`; the terminal event is not re-delivered; the entry is already absent from the committed state; no `Claim` is ever sent. The bond remainder and the fee reward stay in the oracle.

Validator, same shape: a warp page covering the `KeyGenCommitted` that completes a rollover round (→ `KeyGenSecretShare`) or the `KeyGenSecretShared` that completes sharing (→ `KeyGenConfirm`); the lost action means the validator never shares or confirms and is excluded at the round deadline.

`max_reorg_depth = 0` variant: every block; a kill between `commit(n)` and `enqueue` loses block `n`'s actions (non-default; F2-CORE-008 discusses depth 0 separately).

Not reproduced (no PoC in Phase 2). Rows 1–3 and 5–10 are code-traced; row 4 is an executed existing test that pins the single-row invariant and the no-uncle resume.

## Considered and rejected

- "The restart replay covers it" — only while `MIN(snapshots) < MAX(snapshots)`. Rows 3–6 show a single row after every warp page and at depth 0, and the second half of the cited test shows the resume skipping the committed page (`warp(4, 6)` after a page that ended at 3; the page's action `Action::Event(10)` is not returned again).
- "A failed `prune` leaves two rows, so that path self-heals" — correct, and it narrows the window: if `prune` at `driver.rs:263` fails, the older row survives and the restart `Uncle` replays the page. The loss needs `prune` to succeed and the kill or failure to land between `driver.rs:263` and the end of `driver.rs:283`.
- "Graceful shutdown cannot hit the window" — correct: the `biased` select finishes the current input before breaking (`driver.rs:186-198`). Only a hard kill, OOM or a fatal storage error does, which is why this is Low.
- "The services re-issue lost effects" — no: F2-CORE-030 shows core has no re-issue hook, and F2-VAL-005/063 and F2-SEN-001 show the services do not re-issue `KeyGenSetup` or `EngineCheck`.
- "Sentinel `Claim`s are re-emitted later" — `handle_arbitration_timeout` removes the entry before emitting (row 9), and F2-SEN-002/003 document that `Finalize`/`Claim` have no retry path.
- "`expires_at` bounds the damage" — the lost actions include the timeless ones (`Claim`, `Finalize`, `Preprocess`), and the failure is the absence of the row, not a late row.
- Overlap: F2-CORE-030 covers resumes discarded by a rollback and the anchor block's effects; F2-CORE-032/063 cover the opposite failure (duplicate enqueue). R2 O4 and R3 O2 describe this mechanism as observations (35–45 %) and each deferred it to "the Critic"; R1 rejected 23 / O12 establishes the single-row state during a warp. Nobody filed it.

## Remediation options

1. Write the snapshot and the queue rows in one SQLite transaction: return the commands from `handle_update` before committing, or pass the encoded `Transaction`s into `SnapshotStore::commit` so both tables are written under one `BEGIN … COMMIT`. Closes the action half completely; effects still need option 3.
2. Enqueue before committing: reorder `update` to encode → enqueue → commit → spawn. A crash then yields a duplicate action (already tolerated, F2-CORE-032/063) instead of a lost one. Cheap; turns at-most-once into at-least-once.
3. Persist pending effects with the snapshot (a `pending_effects` table written in the same transaction, cleared when the resume is applied) and re-spawn them in `Driver::new`. This is the same hook F2-CORE-030 needs and closes the effect half of both findings.
4. Minimal: during a warp keep the previous page's snapshot (prune to `MAX - 1` rather than `MAX`) so the restart `Uncle` always exists. Costs one extra row and one re-applied page per restart; re-applying a page re-emits its actions (duplicates, again tolerated).

Tests to add: a driver-level test with a mock `Service` whose `TransactionStorage` fails `enqueue` once after `commit`, asserting that after `Driver::new` + replay the page's actions are present in `transactions`; extend `warps_and_prunes_intermediate_snapshots` to assert that the commands returned for `logs(1..=3)` are recoverable after `drop(machine)` (today they are not).
