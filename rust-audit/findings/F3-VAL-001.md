## Claim

A single malicious key-generation participant can force a chosen honest validator's FROST verifying share to the identity point (`y = (0, 0)`) by crafting its own non-constant commitment coefficient points, which the contract never checks. The Rust validator layer deliberately treats an identity verifying share as valid (`verify_secret_share` accepts it, #1025), so the honest victim builds and submits `keyGenSecretShare` with `y = (0, 0)`. On-chain that call reverts in `FROSTParticipantMap.set` -> `Secp256k1.requireNonZero(y)`, so the victim's `KeyGenSecretShared` event never lands. Every other validator waits for the missing share until the round deadline, then `handle_key_gen_timeouts` excludes the (honest) victim via `exclude_all_others(shared)` and restarts the ceremony without it. No complaint path attributes the cancellation to the attacker, so the honest victim has no recourse.

The core problem is fault amplification. The attacker also loses its own slot (crafting the cancelling coefficient as a point with unknown discrete log means it cannot later produce verifiable secret shares, so it is excluded too), so one Byzantine participant produces two exclusions in a round. Aegis runs 5 validators with `min_participants` 4, so the set is sized to tolerate exactly one dropout (A2 allows one Byzantine of five). Two exclusions leave three participants, below the minimum, so the epoch's key generation is skipped (`EpochSkipped`). Repeating this each rollover while the attacker sits in the active group freezes the validator set: no epoch can ever roll over, so a departing or compromised validator can never be rotated out. At threshold 3 the attacker can instead cancel two distinct honest victims for the same effect without self-sacrifice reasoning.

## Trigger

1. A malicious validator `A` participates in an epoch-`N` key generation and waits until the other `count - 1` commitments are on-chain (commit order is observable; the coordinator is a permissionless message bus).
2. `A` crafts its non-constant commitment coefficient point `c[1]` (the `-evaluation * x.invert()` construction in the `accepts_cancelled_public_key_shares` test) so the combined group commitment evaluates to the identity at a chosen honest victim `V`'s identifier, keeping a valid `c[0]` proof of knowledge and a valid `q` proof of possession. `A` submits last; the contract and every honest validator accept the commitment.
3. The ceremony enters the share round. `V` recomputes its own verifying share as the identity, marshals it to `y = (0,0)`, and broadcasts `keyGenSecretShare`; the call reverts on `requireNonZero`. The queue does not check receipts, so `V` believes it submitted. `A` cannot produce verifiable shares for its crafted coefficient, so it also fails the round.
4. At the share deadline the honest validators exclude every non-sharer: both `A` and `V`. Only 3 of 5 remain, below `min_participants` 4, so epoch `N` is skipped (`participants_set` returns `None` -> `EpochSkipped`). Repeating this each rollover freezes the active validator set while the attacker participates; each round also excludes a fresh honest victim.

## Considered and rejected

- Is the victim's share rejected earlier in Rust, before it is submitted? No. `generate_secret_shares` computes `VerifyingShare::from_commitment` (returns the identity point with no error) and `finalize`/`part2` operate on secret scalars unaffected by the cancellation; `solidity_secret_share` then emits `y = (0,0)` (keygen.rs:195-223, marshal.rs:49-60). The only rejection is on-chain.
- Does the contract reject the attacker's commitment? No. `keyGenCommit` validates only `c[0]` (proof of knowledge, forces it non-zero through `mulmuladd`) and `q` (proof of possession); `c[1..]` are emitted in the event but never validated (FROSTCoordinator.sol:361-380). The Rust `verify_commitment` accepts the same crafted coefficients (they are valid curve points), confirmed by `persists_cancelled_group_commitment_coefficients` passing.
- Is this only genesis-ceremony liveness (A16, Informational)? No. The exclusion and restart path is the non-genesis branch (`restart_key_gen_excluding` with `EpochId::Number`), so it reaches epoch rollovers and later epochs, which A16 keeps at full severity.
- Is it the same as issue #69 (one dishonest participant removed per keygen)? No. #69 is a passive non-participant costing one timeout. Here an _honest_ validator is excluded by _attacker-controlled_ input, with no complaint recourse, and two can be removed per round at threshold 3, which is the qualitatively worse case the severity scale calls High.

## Remediation options

1. Make the Rust layer reject an identity verifying share the same way the contract does: have `verify_secret_share` (or the share-publishing path in `finalize_key_gen_commitments`) treat a self verifying share of the identity as a fault and raise a complaint against whichever commitment cancelled it, so the attacker is excluded instead of the victim. Tradeoff: attributing the cancellation requires recomputing each participant's contribution to the victim's share; more work, but it restores the intended "misbehaving participant is identified" property.
2. Reconsider the #1025 decision to persist/accept identity verifying shares at the validator layer given the contract forbids them: if identity verifying shares cannot exist on-chain, the Rust acceptance is dead accommodation that only hurts the victim. Reject identity `y` locally and surface it as an excludable fault of the last committer. Tradeoff: must still handle the legitimately cancellable non-constant group coefficients (which are a separate, on-chain-valid case).
3. Change the contract to allow an identity verifying share (drop `requireNonZero` in `set`) so the victim can publish and be handled downstream. Tradeoff: a contract change, out of this audit's scope, and identity keys are usually something a signing contract wants to forbid.

Tests to add: a validator integration test where one participant cancels another's verifying share and the harness asserts the honest victim is not the one excluded. No code is committed.
