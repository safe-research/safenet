## Claim

Three independent hardening gaps, identical across all three service images:

1. **No `USER`.** `debian:trixie-slim` leaves the default user as root, and none of the three Dockerfiles switches away from it, so every service runs as UID 0 inside its container. For the validator and the sentinel that process holds the signer private key and the SQLite file containing FROST key shares and signing nonces in plaintext (a documented A1 design choice); running it unprivileged costs nothing here because the binary needs no privileged port — the engine's default bind is 5473 and the metrics listener's is an ephemeral port — and one writable data directory.
2. **No digest pinning, and the two stages float independently.** The builder is `rust:1-slim` and the runtime is `debian:trixie-slim`; neither is pinned to a digest, so `cargo build --locked` reproduces the dependency graph exactly while the compiler, the C toolchain and the `libsqlite3-dev` the binary links against are whatever the tag resolved to that day. Because `rust:1-slim`'s own Debian base moves on Docker Hub's schedule and `debian:trixie-slim` is pinned to a release codename, the two can drift apart; the failure mode when the builder's base moves ahead of trixie is a runtime `GLIBC_2.xx not found` on a freshly built image, with no source change to explain it.
3. **The pipeline passes a build argument no Dockerfile declares.** `.github/workflows/docker.yml` builds each of these files with `build-args: COMMIT_SHA=${{ github.sha }}`, but no `ARG` statement exists in any Dockerfile in the repository. BuildKit warns and continues, so the published images carry no label or embedded value tying them to a commit — the one piece of provenance the pipeline explicitly tried to supply is dropped on the floor.

## Trigger

None identified for (1) as a standalone escalation — under A1 the host and the operator are trusted, and there is no in-container privilege boundary to cross. The value of `USER` here is blast-radius reduction: it is the difference between a container escape or a checker bug landing as UID 0 on the host namespace and landing as an unprivileged UID. (2) triggers on a rebuild of an unchanged commit after Docker Hub republishes `rust:1-slim`. (3) is unconditional: every image published by the pipeline today lacks the commit label.

## Considered and rejected

- **"`crates/core` is missing a Dockerfile."** It is not missing; `core` is a library crate and the map never claims one. `PROMPT.md` §4's `crates/*/Dockerfile` glob resolves to three files (baseline §4). Not a finding.
- **"Secrets or a config file get baked into the image."** They do not reach the _runtime_ image: the final stage copies exactly one path, the compiled binary (`COPY --from=builder /usr/src/app/target/release/<bin> ./<bin>`), and the config arrives at run time through `ENTRYPOINT ["./<bin>"]` plus the pod spec's `--config-file` argument. The `ENTRYPOINT`-not-`CMD` choice is deliberate and correctly commented (`crates/validator/Dockerfile:34-37`). The _builder_ stage is broader — `Dockerfile.dockerignore` is `/**` with `!/Cargo.toml`, `!/Cargo.lock`, `!/crates/**`, so everything under `crates/` enters the build context and the builder layer, including any real `validator.toml` a developer left beside the sample. That layer is not pushed, so it is recorded as an observation in the coverage log rather than claimed here as exposure.
- **"`ca-certificates` is unnecessary because rustls uses bundled roots."** Not asserted: the lock contains `webpki-roots` at 0.26.11 and 1.0.7, but which root source `reqwest 0.13` selects under `default-features = false, features = ["json", "rustls"]` cannot be determined without the dependency source (A6). Left alone.
- **"`WORKDIR /usr/src/app` would not be writable for a non-root user."** True, and it is the one real cost of remediation: the validator and sentinel need a writable path for the SQLite file. The sample configs already point that at `/var/lib/safenet/<service>/data/storage.db` (`crates/validator/validator.sample.toml:21`), a volume mount, so a `USER` switch plus a `chown` on that directory is sufficient — the image itself needs no writable location.

## Remediation options

1. Add a non-root user to each runtime stage (`RUN useradd --system --uid 10001 safenet` then `USER safenet`), and document that the mounted data directory must be owned by that UID. Tradeoff: an operator upgrading an existing deployment must chown the volume once.
2. Pin both bases by digest (`FROM rust:1.9x-slim@sha256:…`, `FROM debian:trixie-slim@sha256:…`) and bump them deliberately, matching the `--locked` treatment the dependencies already get. If full digest pinning is too much churn, pin at least the Rust minor version so builder and runtime cannot diverge silently.
3. Declare `ARG COMMIT_SHA` in each Dockerfile and turn it into an OCI label (`LABEL org.opencontainers.image.revision=$COMMIT_SHA`) in the runtime stage, so the argument the pipeline already passes stops being discarded.
4. Optional: add `EXPOSE 5473` to the engine image as documentation of the default bind.

Tests to add: none unit-testable. A CI step that runs `docker inspect` on the built image and asserts a non-root `User` and a non-empty `revision` label would gate all three.

## QA (QA-XC)

**Reproduced by inspection.** All three claims verified directly against this checkout. This does **not** put the finding in the 90-100 band, which requires `E1`; nothing was executed (A9 FALSE).

- **Claim 1 (no `USER`).** `grep -n "USER" crates/*/Dockerfile` returns nothing. I read `crates/sentinel-engine/Dockerfile` in full: builder `rust:1-slim`, runner `debian:trixie-slim`, `WORKDIR /usr/src/app`, `apt-get install ca-certificates`, `COPY --from=builder`, then `ENTRYPOINT ["./sentinel-engine"]`. No user is set, so every process runs as uid 0.
- **Claim 2 (no digest pin).** All six `FROM` lines across the three Dockerfiles use floating tags — `rust:1-slim` three times, `debian:trixie-slim` three times. No `@sha256:` anywhere.
- **Claim 3 (the provenance argument is discarded).** `.github/workflows/docker.yml:70` passes `build-args: COMMIT_SHA=${{ github.sha }}`, and `grep -rn "ARG" crates/*/Dockerfile` returns **no match** — no Dockerfile declares `ARG COMMIT_SHA`, so the value is dropped and the images carry no record of the commit they were built from. This is the claim whose trigger is unconditional and present in every published image today, and it reproduces exactly as filed.

**No PoC written, deliberately.** A Rust test proving "the Dockerfile runs as root" would be padding. The right check is the one the finding and C-XC both propose: a CI step running `docker inspect` and asserting a non-root `User` and a non-empty revision label. That is a pipeline change, not a test, and it belongs in `.github/workflows/docker.yml`.

**Remediation check — sound, with one real cost correctly identified.** Adding `USER` needs the data directory chowned to the new uid: `WORKDIR /usr/src/app` is root-owned, and the samples mount data at `/var/lib/safenet/<service>/data`, so the handbooks' `docker run --volume` examples need a matching note or existing deployments break on upgrade. Pinning base images by digest is sound and should be paired with an automated bump (otherwise the pin silently ages into an unpatched base, which is worse than the floating tag). Declaring `ARG COMMIT_SHA` and emitting it as an OCI `org.opencontainers.image.revision` label is unambiguously correct and costs one line per file.

Under A1 none of this is attacker-reachable, so **Low is right and I resisted raising it** for the same reason C-XC did: the process holding FROST key shares is a consequence of A1's documented plaintext-at-rest design, not of the missing `USER`.

**Certainty: unchanged at 85%.** My reads confirm the Critic's rather than adding a new class of evidence, and the 89% ceiling stands. Question 17 of `rust-audit/poc/UNRESOLVED-DEPENDENCY-QUESTIONS.md` (which TLS root source `reqwest` selects, and therefore whether the `ca-certificates` install is load-bearing) is the only open item that touches this file.
