## Claim

`handle_nonce_topup` writes a reservation `chunks[c] = None` into snapshot state and only then asks the effect handler for a nonce tree. If that `Effect::NonceTree` does not resume with a commitment - the handler converts every error into `Resume::Noop`, in particular `nonces::Error::Unavailable` when the group's generator stream is not running (see F2-VAL-031 for the triggers) - nothing removes or retries the reservation. Two consequences follow:

1. `available()` counts the phantom reservation as 1024 nonces, so no further top-up is requested until the group's sequence has entered the phantom chunk; every `Sign` whose sequence falls into it makes `observe` return `None` and `handle_sign` drops the session ("not participating in signing request without a canonically linked nonce").
2. `expected_chunk()` derives the next reservation index from the highest **local** key (`last + 1`), but the coordinator's `FROSTNonceCommitmentSet.commit` assigns `max(next_onchain, sequence_chunk)`, where `next_onchain` counts only chunks that were actually committed. With one dangling `None` at index `c`, the validator's next top-up (fired at offset 925 of chunk `c`) reserves `c+1` while the contract assigns `c` with `startOffset = 925`; `handle_preprocess` links the event's chunk `c` and leaves the `None` at `c+1` in place. The pattern repeats for every following chunk.

Net effect: once a single `NonceTree` effect has failed, the validator can only reveal nonces for offsets 925..1023 of every subsequent chunk and drops the sessions of offsets 0..924 - about 90% of all signing ceremonies - until the epoch's group is retired (`NonceState` is per epoch; `blocks_per_epoch` defaults to 1440, about two hours on Gnosis) or until the sequence jumps by two full chunks without a top-up. Two such validators in a 3-of-5 (or one in a 2-of-3) group make most ceremonies, including the next rollover attestation, fail. No attacker is needed; the degradation is silent apart from `warn` log lines.

## Trigger

Worked sequence (all numbers concrete; `SEQUENCE_CHUNK_SIZE = 1024`, `NONCE_TOPUP_THRESHOLD = 100`):

1. Healthy state for the active group `G`: `chunks = {0: Some(r0)}`, contract `next = 1`, `next_sequence = 925`.
2. `NewBlock`: `available() = 1024 - 925 = 99 < 100` -> `reserve_chunk()` -> `expected_chunk = max(0+1, 0) = 1` -> `chunks = {0: Some(r0), 1: None}` -> `Effect::NonceTree{G}`. The state is committed with this block's logs.
3. The effect fails. Any of: the generator stream for `G` is not running (deterministic after a restart, F2-VAL-031); the process receives SIGTERM/crashes while the effect is in flight (the reservation is already committed, the effect is aborted with the `EffectManager`); a SQLite error in `register_nonces_chunk`. Result: `Resume::Noop`; nothing touches `chunks[1]`.
4. Sequences 925..1023 are served from chunk 0. Sequences 1024..1948 (925 ceremonies) hit `observe -> None`: every `WaitingForRequest` session for those messages is dropped at this validator. `available()` stays >= 99 + 1024 the whole time, so no top-up fires.
5. At sequence 1949 (`chunk 1, offset 925`): `available() = 99` -> `expected_chunk = max(1+1, 1) = 2` -> `chunks = {1: None, 2: None}` -> `NonceTree` (now succeeds) -> `Action::Preprocess`. The contract: `_sequence(1949) = (1, 925)`, `next = 1`, `1 > 1` is false -> assigns chunk **1** with `startOffset 925`. `Preprocess{chunk: 1}` -> `link(1, r1)` -> `chunks = {1: Some(r1), 2: None}`.
6. Sequences 1949..2047 are served; sequences 2048..2972 are dropped; at 2973 the top-up reserves 3 while the contract assigns 2; and so on for every chunk until the epoch rolls over.

Resynchronisation only happens if the sequence advances by more than one full chunk past the last local key without a top-up landing (e.g. more than 2048 signatures during an outage, so `split_off` empties `chunks` and `expected_chunk` falls back to the sequence's chunk), or when the epoch's group is retired.

## Considered and rejected

- `ensure_chunk_reservation` (state/preprocess.rs:216-225) only runs on the **success** resume; it cannot clear a reservation, and no failure resume exists (Basis 8).
- A reorg replay does not create phantoms by itself: the replayed top-up recomputes the same index (deterministic from the same state), the store keeps the previously generated chunk, and the earlier `Preprocess` transaction is durable in the queue, so the event eventually links the same index. The defect needs the effect to _fail_, not to be replayed.
- The per-group `Semaphore(1)` duplicate path (`Ok(None)` -> `Resume::Noop`, service/effect.rs:161-164) is not a failure: the duplicate's reservation is the same index the in-flight request will link. It becomes a phantom only if the in-flight request itself fails.
- The contract cannot be blamed: it has no knowledge of local reservations; the mismatch is entirely in `expected_chunk` counting `None` entries (Basis 3 vs 5).
- `handle_nonce_topup` only inspects `state.active_epoch` (state/preprocess.rs:86-89); a phantom at chunk 0 of a **not yet active** group (F2-VAL-031, `finalize_key_gen`) is therefore not even re-evaluated before the epoch activates.

## Remediation options

1. Make the failure observable and self-healing: have the handler resume with an explicit `Resume::NonceTreeFailed { group_id }` and let the transition remove a trailing `None` reservation; additionally exclude `None` entries from `available()` so the top-up re-fires on the next block. Tradeoff: a legitimately pending request would be re-requested each block; the per-group semaphore makes duplicates cheap (`Ok(None)`).
2. Mirror the contract in `expected_chunk()`: derive the next index from the highest **linked** chunk (`Some`) and the current sequence rather than from reservations, and on `handle_preprocess` drop any `None` entry whose index differs from `event.chunk`. This stops the cascade even if a phantom is created.
3. Re-issue `Effect::NonceTree` on every `NewBlock` while the last entry is `None` and no `Preprocess` action is pending; idempotent thanks to the semaphore.

Tests to add: a pure state-machine test that fails the `NonceTree` resume at sequence 925 and then drives `Sign` events to sequence 3000, asserting a `Preprocess` for chunk 1 is emitted before sequence 1024 and that `observe` returns `Some` for offsets 0..924 of chunk 2; an Anvil flow (`scripts/run_validator_reorg_nonce_test.sh` as a base) that restarts a validator with a cold generator and checks it still reveals for every sequence. No code is committed.

Remediation check. **Option 1, first half, is sound** (an explicit `Resume::NonceTreeFailed { group_id }` that removes a _trailing_ `None` reservation; a duplicate resume finds none and is a no-op, so "effects may run more than once" holds). **Option 1, second half, is unsound as written**: excluding `None` entries from `available()` without changing `handle_nonce_topup` makes the top-up run on every block while a legitimate request is in flight, and each run calls `reserve_chunk()`, which inserts a _new_ `None` at `last + 1` (preprocess.rs:204-208, 231-237) — `expected_chunk` would then run away from the contract by one chunk per block, manufacturing the very desync the finding describes. If capacity is to ignore reservations, the top-up must reuse the existing trailing reservation (`ensure_chunk_reservation` semantics), not reserve anew. **Option 2 is sound**: deriving `expected_chunk` from the highest _linked_ chunk and the current sequence matches the contract exactly (the validator sees every one of its own `Preprocess` events, so "highest linked + 1" is the contract's `next`), and dropping `None` entries whose index differs from `event.chunk` in `handle_preprocess` stops the cascade; it does not by itself recover the first stranded chunk, so pair it with the failure resume. **Option 3 needs a backoff**: "no `Preprocess` action pending" is not observable from pure state, and once the first request has completed the per-group semaphore no longer deduplicates, so re-issuing every block would generate and commit extra chunks whenever the `Preprocess` transaction takes more than one block. Recommend 1 (first half) + 2.

## In-flight impact (round 3)

The stale branch `origin/wip/nonce-gen-optimizations` (`abf32d8`, the prototype of the Nonces series, 189 commits behind) implements the second half of remediation option 2: its `NonceState::link` clears every pending reservation before recording the onchain assignment (`crates/validator/src/state/preprocess.rs:50-51` on the branch, `self.chunks.retain(|_, root| root.is_some()); self.chunks.insert(chunk, Some(root));`) and `reserve_chunk` refuses to reserve while any reservation is pending (`:38-39`), whereas `main`'s `link` is a plain insert (`preprocess.rs:211-213`) that leaves the dangling `None` for `expected_chunk` to count — consequence 2, the cascade. Relation: **partially resolves consequence 2, in a superseded design**; consequence 1 (the phantom counted as capacity when the `NonceTree` effect fails) is not addressed, because the branch's `available()` (`:76-88`) counts pending reservations exactly as `main`'s does, so option 1 (an explicit failure resume) is still needed. Take the `link` semantics from the branch when implementing option 2; do not merge the branch. Details: `state/run2/in-flight/misc-branches.md` §4.2; `report/IN-FLIGHT.md` Round 3.
