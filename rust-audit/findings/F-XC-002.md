## Claim

The repository has a secret-redaction convention — four types hand-write a `Debug` impl that prints `"redacted"` instead of the key material — but the convention is applied by hand, is applied to exactly the types whose secret lives in a _local_ field, and is _not_ applied to the two types whose secret lives inside a `frost-core` container. Those two types, `Secrets` and `KeyShare`, `#[derive(Debug)]`, and both are reachable from a `tracing` statement:

- `KeyShare` is carried by `Effect::StartNonceGeneration` and `Effect::ReconcileGroupSecrets`. `crates/validator/src/service/effect.rs:249` formats the whole `Effect` with `?effect` at **`warn!`**, which the default `log_filter = "info"` emits. Any effect failure — a transient SQLite error during `ReconcileGroupSecrets` is the cheapest one — writes every tracked `KeyShare` through `Debug` into the log at the default verbosity.
- `Secrets` (the DKG encryption key, the FROST round-1 secret package and the proof of knowledge) is carried by `Resume::Setup`. `crates/core/src/effects.rs:59` and `:78` format every resume with `?resume` at `trace!`, and `crates/core/src/driver.rs:261` does it a third time. The same generic sites also format every `Effect` (`effects.rs:55`) and every `Update` (`driver.rs:238`).

The `core` sites are the cross-cutting part: they are generic over the service's own `Effect` and `Resume` types and therefore impose no constraint on what those types print. `core` requires only `Effect: Debug` and `Resume: Debug` (`effects.rs:40-41`) and then logs them; whether that is safe is decided entirely in the downstream crate, with no compile-time or review-time gate. The validator is the crate that puts secrets in those types.

Whether the bytes actually appear is decided by `frost-core`'s own `Debug` impls for `round1::SecretPackage` and `keys::KeyPackage`. **That is not verifiable in this checkout** — no dependency source is on disk (baseline §1, A6) — so the leak itself is class `I` and the finding is written as "the repo's own hygiene has a hole and depends on an upstream property nobody here can check", not as "the key is printed".

## Trigger

Concrete, at the default configuration (`log_filter = "info"`, as shipped in all three sample TOMLs): the state machine emits `Effect::ReconcileGroupSecrets { groups }` carrying the current `Arc<KeyShare>` for each retained group; the handler's SQLite write fails once (disk full, the file locked by a concurrent backup — `docs/validator-handbook.md` recommends backups); the `Err` arm at `service/effect.rs:249` fires and formats the whole `Effect`, key shares included, into the process log. Under A1 the log file is on a trusted host, but logs are the artefact most likely to be shipped to an aggregator, attached to a bug report, or read by an operator who is not entitled to the share.

For `Secrets` the trigger additionally requires `log_filter` to include `trace` for the `safenet_core` target, which the handbooks present as a normal debugging step.

## Considered and rejected

- **"`frost-core` redacts, so nothing leaks."** Possible, and it is why the severity is Medium rather than Critical. It cannot be checked here (A6, baseline §1) and the codebase does not rely on it explicitly anywhere — no comment at `keygen.rs:27` or `:433` says "upstream redacts". A security property that depends on an unstated upstream behaviour and would silently regress on a dependency bump is a finding in its own right, independent of today's answer.
- **"The signer private key leaks too."** It does not. `crates/core/src/tx/signer.rs:96-100` hand-writes `Debug` to print the address only, and the core analysis' rejected list records the same (`analysis-core.md:503`). Checked and excluded.
- **"The signing nonces leak through `Resume::Nonce`."** They do not: `Resume::Nonce` carries `Box<Nonces>`, and `Nonces` redacts `signing_nonces` (basis row 8). `NonceChunk` likewise has a manual impl at `preprocess.rs:150`. This is the evidence that the convention exists and that `Secrets`/`KeyShare` are the two places it was not applied.
- **"The metrics leak."** Checked separately and they do not: every label in `crates/core/src/metrics.rs`, `crates/validator/src/metrics.rs` and `crates/sentinel/src/metrics.rs` is a `&'static str` produced by a `label` method on a closed enum. The single non-static label is `"method" => method.to_owned` (`crates/core/src/metrics.rs:33`), whose value is `request.method` from an outgoing alloy RPC request (`crates/core/src/provider/mod.rs:71`) — a closed set chosen by this codebase, so neither secret-bearing nor unbounded in cardinality.
- **"The engine returns a secret over HTTP."** It does not. The engine holds no keys, and both extractor rejections are `&'static str` (`crates/sentinel-engine/src/api/extractors.rs:22-25`, `:43-46`); the only response body is `Json<Verdict>`.
- **`error!`/`warn!` on error types.** `InternalError` (`validator/service/effect.rs:259-275`) stores `err.to_string`; the reachable `Display` is `frost::Error` (`crates/validator/src/frost/error.rs:10`, `:16`), whose payload is a `frost_secp256k1::Error` variant and an `Address`. No secret field is formatted by this repo's own code.
- **Ownership note.** The single-site defect at `validator/service/effect.rs:249` is VAL-H10 and belongs to R4/R6; this finding is filed cross-cutting because the generic `core` sites (`effects.rs:55`, `:59`, `:78`, `driver.rs:238`, `:261`) log _whatever_ the downstream service puts in its `Effect`/`Resume`, which is a workspace-level contract, not a validator bug.

## Remediation options

1. Hand-write a redacting `Debug` for `Secrets` and `KeyShare` the way `EncryptionKey` and `Nonces` already do — print the group/participant identifiers and `"<redacted>"` for the share. Cheapest, entirely local, and removes the dependency on upstream behaviour. Tradeoff: debugging a DKG failure loses a field that was probably never readable anyway.
2. Make the contract explicit in `core`: document on `EffectHandler` that `Effect` and `Resume` `Debug` output is logged verbatim at `trace`, and that secret-bearing variants must redact. Optionally replace the three `?effect`/`?resume` sites with a narrower trait (`fn label(&self) -> &'static str`, which the validator already has as `Effect::metric_kind`) so `core` logs a discriminant instead of the payload.
3. Add a `zeroize`-style newtype (`Redacted<T>`) used by every secret field, so the property is enforced by the type system rather than by remembering.

Tests to add: a unit test per secret type asserting `format!("{:?}", value)` contains neither the scalar bytes nor a plausible hex run — cheap, and it fails loudly if a future dependency bump changes upstream `Debug`.

### What I add: the reachability of each sink is not uniform, and the finding under-states one half

I traced the payload types myself before reading the argument. `validator/src/service/effect.rs:24-62` defines `Effect` with two variants that carry key material — `StartNonceGeneration { key_share: Arc<KeyShare> }` and `ReconcileGroupSecrets { groups: BTreeMap<B256, Option<Arc<KeyShare>>> }` — and `Resume` (`:78-102`) with `Setup { secrets: Box<Secrets> }`. So:

- the **`warn!` sink (`effect.rs:249`) needs no operator action at all.** It fires at the shipped `log_filter = "info"` (all three samples), on any `try_perform_effect` error. `ReconcileGroupSecrets` resolves to writes against the secret store, so a single SQLite failure — a locked file during the backup `docs/validator-handbook.md:75` tells operators to take, or a full disk — formats every live `Arc<KeyShare>` through `Debug`. That is a concrete, in-scope trigger.
- the **`trace!` sinks require the operator to raise the level.** That is a real but weaker path.

This asymmetry is why my number differs from C-CORE-B's 50% on `F-CORE-036`: that finding's claim is confined to the five `trace!` sinks, and 50% is right for it. This finding's claim additionally covers a sink that is live in the default configuration, which is a materially stronger mechanism.

I also re-checked the finding's own rejected list and found it sound: `Signer` redacts (`tx/signer.rs:96-100`, address only), `Nonces`/`NonceChunk` redact, no `expect` string interpolates a value (I read all 15 — see F-XC-001's Critic section), and the engine's extractor rejections are `(StatusCode, &'static str)`.

## Verification (V-VAL, Phase 5)

**Executed. The class-`I` leg — "whether the bytes actually appear" — is settled: they do not.**

This finding correctly declined to claim "the key is printed" and wrote itself as "the repo's own hygiene has a hole and depends on an upstream property nobody here can check". The upstream property has now been checked, by execution and by reading the pinned source. It holds.

The full evidence, the verbatim `format!("{:?}", …)` renderings of `Effect::StartNonceGeneration`, `Effect::ReconcileGroupSecrets`, `Resume::Setup` and `Resume::Nonce`, and the `frost-core` 3.0.0 source table, are in **F-VAL-062's `## Verification (V-VAL, Phase 5)` section**; they are not duplicated here. The short form:

- `SigningShare` → `SigningShare("<redacted>")` (`frost-core-3.0.0/src/keys.rs:126-133`);
- `dkg::round1::SecretPackage` → `coefficients: "<redacted>"` (`src/keys/dkg.rs:191-204`);
- `dkg::round2::SecretPackage` → `secret_share: "<redacted>"` (`src/keys/dkg.rs:337-350`);
- so `KeyShare` (plain derive over `KeyPackage`) and `Secrets` (plain derive) both render with every secret field redacted, and **nothing secret reaches `warn!(?effect, …)` at `validator/service/effect.rs:249` or any of the five `core` sinks today.**

Beware one trap if this is ever re-checked with a quick substring search: `KeyShare::dummy` seeds the signing share with `Scalar::ONE` _and_ the identifier with `Identifier::try_from(1)`, so `0000…0001` appears in the rendering as the **identifier**, which is public. A naive `contains("0000…0001")` reports a leak that is not there — it did, on the first run. Isolate the `signing_share` field before asserting.

**What survives is exactly the finding's own framing, and it is worth keeping.** The convention is applied by hand; it is applied to precisely the types whose secret lives in a local field and not to the two whose secret lives inside a `frost-core` container; and the safety of those two rests entirely on an upstream `Debug` impl that no test in this repository pins. A `frost-core` minor bump that replaced a hand-written `Debug` with a derive would turn this into a live disclosure with no signal at the boundary. That is a real hygiene defect and the remediation is unchanged.

The `core` half of the finding — that `effects.rs:40-41` requires `Debug` and then logs, imposing no constraint on what the downstream type prints, with no compile-time or review-time gate — is untouched by this run and remains as the Critic left it.

Severity **Medium / Medium → Low / Low**. Certainty **74% → 88%**: the finding is now precisely characterised in both directions. Status **Verified (reduced)**. The guard test the remediation asks for exists at `poc/F-VAL-062/debug_redaction.rs::signing_share_field_alone_is_redacted` and should be landed in-tree.
