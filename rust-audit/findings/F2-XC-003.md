## Claim

Both runtime images start the service as uid 0: neither Dockerfile has a `USER` instruction, and `ENTRYPOINT ["./validator"]`/`["./sentinel"]` runs in `/usr/src/app` as root. The service owns a SQLite file that the handbook says must be treated as containing secret keys; that file (and any pre-created one, see F2-XC-002) ends up root-owned on the volume, and any code-execution bug reachable through the process (the HTTP stack behind an exposed `metrics_address`, the RPC client, SQLite) yields root inside the container instead of an unprivileged user.

Reproducibility is weak as well: the builder is `rust:1-slim` and the runtime `debian:trixie-slim`, both floating tags without digests, and there is no `rust-toolchain.toml`, so the compiler, the standard library and the system `libsqlite3` (which the binary links dynamically, and whose compile flags matter for F2-XC-005) change underneath the same commit. CI passes a `COMMIT_SHA` build argument that neither Dockerfile declares, so it is dropped; `--version` prints only `CARGO_PKG_VERSION` (`0.2.0`), and an image cannot be tied to a commit from inside. There is no `HEALTHCHECK`, even though the binaries expose `/health`.

## Trigger

None needed for the root user (it is the steady state). The reproducibility point manifests whenever `rust:1-slim` or `debian:trixie-slim` moves.

## Considered and rejected

- "Orchestrators set `runAsNonRoot`": nothing in the repository's compose/kube material was found doing so for these images (`scripts/run_devnet.sh` is a podman devnet; the handbooks run plain `docker run`), and the image should be safe by default.
- "`rust:1-slim` is intentionally floating to get security fixes": that is a reasonable choice for the builder, but a digest pin plus automated bumps gives the same fixes with a reviewable diff; the runtime image's `libsqlite3` is the one whose drift matters here.
- The `Dockerfile.dockerignore` convention is correct for BuildKit (`docker/build-push-action` with buildx); its `!/crates/**` whitelist copies the whole `crates/` tree including the out-of-scope engine, which is harmless because the workspace needs it to resolve.

## Remediation options

1. Add an unprivileged user to the runtime stage (`RUN useradd --system --uid 10001 safenet`, `USER 10001`), `chown` the working directory, and document that the data volume must be writable by that uid. Trade-off: existing root-owned volumes need a one-time `chown`.
2. Pin `FROM` lines by digest and add a `rust-toolchain.toml` (`channel = "1.98"`); let Dependabot/Renovate bump both.
3. Declare `ARG COMMIT_SHA` and surface it (e.g. `ENV SAFENET_COMMIT=$COMMIT_SHA` and print it from `--version`), and add a `HEALTHCHECK` when `metrics_address` is fixed.

Tests to add: none; a CI step asserting `docker run --rm <image> id -u` is non-zero is cheap.
