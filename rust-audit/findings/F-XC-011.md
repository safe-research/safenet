### 1. `quinn-proto` 7.5 HIGH is **not reachable**, and a report that leads with it misdirects the team

This is the highest number in the `cargo audit` output and the least important line in it.

```
$ cargo tree -i quinn-proto --workspace --locked
warning: nothing to print.
$ cargo tree -i quinn --workspace --locked
warning: nothing to print.
$ cargo tree -i quinn-udp --workspace --locked
warning: nothing to print.
$ ls target/debug/deps/ | grep -ci quinn
0
```

`quinn`, `quinn-proto` and `quinn-udp` are in `Cargo.lock` (`:3560-3616`) because `reqwest` names `quinn` as an **optional** dependency behind its HTTP/3 feature. That feature is not enabled here:

```
$ cargo tree -e features --locked --workspace | grep -o 'reqwest feature "[a-z0-9_-]*"' | sort -u
reqwest feature "__rustls"
reqwest feature "__rustls-aws-lc-rs"
reqwest feature "__tls"
reqwest feature "json"
reqwest feature "rustls"
```

No `http3`, no `quic`. `cargo audit` reads `Cargo.lock`, which records the union of every resolvable dependency including optional ones; it does not read the _activated_ feature graph. So the 7.5 HIGH is an artefact of how `cargo audit` scopes itself. **No Safenet binary contains a line of `quinn-proto`.** Nothing to remediate beyond the lockfile hygiene in item 5.

### 2. `h2` is reachable — on the engine's check API, and (contrary to the obvious reading) **not** on the metrics endpoint

Both legs needed measuring rather than reasoning, and the measurements went opposite ways to what the manifests suggest.

**(a) The engine's transaction-checking API is a live HTTP/2 server.** The obvious static read is that it is not: the engine takes `axum = "0.8"` with default features, and axum 0.8's `default` feature list is `form, http1, json, matched-path, original-uri, query, tokio, tower-log, tracing` — **no `http2`**. That read is wrong. `axum feature "tokio"` pulls `hyper-util feature "server-auto"`, which turns on `hyper-util/http2` and `hyper/http2`; and `axum::serve` builds a `hyper_util::server::conn::auto::Builder` (`axum-0.8.9/src/serve/mod.rs:17`, `:391`), whose `serve_connection` sniffs the HTTP/2 connection preface and dispatches to the h2 stack whenever hyper-util's `http2` feature is compiled in (`hyper-util-0.1.20/src/server/conn/auto/mod.rs:39`, `:351-358`). axum's _own_ `http2` feature gates only `builder.http2.enable_connect_protocol` (`serve/mod.rs:393-394`), not whether h2 is served at all.

I tested this against the production router rather than trusting the feature graph. Temporary test appended to `crates/sentinel-engine/src/engine/mod.rs`, run, reverted: bind `axum::serve(listener, crate::api::router(engine))` on loopback, write the literal preface bytes plus an empty SETTINGS frame, read the reply.

```
H2-PREFACE reply 55 bytes: [00, 00, 18, 04, 00, 00, 00, 00, 00, 00, 03, 00, 00, 00, c8,
                            00, 04, 00, 10, 00, 00, 00, 05, 00, 00, 40, 00, 00, 06, 00, 00, 40]
  frame_type=0x04 (0x04 == SETTINGS => server spoke HTTP/2)
  looks_like_http1_text=false
```

A SETTINGS frame, with real settings values. The engine speaks HTTP/2 by prior knowledge, so RUSTSEC-2026-0258's unbounded-empty-DATA-frame flood applies to it.

**(b) The Prometheus metrics listener is _not_ an HTTP/2 server**, so the advisory does not apply there. `metrics-exporter-prometheus` 0.18.3 constructs `hyper::server::conn::http1::Builder` explicitly and calls `serve_connection` on it (`exporter/http_listener.rs:9`, `:77`, `:122`) — HTTP/1 only, whatever `hyper`'s feature set is. Same test against `safenet_core::observability::metrics::serve(...)`:

```
METRICS H2-PREFACE reply 0 bytes
  raw: ""    hex: []    is_http1_text=false    is_h2_settings=false
```

No SETTINGS frame and no HTTP/1 error either; the connection is simply dropped. **The metrics endpoint is out of scope for this advisory.**

**Impact, and why this is Low rather than Medium.** Under **A3** the engine's check API is reached only by the co-deployed sentinel, and `default_bind_address` is loopback (`crates/sentinel-engine/src/config.rs:57`, asserted at `:88` as `127.0.0.1:5473`). The shipped sample explicitly documents widening it — `# bind_address = "0.0.0.0:5473"` with the comment "bind to all interfaces when a sentinel in another container must reach the engine over a private container network" — which is the deployment where this stops being theoretical, and it is a documented, expected one. There is no authentication on the check API. So: a real remote DoS primitive against the engine, gated behind a network position A3 says an attacker does not have. Losing the engine is a liveness event for the sentinel, not an integrity one — the sentinel's own handling of an unavailable engine is `F-ENG-005`/`F-XC-008` territory. **Low.**

### 3. `ruint`'s U256 shift bug is real but **the affected API is never called**

This is the advisory the audit's own priors pointed at, and it does not survive contact with a grep. Two corrections matter.

**First, the advisory is narrower than "U256 arithmetic".** Its `[affected.functions]` list is exactly eight entries and they are all explicit shift methods: `overflowing_shl/shr`, `checked_shl/shr`, `saturating_shl/shr`, `wrapping_shl/shr`. Its own text says _"Shifted values were correct; only the flag was wrong."_ **`U256` comparison, addition, subtraction, multiplication, division and `from_be_bytes`/`to_be_bytes` are not affected at all.** The engine's `U256` value comparisons in the checkers — which is where most of this audit's `U256` surface lives — are untouched by RUSTSEC-2026-0220.

**Second, Safenet calls none of the eight, and shifts a `U256` exactly once, in a test.**

```
$ grep -rn "checked_shl\|checked_shr\|overflowing_shl\|overflowing_shr\|saturating_shl\|saturating_shr\|wrapping_shl\|wrapping_shr\|strict_shl\|strict_shr\|to_base_be\|to_base_le" crates/ --include='*.rs'
(no matches)
```

72 raw `<<`/`>>` grep hits across `crates/` reduce, after removing turbofish and generic-parameter noise, to **three** real shift operators:

| Site | Operand | Verdict |
| --- | --- | --- |
| `crates/validator/src/merkle.rs:56` — `current >>= 1;` | `usize` | std, not ruint |
| `crates/sentinel-engine/src/checkers/address_poisoning.rs:66` — `out[2*i] = byte >> 4;` | `u8` | std, not ruint |
| `crates/sentinel/src/service.rs:922` — `U256::from(chain_id) << 160 \| U256::from_be_bytes(...)` | **`U256`** | **test-only** |

The third is the only `U256` shift in the workspace, and it is inside the test module: `grep -n "cfg(test)" crates/sentinel/src/service.rs` gives `840:#[cfg(test)]` / `841:mod tests {`, and 922 > 840. It is the helper `fn safe_id`, which mirrors `SafeId.create` for fixtures. It is in no shipped binary, and its shift amount is the constant `160`, not attacker input.

I record the two ways this could still have bitten, so the next reader does not have to re-derive them:

- ruint's `Shl` operator for primitive right-hand sides **does** delegate to the affected `wrapping_shl` (`ruint-1.18.0/src/bits.rs:684-686`), and `Shl<Self>` to `overflowing_shl_big` (`:617-619`). So `<<` is on the affected path in principle. The `wrapping_shl` defect needs a shift amount `>= 2^32`; `160` is a literal.
- The advisory's infinite-loop leg (`to_base_be` / `Display` looping forever) is scoped to **no-alloc builds** and **non-limb-aligned widths**. Neither applies: ruint is built here with `alloc`, `alloy-rlp`, `serde` and `std`; `U256` is limb-aligned; the one non-limb-aligned width in use, `U96` in `crates/sentinel/src/state.rs`, is only ever built with `U96::from(..)` and serialised — never shifted, never base-converted.
- `alloy-primitives` 1.6.0's own uses of the affected functions are all in `src/signed/ops.rs`, i.e. `I256`. `grep -rn "I256\|Signed<" crates/ --include='*.rs'` returns **no matches**.

**Latent, not exploitable.** Upgrade on the general principle that a shift bug in the workspace's bignum type is a bad thing to leave sitting there for whoever adds the next `<<`, not because anything is wrong today.

### 4. `crossbeam-epoch` is not reachable

Reached twice (`rayon` → validator; `metrics-util` → `metrics-exporter-prometheus` → core), but the advisory requires `Debug`/`fmt::Pointer`-formatting an _invalid_ `Atomic`/`Shared`. Neither consumer does:

```
$ grep -rn "Atomic\|Shared" .../rayon-core-1.13.0/src/*.rs      | grep -E '\{:\?\}|fmt::Pointer|\{:p\}'
$ grep -rn "Atomic\|Shared" .../metrics-util-0.20.4/src/**/*.rs | grep -E '\{:\?\}|fmt::Pointer|\{:p\}'
(no matches in either)
```

I checked this rather than assuming it, because this audit has separately found secrets reaching `Debug` sinks — but those are Safenet's own types. No Safenet code holds an epoch pointer at all: `crossbeam-epoch` is entirely interior to `rayon`'s deque and `metrics-util`'s registry.

### 5. The warnings: 4 unmaintained, 3 unsound, 4 yanked

`cargo audit` reports "11 allowed warnings". Their composition is **4 + 3 + 4**, not (as a first read of the log suggests) four unmaintained plus one unsoundness plus one yanked.

**Unmaintained (4):** `atomic-polyfill` 1.0.3 (RUSTSEC-2023-0089), `derivative` 2.2.0 (RUSTSEC-2024-0388), `paste` 1.0.15 (RUSTSEC-2024-0436), `proc-macro-error2` 2.0.1 (RUSTSEC-2026-0173). All four are transitive and none carries a vulnerability. `proc-macro-error2` is the one with a schedule attached to it: rustc itself emits, on **every** build in this workspace, `warning: the following packages contain code that will be rejected by a future version of Rust: proc-macro-error2 v2.0.1`. That is a build-breakage clock, not a security issue, and it belongs in the same remediation as the rest.

**Unsound (3):**

| Crate | Advisory | Reaches | Assessment |
| --- | --- | --- | --- |
| `anyhow` 1.0.102 | RUSTSEC-2026-0190, `Error::downcast_mut` | **nothing** — `cargo tree -i anyhow` prints "nothing to print"; `ls target/debug/deps \| grep -c "^libanyhow\|^anyhow-"` → **0** | Not built. Same class as `quinn-proto`. |
| `event-listener` 5.4.1 | RUSTSEC-2026-0221, `!Send` tags cross threads via `StackSlot` | `sqlx-core` 0.9.0 → `sqlx` → all four crates | Compiled. Needs `sqlx` to use the affected `StackSlot` path with a `!Send` tag; Safenet never touches `event-listener` directly. Latent. |
| `lru` 0.16.4 | RUSTSEC-2026-0253, use-after-free from missing panic safety in `LruCache::pop` | `alloy-provider` 2.0.5 → `alloy` → all four crates | Compiled, and on a hot path (the provider's block/receipt cache). Requires a **panic inside a user destructor during `pop`**; the cached values are alloy's own plain data types with no user `Drop`. Latent. |

**Yanked (4) — a supply-chain signal, distinct from a vulnerability.** A yank carries no advisory and no CVSS. What it means is that the publisher withdrew that exact version, so a future `cargo update`, a lockfile regeneration, or any clean CI checkout that resolves afresh may fail or silently move to a different version. It is a **build-reproducibility and provenance** risk, and `cargo audit`'s default configuration does not fail on it — which is exactly why it needs saying out loud rather than being left in the warning pile.

| Yanked crate | Path | Compiled? |
| --- | --- | --- |
| `spin` 0.9.8 | `flume` 0.12.0 → `sqlx-sqlite` 0.9.0 → `sqlx` → **all four crates** | **Yes** — 8 artefacts in `target/debug/deps` |
| `bitcoin-io` 0.1.100 | lockfile parent `bitcoin_hashes` | No — 0 artefacts, `cargo tree -i` empty |
| `bitcoin_hashes` 0.14.100 | lockfile parent `secp256k1` | No — 0 artefacts |
| `chacha20` 0.10.0 | lockfile parent `rand` (optional) | No — 0 artefacts |

**`spin` 0.9.8 is the one that matters**, and it is the only yanked crate actually linked into all three shipped binaries. It reaches them through the SQLite driver, i.e. through the code path every service uses for its own state store. There is no advisory against it; the exposure is that a version the publisher has withdrawn is a hard dependency of the persistence layer, and nothing in CI would notice if it became unresolvable.

## Severity

**Low.** Set on reachable impact, deliberately not on any advisory's own CVSS.

The only advisory that reaches a network-facing surface is `h2`, and it reaches exactly one: the engine's check API, which under **A3** is addressable only by the co-deployed sentinel and binds loopback by default. Its impact there is loss of engine liveness — and the sentinel's behaviour when the engine is unavailable is already tracked by `F-ENG-005` and `F-XC-008`. No advisory here touches signing, consensus, key material, transaction construction or verdict correctness. Nothing here is an integrity finding.

Had I scored on CVSS the report would have opened with a 7.5 HIGH that is not in the binary.

## Remediation

1. **`cargo update -p h2` to `>= 0.4.16`.** The one item with a reachable network surface. A patch bump inside `hyper`'s own range; no manifest change, no API change.
2. **`cargo update -p ruint` to `>= 1.20.0`.** Latent today. Do it anyway: it is a free patch bump, and it removes the trap for whoever writes the next `U256 <<`, which the current single test-only instance shows is a shape this codebase does reach for.
3. **Add the advisory gate `F-XC-007` asked for.** This is the finding's real remediation — every fact above would have surfaced on its own the first time CI ran, instead of in Phase 5 of an audit. Add to `just check` and to `.github/workflows/`: `cargo audit --deny warnings --deny yanked`. Pair it with a `deny.toml` that `allow`-lists, **with a dated expiry and a one-line reason**, the entries this file establishes are unreachable: RUSTSEC-2026-0185 (`quinn-proto`, optional feature never enabled), RUSTSEC-2026-0204 (`crossbeam-epoch`), RUSTSEC-2026-0190 (`anyhow`, not built), and the four unmaintained warnings. Do **not** allow-list `h2`, `ruint`, `event-listener`, `lru` or the yanked entries. An allow-list without expiry dates decays into a permanent mute, which is worse than no gate.
4. **Deal with `spin` 0.9.8 as a supply-chain item, not a vulnerability.** It is linked into all three binaries via `sqlx-sqlite` → `flume`. There is nothing to patch — `flume` must move — so the action is to pin it consciously and track `flume`'s upgrade, and to run `--deny yanked` in CI so the day it becomes unresolvable is a red build and not a mystery.
5. **Shrink the lockfile so `cargo audit` stops reporting phantoms.** Five of the fifteen entries (`quinn-proto`, `anyhow`, `bitcoin-io`, `bitcoin_hashes`, `chacha20`) are in `Cargo.lock` and in no binary. This is `F-XC-007`'s item 2 restated with data behind it, and it is what makes the gate in item 3 cheap enough to keep green. Note that `F-XC-007`'s specific instance of item 2 — `sqlx-mysql`/`sqlx-postgres` — **does not hold**; see the Verification section of `F-XC-007`.
6. **Track `proc-macro-error2` 2.0.1 separately.** rustc already warns on every build that it will be rejected by a future compiler. It is a scheduled build breakage, not a security item, and it should not sit inside a security allow-list where its deadline is invisible.

## Tests to add

The gate in remediation 3 _is_ the test. There is no unit test to write here: a `cargo audit` invocation is the assertion, and a per-advisory reachability test would encode conclusions that go stale the moment a feature flag or a dependency edge moves.

One thing is worth an actual test, and it is not an advisory: **`crates/sentinel-engine` serves HTTP/2 without any manifest saying so.** That surfaced only because I sent a preface at it. A three-line test in `crates/sentinel-engine/src/api/` asserting which protocols the check API answers would turn a silently feature-unified property into a stated one, and would fail loudly if a future `axum`/`hyper-util` bump changed it in either direction.

## Verification (V-XC, Phase 5)

This finding was authored in Phase 5 and is verified by construction — every row of every table above is either an executed command or a grep of a source file now on disk, and both HTTP/2 legs are protocol-level tests I ran against the production constructors rather than inferences from the feature graph.

**What I ran.** `cargo audit` (by the manager, log preserved); `cargo tree -i` for `quinn-proto`, `quinn`, `quinn-udp`, `ruint`, `h2`, `crossbeam-epoch`, `anyhow`, `lru`, `event-listener`, `spin`, `bitcoin-io`, `bitcoin_hashes`, `chacha20`, `sqlx-mysql`, `sqlx-postgres`; `cargo tree -e features` for `ruint`, `reqwest`, `axum`, `hyper`, `hyper-util`, `metrics-exporter-prometheus`; artefact counts in `target/debug/deps`; the shift-operator sweep of all four crates; source reads of `ruint-1.18.0/src/bits.rs`, `alloy-primitives-1.6.0/src/signed/ops.rs`, `axum-0.8.9/src/serve/mod.rs`, `hyper-util-0.1.20/src/server/conn/auto/mod.rs`, and `metrics-exporter-prometheus-0.18.3/src/exporter/http_listener.rs`; and two temporary tests appended to `crates/sentinel-engine/src/engine/mod.rs`, run, then reverted with `git checkout --` (verbatim output in the h2 section above and in `rust-audit/state/logs/v-xc-advisory-reachability.txt`).

**Where execution contradicted the going assumption.** Three places, all recorded above rather than quietly corrected:

1. The `ruint` advisory was expected to be "the one that matters" because the engine does `U256` work throughout. It is not: the advisory covers only shift operations, and the workspace performs exactly one `U256` shift, in a test helper.
2. The metrics endpoint was expected to be separately affected by `h2`. It is not — it is an HTTP/1-only server and answered the preface with zero bytes.
3. The engine's axum API was _not_ expected to speak HTTP/2 (axum's `http2` feature is off). It does, via `hyper-util/server-auto` feature unification, and the SETTINGS frame proves it.

**Basis class:** E1 for claims 1-4 and 6-12 (executed), E2 for claim 5 (source read). **Certainty: 95%.** The reachability facts are executed and reproducible. The residual 5% is that "the vulnerable API is not called from Safenet's own code" is not the same as "no transitive dependency calls it on Safenet's behalf on a path I did not trace" — I traced the direct consumers of `ruint` and `crossbeam-epoch` and found nothing, but I did not exhaustively audit alloy's or rayon's internals, and A8 remains FALSE so there is no differential corpus to fall back on.
