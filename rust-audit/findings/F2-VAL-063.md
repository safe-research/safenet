## Claim

`start_key_gen` writes `RolloverState::CollectingCommitments { secrets: Participating { secrets: None } }` and emits `Effect::KeyGenSetup` exactly once. The effect is the only thing that ever fills `secrets: Some(..)` and queues `KeyGenAndCommit`. If it fails (`store_keygen_secrets` database error) the handler returns `Resume::Noop`, and if its resume is lost (process restart after the block's snapshot committed with `secrets: None` but before the next commit persisted the resumed state) nothing re-emits it: no `NewBlock` routine and no replayed log re-evaluates a `Participating { secrets: None }` state. For a rollover DKG the validator then never publishes its commitment; at the deadline its peers exclude it and it re-enters the restarted group as an observer (or, if every other participant had already committed, the "stuck setup" branch skips the epoch for this validator). The validator forfeits the whole epoch's participation from a single transient failure or an unlucky restart, and if enough validators restart at the same epoch boundary (rolling upgrades are naturally scheduled) the restarted set can fall under the two-thirds viability bound and the epoch is skipped for everyone. The genesis instance of the same gap (no deadline, so no recovery at all) is Informational under A16.

## Trigger

Rollover DKG for epoch `k+1` starts on `NewBlock B` (`handle_rollover_new_block`, keygen.rs:912-955). Two independent ways to reach the stranded state:

- Failure: `store_keygen_secrets` returns an error at that instant (`SQLITE_BUSY` on the shared pool while the transaction queue and reconcile task also write, disk full, I/O error). The handler logs `failed to perform effect` and resumes `Noop`; the state keeps `secrets: None` until the deadline, when the validator is excluded.
- Loss: the setup effect had not resumed when block `B`'s logs were committed (effect = RNG + `dkg::part1` + JSON + SQLite `INSERT` with fsync, versus one `eth_getLogs` round trip), so the snapshot at `B` holds `secrets: None`; the process is then stopped before block `B+1`'s logs commit. After restart the indexer warps from `B+1` and re-applies logs only; `handle_rollover_new_block` sees `target_epoch >= next_epoch` (already targeting `k+1`) and does nothing; no effect is re-emitted. (A stop _before_ block `B`'s commit is fine: the restart re-derives the start from the block clock.)

In both cases peers see one missing commitment, exclude the validator at `deadline`, and the validator observes the restarted group without a key share for epoch `k+1`. If three of a six-validator set are restarted in the same window, `min_participants(6) = 5` is missed and the epoch is skipped for all.

## Considered and rejected

- Idempotency of the store makes a _re-issued_ effect safe (`store_keygen_secrets` returns the existing row, store.rs:183-197), so re-emitting is the right fix; the defect is only that nothing re-emits.
- `ReconcileGroupSecrets` retains the group's secrets for a `Participating { .. }` commitment round (preprocess.rs:143-156) but does not restart the setup; it is deliberately a no-op for this phase.
- The PR #851 "stuck" branch (row 5) handles the case where _everyone else_ committed and needs `deadline: Some`; it converts the loss into an epoch skip rather than a retry, and does not fire in the partial-commit case, where the generic timeout excludes the validator instead.
- A16: the genesis-only variant (no deadline, state stays `CollectingCommitments` forever, `Halted` never reached) is a genesis-ceremony liveness defect and is rated Informational/`known`; the rollover path above is what carries the Medium rating.

## Remediation options

1. On `NewBlock`, re-emit `Effect::KeyGenSetup` whenever `rollover` is `CollectingCommitments { secrets: Participating { secrets: None, .. }, .. }` (rate-limited to once per block); the store's insert-or-reuse semantics make this idempotent and reorg-safe. Smallest change.
2. Surface failure to the state machine (`Resume::SetupFailed { group_id }`) so the transition can schedule an immediate retry with backoff, distinguishing "failed" from "still running".
3. Persist the resume: commit a snapshot after `handle_resume` for resumes that carry secrets (`Setup`, `NonceTree`), or make the driver re-spawn effects recorded in a small durable outbox on startup. Larger change in core; also closes F2-VAL-062's crash window.

Tests to add: a state test that applies `NewBlock` starting a DKG, drops the emitted effect, applies another `NewBlock`, and asserts `KeyGenSetup` is emitted again; a handler test with a closed pool asserting the resume is distinguishable from success. No code is committed.
