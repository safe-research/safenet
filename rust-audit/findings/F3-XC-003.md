## Claim

Both Dockerfiles state that the workspace's `sqlx` dependency does not enable `bundled`, install `libsqlite3-dev` and `pkg-config` in the builder and `libsqlite3-0` in the runtime image, and explain that the binary "links against the system SQLite rather than bundling it". That is wrong for sqlx 0.9.0: its `sqlite` feature, which `Cargo.toml:19` enables, expands to `sqlite-bundled` (plus `sqlite-deserialize`, `sqlite-load-extension`, `sqlite-unlock-notify`). Both binaries therefore compile in SQLite 3.51.3 from `libsqlite3-sys` 0.37.0 and do not link `libsqlite3.so` at all.

Consequences: the runtime image ships an unused `libsqlite3-0` and the builder an unused `libsqlite3-dev`; more importantly, the comments point maintainers at the wrong patch route. Rebuilding the image on a refreshed `debian:trixie-slim` does not change the SQLite the services run. A SQLite fix arrives only through a `libsqlite3-sys` bump in `Cargo.lock`. The queries are fixed, parameterised SQL, so no SQLite advisory is known to be reachable today; this is a maintenance and documentation defect. The run-3 baseline repeats the same assumption ("system SQLite, no `bundled`", `rust-audit/state/run3/baseline.md` section 6, A6 table).

## Trigger

None at runtime. The defect shows when a maintainer responds to a SQLite advisory by rebuilding the images, or audits the image by its Debian package list: neither reflects the SQLite version the services execute. The ldd check was run on the debug binaries in the local run folder's `target-base`; the Dockerfiles build `--release --package <service>`, which resolves the same features (`-p validator` and `-p sentinel` in Basis 3).

## Considered and rejected

- Could the release build or `--package` selection drop `bundled`? No. The feature comes from the workspace dependency declaration that every user of `sqlx.workspace = true` inherits; Basis 3 is resolved per package exactly as the Dockerfiles build.
- Is `sqlite-load-extension` (also implied by `sqlite`) a risk? Not found: the connection URL parser accepts only `mode`, `cache`, `immutable` and `vfs` (sqlx-sqlite-0.9.0/src/options/parse.rs:39-108); extensions load only through `SqliteConnectOptions::extension` (not called in scope) or a `sqlx.toml` key that needs the `sqlx-toml` feature, which is not enabled.
- Is the bundled SQLite older than Debian's? No: 3.51.3 (2026-03-13) is newer than trixie's 3.46 series, so nothing is lost today.
- Introduced since run 2? No. Dockerfiles, `Cargo.toml:19` and the locked `sqlx` 0.9.0 / `libsqlite3-sys` 0.37.0 are unchanged since `fe9e84c`.

## Remediation options

1. Keep bundling (the simpler, reproducible choice): delete `libsqlite3-dev`, `pkg-config` and `libsqlite3-0` from the Dockerfiles, correct both comments, and note in the handbooks that SQLite updates come with `libsqlite3-sys` bumps.
2. Or link the system library on purpose: depend on sqlx with `default-features = false` and `sqlite-unbundled` plus the needed extras, keep the packages, and add a CI check (for example `ldd target/release/validator | grep libsqlite3`) so the intent cannot drift again.

Tests to add: a CI step that asserts the chosen linkage. No code is committed.

Confirmation. libsqlite3-sys 0.37.0 compiles its amalgamation whenever `bundled` is on (`libsqlite3-sys-0.37.0/build.rs:70-79`) unless `LIBSQLITE3_SYS_USE_PKG_CONFIG` is set (`build.rs:52-56`); neither Dockerfile sets it, so the image build (`cargo build --release --locked --package <svc>`, `Dockerfile:18`) resolves the same features as the debug builds checked here. The comments have been wrong since the Dockerfiles were added (#640, `20cad66`, 2026-07-29), when the lock already held sqlx 0.9.0 and libsqlite3-sys 0.37.0. The reviewer's reason why `sqlite-load-extension` is harmless holds: the URL parser accepts only `mode`, `cache`, `immutable` and `vfs` and rejects any other key (`sqlx-sqlite-0.9.0/src/options/parse.rs:37-108`). Not verified: the aside that trixie ships the 3.46 series (no network).

A third remediation: `ENV LIBSQLITE3_SYS_USE_PKG_CONFIG=1` in the builder stage makes the current comments and packages true without touching Cargo features, since `build.rs:53-56` takes the linked path even with `bundled`. It trades the bundled 3.51.3 for whatever `libsqlite3-0` the image installs, and needs a check that the system library exports every symbol the enabled sqlx features use (`unlock-notify`, `deserialize`, `load-extension`). Option 1 (keep bundling, fix the comments, drop the packages) stays the simpler choice.

QA recipe: already E1. Docker and Podman builds are not allowed (PROMPT section 1), so mirror the image with `cargo build --release --locked -p validator` and `-p sentinel` in a scratch target, then `ldd target/release/validator | grep -c libsqlite3` (expect 0) and `grep -c -a '2026-03-13 10:38:09 737ae4a3' target/release/validator` (expect 1). For the third remediation, rebuild with `LIBSQLITE3_SYS_USE_PKG_CONFIG=1` on a host with `libsqlite3-dev` and expect `libsqlite3.so.0` in `ldd`.
