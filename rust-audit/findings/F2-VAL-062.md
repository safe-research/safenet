## Claim

`handle_nonce_topup` and `finalize_key_gen` write a `None` chunk reservation into snapshotted state _before_ emitting `Effect::NonceTree`, and `available()` counts that reservation as 1024 nonces of capacity. The effect handler maps every failure - including `nonces::Error::Unavailable`, returned whenever the group's process-local generator stream has not been started - to `Resume::Noop`, which the state machine cannot distinguish from "nothing to do". Nothing retries the effect and nothing removes the reservation, so a single failure leaves a permanent phantom chunk: no further top-up is requested while it is counted, and every `Sign` whose sequence lands in that chunk is answered with "not participating" (up to 1024 consecutive signing sessions, i.e. potentially the rest of a quiet epoch). The failure is reachable without any fault injection: after a process restart the generator map is empty, and on the first `NewBlock` the top-up effect (spawned fourth) and the `ReconcileGroupSecrets` effect that would start the generator (spawned fifth) run concurrently; if the top-up task takes the `nonce_generator` mutex first, `generator.next(group_id)` fails with `Unavailable` immediately.

## Trigger

1. A validator in a finalized epoch is restarted (upgrade, OOM, host reboot) while `available() < 100` at the first new block after restart. This holds whenever the top-up threshold was crossed during the downtime (sequence advances with every `Sign` the group sees, including permissionless `Coordinator.sign` calls by third parties) or when the process died between a `NewBlock` that reserved a chunk and the commit of that block's logs (the in-flight `NonceTree` is aborted with the `EffectManager`, and the reservation is in the snapshot only if the logs committed).
2. On the first `NewBlock`, `handle_nonce_topup` reserves chunk `k` and emits `NonceTree`; `handle_group_reconciliation` emits `ReconcileGroupSecrets`. Both tasks start. If the `NonceTree` task acquires `nonce_generator` first (row 10 shows the reconcile task does a database write while holding the lock, so the order is a scheduler coin flip), `generator.next` returns `Unavailable` (row 6), the handler logs `failed to perform effect` and resumes `Noop` (row 5).
3. `chunks[k] = None` persists in every later snapshot. `available()` stays >= 1024 - offset (row 3) so no new top-up is emitted; once the sequence enters chunk `k`, every `Sign` is dropped (row 4) until the sequence passes offset 924 of chunk `k` and a fresh reservation `k+1` is finally requested. Peers exclude the validator from each of those ceremonies after `signing_timeout`.

The same stranded state results from any `register_nonces_chunk` database failure (`SQLITE_BUSY`, disk full) at effect time, and from a generator worker thread that exited (`nonces.rs:127-133`), since `start` is a no-op for an existing entry (`nonces.rs:36-39`).

## Considered and rejected

- Does the replayed `StartNonceGeneration` from `confirm_key_gen` (keygen.rs:1352) start the stream before the top-up? Only when the DKG confirmation lies after the last snapshot; for a restart in the middle of an epoch nothing but the first `NewBlock`'s reconcile starts the generator (row 7).
- Does `ensure_chunk_reservation` (preprocess.rs:216-224) repair it? It is called only from `handle_nonce_tree`, i.e. on a _successful_ resume; a failed effect never reaches it.
- Does the store's duplicate-request path (`Ok(None)`, effect.rs:161-164) cover this? No, that path is for a concurrent request on a started stream; `Unavailable` is an error and takes the `?` path.
- Is the impact bounded? Yes, to one chunk (1024 sequences) per incident, and to this validator, so Medium rather than High; but an attacker who can drive sequence consumption cheaply (permissionless `sign`, see VAL-H6 lead) can make threshold crossings, and therefore restarts landing on them, frequent. Genesis is not special here (A16 not applicable).

## Remediation options

1. Make failure explicit: return `Resume::NonceTreeFailed { group_id }` (or `Resume::NonceTree { group_id, commitment: None }`) from the handler and have the transition drop the `None` reservation, so the next `NewBlock` re-requests it. Small, keeps effects idempotent.
2. Order the startup correctly: emit `ReconcileGroupSecrets` (or a dedicated start effect) _before_ the top-up in the `NewBlock` command list, and have `NonceGenerator::next` start a missing stream lazily when the handler still holds the key share (it does, via the reconcile map) instead of failing. Removes the race but not the database-failure case.
3. Exclude `None` reservations from `available()` and re-emit `NonceTree` for any `None` reservation older than N blocks on `NewBlock`. Self-healing without a new resume variant; costs occasional duplicate chunk generation.

Tests to add: a handler test that performs `NonceTree` on a fresh `Handler` and asserts the resume is distinguishable from success; a state test that applies `NewBlock` with `available() < 100`, feeds `Resume::Noop`, and asserts a later `NewBlock` re-emits `NonceTree`. No code is committed.
