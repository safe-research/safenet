## Claim

Each validator derives every group id from its own `participants` list, `active_from`/`active_before` windows and `genesis_salt`, and nothing compares the result with the chain or with the other validators. At startup the validator reads only `getCoordinator()`, although `Consensus` stores the genesis group id (`getEpochGroupId(0)`). A validator whose genesis set or salt differs from the deployment ignores the genesis `KeyGen` event without a log line and never joins genesis. For later epochs a divergent list makes the validator open its own group onchain each epoch, while the others wait out the 120-block commitment round, exclude it, and skip the epoch whenever the remaining members fall below `min_participants`. The operator sees no error, only "starting key generation" with a group id that differs from the other operators'.

## Trigger

1. Genesis: one of the five Aegis operators lists four genesis participants (one entry missing or mistyped) or a non-zero `genesis_salt`. Its derived genesis id differs from `0x965f661d...` (docs/configuration.md:7), the genesis `KeyGen` event is dropped (row 4) and nothing is logged. Genesis has no deadline and cannot restart (row 8), so it never completes. On its own this is genesis liveness (A16, Informational).
2. Rollover: a sixth validator F is added with `active_from = N`, and three of the five existing operators plus F update their configs before epoch N while two do not. For epoch N the updated four derive a six-member group and the two lagging nodes a five-member group (row 5). The six-member side excludes the two silent members after 120 blocks and has 4 < `min_participants(6)` = 5 members left, so it skips the epoch; the five-member side has 2 < 4 left and skips too (row 7). Every epoch is skipped until the configs agree, each lagging node opens its own group onchain every epoch (row 6), and no log line says the lists differ. The active group keeps attesting, so the cost is rollover liveness and gas.

## Considered and rejected

- `deny_unknown_fields` and the startup `InvalidValidators` check catch typos in key names and lists too small to form a genesis group (rust-audit/state/run3/logs/R6-config-typos.txt), but not a well-formed list that differs from the other operators'.
- Comparing later epochs against the chain is not possible before a `KeyGen` exists; a `KeyGen` whose indexed `context` equals the local `group_context(consensus, number)` but whose `gid` differs is a clear divergence signal, and `handle_genesis_key_gen` ignores every non-genesis `KeyGen` (keygen.rs:39-40).
- Operator error is in A1's domain, but the remedy is a fail-loud check, not protection against a malicious operator, so Low.
- Run 2 commit `fe9e84c`: main.rs and service/mod.rs are unchanged since then (map section 4.1), so this is pre-existing.

## Remediation options

1. At startup, call `getEpochGroupId(0)` and refuse to start (or log an error) when it differs from `genesis.group().id()`; log the derived genesis id at info either way.
2. While waiting for genesis, warn on a `KeyGen` event with an unknown id; during rollovers, warn on a `KeyGen` whose `context` matches the local epoch context but whose `gid` differs from the local group.
3. Expose the derived group id of the current key generation as a metric label so operators can compare it across nodes.

Tests to add: a startup test with a participant list that does not reproduce the configured `Consensus` genesis id.

Notes:

- "Fails silently" is exact for genesis, where the drop path logs nothing. For rollovers the operator does see "key generation commitment collection timed out" and "could not form new participant set to restart keygen" (`state/keygen.rs:1057`, `:1233`), but no message names a list mismatch.
- Remediation 1 has a concrete reference for Aegis: the genesis group id is published in `docs/configuration.md:7`, and `getEpochGroupId` is a public view (`Consensus.sol:165-167`) that only needs adding to the bindings.

Added trigger, routed by the head as O-COV-1: `blocks_per_epoch` (`config.rs:61-63`, default 1440) belongs in this finding. It is the same class (a consensus parameter taken from local configuration that every validator must share, never cross-checked) and the same fix site as remediation 2. `Consensus` holds no epoch length; `_requireValidRollover` only asks for `rolloverBlock > block.number` (`Consensus.sol:395-397`). The validator derives both the epoch number at which key generation starts (`next_number(b) = 1 + b / blocks_per_epoch`, `consensus/epoch.rs:6-9`, used at `state/keygen.rs:938-961`) and the rollover block it signs (`epoch * blocks_per_epoch`, `state/keygen.rs:516-518` and the confirm callback at `:1360-1366`) from that value. A validator with a different value starts key generation at other blocks and, except by coincidence, for other epoch numbers, so its group context and group id differ (`consensus/group.rs:193-201`, `group_context`): it opens its own group and is excluded from its peers' group, exactly as in trigger 2, and two such validators in the Aegis set skip every epoch. If the epoch numbers do coincide and the divergent node is the last confirmer, its callback proposes a different `rolloverBlock`, the active group ignores that `Sign` (it tracks a different message), and the `WaitingForRequest` timeout restarts signing with the honest message (`state/sign.rs:513-551`), so it costs one `signing_timeout` and recovers. A startup check cannot catch this one (nothing onchain to compare); the warning in remediation 2 can, extended to "a `KeyGen` whose context names this `Consensus` with an epoch number the local schedule does not expect". The timeout parameters (`key_gen_timeout`, `signing_timeout`) drive the same deterministic timeouts (`docs/overview.md:23`) and so belong to the same class; I did not trace their divergence.

QA recipe: run the `361aaf3` validator binary against a loopback Anvil with the contracts deployed by `deploy_validator_contracts` (`scripts/lib/shared_test_scripts.sh`) and a configuration whose `participants` omits one genesis address, then trigger the genesis `keyGen` as the integration scripts do. Expected today: the instance starts, never logs "starting key generation" for the deployed genesis id and never fails. For the rollover half and for `blocks_per_epoch`, run two configuration sets with a short `blocks_per_epoch` and watch the divergent instance open its own group id at the epoch boundary.
