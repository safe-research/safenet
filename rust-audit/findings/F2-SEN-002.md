## Claim

`committed_count` only counts `Committed` logs that arrive while the FSM is in `CollectingCommitments`, which is entered when _our_ engine resumes. Every other sentinel's commitment that lands before that moment (a faster engine, or a sentinel that commits in the block after the proposal on purpose) is logged as "unexpected" and forgotten. The early-finalize trigger `revealed_count >= committed_count` and the onchain `everyoneRevealed` therefore diverge, with two outcomes:

1. If another sentinel's reveal reaches our undercounted total before our own reveal is observed, `finalize()` sees `self_revealed == false`, removes the entry and emits nothing. Our already-queued `Reveal` still lands, the request resolves in our favour, and the sentinel **never claims** its bond and fee share (the later `OracleResult` hits an untracked id).
2. If our reveal is observed first, `Finalize` is emitted while the onchain `revealedCount < committedCount` and `block <= revealDeadline`: it reverts with `FinalizeTooEarly`. The FSM is now in `WaitingForOutcome`, which has no deadline and no retry. If no other sentinel finalizes, the request stays `PENDING` and every bond stays locked.

A single registered sentinel that commits early and never reveals makes outcome 2 happen to every honest sentinel on every request at once, at a cost of `slashAmount` per request that is only ever collected if a third party calls `finalize` after the reveal deadline. That stalls the oracle (no `OracleResult`) and locks all honest bonds until manual intervention.

## Trigger

Sentinels `M`, `O` (others) and `H` (this sentinel). Request terms: `commit_deadline = 120`, `reveal_deadline = 130`.

**Honest race (outcome 1)**

1. Block 100: proposal + `NewRequest` → `H` in `WaitingForEngineCheck { request: Some }` (claim 1). `H`'s engine performs RPC-backed checks and answers after ~8 s.
2. Block 101: `Committed(M)` (claim 10) → `H` discards it (claim 2).
3. Block 102: `H`'s resume → `CollectingCommitments { committed_count: 0 }` (claim 3). Block 103: `Committed(H)` → 1. Block 104: `Committed(O)` → 2. Onchain `committedCount = 3`.
4. `NewBlock(121)`: `H` queues `Reveal`. Block 122: `Revealed(M)` → `revealed_count = 1`. Block 123: `Revealed(O)` → `2 >= 2` (claim 4) → `finalize()` with `self_revealed = false`, `timed_out = false` → entry removed, no action (claim 5).
5. Block 124: `Revealed(H)` lands (already queued) → "ignoring reveal for an untracked request". `O` (which counted all three) finalizes; `OracleResult` → ignored by `H` (claim 9). `H`'s bond and fee share sit in the contract until someone calls `claim()` from `H`'s key by hand. No metric or error records the loss.

**Adversarial stall (outcome 2)**

1. `M` commits at block 101 on every request and never reveals. Every honest sentinel whose engine takes more than one block misses `Committed(M)`; honest `committed_count = h` (the honest count).
2. When the `h`-th honest reveal lands, each honest FSM sees `revealed_count = h >= h` with `self_revealed = true` → emits `Finalize` → `WaitingForOutcome` (claim 6).
3. Onchain `revealedCount = h`, `committedCount = h + 1`, `block <= revealDeadline` → every `Finalize` reverts `FinalizeTooEarly` (claim 8). Gas is spent; the FSM is not informed.
4. After block 130 anyone may finalize, but every honest FSM is parked in `WaitingForOutcome` with no deadline (claims 6, 7) and `M` will not. The request stays `PENDING`; honest bonds stay locked; the Safe transaction never receives an `OracleResult`. `M`'s cost is `slashAmount`, collected only if a third party eventually calls `finalize`. If `M` can place its `commit` in the same block as the proposal, the miss is deterministic for every honest sentinel regardless of engine speed (the batch is applied before the effect is spawned, crates/core/src/state/mod.rs:213-223).

## Considered and rejected

- "`handle_oracle_result` recovers from `CollectingVotes { self_revealed: false }`": it does when `OracleResult` arrives _before_ `finalize()` runs locally (test `oracle_result_recovers_a_slashed_bond_when_our_own_reveal_was_missed`, service.rs:1859-1923). Outcome 1 removes the entry first, so there is nothing left to recover.
- "The reveal-deadline path re-finalizes": `handle_block_advance` only calls `finalize()` from `CollectingVotes` (service.rs:450-465); `WaitingForOutcome` is retained unconditionally (466).
- "Another sentinel's `finalize()` will resolve it": only if that sentinel counted every commit; a same-block or next-block commit is missed by every sentinel whose engine is slower than the committer, and the adversary controls the committer.
- "Counting commits before the verdict is impossible because the request is unknown": `NewRequest` is already retained in `WaitingForEngineCheck { request: Some }` (claim 1); a counter fits there and in `WaitingForRequest`.

## Remediation options

1. Track `committed_count` from `NewRequest` onward: add the counter to `Request` (and to `WaitingForRequest`), increment it in `handle_committed` for every state that has the request, and carry it into `CollectingCommitments`. Also record `self_committed` there so a replayed own commit is never lost (see F2-SEN-001). Low cost; removes the divergence at its source.
2. Stop early-finalizing on local tallies: emit `Finalize` only at `reveal_deadline + 1` (always valid onchain), or read `getRequest(id).progress` via an effect before emitting it. Tradeoff: a block or two of extra latency per request.
3. Give `WaitingForOutcome` a deadline (`reveal_deadline + 1`): if no terminal event has arrived by then, re-emit `Finalize`. This also covers any other reason a `Finalize` reverts. Cheap and independent of 1–2.
4. Never drop a bonded entry (see F2-SEN-003): when `self_revealed` is false, transition to `WaitingForOutcome` without `Finalize` so the eventual `OracleResult`/`DisputeTriggered`/`RequestTimedOut` still claims.

Tests to add: flow test inserting `committed_event(id, OTHER)` between `proposed_event` and `resolve_engine_check` and asserting the final `Claim`; flow test where `Finalize` is emitted early, no terminal event arrives, and `NewBlock(reveal_deadline + 1)` re-emits `Finalize`.

**Economic check against the contract.** No sub-case slashes the honest sentinel. The costs are: uncollected bond + fee share (silent; manual `claim()` recovers them), the gas of one reverted `Finalize`, and — adversarial variant — no `OracleResult` for the request while every this-software sentinel is parked, all bonds locked, until someone calls the permissionless `finalize` after `revealDeadline`. Tempered by: nothing is slashed, `finalize`/`claim` are permissionless and undeadlined, so funds are locked, not lost; hence not Critical. A16/A17 not engaged.

**Relations.** Root cause shared with F2-SEN-001 (this file is canonical for the _undercount_); outcome 1 reaches the drop that F2-SEN-003 is canonical for; outcome 2 relies on the missing deadline that F2-SEN-004 is canonical for.
