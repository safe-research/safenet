## Claim

Reaching `CollectingVotes` guarantees our bond is onchain (`self_committed` is required to get there). Yet when the reveal window closes, or the local early-finalize fires, with `self_revealed == false` and at least one reveal counted, `finalize()` removes the entry and emits nothing. Onchain a non-revealing committer still owns `bondTarget − slashAmount` (governance enforces `slashingMultiplier ≤ bondMultiplier`), and a committer whose reveal _did_ land but was not observed owns the full bond plus a fee share. Neither is ever claimed, no metric is recorded, and the request id is forgotten so the later `OracleResult`/`DisputeTriggered`/`RequestTimedOut` cannot trigger the recovery paths that the code otherwise provides for unexpected states.

Two realistic ways to end up there without any adversary: the reveal transaction is not mined before `reveal_deadline` (fee spike, RPC outage, the nonce stuck behind an earlier transaction), or a restart during the reveal window. In the restart case the warp delivers `Revealed` logs while the rolled-back FSM is still in `CollectingCommitments` (warps deliver no `NewBlock`, so the phase change that would accept them is deferred), the logs are discarded, and any reveal observed live afterwards produces the drop.

## Trigger

Terms: `commit_deadline = 120`, `reveal_deadline = 130`; two sentinels `H` (this) and `O`; `max_reorg_depth = 5`.

**Restart during the reveal window**

1. `NewBlock(121)`: `H` emits `Reveal` → `CollectingVotes`. Block 122: `Revealed(H)` → `self_revealed = true`. Snapshot 122 records it.
2. Process stops after block 124 (anchor 119 = `CollectingCommitments { self_committed: true }`). Restart when latest = 129: `Uncle{120}`, `Warp{120..=124}`.
3. Warp page carries `Revealed(H)@122` → discarded (claims 6, 7). `NewBlock(125)`: `Reveal` re-emitted (reverts `AlreadyRevealed`), `CollectingVotes { revealed_count: 0, self_revealed: false }`.
4. Block 127: `Revealed(O)` → `revealed_count = 1`. `NewBlock(131)`: `!self_revealed && !timed_out` → entry removed, no action (claims 1, 2). `O` finalizes; `OracleResult` for an untracked id is ignored; `H`'s full bond and fee share remain unclaimed.

**Reveal not mined in time**

`H` commits; its `Reveal` is queued at block 121 but the account's previous transaction is stuck (or the node rejects submissions for a few minutes). `O` reveals at 123. At `NewBlock(131)` the entry is dropped (claim 1). `O`'s `finalize()` slashes `slashAmount` from `H` and leaves `bondTarget − slashAmount` claimable (claims 4, 5) — with the integration script's multipliers (`BOND_MULTIPLIER=4`, `SLASHING_MULTIPLIER=2`) that is half the bond. `H` never claims it and records no `RevealMissed` (that metric is only emitted from `handle_oracle_result`, service.rs:801-806).

## Considered and rejected

- "Nothing is claimable when we did not reveal": false whenever `slashAmount < bondTarget` (claim 5), and false whenever our reveal landed but was not observed (restart case).
- "Dropping saves the gas of a pointless `Finalize`": the `Finalize` is optional; the problem is dropping the _entry_, which also drops the `Claim`. The `oracle_result_recovers_a_slashed_bond_when_our_own_reveal_was_missed` test (service.rs:1859-1923) shows the intended behaviour when the terminal event beats the deadline; the deadline path contradicts it.
- "The operator will notice": nothing is logged above `warn` and the `requests_resolved_total` counter is not incremented on this path (service.rs:631-637 emits no metric).

## Remediation options

1. Replace the drop with a transition to `WaitingForOutcome { approve, slash_amount }` without emitting `Finalize` (or with it — a duplicate merely reverts). The existing `handle_oracle_result`/`handle_dispute_triggered`/`handle_request_timed_out` handlers then claim. Add a deadline to `WaitingForOutcome` (see F2-SEN-002/004) so a request nobody finalizes is eventually finalized by us.
2. Additionally reconcile `Revealed(self)` in `CollectingCommitments` (set a `self_revealed` flag carried into `CollectingVotes`) so warp-delivered own reveals are not lost.
3. Emit a `reveal_missed`-style metric and a `warn!` on the path so operators can act.

Tests to add: flow test with `Revealed(OTHER)` only and `NewBlock(reveal_deadline + 1)` asserting the entry survives and a later `OracleResult` emits `Claim`; a state-machine test that restarts inside the reveal window with our reveal in the warped range.
