## Claim

On a fresh start (empty snapshot store) the block watcher emits `New` for every block in `recent` at or after `start_block` (all of them when `start_block` is unset) and keeps the node's block at `latest - max_reorg_depth` as its in-memory `safe` anchor. The state machine commits its first snapshot at the first emitted block; nothing is ever committed at the anchor (`safe`) or at `start_block - 1`. The watcher, however, will uncle any block in `recent` - including, when `start_block` is inside the reorg window, blocks below `start_block` that were never emitted - because reorg detection unwinds `recent` all the way down to `safe` (the tested `supports_deep_reorgs_during_indexing` behaviour). The first `Uncle{k}` whose parent `k-1` has no snapshot makes `SnapshotStore::reorg` return `MissingSnapshot(k-1)`; `handle_update` propagates it and the driver exits with "unrecoverable driver error". Because the failed rollback leaves the store unchanged, the orphaned first block's snapshot survives; on restart `initialize` sees `safe == latest == k`, emits no uncle and warps from `k+1` (the unverified-anchor path of F2-CORE-001), so the service continues from state derived from the orphaned block.

Two triggers. With `start_block` set to the head (or anywhere inside the window) a **one-block** reorg of the head during the first window suffices. With the default fresh start, a reorg unwinding the whole window - within `max_reorg_depth`, which the watcher itself handles - reaches the first emitted block `safe + 1`. Either way a reorg that A5 says is handled crashes the service and then poisons its restart. This is not genesis-specific (A16): any fresh start of either service starts this way - a sentinel joining, a re-index after a database wipe, a move to a new host with an empty database.

## Trigger

Sequence A (`start_block` at the head). Config `max_reorg_depth = 2`, `start_block = Some(1000)`, empty store; node latest 1000. `initialize`: `safe = 998`, scan 998..=1000, anchor 998, `recent` = {999, 1000}, queue = `[New{1000}]` (999 is filtered out by `start_block`). Driver: `New{1000}` (`Initialized` -> `BlockEvents{1000}`), `Logs{1000..=1000}` -> `commit(1000)`, `BlockPending{1001}`; `prune(998)` deletes nothing. The chain reorgs one block: `next()` fetches 1001' with `parent_hash != hash(1000)` -> `Uncle{1000}`. `handle_update`: `1000 < 1001` -> `reorg(1000)` -> `DELETE ... >= 1000`, `SELECT ... = 999` -> none -> `MissingSnapshot(999)`; the transaction is dropped, the store is still {1000}; `Error::State(Storage(..))` -> the driver exits. Restart: `status()` = {1000, 1000}; no uncle (`1001 <= 1000` is false); `Warp{1001..=safe'}`; `BlockPending{1001}` accepts it. The state keeps the orphaned block 1000's events.

Sequence B (default fresh start). `max_reorg_depth = 5`, no `start_block`, node latest N: the first emitted block is N-4 and the first snapshot is at N-4. A reorg replacing N-4..=N (depth 5, within the window) unwinds `Uncle{N}` .. `Uncle{N-3}` successfully and fails at `Uncle{N-4}` with `MissingSnapshot(N-5)`; the restart resumes from {N-4}.

Sequence A' (`start_block` inside the window but below the head). `recent` also holds blocks below `start_block`; a reorg deeper than `latest - start_block + 1` but within depth emits `Uncle{k}` with `k < start_block` - a block never indexed; `reorg(k)` deletes every snapshot and fails on `k-1`, store unchanged, same exit.

Mock for QA: `Watcher::new(mocked, config { max_reorg_depth: 2, start_block: Some(1000), .. }, None)` with `block(1000)`, `block(998)`, `block(999)` queued on the asserter; drive `New{1000}` and an empty logs answer through a `StateMachine::new(_, SqlitePool::connect("sqlite::memory:"))` via `handle_update`; then `push_success(block_with(1001, |h| h.parent_hash = keccak256("reorg1000")))`, take `Uncle{1000}` from `watcher.next()` and assert `handle_update` returns `Err(Error::Storage(storage::Error::MissingSnapshot(999)))`; re-open the store and assert `status() == Some(BlockStatus { safe: 1000, latest: 1000 })`.

## Considered and rejected

- _A16 makes this genesis-only._ No: every fresh start of either service begins this way (a new sentinel, a re-index after a wipe, a migration to an empty database); the validator's genesis start is only one instance, and later-epoch starts keep full severity.
- _A17 excludes it._ The trigger is a chain reorg plus the service's own persistence; no out-of-band database access.
- _It is fail-stop, so nothing is corrupted._ The failed rollback is atomic (`storage.rs:127-141`) and the orphaned snapshot survives; the restart path then trusts it by number (F2-CORE-001), so the loud exit becomes a silent divergence one restart later.
- _R1's rejected item 8 covers it._ That item shows `prune` never deletes an _existing_ anchor snapshot (`storage.rs:152-156`). Here no snapshot at the anchor was ever committed: `Status::Initialized` accepts the first `New` without a commit (`state/mod.rs:190-198`) and the first commit is on the first emitted block's `Logs` (`state/mod.rs:236`).
- _The watcher handles the reorg._ It does, in memory (`supports_deep_reorgs_during_indexing`); the defect is that the store cannot follow the watcher to the anchor on a fresh start.
- _Nobody sets `start_block` inside the window._ It is undocumented (Basis 12), which cuts both ways; the default-path trigger (sequence B) needs no configuration, only a full-window reorg, and the watcher's own tests treat that as a handled case.

## Remediation options

1. On a fresh start commit an initial snapshot (the `init()` state) at the anchor before the first `New` is applied: `safe` on the default path, `start_block - 1` when `start_block` is inside the window (in `StateMachine::with_init` when the store is empty, or from the driver using `watcher.block_status().safe`). Cheap, keeps `MissingSnapshot` a true invariant violation, and gives the restart path a genuine anchor. Tradeoff: one extra row; the anchor state is the empty state, which is correct by construction for a fresh index.
2. In the block watcher, on a fresh start treat the block before the first emitted one as the anchor (`safe = start_block - 1` when `start_block` is inside the window) and raise `ExceededMaxReorgDepth` when a reorg reaches it - consistent with the persisted-anchor semantics. Tradeoff: narrows the tolerated depth right after a start.
3. Handle `MissingSnapshot` on an `Uncle` by returning to `Status::Initialized` and re-indexing from the uncled block. Riskier: silently discards state, and does not fix the restart path.

Tests to add: fresh start with `start_block` at the head and a one-block reorg (sequence A) asserting the rollback succeeds - or fails with a dedicated error - and that a restart does not resume from the orphaned snapshot; default fresh start with a full-window reorg (sequence B). No code is committed.
