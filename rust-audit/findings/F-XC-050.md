## Claim

`handle_key_gen_confirmed` inserts `event.participant` into the `confirmations` set with **no check that the address is a member of the group** (`state/keygen.rs:448`), and then closes the round on a pure cardinality test, `confirmations.len as u16 != count` (`:449`). The same absence holds in `handle_key_gen_committed` (`:173-175`, which gates on `verify_commitment` alone) and in `handle_key_gen_complained` (`:714`, no check at all). None of the three consults `group.participants`.

Under A7 that is sound: the coordinator's `FROSTParticipantMap.register` verifies a Merkle proof against the participant root that the group id itself commits to, so contract membership and local membership coincide. But the validator does not require the event to have come from the coordinator — that is F-VAL-060, filed and Draft. Once one address on the operator-configured `oracles` allow-list can emit a `KeyGenConfirmed` log, the membership guarantee is gone and the cardinality test is the only gate left.

The consequence is worse than an early close. When `next_epoch` is `EpochId::Genesis`, the closing branch calls `finalize_key_gen(..., status.key_share)` (`:474-482`). `KeyGenConfirmation::key_share` returns `Some` **only** when this validator's own confirmation has already reached `KeyGenConfirmation::Confirmed` (`:1417-1422`); in every other status it returns `None`. And `finalize_key_gen` with `None` does nothing at all — no `state.epochs` entry, no `Effect::NonceTree`, and **no log line of any kind** (`:1307-1324`). The validator leaves genesis with no epoch, no key share and no nonce chunk, while the group onchain still counts it toward the threshold. There is no error, no warning, and no metric: the only symptom is a validator that never signs again.

`count` distinct injected addresses are enough — the set is keyed by address, and nothing requires the addresses to be real, distinct from each other in any meaningful sense, or members.

## Trigger

Precondition: exactly the precondition of F-VAL-060 — one address in `config.validator.oracles` belonging to a contract that can be made to emit a log whose `topic0` is a `FROSTCoordinator` event selector with a body that decodes as that event. Under A7 none of the three reference oracles in this repository can; a third-party, upgradeable or later-compromised oracle can.

1. Observe the genesis `KeyGen` event and read `gid` and the participant count `n` from it (both public).
2. While the target validator is in `RolloverState::CollectingConfirmations` for that `gid` — the window between its own share verification and its own `KeyGenConfirmed` landing onchain — emit `n` logs with `topic0 = keccak256("KeyGenConfirmed(bytes32,address)")`, `topics[1] = gid`, and `n` distinct non-member `participant` addresses. One transaction is enough.
3. `confirmations.len` reaches `count` while `status` is still `Collecting`, so `status.key_share` is `None`.
4. `finalize_key_gen` returns `(state, Vec::new)` and the rollover moves to `EpochSkipped`. No epoch is recorded. The validator publishes no nonce tree and produces no signature share for the life of the group, while the onchain group still counts it toward the threshold.

The commitment-round variant (basis 5) is the same shape one round earlier: `n` injected `KeyGenCommitted` logs with attacker-generated but internally valid commitments close `CollectingCommitments` with a commitment set that contains no honest peer, and the derived group key is one no other validator will agree with.

## Considered and rejected

- **"The `group.id == event.gid` guard stops this."** It does not. `gid` is a public value from the genesis `KeyGen` event; the guard only fixes which ceremony the injected event lands in.
- **"`confirmations` is a set, so duplicates cannot inflate it."** Correct, and the trigger uses `n` _distinct_ addresses. Nothing constrains what those addresses are.
- **"The honest validator would still finalise later, when its own confirmation completes."** No. The round has already left `CollectingConfirmations`; `handle_key_gen_confirmed`'s `match` falls through to `_ => (state, Vec::new)`, and there is no second finalisation path.
- **"This is already F-VAL-060."** F-VAL-060 establishes the _injection_ and enumerates `KeyGenComplained`, `Sign`, `SignRevealedNonces`, `KeyGenComplaintResponded`, `TransactionProposed` and `EpochStaged` as consequences. `KeyGenCommitted`, `KeyGenSecretShared` and `KeyGenConfirmed` are **not** in that list, and the silent-`None` finalisation is not claimed anywhere. This finding is the missing consequence, not a restatement; F-VAL-060 stays canonical for the injection mechanism.
- **"R4 already recorded this."** R4 recorded it as Observation O9 and explicitly marked it _conditional on R6's VAL-H2_. R6 filed VAL-H2 as F-VAL-060 without picking the observation up. The condition is met and the observation was never promoted — that is why it is here.
- **Under A7 alone this is not a finding.** Stated plainly: with the coordinator as the only emitter, the contract's `register` makes every one of these three handlers safe. The finding exists because F-VAL-060 removes that premise, and because the Rust side has no defence in depth for the case.

## Remediation options

1. **Bind the event to its emitter** (F-VAL-060's fix). Give `state::Transition` the coordinator and consensus addresses and reject any Coordinator/Consensus event whose `log.address` is not one of them. This closes the whole class and is the only fix that does. Cost: one field and one comparison per event; no protocol change.
2. **Check membership in all three handlers.** `group.participants.contains(&event.participant)` in `handle_key_gen_committed` (`:173`) and `handle_key_gen_confirmed` (`:448`), and for `event.accused` in `handle_key_gen_complained` (`:714`). Free today under A7, and it survives a future contract change. This is the same defence-in-depth item listed as F-VAL-003 remediation option 4; adopting it there covers this finding's second half too.
3. **Make the silent branch loud.** `finalize_key_gen` should `tracing::error!` (and increment a metric) when it finalises an epoch this validator was a participant in with `key_share == None`. That is a two-line change and it converts every variant of this failure from silent to alertable, including non-injection causes. Tradeoff: none.
4. **Assert the invariant.** `debug_assert!(confirmations.is_subset(group.participants))` before the cardinality test documents the assumption the code is making even in release builds where it is compiled out.

Tests to add: a `handle_key_gen_confirmed` unit test that feeds `count` non-member addresses and asserts the state stays in `CollectingConfirmations`; a `finalize_key_gen` test asserting that a `None` key share for a participating validator is logged and metered. `state/keygen.rs` currently has **0** tests (`state/baseline.md` §5), so both are new fixtures. No code is committed.

### Counter-evidence the finding omits

The log stream reaching `apply_transition` is address-filtered, twice:

- node-side, on both fetch strategies — `crates/core/src/index/events.rs:407` and `:417`, `.address(self.addresses.clone).event_signature(...)`;
- client-side on the `use_client_filtering` path — `events.rs:460`, `self.addresses.contains(&log.address) && log.topic0.is_some_and(...)`.

So a `KeyGenConfirmed`-shaped log from an **arbitrary** attacker contract never reaches the state machine, and the unqualified reading of this finding's title is refuted. What survives is the narrower claim the Trigger section actually makes: the watched set is `vec![consensus, coordinator]` plus `config.validator.oracles` (`crates/validator/src/main.rs:56-57`, passed at `:76`) and the filter is the **cross product** of addresses × topics, so a watched _oracle_ address can emit a Coordinator-selector log and it passes both filters. I verified that independently and it is correct. The drafting critic conditioned the finding on F-VAL-060 honestly; it simply did not put the filter in the Basis table, which leaves a reader unable to see how narrow the precondition is.

**The precondition is therefore not "an injected event" but "an attacker-controlled or upgradeable contract on the operator's `oracles` allow-list."** F-VAL-060's own reviewer put that at ~25% and C-VAL-B set F-VAL-060 to **50%**. This finding needs everything F-VAL-060 needs, plus more, so it cannot be certified above it.

### The window is much narrower than the finding states

This is the substantive correction. The consequence requires `status.key_share == None` at the instant the round closes, i.e. `KeyGenConfirmation::Collecting`. But `confirm_key_gen` sets `Confirmed` the moment `shares.len as u16 == count`, and that happens in `handle_key_gen_secret_shared` at the **same transition** that first enters `CollectingConfirmations` (`state/keygen.rs:383-407`) — strictly before any `KeyGenConfirmed` event can be processed. So a participating validator whose received shares were all valid is **already** `Confirmed` before confirmations start arriving, and `key_share` returns `Some`. The `Collecting` status persists only via the arm at `:405` (`KeyGenParticipation::Participating(_) => KeyGenConfirmation::Collecting(shares)`), which is reached only when at least one received share failed verification and a complaint is outstanding.

The trigger therefore needs, simultaneously: the F-VAL-060 oracle precondition, **and** an active unresolved complaint at the victim, **and** the injection timed inside that window. The finding claims none of the last two. For an `Observing` validator the `None` is correct behaviour, not a defect. Against that, the title's "one injected `KeyGenConfirmed`" is fair in the marginal case (`count - 1` genuine confirmations already in), even though the Trigger section describes the `n`-address worst case — the two are consistent and the marginal case is the realistic one.

### Finding verdict

**Plausible. Certainty 48%. Severity High / Medium.**

Plausible, not Confirmed: the mechanism is verified `E2` throughout — the missing membership check, the pure-cardinality close and the silent `None` finalisation are all real and I re-derived each — but the trigger is unproven, resting entirely on F-VAL-060's oracle precondition (50%, itself ~25% by its own reviewer) _and_ on the complaint window above, which the finding does not establish. That is the brief's definition of Plausible.

Certainty 48%: bounded below F-VAL-060 because this finding strictly requires it and adds two further conditions. It would rise to the 70s the moment F-VAL-060's precondition is demonstrated against a real deployment's `oracles` list.

Severity Medium, down from High: under A7 with the coordinator as sole emitter this is not a finding at all, as the drafting critic says plainly. Under the oracle precondition, the impact is one validator silently dropping out of a group while the chain still counts it toward the threshold — serious for that validator's liveness and genuinely hard to diagnose (no log, no metric), but it exposes no secret, forges nothing, and stays within what A2's fault bound already tolerates unless repeated across more than a third of the set. Medium, matching C-VAL-B's downgrade of F-VAL-060, is the consistent rating.

**Remediation note.** Option 3 — make `finalize_key_gen` log and meter a `None` key share for a validator that participated — is worth doing on its own merits regardless of this finding's verdict. It is two lines, it costs nothing, and it converts _every_ cause of this failure mode (including F-VAL-004's and F-VAL-005's) from silent to alertable. I would rank it above option 2.

**To move this out of Plausible**, QA needs to settle F-VAL-060's precondition first; only then is a PoC meaningful. The cheap independent step is the unit test the finding already proposes — feed `count` non-member addresses to `handle_key_gen_confirmed` and assert the state leaves `CollectingConfirmations` with `key_share == None` — which converts the _mechanism_ to `E1` without settling reachability, plus an assertion that the status is still `Collecting` only when a complaint is outstanding, which would confirm or kill my window correction.
