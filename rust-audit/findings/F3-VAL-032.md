## Claim

Three statements that describe the single-use guarantee for signing nonces are stronger than the code:

1. The module header says a ceremony "only ever" gets its first pair and that a used ceremony "is never given a fresh pair" (`store.rs:18-22`), and the effect documentation says repeating `GenerateNonces` "returns the nonces generated the first time" (`service/effect.rs:32-35`). Both hold only while the row exists. Once the group's rows are collected (`store.rs:361-383`), a replay that re-runs `GenerateNonces` for the same signature id inserts a fresh pair, because the insert only skips on conflict (`store.rs:228-232`). The header's later caveat says such a secret "is treated like any other that is missing rather than being recreated" (`store.rs:38-41`); for signing nonces it is recreated.
2. `take_signing_nonces` says the returned nonces "live on only in the snapshot state" (`store.rs:263-265`). They are never written to the snapshot: `Resume::Nonces` is consumed by `handle_nonces`, which leaves the state unchanged and only emits the share action (`state/sign.rs:339-384`). A resume that is lost to a shutdown or an aborted effect therefore burns the pair, and the ceremony goes on without this validator.

The code itself stays safe: a fresh pair for an old signature id cannot produce an accepted share, because the first commitment onchain is the old one and frost-core rejects nonces that do not match the signer's commitment (`frost-core-3.0.0/src/round2.rs:140-143`); replayed actions past their deadline are not sent (`crates/core/src/tx/storage.rs:172-175`). The risk is a future change built on the documented invariant, for example code that publishes a regenerated commitment, or code that expects to recover taken nonces from the snapshot.

## Trigger

1. A group's last session ends at block X; the next reconciliation schedules its rows at X (`state/secrets.rs:19-30`, `store.rs:312-352`). The validator stops, stays down for at least 5 blocks, and restarts.
2. On restart the watcher replays from the oldest retained snapshot, which can be below X (`crates/core/src/index/blocks.rs:309-332`), and the first live block's housekeeping collects the rows scheduled at X, since X is at or below the chain's current safe block (`crates/core/src/driver.rs:256-263, 292-294`). Effects spawned during the warp race with that collection.
3. If a replayed `Sign` for one of that group's ceremonies runs `GenerateNonces` after the collection, the store inserts a fresh pair for the old signature id (basis 3), contradicting basis 1, 2 and 6.

For the snapshot statement: a `SIGTERM` that arrives after `take_signing_nonces` committed and before the resume is applied (`crates/core/src/driver.rs:176-182` stops before collecting finished resumes; `crates/core/src/effects.rs:35-43` aborts running tasks) leaves the pair cleared in the store and absent from the snapshot.

## Considered and rejected

- Not a nonce reuse: a collected pair is deleted, never returned, and a fresh pair is independent. A share from the fresh pair fails `IncorrectCommitment` while the old commitment is first onchain; if the old commitment never landed, the fresh pair is used at most once.
- The burn on shutdown is the intended trade-off (burning beats reuse); this finding is only about the wording, which suggests a recovery source that does not exist.

## Remediation options

1. Reword the module header, the caveat and the `GenerateNonces` documentation: a used signature id gets no fresh pair while its row exists; after the group's rows are collected, a replay generates a fresh pair, which is harmless because frost rejects nonces that do not match the first commitment onchain.
2. Replace "live on only in the snapshot state" with: the returned nonces exist only in memory until the share is computed; if the resume is lost (shutdown, aborted effect), the pair is burned and the ceremony continues without this validator.
3. Optional hardening: keep a used marker per signature id until the signature id's group is collected and below the snapshot boundary on every branch, or refuse to generate for a signature id whose `Sign` block is at or below the safe block. Neither is needed for safety today.

Tests to add: none required for the wording; a store test that collects a used row and calls `store_signing_nonces` again would pin the current recreate behaviour.
