## Claim

**`cargo audit` was not run in this audit and no advisory status is asserted anywhere in this finding.** There is no toolchain on the review host (baseline §1, A9 false), so nothing here says anything about RUSTSEC or CVE status for any of the 516 packages in the lock. What follows is what a static read of the manifests, the lockfile and the call sites establishes.

1. **No advisory gate exists in the pipeline either.** `just check` runs `cargo fmt`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and an OpenAPI lint; `just test` runs `cargo test --workspace`. There is no `cargo audit`, no `cargo deny`, no Miri, no fuzzing and no sanitizer job anywhere in `.github/workflows/` or the `Justfile`. The absence of the gate is the finding — not any particular advisory, which nobody in this run is in a position to name. For a service that holds threshold key shares and signs onchain, the distinguishing property of an advisory gate is that it fires _between_ releases, without anyone deciding to look.

2. **Two database drivers the code never uses are in the resolved graph.** `sqlx` is declared with `features = ["sqlite", "runtime-tokio"]` but without `default-features = false`, so the default `macros` feature stays on and the lock resolves `sqlx 0.9.0` with `sqlx-mysql` and `sqlx-postgres` as dependencies. The workspace uses no compile-time query macro at all — every statement is a runtime `sqlx::query(...)`, and `grep -rn 'sqlx::query!\|query_as!\| query_scalar!\|sqlx::migrate!' crates/` returns nothing — so `default-features = false` would remove both drivers and everything under them, including the third `rand` major line (`rand 0.10.1` enters solely through `sqlx-postgres`, baseline §6) and MySQL/Postgres auth primitives such as `md-5 0.11.0`.

3. **Umbrella features are enabled where the code uses one corner.** `alloy` takes `features = ["full", "json-rpc"]` and the lock accordingly contains `alloy-transport-ws`, `alloy-transport-ipc`, `alloy-signer-local` and `tungstenite 0.28.0`; the services build one HTTP provider (`core/provider/mod.rs:130-133`) and use their own `Signer` (`core/tx/signer.rs`). `tokio` takes `features = ["full"]` workspace-wide, which includes `process` — no crate spawns a subprocess.

4. **`regex` is pulled into `core` for three literal substrings.** The only use is `is_transaction_underpriced`, matching `"replacement transaction"`, `"underpriced"` and `"INTERNAL_ERROR: could not replace existing tx"` case-insensitively against an RPC error message. None contains a metacharacter, and the crate brings `regex-automata`, `regex-syntax`, `aho-corasick` and `memchr` with it. `str::to_ascii_lowercase.contains(..)` is the same behaviour.

5. **The two crypto stack questions the baseline raised both resolve cleanly, and are recorded here so no later agent re-opens them.** (a) Two SHA-256 implementations are linked in — `sha2 0.11.0` for `safenet-core` and `sha2 0.10.9` under `k256`/`frost-secp256k1` — but **no hashing-parity-critical call site is ambiguous about which it uses**: every hash that must match Solidity is `alloy::primitives::keccak256`, and the only two SHA-256 uses each name their stack by import path — `k256::sha2::Sha256` for ECDH hash-to-field and plain `sha2::Sha256` for core's HKDF. (b) The validator's own RNG does share a `rand_core` line with the FROST libraries it feeds: `rand 0.8.6`, `frost-core 3.0.0` and `frost-secp256k1 3.0.0` all depend on `rand_core 0.6.4`, and the fact that `keygen::setup` can pass its `&mut R` straight into `dkg::part1` is a compile-time proof of it. `rand 0.8` is nonetheless a superseded line (0.9 and 0.10 both exist and are both already in this lock transitively), which is a maintenance fact, not a defect.

## Trigger

None identified — this is hardening, not a reachable defect. The nearest thing to a trigger is temporal: a vulnerability is published against any of the 516 locked packages and nothing in the pipeline notices, because nothing in the pipeline looks.

## Considered and rejected

- **"Duplicate major versions are themselves a bug."** They are not, and the 43 duplicate names the baseline counted (§6) are overwhelmingly ordinary transitive churn — `windows-*` shims, `hashbrown`, `syn`, the arkworks family. The two that would matter for correctness were checked individually and both are fine (basis rows 9-11). No finding on duplication as such.
- **"`sqlx-macros` is a proc macro, so it is not in the binary."** True of `sqlx-macros` itself, but the lock lists `sqlx-mysql` and `sqlx-postgres` as direct dependencies of the `sqlx` _lib_ (basis row 5), not only of the macro crate. Whether the linker ultimately strips the unused code is not verifiable without a build and is not claimed; the dependency-graph and build-time cost are.
- **"`alloy`'s ws/ipc transports are dead code."** Not asserted as dead — `Provider::connect` passes the configured URL to `ClientBuilder::connect`, which dispatches on scheme, so a `ws://` RPC URL is a supported configuration. The point is only that `full` is broader than `full` needs to be for what is used.
- **"`sha2 0.11` in `core` risks a hashing mismatch with Solidity."** Rejected on evidence: core's `sha2` is used at exactly one place, `kdf.rs`, whose output is the sentinel's local reveal salt (`crates/sentinel/src/hashing.rs`), never a consensus hash. Every Solidity-parity hash in the workspace is `keccak256` from `alloy::primitives`. This was the specific question the baseline asked and it is now answered.
- **`Cargo.lock` hygiene.** Checked and fine: it is committed, format version 4, and both the clippy gate and all three Dockerfiles build with `--locked`, so a resolution drift cannot slip in unnoticed.

## Remediation options

1. Add `cargo deny check` (advisories + bans + licences) or `cargo audit` as a job in `ci.yml`, scheduled daily as well as on PR so it fires between releases. Tradeoff: an advisory with no available fix turns CI red; `deny.toml` supports time-boxed exceptions for exactly that.
2. Set `sqlx = { version = "0.9", default-features = false, features = ["sqlite", "runtime-tokio"] }`. Zero code change is required because no compile-time macro is used (basis row 6); verify by building. This removes two database drivers and one `rand` major line from every shipped binary.
3. Narrow `alloy` from `full` to the transports and types actually used, and `tokio` from `full` to the runtime features each crate needs. Mechanical, and the compiler names anything missing.
4. Replace the three `iregex!` calls with `str` comparisons and drop `regex` from `crates/core/Cargo.toml`.
5. Record in `AGENTS.md` which crypto stack each SHA-256 call site belongs to, so the property verified in basis rows 9-10 stays true as call sites are added.

Tests to add: none. Items 2-4 are validated by the build and the existing suite; item 1 is the gate itself.

### The process claim is vindicated by execution

`cargo audit` 0.22.2 now exists on the host and has been run. It **exits 1**: 4 vulnerabilities and 11 warnings (`rust-audit/state/logs/cargo-audit.txt`). The finding's central claim — that there is no `cargo audit`, no `cargo deny`, no Miri, no fuzzing and no sanitizer anywhere in `.github/workflows/` or the `Justfile`, and that "the absence of the gate is the finding" — is now demonstrated rather than argued. Had the gate existed, the pipeline would have been red, and every one of those fifteen entries would have been triaged when it landed rather than in Phase 5 of an audit.

**Full advisory triage is `F-XC-011`**, filed this phase. Its short form: exactly one advisory (`h2` RUSTSEC-2026-0258) reaches a network-facing surface; the single **7.5 HIGH** (`quinn-proto` RUSTSEC-2026-0185) is **not in any build graph and not in any binary**; the `ruint` `U256` shift advisory is latent because none of its eight affected functions is called anywhere in `crates/`; and of the four **yanked** crates only `spin` 0.9.8 is actually compiled, reaching all three binaries through `sqlx-sqlite` → `flume`.

### Item 2 of this finding — `sqlx-mysql` / `sqlx-postgres` — is **Refuted**

The finding's item 2 argues that `Cargo.toml:19` takes `sqlx` without `default-features = false` and so pulls `sqlx-mysql` and `sqlx-postgres` into the build, and question 19 of `rust-audit/poc/UNRESOLVED-DEPENDENCY-QUESTIONS.md` was raised to decide whether that reached the shipped binaries. It does not — and the premise is wrong one step earlier than the question assumed. They are not stripped by the linker; **they are never compiled at all.**

```
$ cargo tree -i sqlx-mysql    --workspace --locked
warning: nothing to print.
$ cargo tree -i sqlx-postgres --workspace --locked
warning: nothing to print.
$ ls target/debug/deps/ | grep -ci sqlx_mysql      -> 0
$ ls target/debug/deps/ | grep -ci sqlx_postgres   -> 0
```

And after `cargo build --release --workspace --locked` (exit 0):

```
$ nm -C target/release/validator       | grep -c -i "sqlx_mysql\|sqlx_postgres"   -> 0
$ nm -C target/release/sentinel        | grep -c -i "sqlx_mysql\|sqlx_postgres"   -> 0
$ nm -C target/release/sentinel-engine | grep -c -i "sqlx_mysql\|sqlx_postgres"   -> 0
```

The single `strings` hit in `validator` and `sentinel` is the `sqlx-core` error message `"database driver does not support force-dropping a database (Only PostgreSQL)"` — a string constant in the shared core, not driver code. `sqlx-mysql` and `sqlx-postgres` appear in `Cargo.lock` (`:4606-4607`, `:4675-4676`, `:4685`, `:4711`) as _optional_ dependencies of `sqlx`, and `sqlx` 0.9's default features do not activate them, so `features = ["sqlite", "runtime-tokio"]` already excludes them even with `default-features` left on.

**Consequence: remediation 2 of this finding is a no-op for binary surface.** Adding `default-features = false` to the `sqlx` line would remove two lockfile entries and nothing else — no bytes leave any binary, no attack surface shrinks. It is still worth doing as lockfile hygiene (it is the same class of cleanup as `F-XC-011` remediation 5, which reduces the phantom entries `cargo audit` reports), but it should not be presented to the team as a surface reduction. The finding's own framing of item 2 — "whether they reach the shipped binary decides whether remediation 2 is a real surface reduction or only a build-time saving" — answers itself: it is **neither**; it is a lockfile-only change.
