## Claim

#974 fixed the `WaitingForDisputeResolution` half of F-SEN-005 by making the dispute-timeout arm of `handle_block_advance` queue `timeoutArbitration()` and `claim()` at the first block past `arbitration_deadline` and then drop the tracked entry (`service.rs:494-506`, `retain` returns `false`). The code comment justifies the drop by assuming the two calls always make progress: `timeoutArbitration()` may revert if another sentinel's call or a late ruling landed first, but by then the request is no longer `FROZEN`, so the queued `claim()` "succeeds either way" (`service.rs:487-491`).

That assumption has a hole: `timeoutArbitration()` can revert while the request stays `FROZEN`. The Aegis fee token is USDC.e, a `FiatTokenProxy` whose transfers revert for a blacklisted account, and every exit from `FROZEN` (`timeoutArbitration`, `resolveDispute`, `markOutOfScope`) pushes the fee refund to the sponsor before changing state. If the sponsor is blacklisted, `timeoutArbitration()` reverts on that push and the request stays `FROZEN`, so the sentinel's queued `claim()` then reverts `RequestNotResolved` (`claim` calls `requireResolved`, which rejects `FROZEN`; `SentinelOracle.sol:309`, `SentinelOracleRequests.sol:240-247`). The contract already documents this hooked/blacklisting-token freeze (`SentinelOracle.sol:62-67`).

Both reverted transactions are mined, so they advance the signer nonce and the queue marks them executed by nonce without ever checking success (`tx/mod.rs:207-217` then `storage.rs:281-292`); neither is retried. The tracked entry was already dropped, so when the blacklist is later lifted and anyone calls the permissionless `timeoutArbitration()`, the resulting `ArbitrationTimedOut` (or a late `DisputeResolved`) is handled by a terminal handler that removes by id, finds nothing, logs "ignoring ... for an untracked request" and emits no action (`service.rs:600-607`, `:545-552`). The sentinel's bond therefore stays in the oracle until a human submits `claim()` by hand, with no metric or log above `trace` to signal it.

This is a regression introduced by #974. Before #974 the sentinel had no `timeoutArbitration` binding or action and the entry was retained forever (F-SEN-005): a frozen+blacklisted request would then be recovered automatically once the blacklist lifted and any third party timed it out, because the retained `WaitingForDisputeResolution` entry would see `ArbitrationTimedOut` and emit `Claim`. #974 traded that passive recovery for an active timeout that drops the entry unconditionally, so a timeout that is itself blocked now loses the recovery path.

## Trigger

1. A dispute freezes a request: at least one sentinel reveals approve and one reveals deny, `finalize` moves it to `FROZEN` with `arbitrationDeadline = block + ARBITRATION_TIMEOUT` (Aegis: 483,840 blocks). Each committed sentinel holds 800 USDC.e bonded; at least two sides are committed, so at least 1,600 USDC.e is locked.
2. The sponsor of that request is blacklisted on USDC.e (a Circle-controlled Gnosis compliance action).
3. The arbitrator does not rule within `ARBITRATION_TIMEOUT`.
4. At `block > arbitration_deadline` every sentinel queues `timeoutArbitration()`+`claim()` and drops its entry. `timeoutArbitration()` reverts (blacklist), the request stays `FROZEN`, `claim()` reverts `RequestNotResolved`. Both reverts are mined, consumed by nonce and never retried.
5. The blacklist is later lifted and someone (the sponsor wanting its fee back, or any address) calls the permissionless `timeoutArbitration()`. `ArbitrationTimedOut` fires; every sentinel ignores it as untracked. The bonds sit reclaimable in the oracle until an operator sends `claim()` by hand, unprompted by any metric or warning.

## Considered and rejected

- "The durable queue retries the claim." No. The queue has no receipt/success check (`state/run3` C3-SEN grep: "no receipt handling in the queue"); a mined revert advances the nonce and is marked executed (basis 5), so the reverted `claim()` is discarded, not retried.
- "A reorg replay re-creates the entry." The drop happens at `deadline + 1`; a replay within `max_reorg_depth` (Aegis 5) re-runs the same drop, and `arbitration_deadline` is 483,840 blocks after the freeze, far outside any replay window. Nothing re-creates the entry.
- "This is just the contract finding from the Aegis env review." The contract behaviour (bonds locked while blacklisted) is item 4 of the 2026-10-07 env review and self-heals on-chain once the blacklist lifts and a timeout lands. The defect here is the sentinel software's failure to _take_ that heal: it dropped the entry, so it never re-claims even after the on-chain state is recoverable. That half is pure Rust and is introduced by #974.
- "Covered by F-SEN-005." F-SEN-005's live claim is the `WaitingForOutcome` state never expiring; #974 fixed its dispute half. This is a new defect in that fix, cross-referenced from F-SEN-005's run-3 Notes as a lead and filed here.

## Remediation options

1. Keep the entry until a terminal event removes it. In the dispute-timeout arm, emit `timeoutArbitration()`+`claim()` but return `true` (retain), so a later `ArbitrationTimedOut`/`DisputeResolved` still finds the entry and re-emits `claim()`. Add a once-flag (or an `expires_at`/retry cadence) so the two calls are not re-queued on every block past the deadline. Tradeoff: the entry lingers until the dispute truly resolves, which is the correct lifetime.
2. Make `claim` idempotent on failure: track a `Claiming`/`WaitingForClaim` state entered after the timeout is observed resolved (on `ArbitrationTimedOut`/`DisputeResolved`), rather than optimistically queuing `claim()` behind a timeout that may revert. This separates "the request is resolvable" from "I have reclaimed", and is the cleaner shape.
3. Operational: a gauge/`warn` for a bond held in a request the sentinel has stopped tracking, so an operator sees a stranded bond. Does not recover funds on its own; pairs with 1 or 2.

Tests to add: a `service.rs` test asserting that after the dispute-timeout arm fires, a subsequent `ArbitrationTimedOut`/`DisputeResolved` for the same id still produces a `Claim` (the F3-SEN-060 PoC, inverted to assert the fixed behaviour). No code is committed.

## Head note (2026-10-09): evidence boundary

The contract half in the Lead triage section above came from a fork test that called `vm.createSelectFork(vm.rpcUrl("gnosis"), 48635154)` with `rpc_endpoints.gnosis = "https://rpc.gnosischain.com"`. `FOUNDRY_OFFLINE=true` does not block RPC, and the test ran outside the private network namespace, so it made read-only calls to the public Gnosis endpoint. That broke this run's no-RPC rule (PROMPT.md Section 1). Re-run inside the namespace, the same test fails at `createSelectFork` with a DNS error. The test and its output were taken out of this folder.

The same result was re-derived with no network in [`poc/F3-SEN-060/offline/`](../poc/F3-SEN-060/offline/) (OFF3): the real USDC.e proxy and FiatTokenV2_2 code and its 14 proxy slots etched from the local Foundry cache, the audit-commit `SentinelOracle` with the Aegis parameters, every command under the namespace. `timeoutArbitration` (and `resolveDispute`, `markOutOfScope`) revert `Blacklistable: account is blacklisted`, each `claim` reverts `RequestNotResolved()`, 2,400.40 USDC.e stay in the oracle, and everything recovers after `unBlacklist`. Same deadline, locked amount and gas as the fork run; two contract mutants make the test fail. The E1 for the contract half now rests on that offline run.

Wording correction: `timeoutArbitration` writes `TIMED_OUT` first (`request.timeoutArbitration()`) and pushes the refund after it (`contracts/src/SentinelOracle.sol:347-348`), not before changing state. The effect is the same: the push reverts and the whole call reverts with it.
