## Claim

`main()` returns `Result<(), Box<dyn Error>>` and propagates `Config::load` errors with `?`. Rust's `Termination` impl prints a returned error with `{:?}`, and `toml::de::Error`'s `Debug` output (toml 1.1.2, pinned in `Cargo.lock`) carries an `input: Some("<entire document>")` field. So every TOML-level configuration mistake - a misspelled optional key, a wrong type, an unknown table, a malformed `signer` value - writes the complete configuration file, including the well-formed `signer` private key, to the process's stderr. Under the documented deployment (`docker run` with logs read via `docker logs`, or a log shipper) the validator's funded, onchain-identity private key ends up in log storage that is routinely shared with third parties and retained. The careful `Debug` redaction on `Signer` (`signer.rs:96-100`) does not help because the leak is the raw document text, not the parsed value. Executed against the audited binary (commit `3ec8bc5`).

## Trigger

Operator writes `validator.toml` with a valid `signer` and any TOML-level mistake elsewhere (for example `blocks_per_epoc = 1440`, `oracles = "0x..."` instead of a list, or a misspelled `[observabilty]` table), then starts the container as documented. The process exits 1 and stderr contains `Error: Parse(Error { ..., input: Some("...signer = \"0x<64 hex>\"...") })`. Reproduced this session with a loopback `rpc` and the public Anvil test key (log above); parsing fails before any RPC or database access, so the run touched no network.

## Considered and rejected

- Is the `Debug` path really taken? Yes: `main` returns `Err(Box<dyn Error>)`, and `impl<E: Debug> Termination for Result<(), E>` prints `Error: {err:?}`. Confirmed by the executed output, which is the `Debug` rendering of `config::Error::Parse(toml::de::Error { .. })`.
- Could the observability layer redact it? No: `observability::init` runs at `main.rs:41`, after `Config::load` failed, so no tracing subscriber is involved; the text goes straight to stderr.
- Does the leak need a malformed key? No: case 1 has a well-formed key and leaks it because the offending field is elsewhere. Case 2 shows the malformed-key variant, where the near-miss key (one nibble off) is printed - still sensitive.
- `Display` instead of `Debug` would also leak in the malformed-signer case: toml's `Display` renders the offending source line with a caret (observed with a scratch crate on toml 1.1.2: the line `signer = "0x..."` is echoed). So switching to `Display` alone is insufficient for that variant.
- The same pattern exists in `crates/sentinel/src/main.rs` (not in R6 scope; flagged for R7/R8 in the coverage log).

## Remediation options

1. In `main`, do not return config errors through `Box<dyn Error>`: match on `Config::load`, log `err.message()` plus the span/key path (`toml::de::Error::span()`, `keys`) without the document, and `std::process::exit(1)`. Cheapest, contained to `main.rs`.
2. Give `config::Error` a manual `Debug`/`Display` that prints only the message and location (never `input`), and make `Config::load` strip `input` (toml exposes the message and span; the input can be dropped by re-creating the error or by formatting at load time). Protects every future caller.
3. Additionally, load `signer` from a separate file or environment variable so that the TOML document never contains the key. Larger change, but it also removes the key from config backups and from `--volume`-mounted files.

Tests to add: a unit test in `config.rs` that feeds a document with a valid signer and an unknown field to the loader's error-rendering path and asserts the rendered string does not contain the signer hex; the same for a malformed signer. No code is committed.

## Critic (C2-VAL-B)

Reproduced independently of R6's log.

Per-claim verdicts: rows 1-7 **Supported** (rows 4-5 are E1 and I re-confirmed them). `main -> Result<(), Box<dyn Error>>` propagates `Config::load` with `?`; `Termination` prints the error with `{:?}`; `toml::de::Error`'s `Debug` (toml 1.1.2, pinned) carries `input: Some(<whole document>)`; `Signer`'s own `Debug` is redacted (signer.rs:96-100) so the leak is the raw text, not the parsed value. `observability::init` runs _after_ the failure, so no subscriber redacts it. All confirmed. No `H` rows.

Finding verdict: **Confirmed**, basis **E1** (executed reproduction saved under `rust-audit/`), so the 90-100 band is open; certainty **92**.

Severity: I set **High / High**. The severity rubric lists "leaks ... signer keys" as Critical, and this does leak the funded signing key — but the trigger is the operator's own config mistake (A1), the key is already at plaintext rest in the config/DB by design, and it leaks to the operator's _own_ stderr. What lifts it above a mere at-rest exposure is the documented deployment: `docker logs`/log shippers route stderr into storage the handbook itself says is shared for debugging ("Never share this file ... including the Safenet team"), and a log pipeline is far more widely replicated and retained than the config file. So the marginal exposure is real and serious, but operator-gated rather than attacker-driven: **High**, not Critical. (A stricter reading of the rubric would say Critical; I record the disagreement rather than inflate.)

Duplicate: same defect as **F2-XC-001** (Critic C2-XC), which is the cross-cutting form covering both the validator and sentinel binaries. Canonical for reconciliation should be **F2-XC-001** (broader scope); F2-VAL-060 is the executed validator instance. Note the **severity disagreement**: F2-XC-001 is rated Medium, I rate this High — reconciliation should reconcile to High given the E1 leak and the shared-log deployment.

Remediation check. **Option 1 is sound**: toml 1.1.2's `de::Error` exposes `message()` and `span()` (`~/.cargo/registry/src/*/toml-1.1.2+spec-1.1.0/src/de/error.rs:64-69`); print those and exit non-zero. **Option 2 is sound and directly supported**: `toml::de::Error::set_input(None)` (same file, line 78) drops the document, so `Config::load` can call it before propagating and no manual `Debug` is needed; after `set_input(None)` the `Display` form no longer echoes the source line either, which closes the malformed-`signer` variant the finding notes. Option 3 is sound and larger. Recommend 2 (one line in `Config::load`, same fix in the sentinel) immediately; F2-XC-001 stays the cross-cutting canonical.
