## Claim

Every outbound HTTP client in the workspace is `reqwest::Client::new` — the two sites are in different crates and neither uses `ClientBuilder`. Three default behaviours follow that a security-sensitive client would normally decide explicitly:

1. **No timeout on the CoW client.** `CowChecker::new` builds a bare client and never sets a per-request timeout, so a request to `api.cow.fi` that stalls stalls indefinitely. The engine applies no server-side deadline either — `x-request-timeout` is parsed and then explicitly discarded (`api/mod.rs:48-50`) — so a hung upstream holds an axum task, and the request the sentinel is waiting on never returns. The sentinel _does_ set a per-request timeout on its own client (`engine.rs:155`), which is why the asymmetry stands out: the crate that guards against a hung peer is the one whose peer is trusted, and the crate whose peer is a third party on the public internet does not.
2. **Proxy environment variables are honoured.** `reqwest`'s default client reads `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` from the process environment. Both containers run as root with no environment scrubbing (F-XC-004), so anything that can set an environment variable on the pod redirects both the sentinel→engine hop and the engine→CoW hop.
3. **Redirects are followed.** The default policy follows up to ten. `error_for_status` is applied after the redirect chain, so a 3xx from the configured engine URL causes the sentinel to POST the Safe transaction — attacker-controlled contents under A2 — to whatever host the redirect names, and to accept the verdict that comes back as its own.

Under A1 and A3 none of these is an escalation by itself, which is why this is Low: the operator sets the environment, and the engine is a trusted co-deployed component. They are filed as one cross-crate finding because the shared root cause is that neither client was ever configured, and because item 1 has a liveness consequence that does not depend on trusting anyone.

## Trigger

For item 1, no adversary is required and the trigger is ordinary: `api.cow.fi` becomes slow or black-holes a connection — a routine third-party availability event — while a Safe transaction whose shape reaches `CowChecker` is being verified. The checker's request never completes, the engine has no deadline of its own (basis row 5), and the security check never returns a verdict. The sentinel's own client eventually times out and maps the result to `CheckOutcome::Unknown` (`engine.rs:180-187`), which drops the request unanswered, so the observable outcome is a sentinel that abstains for as long as the third party is unwell. Note that the engine-side task is _not_ freed by the sentinel's timeout: nothing cancels it, so a sustained CoW outage accumulates stalled tasks.

For items 2 and 3 the trigger is a configuration or environment change rather than a message: setting `ALL_PROXY` in the pod environment, or an engine URL that answers 3xx.

## Considered and rejected

- **"The engine's own trust boundary makes redirects harmless."** Under A3 the engine is trusted, so the redirect leg is Informational — which is exactly how it is filed. It is included because the URL is operator-supplied config (`crates/sentinel/src/config.rs:58`, `pub engine: Url`) and the redirect target is not, so the set of hosts that can receive a proposal is larger than the set the operator configured.
- **"The CoW response is authenticated, so a hijacked CoW client cannot forge a verdict."** Correct and worth recording: the checker recomputes the EIP-712 order UID and rejects a response whose UID does not match the one requested (`crates/sentinel-engine/src/checkers/cow.rs:296`, `Ok(order) if order_uid.as_ref != &compute_order_uid(chain_id, &order)[..]`), and the engine analysis reaches the same conclusion (`analysis-sentinel-engine.md:415`). So the proxy/redirect concern on the CoW leg is availability, not verdict integrity. The timeout half stands regardless.
- **"`default-features = false` already narrows this."** It narrows the feature set (no default TLS backend, no charset handling); it does not change the client's redirect policy, its proxy handling or its lack of a default timeout, which are runtime defaults of `Client::new` rather than features (basis row 7).
- **"TLS pinning is missing."** Not filed. Pinning a public API's certificate is a defensible choice either way and there is no evidence the team intended it; the analysis mentions it (row 9) and it is left as an observation rather than promoted.
- **Ownership note.** `sentinel/engine.rs` is R7's file and `cow.rs` is R9's. This is filed cross-cutting because the defect is the identical omission at both sites and the remediation is a single shared convention; a reviewer looking at either file alone sees only half of it.

## Remediation options

1. Give the CoW client an explicit `ClientBuilder` with `.timeout(..)` and `.connect_timeout(..)` sized to the engine's own request budget, and pass it in through the existing `CowChecker::with_client` seam, which was clearly built for this. Cheapest fix and it closes the only leg with a no-adversary trigger.
2. Adopt one shared constructor for both crates — a `safenet_core::http::client` returning a `reqwest::Client` with a timeout, `redirect::Policy::none` and `.no_proxy` — so the policy is decided once and both call sites inherit it. Tradeoff: `no_proxy` breaks deployments that legitimately egress through a proxy, so it should be a config option rather than a hard-coded choice.
3. Enforce the caller's budget server-side: honour `x-request-timeout` at `api/mod.rs:48-50` (the TODO is already there and is a `known` item, `codebase-map.md:198`) by wrapping the check in `tokio::time::timeout`, so a hung upstream bounds one request rather than accumulating tasks.

Tests to add: a test that points `CowChecker` at a listener which accepts and never responds, and asserts the checker returns within the configured budget — impossible to write today because there is no budget to assert against.

### `E2` from this repo versus `I` about `reqwest` — the split the run requires

`reqwest 0.13.4`'s source is not on disk (baseline §1), so the three numbered items in the Claim are not of equal standing and the report must not present them as if they were.

**`E2`, established entirely from code in this checkout:**

- Both clients are constructed by `Client::new` with no `ClientBuilder` anywhere (rows 1, 3, 6).
- `ReqwestOrderApi::fetch_order` (`cow.rs:191-204`) is `self.client.get(...).send.await? .error_for_status?.json.await` — **no `.timeout(...)` on the builder and none on the request**. There is nothing in this repository that bounds that call.
- The sentinel's equivalent call _is_ bounded, at the request rather than the client (`engine.rs:156`, wired at `effect.rs:66`). The asymmetry the Claim leads with is therefore a fact about this repository, not an inference about `reqwest`.
- The engine imposes no server-side deadline that could substitute: the caller's budget is parsed and discarded (`api/mod.rs:48-50`) and the router carries only `TraceLayer` (`api/mod.rs:28-31`).

That is item 1 in full. It stands without any knowledge of `reqwest`'s defaults, and it is the only item with a trigger that needs no adversary and no configuration mistake.

**`I`, and unresolvable this run:** that `Client::new` honours `HTTP_PROXY`/`HTTPS_PROXY`/ `ALL_PROXY`, and that its default redirect policy follows up to ten hops. These are items 2 and 3 in their entirety. Basis row 8 says so explicitly and R10 does not dress them up — but the Claim's framing ("Three default behaviours follow") reads as three findings of one kind, and only one of the three is verifiable here. Row 7's observation that `default-features = false` narrows features and not runtime defaults is itself part of the same `I`.

I decline to settle items 2 and 3 from recollection of upstream documentation; that is precisely the move the brief classes as `H`.

### Overlap and canonical files

- **Item 1 duplicates `F-ENG-005`** (R8/C-ENG-A), whose Claim already states "neither outbound client has a timeout", names `CowChecker::new`, cites the same `let _ = timeout;`, and adds what this file lacks: that the crate does not take `tower` and takes `tower-http` with only the `trace` feature, so no `TimeoutLayer` or `ConcurrencyLimitLayer` is even compiled in, and that under A2 the attacker's own transaction fields choose which outbound call the engine makes. **`F-ENG-005` is canonical for the missing-timeout defect.** It is strictly the better file on that point and it also covers the alloy/RPC side, which this one does not.
- **Items 2 and 3 are canonical here.** The proxy-environment and redirect-policy concerns appear in no other finding, and they are genuinely cross-crate: the same unconfigured constructor in two crates, with one shared remediation (`safenet_core::http::client`, remediation 2).
- **`F-SEN-012` (R7) does not overlap.** It is about the sentinel making exactly one attempt and never re-asking after a `CheckOutcome::Unknown` — a retry-policy defect, downstream of whether a timeout exists. The two compose (a CoW stall consumes the sentinel's one attempt) and the report should say so, but neither subsumes the other.

Net: this file should be read as "the proxy and redirect defaults were never chosen", with item 1 cross-referenced to `F-ENG-005` rather than counted twice.

### One correction to the Trigger

The Trigger says a sustained CoW outage means "the engine-side task is _not_ freed by the sentinel's timeout: nothing cancels it, so ... stalled tasks" accumulate. The mechanism is right, but `F-ENG-007` (R8) establishes the adjacent fact that shutdown _drops_ the serve future rather than draining it — so the accumulation is bounded in practice by process restart rather than by anything in the request path. Immaterial to the verdict; worth not overstating in the report.

I wrote the control deliberately. A remediation check that only demonstrates the defect is half a check: if `.timeout` does not bound the call, the finding's fix is wrong and the fallback is a `tokio::time::timeout` wrapper at the call site, which cannot fail to bound it.

The 5.03 s runtime is itself the result: the first test wraps `api.fetch_order(&base_url, &order_uid)` in a 5 s `tokio::time::timeout` against a loopback listener that completes the TCP handshake and then holds the socket without ever answering, and it asserts the timeout **elapsed**. ### What that settles

Question 4 of `rust-audit/poc/UNRESOLVED-DEPENDENCY-QUESTIONS.md` — "can an un-timed `reqwest` request actually hang indefinitely?" — is answered **yes**, at least far past any budget the engine's own request deadline allows. `reqwest::Client::new` applies no request timeout and no connect timeout of its own; there is no hidden internal cap that would have re-scored this downwards. This is the question's first outcome row.

The failure mode needed is unremarkable: a server that accepts the connection and does not answer. That is an ordinary third-party availability event at `api.cow.fi`, not a network partition (which the OS would eventually reset) and not anything an attacker has to arrange.

The control result matters as much as the positive one: **the remediation works as written.** `CowChecker::with_client` (`crates/sentinel-engine/src/checkers/cow.rs:234`) already exists as the seam, so the fix is to build the client with a timeout and pass it there — no new API, no `tokio::time::timeout` wrapper needed at the call site.

### Scope of what is verified

This section verifies **item 1 only** — the missing timeout on the CoW client. The finding's other two legs (proxy environment variables honoured by default, and redirects followed by default) were not exercised and remain as filed at their original basis class; they need a different experiment and, unlike item 1, neither is a liveness question.

### Verdict

**Basis class: item 1 moves from `I` to `E1`.** Executed against the real private `ReqwestOrderApi`, with a control proving the fix.

**Severity: Low / Low — unchanged.** Under **A3** the engine is reached only by the co-deployed sentinel, and the consequence of a wedged CoW lookup is that `CowChecker` cannot produce a verdict. It does not produce a _wrong_ verdict. The reason this is not higher is the same reason it is worth fixing: the degradation is silent, which is `F-XC-010`'s complaint, verified in the same phase. `F-ENG-005` remains the canonical home for the severity call across the four findings that share this premise.

**Certainty: 80% → 94%.** Executed, with a control. The 6% is that the observed behaviour is "exceeds 5 s", which is what the test can assert; "indefinitely" is an extrapolation from the absence of any cap in the client construction rather than something a 5 s test can prove.

**Downstream:** this is the pivotal `I` leg for `F-ENG-005` (80%), `F-ENG-043` (74%), `F-CORE-011` (60%) and `F-CORE-039` (55%) as well. All four may now treat "an un-timed `reqwest` call can park past any budget" as `E1` rather than `I`, on this evidence.
