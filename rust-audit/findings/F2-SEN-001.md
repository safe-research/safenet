## Claim

The decision the sentinel commits to (`approve`, `reason`) exists only in the live FSM state after the engine resume, and that state is not snapshotted until the next log batch. Every restart rolls the FSM back to the earliest retained snapshot (`latest - max_reorg_depth`, default 5 blocks) and every live reorg rolls it back to the uncled block's parent. If that anchor predates the resume, the sentinel can no longer connect its own onchain `Committed` to a vote:

- **(a)** the anchor holds `WaitingForEngineCheck`, the proposal block is not replayed, so no effect is re-spawned; the replayed `Committed(self)` is discarded as "unexpected"; no resume ever arrives; the entry is dropped at `commit_deadline + 1` without a `Reveal`;
- **(b)** the proposal is replayed and a fresh effect is spawned, but `Committed(self)` is delivered before the new resume (deterministically when both sit in the same warp page, since a whole log batch is applied before any effect is spawned) and is discarded; the resume then starts a new `CollectingCommitments` with `self_committed: false`, which is dropped at `commit_deadline + 1`;
- **(c)** the re-run engine check answers differently (chain state moved, engine restarted, `abstain`): an `Unknown` drops the entry; a different `approve`/`reason` produces a `Reveal` whose hash no longer matches the onchain commitment (`InvalidReveal`).

In all three the commitment stays `PENDING` onchain while the bond is locked. Once any other sentinel reveals and someone finalizes, `slashAmount` is transferred to the protocol funds receiver and the remainder is never claimed because the entry is gone. Actual loss of bonded funds with no attacker required; an attacker who can trigger restarts or short reorgs weaponises it against every sentinel at once.

## Trigger

Default `max_reorg_depth = 5`. Blocks are numbered for clarity; `TransactionProposed` and `NewRequest` are emitted by the same `Consensus.proposeTransaction` call (contracts/src/Consensus.sol:264-266) and therefore arrive in the same log batch.

**Variant (a) — restart, anchor holds `WaitingForEngineCheck`, no effect re-spawned**

1. Block 100: proposal → snapshot 100 = `WaitingForEngineCheck { request: Some(..) }`; effect spawned (claim 8).
2. Engine answers after block 100's batch is committed: resume → `CollectingCommitments { self_committed: false }`; `ApproveToken` + `Commit` inserted into `transactions` (claim 10). Snapshot 100 still says `WaitingForEngineCheck` (claim 1).
3. Block 101 batch → snapshot 101 = `CollectingCommitments`. Block 102: `Committed(self)` → `self_committed = true`.
4. Process stops after processing block 105 (safe = 100; snapshots 100..=105 retained, claim 3).
5. Restart: `Uncle{101}` restores snapshot 100 (claim 2). Block 100 is not replayed, so no `EngineCheck` effect exists. Replay of 101.. delivers `Committed(self)` → discarded (claim 4).
6. No resume ever arrives (claim 5). At `NewBlock(commit_deadline + 1)` the entry is dropped (claim 7). No `Reveal` is ever emitted.
7. Onchain the commitment is `PENDING`; when another sentinel reveals and anyone finalizes, `slashAmount` leaves the bond (claim 11) and the remainder is never claimed because the request is untracked.

The window is any shutdown with `latest ∈ [N + 5, R + 4]`, where `N` is the proposal block and `R` the first block whose batch persisted the resume. With an engine that answers within a block it is one block wide per request; with an engine that takes `k` blocks it is `k` blocks wide. Sentinels commit to every request, so all requests in the window are hit together.

**Variant (b) — restart after ≥ 3 blocks of downtime, proposal within the last 4 blocks before shutdown**

Proposal at 101, `Committed(self)` at 103, shutdown after 105 (anchor 100), restart when latest = 110 (safe 105): `Uncle{101}`, `Warp{101..=105}`. The warp page carries `TransactionProposed@101`, `NewRequest@101`, `Committed(self)@103` in one `Logs` update: the proposal creates `WaitingForEngineCheck`, `NewRequest` stores the request, `Committed(self)` is discarded (claims 4, 8). Only then is the effect spawned; its resume yields `CollectingCommitments { self_committed: false }` (claim 6) and a duplicate `Commit` that reverts `AlreadyCommitted`. At `commit_deadline + 1` the entry is dropped (claim 7). Outcome as in (a). Without downtime the same ordering is the likely outcome of the unbiased select (claim 9): replayed blocks are queued, the effect needs an HTTP round trip plus the engine's own RPC work.

**Variant (c) — live reorg or restart where the re-run engine answers differently**

Same rollback as (b) but `Committed(self)` arrives after the new resume. If the engine now answers `abstain` or fails (claim 6) the entry is dropped; if it answers with a different `approve`/`reason` the state and the later `Reveal` carry the new pair while the onchain hash was computed from the old one → `InvalidReveal` (claim 12). A live reorg of depth `d ≤ max_reorg_depth` that uncles the resume block produces the same rollback without a restart.

## Considered and rejected

- "The stale-resume guard prevents harm": it prevents _state creation_ for an orphaned request (tests `stale_engine_check_resume_after_reorg_is_ignored` at service.rs:1928-1938 and `stale_engine_check_resume_does_not_disturb_an_already_advanced_request` at 2141-2157) but nothing reconciles a `Committed(self)` seen while the FSM does not yet know the vote.
- "The re-spawned effect resumes before the replayed `Committed`": impossible when both are in one log batch (claim 8); unlikely otherwise (claim 9). Either ordering that ends before `Committed(self)` is counted strands the request.
- "`approve_and_slash_amount` recovery catches it": it returns `None` for `WaitingForEngineCheck`/`WaitingForRequest` and for `CollectingCommitments { self_committed: false }` (crates/sentinel/src/state.rs:118-126), so the terminal-event handlers do not claim either, and no `Reveal` is emitted in any case.
- "A17 makes restarts out of scope": A17 excludes out-of-band database access. This is the service's own persistence ordering; the database is intact.
- "The snapshot at the anchor could already be `CollectingCommitments`": only if the resume was persisted at or before the anchor, i.e. `R ≤ latest - 5`; the trigger is precisely the complement.

## Remediation options

1. Persist the vote decision durably and outside the rollbackable snapshot at resume time (e.g. a `commitments(request_id, approve, reason, salt_hash)` table written in the same transaction as the queued `Commit`), and consult it when `Committed(self)` arrives in any pre-commit state. This mirrors the validator's non-rolled-back `SecretStore`. Tradeoff: a second persistence path to keep consistent.
2. Reconcile against the chain: on `Committed(self)` in any state other than `CollectingCommitments`, and on restart for every tracked request, read `getCommitment(id, self)` and, if `commitHash != 0`, derive the vote by hashing the two possible candidates (`(true, "")` and `(false, rule)` for the re-run engine's rule) against the stored hash. Tradeoff: a `deny` whose rule the re-run engine no longer returns cannot be reconstructed; combine with option 1.
3. Make restart replay effect-safe in core: snapshot resumes immediately (a `commit` after `handle_resume`) so the anchor can never predate a consumed resume. Tradeoff: one extra SQLite write per resume; does not cover live reorgs that uncle the resume block.

Tests to add: a `StateMachine`-level test that commits snapshot N with `WaitingForEngineCheck`, applies a resume, restarts the machine, replays `Committed(self)` and asserts a `Reveal` is still emitted at `commit_deadline + 1`; a flow test feeding `Committed(self)` before the resume; a flow test where the second resume differs from the first and asserting the `Reveal` matches the first commit hash.

## Re-validation at fe9e84c (R7Δ)

**Verdict: Still valid.** The mechanism is untouched by PR #914: `handle_committed` still discards `Committed(self)` in every state but `CollectingCommitments` (`crates/sentinel/src/service.rs:307-319`, unchanged), a resume is still consumed only from `WaitingForEngineCheck` (`156-171`, unchanged), `Unknown` still drops the entry and a verdict still starts `CollectingCommitments { self_committed: false }` (`176-179`, `214-224`, unchanged). What the delta changes is only _when_ the two pre-commit states expire:

- `WaitingForEngineCheck { request: Some }` is now dropped at `block == commit_deadline` instead of `commit_deadline + 1` (`service.rs:407-412`: `block < request.as_ref().map_or(*deadline, |request| request.commit_deadline)`), so variant (a) loses its entry one block earlier — the replayed `Committed(self)` is discarded in exactly the same way, and no `Reveal` is ever emitted.
- `CollectingCommitments { self_committed: false }` is still dropped at `commit_deadline + 1` (`service.rs:433-435`: `if !*self_committed { return block <= *commit_deadline; }`), so variants (b) and (c) are unchanged. The extra block of pending state does not rescue (b): the own `Committed` was already delivered (and discarded) before the resume, so nothing new arrives in that block.
