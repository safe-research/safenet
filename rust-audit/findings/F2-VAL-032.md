## Claim

`handle_sign` removes the signing session keyed by `event.message` before it checks that the event's group matches the session's group. The match arm `(None, Some(SigningState::WaitingForRequest { .. }))` neither re-inserts the session nor carries the `group_id == event.gid` guard of the first arm, and it is reached whenever `observe` yields `None` - which is always the case when `event.gid` is a group this validator does not track (`epochs.find(..)` returns `None`).

`FROSTCoordinator.keyGen` is permissionless (any participant root, count and threshold with `threshold > 1`, any context) and `sign` only requires a FINALIZED group and a non-zero message. An attacker therefore finalises a 2-of-2 group `G_att` under two of its own keys once (about six transactions) and can afterwards emit `Sign(G_att, m)` for any message `m` of its choosing. The validator watches the coordinator address and dispatches every `Sign` event to `handle_sign` regardless of `gid`.

Honest validators hold a `WaitingForRequest` session for a message exactly in the windows where the legitimate `Coordinator.sign` is _not_ in the same transaction as the event that created the session: after every signing timeout (`restart_signing_ceremony` and the `WaitingForRequest` deadline branch), for at least one block, at a block number that is public and deterministic (`deadline = event block + signing_timeout`). One attacker transaction mined in that block makes every honest validator drop the session simultaneously; the legitimate `Sign` that follows hits the `(_, None)` arm and is ignored, and nobody reveals a nonce. For an epoch rollover the message is only recreated by a later key-generation confirmation (Basis 9), so one cheap transaction per timed-out rollover blocks validator-set rotation indefinitely; a malicious validator inside the fault bound forces the timeout at will by withholding its reveal, which the protocol otherwise tolerates. For transactions, the proposal has to be re-proposed by the sentinel before it can be attested. The same arm is also the endpoint of the known H6 vector: pushing the group's sequence past the last linked chunk with junk `sign` calls on the _legitimate_ group makes `observe` return `None` for the real request and drops it without any timeout.

## Trigger

Rollover blocking with one malicious validator `M` (inside the fault bound) and one attacker EOA pair (may be `M`'s operator):

0. One-off: `keyGen(root_att, 2, 2, ctx)`, two `keyGenCommit`, two `keyGenSecretShare`, two `keyGenConfirm` from the attacker's two keys -> `G_att` FINALIZED (Basis 6, 7).
1. The last DKG confirmation for epoch `e+1` lands at block `B`; every honest validator creates `WaitingForRequest{m_rollover, responsible: confirmer}` (Basis 9); the confirmer's callback signs in the same transaction, so `Sign(G, m)` follows immediately and honest validators move to `CollectNonceCommitments{deadline: B + 6}` and reveal.
2. `M` does not reveal. At `NewBlock(B + 6)` every honest validator runs `handle_signing_timeouts`: `signers.retain(revealed)` removes `M`; `restart_signing_ceremony` yields `WaitingForRequest{responsible: H}` where `H` is the last honest revealer; only `H` queues `Action::Sign`, to be mined at `B + 7` or later (Basis 8).
3. The attacker, knowing `B + 6` in advance, has `sign(G_att, m_rollover)` mined in block `B + 6` (or ahead of `H`'s transaction in `B + 7`). `Logs{B + 6}` deliver `Sign(attacker, G_att, m_rollover, sid', seq')`: `epochs.find(G_att)` is `None` -> `nonce = None`; `state.signing.remove(m_rollover)` is `Some(WaitingForRequest{..})` -> Basis 3 arm -> session gone at every honest validator.
4. `H`'s `Sign(G, m_rollover, sid'', s)` lands: `(Some(nonce), None)` -> Basis 4 second arm -> ignored. No reveal, no shares, no `EpochStaged`. The rollover message is not recreated (Basis 9); the network stays on epoch `e`. Cost: one ~60k-gas transaction per DKG (default one per 1440 blocks).

Transaction variant: any proposal whose ceremony times out once (a slow validator, an RPC hiccup, F2-VAL-030) is killed the same way at its restart; alternatively the attacker pushes the legitimate group's sequence past the last linked chunk with junk `sign(G, x)` calls right before a proposal (H6) so the real `Sign` itself hits the `None` arm. The H6 cost is bounded by the validators' remaining capacity, which is public (`Preprocess` events, `groupSignCount`), so the attacker waits until it is close to the 100-nonce top-up threshold.

## Considered and rejected

- The group-id guard on the first arm (Basis 2) does not protect the `None` arm; the `(_, Some(other))` arm re-inserts other states but `WaitingForRequest` with `None` is matched earlier (Basis 3 precedes Basis 4 in the match).
- `observe` is not called for the sybil group, so there is no sequence side effect that would make the drop "correct".
- VAL-H2 (events not bound to the emitting address) is not needed: the real coordinator emits the event. Fixing H2 would not fix this.
- The sentinel might re-propose a dropped transaction (R7's area); rollovers have no equivalent.
- `WaitingForRequest` with `responsible: None` is dropped at its own deadline anyway (sign.rs:586-590), but that deadline is a further `signing_timeout` away; the attacker collapses the window to zero.

## Remediation options

1. Move the group check before the removal: look the session up with `get`, return early (re-insert nothing) unless `session.group_id == event.gid`, and only then `remove` and act. For the `None` case (unlinked chunk) keep the session in `WaitingForRequest` so that a later restart can still succeed; the existing deadline drops it if nothing happens. Tradeoff: none of substance.
2. Ignore `Sign` events for groups absent from `state.epochs` at the top of `handle_sign` (cheap and closes the sybil variant by itself).
3. Contract side (reference only, out of scope for this audit): restrict `sign` to group members or to the `Consensus` contract.

Tests to add: a pure transition test that puts a session in `WaitingForRequest` for group `G`, applies `Sign{gid: G_other, message}` and asserts the session is unchanged; a test for the unlinked-chunk case asserting the session survives; an Anvil flow with a second finalised group. No code is committed.

The `(_, Some(other))` arm that re-inserts is _after_ it in the match, so `WaitingForRequest+None` is matched first (verified ordering). No `H` rows.

Who can emit `Sign` (per the reference contracts, as the brief asks): **anyone**. `FROSTCoordinator.keyGen` is permissionless (`require(count >= threshold && threshold > 1)`, any participant root/context, FROSTCoordinator.sol:349-361); `sign(gid, message)` requires only a FINALIZED group and `message != 0` and emits `Sign` for that `gid` (536-548). So an attacker finalises a self-owned 2-of-2 group once, then calls `sign(G_att, m)` with any `m` — including a victim's public rollover message hash. There is no `onlyMember`/`onlyConsensus` restriction on `sign`. Confirmed against `contracts/src`.

The window is real: after a signing timeout `restart_signing_ceremony`/the `WaitingForRequest` deadline branch leave every honest validator in `WaitingForRequest` at a deterministic block, with the legitimate `Sign` submitted as a _separate_ transaction by the responsible party (sign.rs:522-561, 608-615). A rollover message is recreated only by a fresh DKG confirmation (keygen.rs:529-548), so one cheap attacker `sign(G_att, m_rollover)` per timed-out rollover blocks rotation, and a single malicious validator (inside the fault bound) forces the timeout at will by withholding its reveal. The initial proposal has no window (event + `sign` in one tx, Consensus.sol:222-223/264-265) — verified — so only restarts are exposed, exactly as claimed. The H6 variant (junk `sign(G,x)` on the _legitimate_ group pushing `sequence` past the last linked chunk so `observe` returns `None` for the real request) reaches the same drop arm.
