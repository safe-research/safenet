## Claim

The validator asks the indexer for logs from `[consensus, coordinator] ++ config.validator.oracles` with the union of every watched `topic0`, decodes each log by `topic0` alone, and dispatches every `Coordinator::*` and `Consensus::*` event without consulting `log.address` (only `OracleResult` receives it). Any contract in the operator's `oracles` allow-list - a trust relationship the configuration describes as "whose results the validator honors" - can therefore emit `KeyGenComplained`, `Sign`, `KeyGenCommitted`, `SignRevealedNonces`, `TransactionProposed`, `EpochStaged`, ... and the validator treats them as genuine protocol messages. Concretely: (a) a forged `KeyGenComplained{accused: me}` during a DKG makes the validator sign and broadcast `keyGenComplaintResponse(gid, plaintiff, f_me(plaintiff))` - the transaction reverts onchain (`NotComplaining`) but its calldata, a plaintext evaluation of the validator's secret polynomial, is public; `t-1` such events with distinct plaintiffs plus the attacker's own legitimate share (if it is a member) recover the validator's key share; (b) a forged `Sign` with a huge `sequence` advances `next_sequence`, prunes every linked chunk and plants a reservation so high that `available()` never drops below the top-up threshold again, so the validator stops signing for the rest of the epoch; (c) a single _malformed_ log with a watched `topic0` from the oracle address makes `decode_and_sort` fail for that block and the driver retries the same fetch forever, halting the validator at that block until the oracle is removed from the config. The escalation is from "can approve transactions for Safes that opted into this oracle" to "controls the validator's entire protocol view".

## Trigger

Precondition: an address `O` in `[validator] oracles` whose code is attacker-controlled (a malicious oracle, or a legitimate upgradeable oracle whose admin key is compromised). All `Coordinator`/`Consensus` event signatures are public (`bindings.rs`), so `O` can emit any of them with arbitrary fields.

1. Share leak: while the validator is in `CollectingShares`/`CollectingConfirmations` for group `gid`, `O` emits `KeyGenComplained(gid, plaintiff = P_j, accused = <validator>, false)` for `t-1` distinct addresses `P_j` (staying below `complaint.total >= threshold`, keygen.rs:722). Each event produces `Action::KeyGenComplaintResponse{secret_share: f_me(P_j)}` (row 5), which is signed and broadcast (row 6) and reverts (row 7) with the scalar in public calldata. With the attacker's own legitimately received share `f_me(A)` this is `t` points of `f_me`. Repeating per honest validator whose config lists `O` yields their shares too.
2. Liveness kill: `O` emits `Sign(any, gid, m, sid, sequence = 2^63)`. `observe` sets `next_sequence = 2^63 + 1` and `split_off` drops every linked chunk (row 8); the next block's top-up reserves chunk `2^53` (`expected_chunk`), whose `None` entry is never filled because the contract assigns the real next chunk to the resulting `preprocess`; `available()` then stays >= 1024 (row 9), so no further top-up ever fires and, once the one re-linked chunk is consumed, the validator ignores every `Sign` for the rest of the epoch ("not participating in signing request without a canonically linked nonce", sign.rs:106-114).
3. Indexer halt: `O` emits a log with `topic0 = Coordinator::Sign::SIGNATURE_HASH` and 5 bytes of data. The fetch for that block returns `Error::DecodeLog` (row 10); the driver retries the same block every 100 ms (row 11); a restart re-fetches the same block. Only removing `O` from the config restores progress.

## Considered and rejected

- "Oracles are operator-trusted (A1), so this is by design." The configuration and handbook scope that trust to approval results; nothing tells an operator that listing an oracle grants it authority over the DKG and signing state machine. Compromise of one oracle should cost the Safes that use it, not every validator's key share and liveness. The severity is proposed under that precondition.
- Could the Consensus contract itself emit a Coordinator-shaped event? No relevant path found; `Consensus.sol` emits only its own events. The precondition is a third-party contract in `oracles`.
- `OracleResult` _is_ bound: `handle_oracle_result` compares the session's oracle with `log.address` (crates/validator/src/state/sign.rs:180-189, `}) if expected == oracle && event.approved => {`). This is the only guarded handler, which shows the mechanism was available.
- Does the transaction queue simulate and drop reverting transactions? No: `submit_transaction` (row 6) signs and sends with the encoder's fixed gas; no `eth_call`/`eth_estimateGas` anywhere in `crates/core/src/tx/mod.rs`.
- `fallible_events` (events.rs:89-91) does not help scenario 3: it applies to query failures in `MultipleQueries`, and `decode_and_sort` runs on the concatenated result afterwards (line 468).
- `as u16` truncation of `commitments.len()` (keygen.rs:196) becomes reachable with injected `KeyGenCommitted` events from non-member addresses (a valid PoK is enough, keygen.rs:171-175) - a further DoS variant (the round never observes `len == count`), not separately filed.

## Remediation options

1. Bind every dispatched event to its expected emitter in `apply_transition`: carry `coordinator` and `consensus` in `state::Transition` (the service already knows both, `service/mod.rs:102-114`) and drop `Event::Coordinator`/`Event::Consensus` logs whose `log.address` differs; likewise require `Event::Oracle` logs to come from `config.oracles`. Small, local change; add a `tracing::warn!` for dropped logs.
2. In core, make address binding structural: let `watcher_events!` associate each ABI variant with an address set and have `decode_and_sort` skip (not fail on) logs whose `(address, topic0)` pair is not registered; treat undecodable logs from non-protocol addresses as ignorable rather than fatal. Fixes all services and scenario 3, at the cost of a core API change.
3. Independently of 1/2, make `handle_sign` reject sequences that are not `next_sequence`-adjacent (or beyond the contract's actual `sequence`, readable via `eth_call`) before mutating `NonceState`, and never plant reservations more than one chunk ahead.

Tests to add: a state-machine test feeding a `Coordinator::KeyGenComplained` log with `address = oracle` and asserting no `KeyGenComplaintResponse` action; an indexer test with a malformed log from a watched non-protocol address asserting the batch is delivered without it. No code is committed.

## Critic (C2-VAL-B)

Traced the watched-address set, the `watcher_events!` decode and the dispatch myself first.

**"Watched address" and reachability of an attacker contract (per the brief):** `watched = [consensus, coordinator] ++ config.validator.oracles` (main.rs:56-57). consensus/coordinator are resolved onchain and trusted; an attacker-deployed contract is watched **only if the operator lists it in `[validator] oracles`**. The config/handbook scope that trust to _approval results_ ("whose results the validator honors"), not to protocol-event injection. So the precondition is a **malicious or compromised allow-listed oracle** (a third-party contract, or a legit upgradeable one whose admin key is compromised) — realistic, since oracles are by definition external, but not a bare-internet attacker.

Per-claim verdicts: rows 1-12 **Supported**. The filter and dispatch ignore `log.address` for every `Coordinator::*`/`Consensus::*` event; only `OracleResult` is bound (state/mod.rs:458-460, `handle_oracle_result` compares `expected == oracle`). Scenario (a): `handle_key_gen_complained` responds with `reveal_secret_share` calldata when `event.accused == self.account` with no origin check (keygen.rs:733-747; `reveal_secret_share` returns the plaintext scalar, frost/keygen.rs:420-428); the queue signs+sends with fixed gas and **no simulation** (tx/mod.rs:241-265 — I grepped, there is no `estimate_gas`/`eth_call`/`.call()` in the queue), so a reverting response still publishes the scalar. Scenario (c): a truncated (5-byte) log with a watched `topic0` fails `abi_decode` in `decode_and_sort` -> `Error::DecodeLog` -> fatal for the batch -> retried forever (events.rs:491-510, driver.rs:208-227). No `H` rows.

**Coverage-Critic point (out-of-range `sol!` enum -> `__Invalid`, not `DecodeLog`):** I checked alloy 1.6.0 (`alloy-sol-macro-expander-1.6.0/src/expand/enum.rs:56-66`): out-of-range `u8` enum values detokenize to `__Invalid = u8::MAX` via `unwrap_or(Self::__Invalid)`, so an out-of-range `Operation` in a `TransactionProposed` **decodes, it does not error**. F2-VAL-061 does **not** rely on the opposite — scenario (c) uses a _truncated data blob_ (which genuinely fails `abi_decode_data_validate`), and rejected-hypothesis #10 already states "Solidity cannot emit an out-of-range enum."
