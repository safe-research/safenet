## Claim

`handle_committed` counts a `Committed` event only while the request is `CollectingCommitments`. A commitment from another sentinel that lands while this sentinel's engine check is still running (state `WaitingForEngineCheck` with the onchain `request` already stored) is logged and dropped, and `commit_vote` then starts the tally at 0. The local `committed_count` is then lower than the oracle's `committedCount`. The early-finalize check in `handle_revealed` compares the reveals it has seen with this low count, so it fires before every committer has revealed:

- Variant A (normal operation, no restart, no reorg, no attacker): the other sentinel's `Revealed` log is ordered before ours. `finalize` sees `self_revealed == false` and `revealed_count > 0` and drops the request. Our `Reveal` transaction is already queued and lands, so our bond is not slashed and the request resolves onchain, but the state machine no longer tracks it and never sends `Claim`. `SentinelOracle.claim` pays only `msg.sender`'s own commitment, so the whole bond (800 USDC.e at the Aegis production parameters) plus the fee reward stay in the oracle until the operator claims by hand.
- Variant B: our own `Revealed` log comes first. `finalize` emits `Finalize` and moves to `WaitingForOutcome`. Onchain fewer commitments are revealed than were made and the reveal window is still open, so `finalize()` reverts with `FinalizeTooEarly`. `WaitingForOutcome` has no deadline and no retry, and the queue does not check receipts, so the request stays there until a third party finalizes it. If every honest sentinel undercounted the same commitment (for example one made in the proposal's own block) and its owner never reveals, nobody finalizes after the reveal deadline: the request stays `PENDING`, the validators never receive an `OracleResult`, and every honest bond stays locked until someone finalizes by hand.

Each occurrence of variant A takes 800 USDC.e out of the sentinel's working balance with no automatic recovery. Once the balance no longer covers a bond, the sentinel's `Commit` reverts in `safeTransferFrom` and it stops voting.

## Trigger

Aegis production parameters: commit window 6, reveal window 6, fee 0.40 USDC.e, bond 2000x (800 USDC.e), slashing 1x (0.40 USDC.e), Gnosis 5 s blocks, block visibility about 1.6 s after slot time.

Variant A, two honest sentinels F (fast engine) and S (slow engine, this node):

1. Block P: `proposeTransaction` emits `TransactionProposed` and `NewRequest`. S moves to `WaitingForEngineCheck { request: Some(..) }` and starts its engine check (timeout 18.75 s with the sample `voting_window` 6).
2. F's engine answers within a few seconds; its `ApproveToken` and `Commit` land in P+1 or P+2. S processes that block about 6.6 s or 11.6 s after slot P; if its own check is still running then, it logs "ignoring unexpected commitment".
3. S's engine answers; `commit_vote` sets `committed_count: 0`; S's commitment lands and the tally becomes 1. Onchain `committedCount` is 2.
4. At P+7 (first block past `commitDeadline` P+6) both queue `Reveal`. F's reveal is ordered before S's in the block (or lands a block earlier).
5. S processes F's `Revealed`: `revealed_count` 1 is not below `committed_count` 1, `finalize` runs, `self_revealed` is false, the request is dropped. S's own `Revealed` and the `OracleResult` emitted by its reveal (the last reveal finalizes onchain, `SentinelOracle.sol:256-258`) hit an untracked request. No `Claim` is ever queued.

Variant B: as above, but S's reveal is ordered first, or a committer never reveals. A malicious active sentinel can force the undercount on every honest sentinel deterministically by committing in the proposal's block: it proposes a transaction itself and sends `commit` at its next nonce in the same block, or batches both through its own EIP-7702 executor delegation. It then withholds its reveal. Every honest sentinel early-finalizes after the honest reveals, each `Finalize` reverts with `FinalizeTooEarly`, and all stay in `WaitingForOutcome`. The attacker can release the request at any time by calling `finalize()` itself, losing its 0.40 USDC.e slash.

## Considered and rejected

- Is the undercount the known #961 item? The trigger is the same code path (a commitment ignored in `WaitingForEngineCheck`), so the finding is tagged `known`. What this adds: #961 and #973 describe our own commitment being ignored after a restart or reorg, so no reveal follows. Here other sentinels' commitments are ignored in normal operation; our reveal does land and the bond is not slashed, yet it is never claimed (variant A), or the request waits forever after a reverted `Finalize` (variant B). The early-finalize check and the `finalize` guard are the mechanism, and neither is mentioned in #961 or #973.
- Does a later event re-track the request? No. After the drop, `handle_revealed`, `handle_oracle_result`, `handle_dispute_triggered` and `handle_request_timed_out` all return early on an untracked id (service.rs:349-355, 824-830, 771-777, 715-721).
- Does someone else claim for us? No. `claim` uses `msg.sender`'s commitment (Basis 10).
- Does the tx queue retry a reverted `Finalize`? No receipt check exists; an executed nonce is marked done from the account nonce (map section 1.2, step 9), so the reverted call is final. `Finalize` has `expires_at: None` but it is never re-sent.
- Is a one-block engine latency gap realistic? The engine timeout is 18.75 s, which is the budget for slow checks; a gap of one or two blocks (about 5 to 10 s) between two sentinels' engine latencies produces the undercount. Not measured on the testnet; the PoC drives the state machine directly.
- Reentrancy, reorgs: not involved.
- Introduced since run 2? No. The same `handle_committed`, early-finalize check and guard exist at `fe9e84c` (`git show fe9e84c:crates/sentinel/src/service.rs`, lines 307-320, 372, 651-655).

## Remediation options

1. Count commitments in every state that can see them: keep a `committed` set (addresses) and `self_committed` in `WaitingForEngineCheck` (or in `Request`) and carry them into `CollectingCommitments` in `commit_vote`. A set also makes replays idempotent for other sentinels' logs, which the current self-only guard does not. Small state growth.
2. Never drop a request this sentinel has committed to: in `finalize`, when `!self_revealed` but the request reached `CollectingVotes` (so `self_committed` was true), move to an outcome-waiting state without sending `Finalize`, so the eventual `OracleResult`, `DisputeTriggered` or `RequestTimedOut` leads to `Claim` (the handlers already support the `RevealMissed` outcome).
3. Give `WaitingForOutcome` a block deadline (for example `reveal_deadline + k`) after which `Finalize` is re-sent; a duplicate reverts harmlessly with `RequestNotPending`.
4. Optionally drop the sentinel's own early `Finalize`: onchain `reveal` already finalizes when the last commitment is revealed (`SentinelOracle.sol:256-258`), so with an accurate tally that `Finalize` always reverts.

Tests to add: flow tests with a `Committed` event during `WaitingForEngineCheck` and both reveal orders, and one where a committer never reveals; the four tests in `rust-audit/state/run3/logs/R8-sentinel-bond-poc.txt` can be reused. No code is committed.
