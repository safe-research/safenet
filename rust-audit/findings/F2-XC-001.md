## Claim

Both binaries load the TOML configuration and propagate any failure out of `main` with `?`. `main` returns `Result<(), Box<dyn Error>>`, so Rust's `Termination` implementation prints the error with `{:?}`. The `config::Error::Parse` variant wraps `toml::de::Error`, whose derived `Debug` includes its `input` field: the complete text of the configuration file. Every deserialization failure, whatever its cause and wherever it is located (an unknown key, a misspelt table name, a `0` for a `NonZeroU64`, a malformed value), therefore writes the entire file, including `signer = "0x<32-byte private key>"`, to the process's stderr.

Container runtimes capture stderr together with stdout; the handbooks tell operators to diagnose problems with `docker logs --follow` (`docs/validator-handbook.md:113-119`, `docs/sentinel-handbook.md:79-85`), and in practice logs are shipped to aggregation systems with broader access and longer retention than the configuration file itself. The disclosed key is the service's onchain identity: the validator's consensus account (able to submit commitments, shares, complaints and attestations in its name) or the sentinel's bond-committing account, plus whatever gas and fee-token funds it holds.

The trigger is an operator mistake in the configuration file, so exploitation needs a malformed config plus read access to the logs; on the Section 8 scale a signer-key leak is Critical, but given the operator-error trigger and the log-access requirement I rate it Medium.

## Trigger

Any configuration file that fails deserialization: the E1 runs used an unknown top-level key, a misspelt `[transaction]` table, an unknown key inside `[index]`, `blocks_per_epoch = 0` and a 31-byte `signer`. `rpc` in every run pointed at loopback (`http://127.0.0.1:9`), `database = "sqlite::memory:"`.

## Considered and rejected

- "Switching to `Display` fixes it": no. `Display` prints the source line at the error span with a caret (claim 7); when the error is on the `signer` line (E1 `val-bad-signer`, `keys: ["signer"], span: Some(36..102)`) the line containing the key is printed. A fix must strip the input, not just change the formatter.
- "stderr is not collected": docker, podman and Kubernetes capture both streams; the handbook's own debugging step is `docker logs`.
- "The tracing JSON logger redacts": it is not involved; the output comes from Rust's `Termination` impl after `main` returns, before or independently of any subscriber.
- Runtime `Debug` of `Config` itself: `Signer`'s manual `Debug` prints only the address (`crates/core/src/tx/signer.rs:96-100`), and `Config` is only logged as `config_file = %path` (`main.rs:43`), so the parsed struct is not the leak; the raw text is.

## Remediation options

1. Stop propagating `toml::de::Error` out of `Config::load`: convert it to an own error carrying only the message, key path and line/column (the error exposes these), and make `main` print errors with `Display` (`eprintln!("{err}")` or `tracing::error!(%err)`) followed by `std::process::exit(1)`, never via `Result` from `main`. Small change, no behaviour change on success.
2. Take the private key out of the TOML text altogether (environment variable or `signer_file` path read into a `Zeroizing` buffer; the handbook already plans KMS support), so no parser buffer or parser error can contain it. Larger change; also addresses F2-XC-007.
3. Defence in depth: read the file into `zeroize::Zeroizing<String>` and audit every top-level error path for payload-bearing `Debug` output.

Tests to add: a test that feeds a malformed config containing a recognisable dummy key and asserts the rendered error text does not contain it (both `Display` and whatever `main` prints).

**Severity: Medium (R8) / High (C2-XC).** The disclosed secret is the service's signer key, Section 8's Critical class ("leaks … signer keys"). It is not Critical because two preconditions are required — a malformed configuration and a reader of stderr or of wherever it is shipped — and neither is attacker-controlled. It is above Medium because (i) the trigger is the single most common operator action, editing a TOML file, and R8's E1 shows any deserialisation error anywhere in the file fires it; (ii) the sink is exactly the diagnostic channel both handbooks direct operators to, which in container deployments flows into shipped log storage and support tickets with an audience and retention far wider than the configuration file's ACL — A1's "plaintext secrets at rest" covers the file, not its replication into logs; (iii) the consequence is full control of the validator's onchain identity (commitments, shares, complaints, attestations in its name) or of the sentinel's bond account and funds. Remediation check: option 1 is sound and minimal. `toml::de::Error::set_input` is public (`de/error.rs:78-80`), so `Config::load` can call `err.set_input(None)` before propagating as an interim fix; with `input` cleared, `Display` also drops the source line (`de/error.rs:119`), which removes claim 7's residual. Printing with `Display` alone is not sufficient, as R8 says.

**Certainty: 95%, unchanged** — already E1 on both binaries and Critic Confirmed; a fifth execution adds no evidence class. **Severity Medium (R8) / High (C2-XC) stands** for the Critic's reasons. A16/A17 not involved.

**Remediation check.** Option 1 is sound and minimal: `toml::de::Error::set_input` is public in the pinned `toml 1.1.2` (`de/error.rs:78-80`), so `Config::load` can strip the document before propagating, after which both `Debug` and `Display` (`de/error.rs:119`) print message, key path and span only; print from `main` with `Display` and exit non-zero explicitly. It changes nothing on the success path. Option 2 (key out of the TOML — env var or `signer_file` into a `Zeroizing` buffer) is sound and also removes the parser buffer from the picture; larger. Option 3 is defence in depth. None touches the runtime contract or the Solidity. Not compiled.
