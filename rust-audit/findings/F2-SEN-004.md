Audited commit: `3ec8bc5`.

## Claim

The contract now emits `DisputeTriggered(requestId, deadline)` precisely so that a participant knows when the permissionless `timeoutArbitration` becomes callable. The sentinel decodes the field and ignores it: `handle_dispute_triggered` stores only `approve`/`slash_amount`, `WaitingForDisputeResolution` carries no deadline, `handle_block_advance` retains it forever, and there is no `timeoutArbitration` binding or action. `WaitingForOutcome` is likewise retained unconditionally. Consequences:

- If the arbitrator never rules (or rules only for some requests), the sentinel's bond stays locked until some third party calls `timeoutArbitration`, although the sentinel is the party with the incentive and the deadline in hand. The same applies to a `Finalize` that reverted (F2-SEN-002): nobody re-finalizes.
- Every stuck entry is serialised into every subsequent per-block snapshot (`State` is one JSON document, `INSERT … ON CONFLICT` per block), so state growth and per-block write cost increase monotonically with the number of unresolved disputes over the lifetime of the database.

## Trigger

1. A request ends disputed: `DisputeTriggered(id, deadline = B + ARBITRATION_TIMEOUT)` → `WaitingForDisputeResolution { approve, slash_amount }` (claim 2).
2. The arbitrator does not rule. Block `deadline + 1` passes; `timeoutArbitration(id)` is now callable by anyone (claim 5).
3. The sentinel does nothing (claims 1, 3, 4). Its bond (`bondTarget`, returnable in full) stays in the contract; the entry is re-serialised in every block's snapshot (claim 7) indefinitely.
4. Variant: our `Finalize` reverted (`FinalizeTooEarly`, F2-SEN-002) or was never mined; `WaitingForOutcome` is retained forever and no second `Finalize` is emitted.

## Considered and rejected

- "PR #883 deferred this deliberately": acknowledged in the code comments, but at the audited commit the deadline is on the wire and unused, and bonded funds depend on a third party's goodwill. Recorded as a defect with the deferral noted.
- "Snapshot growth is negligible": per entry it is, but unbounded retention in a document that is rewritten every block is the only unbounded growth in the sentinel's persisted state.

## Remediation options

1. Store `deadline` in `WaitingForDisputeResolution` and add a `TimeoutArbitration { id }` action emitted at `deadline + 1` (binding `timeoutArbitration(bytes32)`), leaving the entry in place until `ArbitrationTimedOut`/`DisputeResolved` arrives. Duplicate calls from several sentinels revert harmlessly (`RequestNotFrozen`).
2. Give `WaitingForOutcome` a deadline (`reveal_deadline + 1` when known, else a configured bound) that re-emits `Finalize`.
3. As a backstop, expire both states after a generous bound (e.g. `2 × ARBITRATION_TIMEOUT`) with an `error!` log so the operator claims manually.

Tests to add: flow test asserting `TimeoutArbitration` is emitted at `deadline + 1` and that `ArbitrationTimedOut` still produces `Claim`.
