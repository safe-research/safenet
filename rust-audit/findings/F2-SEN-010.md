## Claim

PR #914 moves the `CollectingCommitments → CollectingVotes` transition one block earlier, to `Message::NewBlock(commit_deadline)`, so that the `Reveal` can be submitted as soon as the commit window is over. The core state machine applies `NewBlock(n)` _before_ block `n`'s logs. The transition snapshots `committed_count` and, once in `CollectingVotes`, `handle_committed` discards every `Committed` log as "unexpected". Consequently every commitment mined in block `commitDeadline` itself — which the contract accepts (`block.number <= commitDeadline`) — is never counted by any sentinel whose own commit landed earlier. At `3ec8bc5` the transition ran at `NewBlock(commit_deadline + 1)`, after those logs, and this undercount did not exist.

The undercount feeds the early-finalize rule `revealed_count >= committed_count` (F2-SEN-002's mechanism) and produces, per affected sentinel, one of:

1. **Bond and fee never claimed.** If the reveals of the _counted_ committers are observed before our own, `finalize()` runs with `self_revealed == false` and at least one reveal, removes the entry and emits nothing. Our queued `Reveal` still lands, the request resolves in our favour, and the later `OracleResult` hits an untracked id: bond and fee share stay in the contract until someone calls `claim()` by hand. No metric, no log above `warn`.
2. **Reverted `Finalize`, then parked forever.** If our reveal is among the counted ones, `Finalize` is emitted while onchain `revealedCount < committedCount` and `block <= revealDeadline`: it reverts `FinalizeTooEarly`, the FSM sits in `WaitingForOutcome` with no deadline and no retry (F2-SEN-004), and the request is resolved only if a sentinel that did count everything (one whose own commit was in the deadline block, whose transition is deferred) finalizes, or a third party does.

Adversarial form: a registered sentinel that places its `commit` in block `commitDeadline` (trivially timed — submit when the head is `commitDeadline − 1`) and never reveals makes every honest sentinel undercount by one on every request; when the last honest reveal lands they all emit `Finalize` early, all revert, all park, and nobody finalizes after `revealDeadline`: no `OracleResult`, every honest bond locked, until manual intervention. This is F2-SEN-002's stall without the need to beat any engine, and without the same-block-as-proposal placement.

## Trigger

Terms as in the crate's own tests: `commit_deadline = 20`, `reveal_deadline = 40`; sentinels `H` (this software, commits early) and `O`. The sequence is the existing test `flow_reveals_on_the_commit_deadline_block` (`service.rs:2164-2240`) plus one log.

1. Block 1 proposal, engine `Approved`, block 5 `NewRequest`, block 6 `Committed(H)` → `CollectingCommitments { committed_count: 1, self_committed: true }`.
2. `NewBlock(20)` → `20 < 20` is false, `self_committed` is true → `Reveal` emitted, `CollectingVotes { committed_count: 1, revealed_count: 0, self_revealed: false }` (claim 1; asserted verbatim by the test at `2222-2234`).
3. `log(20, Committed(O))` — `O`'s commit was mined in block 20, which the contract accepts (claim 6). `handle_committed` finds `CollectingVotes` → "ignoring unexpected commitment" (claim 5). Onchain `committedCount = 2`, local `committed_count = 1`.
4. `NewBlock(21)`. Both reveals are submitted against head 20 and land in block 21 or 22.
   - **Outcome 1:** `log(21, Revealed(O))` observed first → `revealed_count = 1 >= 1` (claim 7) → `finalize()` with `self_revealed == false`, `timed_out == false` → entry removed, no action (claim 8). `log(22, Revealed(H))` → "ignoring reveal for an untracked request". `O` (or a third party) finalizes; `OracleResult` → ignored (claim 9). `H` never claims.
   - **Outcome 2:** `log(21, Revealed(H))` observed first → `self_revealed = true`, `1 >= 1` → `Finalize` emitted, `WaitingForOutcome` (claim 8). Onchain `revealedCount = 1 < committedCount = 2`, `block <= 40` → `FinalizeTooEarly` (claim 10); gas spent, FSM not informed. If `O` reveals and finalizes, `OracleResult` reaches `WaitingForOutcome` and `H` claims; if `O` never reveals, `H` is parked forever (claim 9) and nobody finalizes.

With `n` sentinels of which `k ≥ 1` commit in block `commitDeadline`, every early committer's count is `n − k`; the early committer whose reveal is observed last among the first `n − k` reveals of the early set takes outcome 1, the others outcome 2. Reveals are all submitted in the same block (`NewBlock(commit_deadline)`), so which sentinel is hit is decided by intra-block ordering of legitimate transactions — no adversary needed.

## Considered and rejected

- "Commits in the deadline block are an edge case": the delta's own comment calls a commit mined in `commit_deadline` "the common case with a short commit window" (claim 4) and handles it — for the sentinel's _own_ commit only.
- "The reveal-deadline path re-finalizes": `handle_block_advance` calls `finalize()` only from `CollectingVotes` (`service.rs:468-483`); by `reveal_deadline + 1` the entry is either gone (outcome 1) or in `WaitingForOutcome`, which is retained unconditionally (claim 9).
- "`handle_oracle_result` recovers a missed reveal": only while the entry exists (`812-834`); outcome 1 removes it first, exactly as in F2-SEN-002 outcome 1.
- "Another sentinel finalizes": only a sentinel whose _own_ commit was in the deadline block counts correctly (its transition is deferred to `NewBlock(commit_deadline + 1)` by `433-435` and it then tallies the block's logs — the delta's second test, `2242-2326`). If the late committer is not this software, crashed, or adversarial, nobody does.
- "A `Revealed` could likewise arrive before the transition and be lost": no — reveals need `block.number > commitDeadline` (claim 6), so the earliest `Revealed` is in block `commit_deadline + 1`, whose logs follow `NewBlock(commit_deadline + 1)`.
- "F2-SEN-002 already covers this": its undercount source is commits landing before our engine resume; at `3ec8bc5` a commit in block `commitDeadline` was tallied (claim 12). Its remediation 1 (count from `NewRequest` onward) does not fix this one — the counter still stops at the transition.
- "Reverting PR #914 fixes it": it would, at the cost the PR was made for (a wasted first block of the reveal window). The STOPGAP comment (`service.rs:398-402`) says the comparisons revert to inclusive once safe-research/safenet#471 runs transitions against the pending block; until then the tally boundary and the reveal emission need to be decoupled.

## Remediation options

1. Keep tallying in `CollectingVotes`: let `handle_committed` accept `CollectingVotes` and increment its `committed_count` (a `Committed` can only be observed there for block `commit_deadline`, so no over-count is possible), and correct the doc at `state.rs:56-58`. Smallest change; leaves the early emission of the `Reveal` intact.
2. Decouple the two boundaries: emit the `Reveal` at `NewBlock(commit_deadline)` but stay in `CollectingCommitments` (with a `reveal_sent` flag to avoid re-emitting) until `NewBlock(commit_deadline + 1)`, then move to `CollectingVotes` with the complete count. More state, no counting in two places.
3. Stop early-finalizing on local tallies (F2-SEN-002 option 2): read `getRequest(id).progress.committedCount` through an effect before emitting `Finalize`, or finalize only at `reveal_deadline + 1`. Removes this whole class at the price of latency or one RPC per request.

Tests to add: `flow_reveals_on_the_commit_deadline_block` extended with `log(20, committed_event(id, OTHER, 500))` after `NewBlock(20)`, then (a) `Revealed(OTHER)@21` asserting the entry survives and `Revealed(self)@22` yields `Finalize`; (b) `Revealed(self)@21` asserting no `Finalize` until `Revealed(OTHER)@22`. No code is committed.

**Corrections to the Trigger (they narrow the honest-case harm, not the verdict).**

1. `self_revealed` is set at `369-371` _before_ the threshold test at `372`. An early committer whose own reveal is the one that reaches `committed_count` therefore takes outcome 2 (`Finalize`, `WaitingForOutcome`), not outcome 1. The sentence "the early committer whose reveal is observed last among the first `n − k` reveals of the early set takes outcome 1" is wrong; outcome 1 needs our own reveal to be observed _after_ `committed_count` other reveals, i.e. our reveal delayed behind those of committers we did not count — F2-SEN-002's ordering route (and F2-SEN-005's backlog), not the default ordering.
2. "Both reveals are submitted against head 20": a deadline-block committer running this software reveals only at `NewBlock(commit_deadline + 1)` (deferred by `433-435`), so its `Revealed` lands at `≥ commit_deadline + 2`; only a foreign or adversarial committer can reveal in `commit_deadline + 1`.
3. Default honest sequence, all sentinels this software, `k ≥ 1` commits in the deadline block: every early committer's tally is `n − k`; when the `(n − k)`-th reveal is observed (its own among them) it emits `Finalize` (`372-375`, `657-671`), which reverts `FinalizeTooEarly` onchain (`revealedCount = n − k < committedCount = n`, `block ≤ revealDeadline`), and it parks in `WaitingForOutcome` (`484`) with no retry. The request is then finalized by the late group — their tally is complete and their early finalize or the deadline path (`471-483`) succeeds — and `OracleResult` reaches the parked entries, which claim (`798-834`). Honest-case cost: one reverted `Finalize` per early committer per request, and dependence on the late group or a third party.
4. The full stall needs every honest commit to precede the deadline block (any honest sentinel whose own commit is in it keeps the full tally and finalizes at `NewBlock(reveal_deadline + 1)`, where `finalize()` passes). That is the normal case whenever engine latency plus one block is under the commit window. Then one active sentinel (`SentinelOracle.sol:246`) committing at head `commitDeadline − 1` and never revealing parks every honest sentinel on that request; its cost is `slashAmount` per request, and every honest bond and fee share stays in the contract until someone calls the permissionless `finalize` after `revealDeadline`, then `claim`. Funds locked, not lost; no log above `warn`, no metric.
