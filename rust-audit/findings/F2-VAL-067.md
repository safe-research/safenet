## Claim

`blocks_per_epoch`, `key_gen_timeout`, `signing_timeout` and `oracle_timeout` are independent `NonZeroU64`s with no relation checked at load time or in `ValidatorService::new` (which validates only genesis viability). The rollover clock abandons any in-flight DKG the moment the block enters the next epoch window and restarts one "including everyone again", while a non-responsive participant is only excluded once a round's `key_gen_timeout` deadline passes (share and confirmation rounds add up to `3 x key_gen_timeout` more). If `blocks_per_epoch <= key_gen_timeout` (or, more generally, smaller than the worst-case DKG duration plus signing), one permanently offline participant makes every attempt time out _after_ it has already been abandoned, so it is never excluded, the next attempt includes it again, and no epoch is ever staged: the active group stays in place indefinitely and every scheduled rotation is silently skipped with a `warn!`. The config test suite itself exercises `blocks_per_epoch = 100` with the default `key_gen_timeout = 120`, which is exactly such a combination, and nothing rejects it.

## Trigger

Config: `blocks_per_epoch = 100`, defaults otherwise (`key_gen_timeout = 120`); one participant offline. At the first block of each window the validator starts a DKG with deadline `+120`; at block `+100` the window rolls, the attempt is abandoned (row 3) before the deadline that would have excluded the offline member (row 4); the new attempt includes it again. Repeat forever; `active_epoch` never advances. With `blocks_per_epoch` between `key_gen_timeout` and about `4 x key_gen_timeout + signing_timeout`, the same livelock appears when a member stalls in a later round. Not executed (needs a chain); every step is unconditional in the cited code.

## Considered and rejected

- Under A1 the operator is trusted, and the defaults (`1440` vs `120`) are safe; the finding is about the absence of a guard rail for a value the sample invites operators to tune (`validator.sample.toml:41-46`) and whose failure mode is silent rotation loss.
- Genesis is unaffected (no deadline, no clock).
- The validator could not compensate at runtime (peers must agree on deadlines), so validation at load time is the right layer.

## Remediation options

1. Reject at load: require `blocks_per_epoch > 4 * key_gen_timeout + signing_timeout` (and `oracle_timeout >= signing_timeout` if that relation is assumed elsewhere) in `ValidatorService::new`, returning a descriptive error. Tiny change.
2. Alternatively warn loudly at startup and expose the derived "worst-case DKG length" in the log, leaving operators the choice.

Tests to add: a `config`/service test asserting the combination is rejected (or warned). No code is committed.
