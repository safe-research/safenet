## Claim

The runtime stage declares no `USER`, so the process - which holds the signer private key in memory, keeps plaintext FROST secrets in the mounted SQLite file and parses untrusted chain data - runs as uid 0 inside the container, and the data volume the handbook mounts at `/var/lib/safenet/validator/data` is populated with root-owned files. Both stages use floating tags (`rust:1-slim`, `debian:trixie-slim`) without digests, so an image rebuilt from the same commit can differ, and the runtime image has no `HEALTHCHECK` (the metrics port is ephemeral by default, so none could be written without a config change). None of this is exploitable on its own; it is the hardening gap between this image and common container baselines.

## Trigger

None (hardening). The relevant scenario is a memory-safety or dependency bug reachable from RPC data (A4) escalating from a root process; running unprivileged limits it to the container's uid.

## Considered and rejected

- `apt-get` layers are cleaned and `--no-install-recommends` is used; the image is otherwise minimal.
- The sentinel image has the identical structure (`crates/sentinel/Dockerfile`, R7/R8 scope).

## Remediation options

1. Add a dedicated user in the runtime stage (`RUN useradd --system --uid 10001 --home /var/lib/safenet/validator safenet`, `USER 10001`), create and `chown` `/var/lib/safenet/validator/data`, and document `--user`/`fsGroup` expectations in the handbook.
2. Pin base images by digest (`rust:1-slim@sha256:...`, `debian:trixie-slim@sha256:...`) and refresh via automation; optionally publish the runtime on a distroless base since the binary needs only `libsqlite3` and CA certificates.

Tests to add: a CI check that the image's configured user is non-root (`docker inspect --format '{{.Config.User}}'`). No code is committed.
