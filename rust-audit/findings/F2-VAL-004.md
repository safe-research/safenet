## Claim

When the `KeyGenSetup` resume arrives after every commitment has already been collected, `handle_key_gen_setup` finalises the commitment round itself. This branch is not equivalent to the normal one in two ways:

(a) It sets the share-round deadline to `commitment_deadline + key_gen_timeout`, whereas every peer that closed the round on the last commitment uses `last_commitment_block + key_gen_timeout`. The local deadline is therefore strictly later (by up to `key_gen_timeout` blocks). All timeouts are otherwise derived from event block numbers, so this is the one place honest nodes' deadlines diverge. If the share round then times out (one participant fails to share), the peers restart with a new group id up to 120 blocks before this validator does; their commitments for the restarted group arrive while this validator is still in `CollectingShares` for the old one and are dropped, so when it restarts it can never reach `count` and skips the epoch while the peers exclude it.

(b) While the round waits for the setup (`secrets: None`, all commitments present) the state stays `CollectingCommitments`, so `KeyGenSecretShared` events emitted by peers who already moved to sharing are dropped. After the late finalisation the validator enters `CollectingShares` with an empty `public_keys` map, never reaches `count`, and at its deadline excludes every peer that shared "too early"; for genesis, which has no deadline, it stays in `CollectingShares` forever.

Both cases need the setup effect to complete after the replay of the remaining blocks, which a reorg replay (fast, back-to-back `New`+`Logs` updates for the reorged blocks) can produce; a slow SQLite insert widens the window.

## Trigger

`n = 6`, `key_gen_timeout = 120`, boundary block `B`, all six `keyGenAndCommit` transactions in `B+1..B+2`, peers' `keyGenSecretShare` in `B+3..B+4`.

1. A 4-block reorg uncles `B+1..B+4` (within `max_reorg_depth = 5`). The state rolls back to `B`'s predecessor; `New(B)` re-runs `start_key_gen` and re-emits `KeyGenSetup` (row 7); the watcher immediately queues `New`/`Logs` for `B+1..B+4` from the new branch, which the driver processes back-to-back while the effect task performs `dkg::part1` and the `store_keygen_secrets` round-trip.
2. The six commitments are accepted with `secrets: None` (row 3). If the effect resumes after the last of them, the late branch runs with `deadline = (B+120)+120` (row 1) while every peer, having closed the round at `B+2`, holds `B+2+120` (row 2).
3. Case (a): participant `P` never shares. Peers restart at `B+122` with `gid'` excluding `P`; their commitments land at `B+123..`; this validator, still in `CollectingShares` for `gid`, drops them (`state/keygen.rs:161-168, 263`) until `B+240`, then restarts to the same `gid'` with an empty map, never reaches `count`, and at `B+360` excludes everyone; `EpochSkipped`. Peers exclude it at their share deadline for `gid'`.
4. Case (b): if `B+3..B+4` (peers' shares) were also part of the replay processed before the resume, they were dropped (row 4); after the late finalisation `public_keys` is empty and stays so; at `(B+240)` row 5 excludes all peers; `EpochSkipped`. For genesis the same state persists indefinitely (row 8).

## Considered and rejected

- _The effect always wins the race._ `dkg::part1` plus one SQLite transaction on the shared pool takes milliseconds, but a reorg replay of `k ≤ 5` blocks is also processed within milliseconds once the headers are fetched, and the effect handler shares the pool with the transaction queue and snapshot commits; the ordering is explicitly unspecified (row 6). No mechanism guarantees the order, which is why the branch exists at all.
- _Peers also drop the restarted group's commitments._ No: peers restart at their (earlier) deadline and are in `CollectingCommitments{gid'}` before any `gid'` commitment lands.
- _`deadline_old + timeout` is what the peers use._ No: `handle_key_gen_committed` pushes from the block of the last commitment (row 2); `handle_key_gen_setup` has no block to derive from and pushes from the previous deadline (row 1, and the doc comment on `finalize_key_gen_commitments`, `state/keygen.rs:1232-1236`).

## Remediation options

1. Carry the block number of the last accepted commitment in `CollectingCommitments` and derive the share deadline from it in both paths. Tradeoff: one extra `u64` in the snapshot; removes divergence (a).
2. Buffer `KeyGenSecretShared` events for the current group id while `secrets: None` (or re-request them via a `Warp`-independent catch-up) and replay them after the late finalisation. Tradeoff: a small bounded buffer in the snapshot; removes (b).
3. Alternatively, make `KeyGenSetup` synchronous with the transition that starts the round (sample the secrets inside the transition from a seeded RNG carried as an effect result, or emit the setup one block earlier). Larger refactor.

Tests to add: a state test applying six `KeyGenCommitted`, two `KeyGenSecretShared`, then `Resume::Setup`, asserting the shares are not lost and the deadline equals `last_commitment_block + key_gen_timeout`.

## Critic (C2-VAL-A)

**Finding verdict: Plausible. Severity Low (unchanged; genesis case (b) Informational/`known`). Certainty 50%.**

Both mechanisms are code-verified; the trigger is a timing race that was not executed.

- **[E2] (a) Deadline divergence is real.** The late-setup branch derives the share deadline as `commitment_deadline + key_gen_timeout` (keygen.rs:130-133), while the normal close derives it as `block + key_gen_timeout` from the last commitment's block (keygen.rs:247-252). Since the commitment deadline was itself `commitment_start + key_gen_timeout`, the late node's share deadline is strictly later (by up to `key_gen_timeout`). This is the one place honest nodes' deadlines diverge; the doc comment on `finalize_key_gen_commitments` (keygen.rs:1234-1236) confirms the two exits "do not agree on a block to derive it from." Supported.
- **[E2] (b) Dropped early shares.** While `secrets: None` with all commitments in, the state stays `CollectingCommitments` (keygen.rs:225-244), so `KeyGenSecretShared` (consumed only in `CollectingShares`, keygen.rs:281-290, 425) is dropped; after the late finalisation `public_keys` is empty and the share timeout excludes everyone (keygen.rs:1047-1067). Genesis has no deadline (keygen.rs:52-53) so case (b) stalls forever there. Supported.

**Why Plausible not Confirmed:** both cases require the `KeyGenSetup` resume to land _after_ a reorg replay of the remaining commitments (and, for (b), the peers' shares) — an effect-vs-replay ordering that the code explicitly leaves unspecified (core state/mod.rs:44-51) but which no observed input forces. `dkg::part1` + one SQLite round-trip vs a few back-to-back `New`/`Logs` updates is a genuine race, not a guaranteed one; the reviewer's 55% self-estimate is fair. Impact is contained (a single validator forfeits one rollover epoch, recoverable) → Low; the genesis instance of (b) is a genesis-only permanent stall → Informational/`known` under A16, correctly tagged. Remediation 1 (carry the last-commitment block, derive both deadlines from it) removes (a) cleanly; 2 (buffer early shares) removes (b). No promotion from the rejected list.
