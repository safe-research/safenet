## Claim

The process-local `NonceGenerator` is empty at start-up. Streams are started only by `Effect::StartNonceGeneration` (emitted once, when the key share is confirmed) and by `Effect::ReconcileGroupSecrets`. The scheduled-pruning series changed the reconciliation so that a request whose block is **below** the persisted `group_secret_reconciliation` marker returns `Resume::Noop` _before_ the generator is retained or started. After a restart the driver rolls the state back to the earliest retained snapshot and replays forward, and in every replay shape there is a window in which a `NonceTree` request cannot be served:

- **Short outage** (fewer than `max_reorg_depth` new blocks): the replayed `NewBlock`s `S+1 .. L-1` all carry blocks below the marker `L`, so their reconciliations are ignored and no stream is started until the reconciliation for `L`.
- **Long outage**: the replay is a `Warp`, during which the state machine applies logs only - no `NewBlock`, hence no reconciliation and no stream start - until the first live block after the warp.
- **First accepted block**: `handle_nonce_topup` runs before `handle_group_reconciliation` in the `NewBlock` transition and its `NonceTree` command is spawned before the reconciliation, so the two tasks race for the `nonce_generator` mutex with nothing ordering them; the `NonceTree` task's critical section is a single map lookup and fails with `Unavailable` if it wins.

Every `NonceTree` produced in these windows fails and, per F2-VAL-030, leaves a permanent phantom reservation. Requests the previous process had already turned into a durable `Preprocess` transaction self-heal when the event is replayed or lands; requests that exist only because of the outage do not: a top-up whose threshold was crossed while the node was down, `finalize_key_gen`'s chunk-0 request for an `EpochStaged` mined while the node was down, or an effect the shutdown aborted between the snapshot commit and the queuing of its action. A validator that restarts across a rollover therefore enters the new epoch with a phantom chunk 0 and misses 90% of that epoch's ceremonies. This is entirely service-caused (no database manipulation, A17).

## Trigger

Deterministic variant (restart across a rollover), `D = max_reorg_depth = 5`:

1. Validator `V` confirms the DKG for epoch `e+1` at block `C`; `StartNonceGeneration{G_{e+1}}` runs in process `P1` and the stream is warm. `V` is stopped at block `L > C + D`; the snapshot store retains `[L-D, L]`; the reconciliation marker is `L`.
2. While `V` is down the rollover attestation completes and `EpochStaged` for `G_{e+1}` is mined at block `E > L`. `V` restarts when the head is `L' >= E + D`.
3. `initialize` queues `Uncle{L-D+1}` (rollback to snapshot `L-D`, before `E`) and `Warp{L-D+1 -> L'-D}`. The warp's log pages replay `EpochStaged`: `finalize_key_gen` inserts `epochs[e+1].nonces = {0: None}` and spawns `Effect::NonceTree{G_{e+1}}`. The handler calls `generator.next(G_{e+1})` on an empty generator (process `P2` never ran `StartNonceGeneration` for `G_{e+1}`, and no reconciliation runs during the warp) -> `Err(Unavailable)` -> `Resume::Noop`. The reservation is committed with the page.
4. At `NewBlock(L'-D+1)` the reconciliation is accepted and starts the stream, but nothing re-requests the tree. When epoch `e+1` activates, `V` drops every ceremony with sequence `0..924` and, by F2-VAL-030, 90% of all later ones for the whole epoch.

Likelihood: for a random restart with an outage of `k` blocks, roughly `k / 1440` per validator (an `EpochStaged` lands once per epoch); certain for a restart deliberately performed during a rollover. Rolling upgrades of several validators inside one rollover window compound.

Racy variant (any restart): `available()` was 150 at shutdown and >= 51 signatures happened while `V` was down. The first `NewBlock` after the warp fires the top-up; its `NonceTree` task is spawned before the reconciliation task and the two race for the mutex (Basis 5, 6, 1). If `NonceTree` acquires first it fails; nothing self-heals because `P1` never issued this request.

Short-outage variant: the previous process was stopped between the snapshot commit that carried a top-up reservation and the queuing of the resulting `Preprocess` action (the effect was aborted, Basis 11). The replayed `NewBlock` re-emits `NonceTree` inside the below-marker window and it fails deterministically (Basis 1, 2, 10).

## Considered and rejected

- Reconciliations _are_ accepted for blocks equal to the marker (store.rs:299-303); this does not help the replayed blocks strictly below it, nor the warp, nor the same-block race.
- `StartNonceGeneration` is emitted alongside `KeyGenConfirm` (Basis 4); it is replayed only if the confirmation event itself lies above the rollback point, and in that case the `NonceTree` is not the one that fails - the success path is the one that self-heals through the durable `Preprocess` transaction.
- Requests whose `Preprocess` transaction the previous process already queued do heal: the transaction queue is durable and `handle_preprocess` links `event.chunk` (state/preprocess.rs:79). The claim is restricted to requests created by the outage or aborted before queuing.
- Housekeeping (`prune_scheduled_secrets`) is unrelated to generator start; it neither starts nor stops streams (service/effect.rs:278-308).
- The old (pre-pruning) reconciliation had no marker and started streams on every block; the below-marker early return is new in this series (`git diff 49d7e39 3ec8bc5 -- crates/validator/src/service/effect.rs`).

## Remediation options

1. In `ReconcileGroupSecrets`, perform `generator.retain(..)`/`generator.start(..)` **regardless** of whether the persisted schedule was accepted; the marker orders on-disk schedules, the generator is process-local and always benefits from the freshest retained set. One-line move of the early return.
2. Start streams lazily where they are needed: carry the `Arc<KeyShare>` in `Effect::NonceTree` (or look it up from the retained map) and call `generator.start` before `next`; `start` is idempotent. This also closes the same-block race.
3. Emit `handle_group_reconciliation` before `handle_nonce_topup` in the `NewBlock` transition, and run a reconciliation once at start-up (e.g. as part of `Driver::new`, or on the first `Warp`/`Uncle`) so the generator is warm before any replayed log can request a tree.
4. Pair with F2-VAL-030's retry so a transient failure is never permanent.

Tests to add: a handler test that performs `NonceTree` for a group with a running stream after a below-marker reconciliation was applied (currently `Unavailable`); an Anvil flow that stops a validator for more than `max_reorg_depth` blocks across an `EpochStaged` and asserts a `Preprocess{chunk: 0}` for the new group is eventually emitted (`scripts/run_validator_integration_test.sh` as a base). No code is committed.

Remediation check. **Option 1 as written is partly unsound**: a below-marker reconciliation carries an _older_ retained set; applying `generator.retain` from it would stop the stream of any group confirmed after that block — the newest group — turning a harmless replay into a fresh cold-generator incident. Calling `generator.start` for every group in the older set unconditionally is safe (idempotent, process-local); `retain` must stay behind the accepted-schedule check. **Option 2 is sound and the best fix**: carry the `Arc<KeyShare>` in `Effect::NonceTree` (the transition has `epoch.key_share`) and `start` before `next`; `start` is a no-op for an existing entry (nonces.rs:36-39), so effects remain idempotent, and it closes all three windows including the same-block race. **Option 3**: the reorder half is ineffective (tasks are unordered, see F2-VAL-062); a start-up reconciliation is sound only if it runs before the first warp page is applied. Option 4 (F2-VAL-030's retry) is needed regardless so that any remaining failure is transient.
