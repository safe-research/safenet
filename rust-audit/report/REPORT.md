What matters:

- One defect blocks the Aegis launch. On the documented sentinel configuration (Direct mode) the sentinel's `approve` of its 800 USDC.e bond runs out of gas at the fixed 55,000 limit, so no commit lands, no Aegis request gets a vote and no oracle-gated transaction is attested ([`F-SEN-008`](../findings/F-SEN-008.md), found again blind as [`F3-SEN-001`](../findings/F3-SEN-001.md)). Setting `executor` (Batched mode) works around it today.
- Run 3 adds two Highs that were already present at `fe9e84c`. Validators send signature shares on an approval that a 3 to 5 block reorg can undo, so a transaction its oracle froze can still be attested ([`F3-VAL-030`](../findings/F3-VAL-030.md)). One Byzantine validator can force every Aegis rollover to be skipped while the blame lands on an honest victim ([`F3-XC-100`](../findings/F3-XC-100.md)).
- The fourth High, the fee ratchet [`F-CORE-060`](../findings/F-CORE-060.md), keeps its band with an open dissent (Section 8.4).
- The sentinel bond family is now Medium: every bond-loss path locks the bond until a manual `claim`, and at most the 0.40 USDC.e slash is lost. The verdict store (#978, #979) that fixed [`F-SEN-015`](../findings/F-SEN-015.md) for live reorgs does not hold in a restart window.

## 2. Fix these first

Ordered by loss and dependency. Each item names the rows it closes and the remediation to take. If a run-3 QA bite check ran an option and found it sound, the item says so. Read Section 3 before choosing an option.

Sequencing:

- Item 1, or its workaround, makes the sentinel's commits land. Every sentinel bond row in item 4 needs that, and today those rows are reachable only in Batched mode. Ship item 4 in the same release.
- The `WaitingForOutcome` expiry ([`F-SEN-005`](../findings/F-SEN-005.md)) must queue an action and keep the entry. It lands with [`F2-SEN-003`](../findings/F2-SEN-003.md)'s keep-the-entry change. Dropping the entry recreates the abandonment, and #974's drop did exactly that ([`F3-SEN-060`](../findings/F3-SEN-060.md)).
- The fix for [`F-SEN-001`](../findings/F-SEN-001.md) needs both halves: track the sentinel's own commit while the engine check runs, and keep that entry until the reveal deadline.
- Persisted pending effects ([`F-CORE-031`](../findings/F-CORE-031.md)) land with [`F-VAL-061`](../findings/F-VAL-061.md)'s `Resume::Failed`, or a re-spawned effect that fails is still a silent `Noop`.
- An absolute fee ceiling for [`F-CORE-060`](../findings/F-CORE-060.md) needs a cancellation path, or the capped row blocks every later nonce. [`F-CORE-061`](../findings/F-CORE-061.md)'s wider underpriced match enlarges the ratchet's surface, so it lands after the ceiling.
- [`F-CORE-067`](../findings/F-CORE-067.md)'s idempotency key must outlive the row, or [`F-CORE-063`](../findings/F-CORE-063.md) is fixed first.
- The per-event fallback fix for [`F-CORE-034`](../findings/F-CORE-034.md) must cover both `block()` and `warp`.

1. **The sentinel cannot bond on Aegis: [`F-SEN-008`](../findings/F-SEN-008.md) with [`F3-SEN-001`](../findings/F3-SEN-001.md), High, launch blocker.** Direct mode is the code default and what the published Aegis sentinel configuration uses (`docs/configuration.md:106-121` has no `[transactions]` table). In Direct mode the fixed 55,000 is the whole transaction's gas limit. A USDC.e approval from a zero allowance needs a limit of at least 55,819 and uses 55,437. Workaround today: set `executor`, so the sentinel submits in Batched mode, where the 55,000 is the call's own budget (CA3's control run: commit, reveal and claim succeed). The published configuration does not set it. The workaround runs through the 7702 executor, a contract change after the audited commit `0be96367` (a process note, not a defect). Fix: raise the `ApproveToken` gas limit (remediation 1). QA3-SEN raised it to 80,000: the approve used 55,437, the commit landed, and the sentinel revealed and claimed.
2. **Attestation on a reorged approval: [`F3-VAL-030`](../findings/F3-VAL-030.md), High.** Keep `WaitingForOracle` after an approving `OracleResult` and emit `GenerateNonces` only once the result is `max_reorg_depth` (5) blocks deep (remediation 1). Sound in QA3-VAL (patched, nothing attests after the reorg) and QA3-2A. Cost: about 25 s per attestation on Gnosis, inside `oracle_timeout` 24. The fix needs `max_reorg_depth` in the validator's transition config. Remediations 2 and 3 do not close the guard path (Section 3).
3. **One validator can force every rollover to be skipped: [`F3-XC-100`](../findings/F3-XC-100.md) with [`F3-VAL-001`](../findings/F3-VAL-001.md), High.** When the commitment round completes, compute every participant's verifying share. If one is the identity, restart without the participant whose commitment completed the round (remediation 1). Sound in QA3-2A: the poisoned group never reaches share collection and the restart keeps 4 of 5. The contract flag alone does not fix it (Section 3).

## 3. Do not ship these fixes

Remediation options in the finding files that a QA, Critic or verification agent judged unsound, kept only where the row is still live.

**Rollback and replay.**

- "Commit the resume": [`F-CORE-031`](../findings/F-CORE-031.md) option 1, which [`F-SEN-001`](../findings/F-SEN-001.md) option 3 and [`F-SEN-015`](../findings/F-SEN-015.md) option 3 rely on. A commit inside `handle_resume` can record a block whose logs have not been applied, and a crash then loses those logs for good (run 1). The restart rollback to the oldest retained snapshot deletes a snapshot at `latest` anyway (run 2). `driver.rs` and `state/storage.rs` are unchanged since `fe9e84c`. Anchoring the rollback at `uncle - 2` (F-CORE-031 option 3) rests on an at-least-once contract that actions do not have, and it worsens [`F-CORE-067`](../findings/F-CORE-067.md).
- [`F3-SEN-004`](../findings/F3-SEN-004.md) remediation 1 alone for F-SEN-001: on a real restart whose head is past `commitDeadline` the entry is dropped before the fresh check resumes (QA3-2B). Removing only the drop guard makes the sentinel reveal when no bond exists (QA3-SEN).
- Re-emitting the engine check while a request waits ([`F3-CORE-032`](../findings/F3-CORE-032.md) remediation 2) without the own-commit piece: when the sentinel's own commit is replayed first, as in a warp, there is still no reveal (QA3-CORE).

**Sentinel drops.**

- Expiring `WaitingForOutcome` by dropping the entry (the shape of [`F-SEN-005`](../findings/F-SEN-005.md) option 3): every terminal handler ignores an untracked id, so the drop recreates F2-SEN-003's abandonment. #974 dropped the dispute entry right after queueing `timeoutArbitration()` and `claim()`, and that drop is [`F3-SEN-060`](../findings/F3-SEN-060.md).

**Indexer.**

- Backoff alone for [`F-CORE-034`](../findings/F-CORE-034.md) and [`F3-CORE-001`](../findings/F3-CORE-001.md): under window, in-flight and burst-12 limits, the stall persists once the watcher enters per-event mode, because every attempt still needs 16 requests admitted at once (QA3-CORE). The fallback fix applied to `block()` alone leaves `warp` stalled.
- [`F3-CORE-002`](../findings/F3-CORE-002.md) remediation 2 without a time bound: a bloom false positive retries that block forever (QA3-CORE).
- Skipping an undecodable log ([`F-CORE-004`](../findings/F-CORE-004.md) option 2): for `Consensus`, `FROSTCoordinator` and `SentinelOracle` an undecodable log means an ABI mismatch, and skipping it silently derives a wrong state. It also contradicts [`F-CORE-002`](../findings/F-CORE-002.md) option 1 on the same code path.
- "Walk back" for [`F-CORE-001`](../findings/F-CORE-001.md) (option 2) has nothing to walk back to unless snapshot retention is decoupled from `max_reorg_depth`.

**Transaction queue.**

- Reading `submitted_at IS NULL` as "never submitted": [`F-CORE-067`](../findings/F-CORE-067.md) option 3, [`F-CORE-062`](../findings/F-CORE-062.md) option 3, and the delete-the-row branch of run 2's cancellation option, now folded into [`F-CORE-064`](../findings/F-CORE-064.md). An underpriced rejection also records `NULL` (`crates/core/src/tx/mod.rs:338-350`), and so does a crash between broadcast and `record_submission`. These options then delete or release rows that sit in a mempool. [`F-CORE-060`](../findings/F-CORE-060.md) option 5 removes the overload.
- Deduplicating on the request alone (run 2's option, folded into F-CORE-067) drops a legitimate repeated `approve`. The key must be the action's identity and include the block hash.
- F-CORE-060 option 2 (re-apply the cap after the bump) bounds no absolute fee and adds a second ratchet. Option 1 without a cancellation path leaves the capped row in flight.
- [`F-CORE-033`](../findings/F-CORE-033.md) option 2 (a semaphore in each handler) is service-local and bounds no memory.

**Validator.**

- [`F3-VAL-030`](../findings/F3-VAL-030.md) remediation 2 (an oracle check in `Consensus.attestTransaction`) and remediation 3 (cancel unexecuted shares): every share `z_i` is public, so anyone who saw the orphaned branch can build a signature that `SafenetGuard` accepts without any re-inclusion (QA3-VAL's guard-path check matched). Only remediation 1 closes it.
- [`F3-XC-100`](../findings/F3-XC-100.md) remediation 3, including the contract flag that stores `y = (0, 0)`, which the team's review of #1025 names as its preferred fix: the key generation then finishes, but `getKey` and `FROST.verifyShare` reject the victim's identity key at every signing. Remediation 2 avoids the skip but leaves the victim unable to sign for the epoch (QA3-2A).
- An `eth_call` from the transition to check the emitter for [`F-VAL-060`](../findings/F-VAL-060.md) (run 2's option): it breaks the pure, non-failing transition.
- [`F-VAL-066`](../findings/F-VAL-066.md) option 4 (a post-write read) races the delete it is meant to catch.

**Dependencies.**

- `cargo update -p` for [`F-XC-011`](../findings/F-XC-011.md) fixes five advisories but not `lru`: `alloy-provider` 2.0.5 pins `lru` 0.16, and the fix is in 0.18.2.

### 4.5 The fix that did not hold: F-SEN-015

@rmeissner took [`F-SEN-015`](../findings/F-SEN-015.md) in the PR thread, and #978 and #979 shipped a verdict store. The store fixes the live-reorg route (5 of 5 variants pass) but does not hold in a restart window: when a restart's warp replays the proposal below the new `safe` block and the sentinel's own commitment falls in the live tail, the first housekeeping after the warp prunes the recorded verdict before the replayed check reads it. The engine is asked again, and the committed vote is never revealed.

- CA3-FIX, real sentinel binary at the Aegis windows (commit 6, reveal 6, `max_reorg_depth` 5): 15 of 20 restarts inside the window lost the verdict; the control lost 0 of 6. CA3 re-ran it: 16 of 16 (10 with the engine down on the replay, 6 with a changed verdict), control 0 of 4.
- The window: a crash right after the commitment block, with the commitment 2 blocks after the proposal, needs exactly 4 blocks of downtime. Each extra block of commit latency widens it by one block. On Gnosis that is a restart 20 to 30 s after a proposal whose engine check took 5 s or more.
- Per affected request on Aegis: 0.40 USDC.e slashed and 799.60 USDC.e left for a manual `claim`. Medium 95. Fix options in Section 2, item 4.

### High (4)

#### [`F-SEN-008`](../findings/F-SEN-008.md): High 97, the sentinel's `approve` runs out of gas on USDC.e

The sentinel sends `ApproveToken` with a fixed 55,000 gas (`crates/sentinel/src/service.rs:867-877`). In Direct mode that is the whole transaction's limit. A USDC.e approval (`FiatTokenProxy` in front of `FiatTokenV2_2`) from a zero allowance needs at least 55,819 and uses 55,437, so it runs out of gas. The `commit` behind it reverts in `safeTransferFrom`, and no `Committed` follows. Each commit spends the exact approval, so every request starts from a zero allowance. Trigger: any proposal on the Aegis SentinelOracle with the documented configuration. Nobody needs to act. If every sentinel runs that configuration, no Aegis request gets a vote, no `OracleResult` is emitted and Safes fall back to the guard's delayed escape hatch. If only some sentinels run Batched mode, they decide every request alone: one approving reveal with no deny resolves `RESOLVED_APPROVED` (C3-SEN), which only matters if a registered sentinel misbehaves. The USDT-family half of run 1's claim does not apply to USDC.e. Fix: Section 2, item 1. **Trail:** run 1 E2 Low 52 (conditional on a proxied fee token), rv-sen Changed (probe on the real token code), R7 E1 as [`F3-SEN-001`](../findings/F3-SEN-001.md) (real FiatToken bytecode from Foundry's cache at Gnosis block 48,635,154), C3-SEN Confirmed (second gas method), QA3-SEN Reproduced end to end on the real binary, PC3 practical, CA3 High 97.

#### [`F3-VAL-030`](../findings/F3-VAL-030.md): High 97, shares sent on a non-final approval can attest a transaction the oracle froze

The validator acts on an approving `OracleResult` in the block where it sees it: it generates and commits nonces at once and, normally one block later, broadcasts `signShareWithCallback` with the `attestTransaction` callback. Nothing waits for the approval to be reorg-safe, and the shares cannot be recalled: the queue rebroadcasts them after a reorg, and every `z_i` is public. Trigger: a reorg of 3 to 5 blocks, inside `max_reorg_depth` 5, whose new branch carries a late deny commit, so the SentinelOracle freezes the request instead of approving it. The orphaned shares still complete the group signature, and `Consensus` attests. CA3 ran it with a real SentinelOracle at the Aegis windows: a depth-4 reorg gave `DisputeTriggered`, a `FROZEN` request, no `OracleResult` and a `TransactionAttested`, 2 of 2. This breaks the rule that arbitrated transactions are never attested. No reorg of 3 or more blocks is verified on Gnosis in 294.8 days of explorer data (95 % upper bound about 3.7 a year). Timely 2-block reorgs come about once every 150 days. Fix: Section 2, item 2. **Trail:** R5 E2 (Critical impact class), C3-VAL Confirmed (High; the guard path needs no re-inclusion), QA3-VAL Reproduced (two real validators, `anvil_reorg 3`, 2 of 2), QA3-2A Reproduced (real signing state machine at 3 of 5), PC3 conditional, CA3 High 97.

#### [`F3-XC-100`](../findings/F3-XC-100.md): High 95, a last committer forces an honest verifying share to the identity

Only the constant term of a DKG commitment is bound by a proof of knowledge, so the participant that commits last can choose its other coefficients after seeing every other commitment and make an honest victim's verifying share the identity. The victim's `keyGenSecretShare` with `y = (0, 0)` reverts `NotOnCurve` in `FROSTParticipantMap.set`. The attacker withholds its own share, and at the share deadline both are excluded. Trigger: an Aegis rollover (5 validators, threshold 3, `min_participants(5) = 4`) with one Byzantine member, which A2 allows: 3 remain, the restart fails and the epoch is skipped. The attack repeats every 1,440 blocks, and the reverted transaction is the victim's. The active group keeps attesting. Fix: Section 2, item 3. **Trail:** L-crypto E1 (real frost code and `FROSTCoordinator`), R4 independently as [`F3-VAL-001`](../findings/F3-VAL-001.md), C3-VAL Confirmed, QA3-VAL Reproduced (`EpochSkipped`), QA3-2A Reproduced (two victims), PC3 conditional, CA3 High 95; the team's review of #1025 rates it Medium.

#### [`F-CORE-060`](../findings/F-CORE-060.md): High 98, the underpriced fee ratchet is unbounded and runs every block

A transaction the node keeps rejecting as an underpriced replacement has both fee fields raised by 10 % every block: the underpriced branch records `submitted_at = NULL`, which the resubmission query treats as always stale. There is no ceiling, and `priority_fee_cap_percentage` applies to the fresh estimate only. The signer's balance is the only brake, and draining it also stops the service. Trigger: a node or gateway that keeps answering "replacement transaction underpriced" or "could not replace existing tx" for a reason other than the fee. Run 1 measured it on Anvil: tip 1, then 11,527, then 201,207 wei, max fee 4,239 gwei against a base fee of 772 wei. Run 3 re-ran it: from an unchanged 210/10 estimate the fees reach 59,550/4,037 after 60 blocks, a 1 % cap ends at 3.17 %, and a batched variant ratchets the whole batch. On 5 s blocks the fees grow by a factor of about 3.1 per minute. Fix: Section 2, item 7. The band is unsettled (Section 8.4). **Trail:** run 1 E1 High 98, run 2 E1 Medium (the accepted arm, ×311.9 after 60 bumps), rv-core-b Still valid (all parts re-run plus a batched variant), R3 as [`F3-CORE-060`](../findings/F3-CORE-060.md) (accepted arm only), C3-CORE Plausible, QA3-CORE Reproduced, PC3 conditional and CA3 Low 75 for that arm.

### 9.3 Method

- **Runtime.** Claude Opus 5.5 at max effort for every agent; the head session was the Manager, and the agents were the team's departments.
- **Discovery, blind.** Map3 wrote a fresh map ([`map.md`](../state/run3/map.md): 75 files, 30 invariants, 75 questions). R1 to R8, L-crypto and L-rust read every in-scope file (`Cargo.lock` through tools), 42 of them with two readers. Four Critics (C3-CORE, C3-VAL, C3-SEN, C3-XC) checked every basis row, and C3-COV checked coverage and mined the observations. QA3-CORE, QA3-VAL and QA3-SEN reproduced 22 run-3 rows through the intended route and bite-checked each. QA3-2A and QA3-2B gave every Medium or higher row a second, independent reproduction by a different route. PC3 judged practicality against Aegis production, and CA3 re-ran every Medium or higher row by both routes and set the final band and certainty. Some blind agents saw file names, counts or commit subjects in a `git status` or log listing. None opened earlier contents, and each recorded what it saw in its log.
- **Re-validation, informed.** rv-core-a, rv-core-b, rv-val, rv-sen and rv-xc re-checked all 103 earlier rows at `361aaf3` and re-ran or adapted their PoCs under `poc/<id>/run3/`. - **Reconciliation.** REC3 mapped both tracks into the ledger and wrote the [removal manifest](../state/run3/removal-manifest.md); OFF3 re-derived F3-SEN-060's contract half offline (Section 9.4).
- **Checkouts.** Builds, tests and PoCs ran in detached worktrees at `361aaf3`, outside the repository. QA copied each PoC's source and output into `rust-audit/poc/`. Integration scripts and ad-hoc Anvil ran in a private network namespace (`podman unshare unshare -n`, loopback only).

### 9.4 Safety boundary

- **The rule.** No live RPC and no network beyond the Cargo registry (PROMPT.md Section 1). Apart from the breach below, every chain ran locally, on loopback Anvil or in Foundry's in-process EVM. Gnosis state came from Foundry's local RPC cache (USDC.e code and storage at block 48,635,154), which a separate configuration review filled on 2026-10-07, before this run.
- **One breach.** LT3's contract test for [`F3-SEN-060`](../findings/F3-SEN-060.md), copied from that earlier review, called `vm.createSelectFork(vm.rpcUrl("gnosis"), 48635154)` with `rpc_endpoints.gnosis = "https://rpc.gnosischain.com"` and ran outside the namespace with only `FOUNDRY_OFFLINE=true`, which does not block RPC. It made read-only calls to the public Gnosis endpoint. CA3 flagged it, and the head confirmed it by re-running the test inside the namespace, where it fails at `createSelectFork` with a DNS error. No other PoC used a non-loopback endpoint.
- **Remedy.** OFF3 re-derived the contract half with no network: the real USDC.e proxy and implementation code and its 14 proxy slots etched from the cache, the audit-commit SentinelOracle with the Aegis parameters, and every command inside the namespace. The result matches the fork run: every exit from `FROZEN` reverts on the blacklisted sponsor, each `claim` reverts, 2,400.40 USDC.e stay in the oracle, everything recovers after `unBlacklist`, and two contract mutants make the test fail. The fork test and its output were moved out of `rust-audit/`, the finding carries a head note, and its contract-half evidence now rests on [`poc/F3-SEN-060/offline/`](../poc/F3-SEN-060/offline/). Future Foundry fork tests run inside the namespace.
- **Other network use.** The Cargo registry and the RustSec advisory database (installing and running `cargo audit`); public documentation and client source read by PC3's researcher consults, cited in the finding files; one forge run that tried to clone a submodule from GitHub and failed before fetching anything (rv-core-b).
- **Local only.** The run folder and the worktrees exist only on the audit host and are not part of this PR. What a finding needs is copied into `rust-audit/poc/` and `rust-audit/state/run3/`.
- The samples still point at `https://rpc.gnosischain.com` next to a parseable key ([`F-XC-009`](../findings/F-XC-009.md)); every configuration the runs used was rewritten to loopback.
