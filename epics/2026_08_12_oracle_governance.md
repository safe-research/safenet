# Plan: Oracle Governance

Component: `contracts/` (Solidity: `SentinelOracle`, new governance-parameter libraries, `SentinelOracleRequests`, `SentinelOracleCommitments`, deploy script), `crates/sentinel` (Rust, claim behavior), `scripts/` (devnet + integration wiring).

---

## Overview

`SentinelOracle` (`contracts/src/SentinelOracle.sol`) today has a single privileged role, `ARBITRATOR`, which both rules on disputes (`resolveDispute`) *and* administers every configurable parameter (`addSentinel`, `removeSentinel`, `scheduleBondMultiplier` — all gated by the same `onlyArbitrator` modifier, `SentinelOracle.sol:79-82,228-242`). `REQUEST_FEE` is immutable (`SentinelOracle.sol:40`), there is no DAO fee cut, slashed bonds and unrevealed-vote forfeitures are hard-coded to flow to `ARBITRATOR` (`SentinelOracle.sol:166,219`), there is no reference to the Charter, and a request that freezes (both sides voted, `SentinelOracleRequest.State.FROZEN`) waits on the arbitrator forever — there is no timeout.

This epic brings the contract in line with the governance table the team has agreed on: it separates **governance** (which administers dynamic, delay-gated parameters) from **arbitration** (which only rules on frozen disputes, and is itself changeable only by deploying a new Oracle), and adds the specific parameters and immutables called out in the request:

- A new immutable `GOVERNANCE` address, distinct from `ARBITRATOR`, that administers every dynamic parameter below. In production this is the address the SafeDAO's Arbitrary Message Bridge (AMB) executor calls through, matching the table's "SafeDAO controls X through governance, bridged via the AMB" for the Sentinel set, fee amount, DAO fee share, bond slashing amount, and protocol funds receiver rows — all five are administered by the one address.
- A new, governed, delay-gated **protocol funds receiver** address that replaces `ARBITRATOR` as the destination for the DAO's fee cut and for slashed/forfeited bonds.
- A new, governed, delay-gated **DAO fee share**, expressed in parts-per-100,000 of the per-transaction fee (fine enough to express sub-0.1% shares), applying uniformly whether a request resolves unanimously or via arbitration. In the arbitration path it reduces only the winning sentinels' fee-equivalent reward — the proposer's fee refund stays whole regardless of the DAO's cut (see Architecture Decision).
- A **configurable fee amount** (`REQUEST_FEE` becomes governed and delay-gated instead of immutable).
- A new, governed, delay-gated **bond slashing amount**, expressed as an integer multiplier bounded between `1` (just covers the fee) and the current bond multiplier (the full bond), bundled into the same schedule/apply step as the bond multiplier so the bound always holds by construction (see Architecture Decision). It governs both slashing cases the contract has today: the arbitration-losing-side slash (`resolveDispute`) *and* the unrevealed-vote griefing forfeiture (`finalize`), unified under one parameter rather than the latter staying a fixed 100%. That in turn means a committer who never reveals can now reclaim the non-slashed remainder of their bond once the request resolves, which today they cannot do at all — see Architecture Decision for why that is safe to open up.
- All of the above reuse the existing immutable `GOVERNANCE_DELAY` (`SentinelOracle.sol:43`) and its existing schedule/apply pattern (`BondConfig`, `SentinelOracle.sol:236-242`) — the delay mechanism already exists for `bondMultiplier`; this epic extends it to four more parameters.
- A new immutable `CHARTER_ENS_NODE` (the ENS namehash of `safenet-charter.safe.eth`) — a passive constructor-supplied reference, not an on-chain ENS lookup.
- A new immutable `ARBITRATION_TIMEOUT`: a `FROZEN` request that is not resolved within that window becomes timed out, refunding the fee to the proposer and returning every committed bond in full — the same outcome every other timeout path already produces.
- Because bonds are no longer always fully forfeited on the losing side of an arbitrated dispute, `crates/sentinel`'s claim logic — today it only claims when its own revealed vote matches the arbitration outcome — needs to always attempt a claim after a dispute resolves, win or lose, so a partially-returned bond does not go unclaimed forever.

None of this is deployed (devnet/integration-only today), so there is no on-chain migration to preserve — only per-PR compile/test consistency.

## Architecture Decision

**One governance address for every dynamic parameter, distinct from the arbitrator.** The table is explicit that the same actor (the SafeDAO, via its AMB executor on Gnosis Chain) controls the sentinel set, the fee, the DAO fee share, the bond slashing amount, and the protocol funds receiver. `ARBITRATOR` keeps exactly one job — ruling on `FROZEN` disputes — matching the table's row for the Arbitrator address ("immutable within an Oracle contract; changeable only through a complete Oracle upgrade... changes to its members or threshold are handled through standard Safe configuration", i.e. `ARBITRATOR` itself is expected to be a Safe whose membership changes without touching this contract). `GOVERNANCE` gets the same treatment: immutable, set once at construction, changeable only by shipping a new Oracle — consistent with how `ARBITRATOR` already behaves, and simplest given neither role has today asked for in-place rotation. Nothing requires the two addresses to differ; a deployment that starts with one Safe holding both roles degrades to today's single-role behavior, which is a safe default rather than a hazard.

**Reuse the existing schedule/apply/`GOVERNANCE_DELAY` pattern (`BondConfig`) rather than generalizing it.** `BondConfig` (`contracts/src/libraries/BondConfig.sol`) is a small, single-purpose library: `schedule` records a pending value and an activation block, `applyPending` flips it over once due, `currentMultiplier` reads through to the pending value once it is due. The fee amount and the DAO fee share need the same three-step shape over a plain `uint256`; the protocol funds receiver needs it over an `address`. Two small new libraries are added — `DelayedUint256` (reused for the fee amount and the DAO fee share, each validated against its own bounds by the caller) and `DelayedAddress` (the protocol funds receiver) — rather than per-parameter copy-pasted structs. This is not a rename of `BondConfig`: it is left in place for the bond multiplier and extended (not replaced) for bond slashing, below. Both new libraries follow `BondConfig`'s exact shape (an `init`, a `schedule`, an `applyPending`, a `current*` reader, its own events and errors) so a reviewer already familiar with `BondConfig` recognizes the pattern immediately.

**Bond slashing is a multiplier bundled into the same config as the bond multiplier, not an independent basis-point fraction.** A losing sentinel's bond is `bondTarget = fee * bondMultiplier` (`SentinelOracle.sol:123`), fixed per-request at creation. Expressing the slash as a second multiplier — `slashingMultiplier`, with the slashed amount per losing sentinel being `fee * slashingMultiplier` — needs no division anywhere (unlike a basis-point fraction of `bondTarget`, which would). The invariant the table asks for ("minimum enough to repay the user fee ... maximum the full bond") becomes exactly `1 <= slashingMultiplier <= bondMultiplier`: at `1`, the slash is `fee`, i.e. exactly what covers the proposer's refund; at `bondMultiplier`, the slash is the whole bond. `BondConfig` is extended with `slashingMultiplier`/`pendingSlashingMultiplier` alongside `bondMultiplier`/`pendingBondMultiplier`, scheduled and applied **together**, in one call, with the invariant checked at schedule time against the *new* bond multiplier being scheduled in the same call. Bundling the two into one atomic step is what makes the invariant hold unconditionally rather than needing to be re-checked against whatever the other, independently-timed parameter happens to be: since every historical "current" pair satisfied the invariant when it became current, and both are snapshotted onto a request together at creation (`slashAmount = fee * slashingMultiplier`, alongside `bondTarget = fee * bondMultiplier`), the invariant `slashAmount <= bondTarget` holds for that request for its entire lifetime, however governance moves either multiplier afterward.

**The one snapshotted `slashAmount` governs both of today's slashing cases, per team direction.** `SentinelOracleRequest` already has two places that forfeit a committer's bond: `resolveDispute` slashes the losing side of an arbitrated dispute (`SentinelOracleRequests.sol:150-154`), and `finalize`'s `unrevealedBond` computation forfeits the *entire* bond of anyone who committed but never revealed once an established side exists (`SentinelOracleRequests.sol:100-103`, "regardless of which side won"). The table's Bond Slashing Amount row only mentions arbitration by name, but the team's direction is to unify both under the one governed parameter rather than leave the second one a permanent, unconfigurable 100% — so `unrevealedBond` becomes `(committedCount - revealedCount) * req.slashAmount` instead of `* req.bondTarget`.

**Unifying the two slashing cases means a never-revealed committer can now reclaim the unslashed remainder of their bond, so `claim()`'s all-or-nothing revealed-vote gate is removed.** Today `claim()` reverts outright for a `PENDING` (never-revealed) vote unless the request timed out (`NotRevealed()`, `SentinelOracle.sol:192-197`), because their whole bond is already gone via the `unrevealedBond` transfer in `finalize`. Once that forfeiture is only `req.slashAmount` rather than the full bond, the remaining `bondTarget - slashAmount` has nowhere else to go and must be claimable, or it is permanently stuck — there is no other function that could release it. `commitment.markClaimed()` (`SentinelOracleCommitments.sol:38-42`) already reverts on a second claim and on `bondAmount == 0` (never committed at all), so removing the vote-based gate does not open any new double-claim or free-money path: it simply lets every committer, once their request is resolved, call `claim()` and receive `bondAmount - slashAmountFor(vote)`, where `slashAmountFor` returns `0` for a winning or timed-out vote and `req.slashAmount` for a losing or never-revealed one, replacing the current boolean `isBondSlashed`.

**The DAO fee share denominator is 100,000, not the usual 10,000 basis points.** A fee share expressed in basis points (hundredths of a percent) cannot represent, say, 0.01% without rounding to zero. Parts-per-100,000 (thousandths of a percent) gives the DAO fee share ten times the precision at the low end, which matters here because 0% and small non-zero shares are both realistic starting points per the table ("a 0% DAO share means 100% goes to Sentinels"). The same unit is used nowhere else in this contract, so there is no existing basis-point convention this displaces.

**In the arbitration path, the DAO's cut comes only out of the winning sentinels' fee-equivalent reward, not the proposer's refund — per team direction.** `resolveDispute` today refunds the proposer's full `fee` (`refundFee = req.fee`, `SentinelOracle.sol:217-218`) *and* pays the winning side an equal amount via `calcFeeReward` (funded from the slashed losing bonds beyond what covers that refund — the two amounts happen to be equal, which is existing, unmodified behavior; see `SentinelOracleRequests.sol:125-134`). `refundFee` is captured before the DAO cut is applied, so the proposer keeps getting the whole fee back exactly as today when a dispute goes to arbitration, and `req.fee` is reduced by `daoCut` only afterward — in storage, for `calcFeeReward` to read when the winning sentinels later call `claim()`. This mirrors `finalize`'s direct-resolution path exactly (there, there is no refund concept at all: the fee is reduced by `daoCut` in storage before any `calcFeeReward` call, full stop), so the same `req.fee -= daoCut` line does the job in both places; only `resolveDispute` additionally has a pre-cut `refundFee` to protect.

**The realized bond slash needs no runtime clamping.** An earlier draft of this plan clamped the *realized* slash amount at `resolveDispute` time to sit between the fee refund and the full bond, to guard against a governance change moving the nominal slashing fraction out of bounds for a request already in flight. Bundling `slashingMultiplier` with `bondMultiplier` and snapshotting both onto the request at creation (as `slashAmount`/`bondTarget`) removes the need for that: the bound is enforced once, at schedule time, and preserved by the snapshot for the rest of the request's life. `resolveDispute` simply reads `req.slashAmount` per losing sentinel with no further arithmetic.

**The DAO fee share is snapshotted onto the request at creation, exactly like `fee` and `bondTarget` already are.** `postRequest` already fixes `fee` and `bondTarget` for the lifetime of a request (`SentinelOracle.sol:122-126`) so that a later governance change cannot retroactively alter a request already in flight. `daoFeeShare` gets the same treatment for the same reason: `calcFeeReward` (`SentinelOracleRequests.sol:125-134`) is a view over already-resolved, already-snapshotted state, and must not depend on whatever the *current* governed value happens to be when a sentinel calls `claim()`, which can be long after resolution.

**The DAO's cut is pushed at the moment a request resolves, not accumulated for a later sweep.** `finalize()` already pushes funds out immediately in the branches that know a definitive outcome (the `unrevealedBond` slash to `ARBITRATOR`, `SentinelOracle.sol:165-167`; the fee refund on timeout, `SentinelOracle.sol:182`). The DAO cut is computed and transferred to the protocol funds receiver in the same place — the two `finalize()` branches that resolve to `RESOLVED_APPROVED`/`RESOLVED_DENIED`, and `resolveDispute` — immediately after the outcome is known, rather than adding a pull-based sweep function nobody asked for.

**`CHARTER_ENS_NODE` is a passive `bytes32`, not an on-chain ENS resolution.** The table's Charter reference row is explicit that "the Oracle contract contains the immutable ENS name, not a specific Charter version" — the contract records which name to resolve, off-chain, elsewhere. An immutable cannot hold a dynamically-sized `string`, and the idiomatic value for referencing an ENS name on-chain is its namehash (EIP-137), so the constructor takes `bytes32 charterEnsNode` (the caller passes `namehash("safenet-charter.safe.eth")`). Nothing in this contract resolves it; it exists so a validator, the explorer, or any other consumer can read the canonical Charter reference straight off the Oracle it is trusting.

**Arbitration timeout reuses the existing `TIMED_OUT` machinery instead of inventing a new outcome.** `SentinelOracleRequest.State.TIMED_OUT` already means "no established side, everyone gets their money back in full": `finalize()`'s no-reveal branch refunds the fee to the proposer and zeroes it (`SentinelOracleRequests.sol:104-111`), and `claim()`'s bond-return logic already returns the full bond unconditionally for `TIMED_OUT` (`SentinelOracleRequests.sol:138`), so every committed bond comes back whole through the existing claim path. A `FROZEN` request that outlives `ARBITRATION_TIMEOUT` is moved to that same state by a new permissionless `timeoutArbitration(bytes32 requestId)`, rather than a bespoke fifth outcome — it *is* the timeout case the request asked for ("as in all other timeout cases").

**A sentinel must claim after a resolved dispute regardless of which side it was on.** `crates/sentinel/src/service.rs:482-520` (`handle_resolved`) currently claims "iff our own revealed vote matches the arbitrator's outcome" and otherwise "drops the request either way" (see the comment at `:482-485` and the test `flow_dispute_drops_without_claim_when_arbitration_contradicts_our_vote`, `:1300`) — correct today, because a losing vote's bond is entirely forfeited, so there is nothing to claim. Once bond slashing is partial (Phase 5), a losing sentinel still has `commitment.bondAmount - req.slashAmount` to reclaim, and `claim()` can only be called by the sentinel itself (it reads `$commitments.get(requestId, msg.sender)`), so a client that stops claiming on a losing vote leaves that remainder permanently unclaimed. `handle_resolved` needs to submit `Claim` unconditionally once a dispute resolves, not only when `approved == approve`.

### Alternatives Considered

- **Express the bond slashing amount as a basis-point fraction of the bond, like the DAO fee share.** Rejected per direction: it requires a division per losing sentinel per resolution (`bondTarget * bps / DENOMINATOR`) and reintroduces the cross-parameter bound problem this plan works around — a fraction is safe only relative to whatever `bondMultiplier` happened to apply when the request was created, which is exactly the coupling the multiplier-bundling approach avoids by construction.
- **Fold `BondConfig` into the new generic `DelayedUint256` library instead of extending it in place for bond slashing.** Considered, but bond slashing's defining property is that it is validated *jointly* with the bond multiplier (`1 <= slashingMultiplier <= bondMultiplier`), which a single-value generic config cannot express — two independent `DelayedUint256` instances would let the two multipliers apply at different times and momentarily violate the invariant. Extending `BondConfig` itself, so both multipliers share one pending slot and one activation block, is the only way to keep the update atomic.
- **Deduct the DAO cut from the proposer's arbitration refund too, treating "the fee" as one pot the DAO always takes its share of first.** Rejected per team direction: the proposer's refund is a distinct guarantee ("your fee comes back if this ends up disputed") from the fee-equivalent reward paid to winning sentinels (which is a genuinely new payment funded by the losing side's slashed bonds), and only the latter is reduced by the DAO's cut.
- **Keep the unrevealed-vote griefing forfeiture at a fixed 100%, independent of the governed bond-slashing multiplier.** Rejected per team direction in favor of unifying both slashing cases (arbitration-losing-side and unrevealed-vote griefing) under the one governed parameter, which in turn means opening up `claim()` so the non-slashed remainder is not permanently stuck.
- **Let `ARBITRATOR` keep administering governance parameters, and only add the new parameters under it.** Rejected: it does not match the table, which names the SafeDAO (via the AMB) as the controller of the Sentinel set, fee, DAO fee share, bond slashing amount, and protocol funds receiver, and names the Arbitrator Safe as a separately-governed party whose only lever on this contract is `resolveDispute`. Keeping them merged would also mean a single compromised or unavailable arbitrator blocks both dispute resolution and parameter governance. Symmetrically, routing `resolveDispute` through `GOVERNANCE` as well was rejected: the table treats dispute resolution as strictly the Arbitrator Safe's job, so it stays on `onlyArbitrator`.
- **Make `GOVERNANCE` (and/or `ARBITRATOR`) a mutable, self-rotatable address instead of immutable.** Rejected: the table treats both as immutable-within-a-deployment concerns (`ARBITRATOR` explicitly so; `GOVERNANCE` by analogy, since it is likewise the AMB-executor address representing the DAO on this chain). Adding rotation is a bigger trust-model change than this epic's scope and is not requested.
- **Let governance sweep the DAO's fee cut and slashed bonds later via a pull function, mirroring a typical fee-pot design.** Rejected: `finalize()` and `resolveDispute` already push funds synchronously to known destinations (`ARBITRATOR`, the proposer) the instant an outcome is known; adding a second, pull-based accounting path for the same class of funds is an unrequested extra mechanism with its own bookkeeping (a running balance, a `sweep()` function, reentrancy considerations) for no stated benefit.

## Tech Specs

### New/extended libraries

- `contracts/src/libraries/DelayedUint256.sol` (new): `T { uint256 value; uint256 pendingValue; uint256 pendingActiveAt; }`, `init`, `schedule(self, newValue, governanceDelay)`, `applyPending(self)`, `current(self) view returns (uint256)` — same shape as `BondConfig`, minus the multiplier-specific naming. Reused for `REQUEST_FEE` and `daoFeeShare`; each caller validates its own bounds (`newValue > 0` for the fee; `newValue <= FEE_SHARE_DENOMINATOR` for the DAO fee share) before calling `schedule`.
- `contracts/src/libraries/DelayedAddress.sol` (new): same shape, `address` instead of `uint256`, `newValue != address(0)` validated by the caller. Used for the protocol funds receiver.
- `contracts/src/libraries/BondConfig.sol` (extended, Phase 5 only): `T` gains `slashingMultiplier`/`pendingSlashingMultiplier` (sharing the existing `pendingBondMultiplierActiveAt` slot — renamed `pendingActiveAt` since it now gates both). `init` takes both `initialMultiplier` and `initialSlashingMultiplier` and validates the invariant below. `schedule` becomes `schedule(self, newBondMultiplier, newSlashingMultiplier, governanceDelay)`, validating `newBondMultiplier > 0`, `newSlashingMultiplier >= 1`, and `newSlashingMultiplier <= newBondMultiplier` together; `applyPending`/`currentMultiplier` gain `currentSlashingMultiplier`; events (`BondMultiplierScheduled`/`Applied`) gain the slashing multiplier as a second value and are renamed `BondConfigScheduled`/`BondConfigApplied`.

### `SentinelOracle.sol`

- **New immutables**: `address public immutable GOVERNANCE`; `bytes32 public immutable CHARTER_ENS_NODE`; `uint256 public immutable ARBITRATION_TIMEOUT`. `REQUEST_FEE` (`:40`) is removed as an immutable.
- **New storage**: `DelayedUint256.T private $feeConfig`, `DelayedUint256.T private $daoFeeShareConfig`, `DelayedAddress.T private $protocolFundsReceiverConfig`, alongside the existing (extended) `$bondConfig` (`:50`).
- **New constant**: `uint256 public constant FEE_SHARE_DENOMINATOR = 100_000`.
- **Constructor** (`:90-114`): gains `governance`, `protocolFundsReceiver`, `charterEnsNode`, `arbitrationTimeout`, `initialDaoFeeShare`, `initialSlashingMultiplier` params, validates and initializes the new/extended configs (`$bondConfig.init` now takes both `initialMultiplier` and `initialSlashingMultiplier`, validated jointly), and stores the new immutables. `governanceDelay` can be `0` in tests/devnet exactly as today.
- **`onlyGovernance` modifier**, mirroring `onlyArbitrator` (`:79-82`): `require(msg.sender == GOVERNANCE, NotGovernance())`.
- **`postRequest`** (`:120-128`): reads `fee = $feeConfig.current()` instead of the immutable `REQUEST_FEE`, and snapshots onto the request, alongside `fee`/`bondTarget`: `daoFeeShare = $daoFeeShareConfig.current()` and `slashAmount = fee * $bondConfig.currentSlashingMultiplier()`. `SentinelOracleRequestMap.create` gains `daoFeeShare`/`slashAmount` parameters and the `Request` struct (`SentinelOracleRequests.sol:30-41`) gains matching `uint256` fields.
- **`finalize`** (`:160-185`):
  - The `unrevealedBond` computation (`SentinelOracleRequests.sol:100-103`) becomes `(self.committedCount - self.revealedCount) * self.slashAmount` instead of `* self.bondTarget` — griefers now forfeit only the governed slash amount, not their whole bond.
  - In the `RESOLVED_APPROVED`/`RESOLVED_DENIED` branches, computes `daoCut = req.fee * req.daoFeeShare / FEE_SHARE_DENOMINATOR`, transfers it to `$protocolFundsReceiverConfig.current()`, and reduces `req.fee` in storage by `daoCut` before emitting — so the existing `calcFeeReward` (which divides `self.fee` by the winning-side count) automatically distributes only the post-cut remainder, with no change to `calcFeeReward` itself.
  - The `unrevealedBond` transfer (`:166`) moves from `ARBITRATOR` to `$protocolFundsReceiverConfig.current()`.
- **`resolveDispute`** (`:212-222`):
  - `slashed = losingSideCount * req.slashAmount` (no division). Because `slashAmount <= bondTarget` holds by construction (Architecture Decision), `slashed <= losingSideCount * bondTarget`, so no transfer here can underflow.
  - `refundFee` is captured from `req.fee` *before* any DAO-cut mutation and transferred to the proposer in full, unaffected by the DAO's cut (per team direction — see Architecture Decision). Only afterward is `daoCut = req.fee * req.daoFeeShare / FEE_SHARE_DENOMINATOR` computed and `req.fee` reduced by it in storage, so the later `calcFeeReward` the winning side reads from `claim()` reflects the cut.
  - The arbitration-side remainder (`slashed - refundFee`, today going to `ARBITRATOR`, `:219`) and `daoCut` both go to `$protocolFundsReceiverConfig.current()` — combined into a single transfer since they share a destination.
- **`claim`** (`:187-206`): the `NotRevealed()` require (`:192-197`) is deleted — `commitment.markClaimed()` (`SentinelOracleCommitments.sol:38-42`) already reverts for a never-committed caller (`bondAmount == 0`) or a repeat claim, so no new footgun is introduced by letting every resolved-request committer through. The current all-or-nothing `bondReturn = req.isBondSlashed(vote) ? 0 : commitment.bondAmount` (`:200`) is replaced by `bondReturn = commitment.bondAmount - req.slashAmountFor(vote)`, where `slashAmountFor` (replacing the boolean `isBondSlashed`) returns `0` for a winning or `TIMED_OUT` vote and `req.slashAmount` for a losing-side revealer or a never-revealed vote in a resolved, non-timed-out request — the same conditions `isBondSlashed` checks today, just returning an amount instead of a bool.
- **`timeoutArbitration(bytes32 requestId)`** (new, permissionless, mirrors `finalize`'s shape): requires `req.state == FROZEN` and `block.number > req.arbitrationDeadline`; transitions to `TIMED_OUT` via a new `SentinelOracleRequest.timeoutArbitration` library function (refund fee, zero it, exactly like the existing no-reveal `TIMED_OUT` branch, `SentinelOracleRequests.sol:104-111`); emits `OracleResult` with a new `ResolveReason.ARBITRATION_TIMEOUT`. `SentinelOracleRequest.Request` gains `uint256 arbitrationDeadline`, set to `block.number + ARBITRATION_TIMEOUT` at the point `finalize()`'s existing logic decides the outcome is `FROZEN` (`SentinelOracleRequests.sol:92-94`).
- **Governance functions** (`:228-242`): `addSentinel`, `removeSentinel` switch from `onlyArbitrator` to `onlyGovernance`; `scheduleBondMultiplier`/`applyBondMultiplier` become `scheduleBondConfig(uint256 newBondMultiplier, uint256 newSlashingMultiplier)`/`applyBondConfig()`, also `onlyGovernance`. New `onlyGovernance` pairs: `scheduleFee`/`applyFee`, `scheduleDaoFeeShare`/`applyDaoFeeShare`, `scheduleProtocolFundsReceiver`/`applyProtocolFundsReceiver` — each a thin wrapper over the corresponding `Delayed*` library call.
- **View functions** (`:248-262`): add `fee()`/`pendingFee()`/`pendingFeeActiveAt()`, `daoFeeShare()`/`pendingDaoFeeShare()`/`pendingDaoFeeShareActiveAt()`, `protocolFundsReceiver()`/`pendingProtocolFundsReceiver()`/`pendingProtocolFundsReceiverActiveAt()`, and `slashingMultiplier()`/`pendingSlashingMultiplier()` (sharing `pendingBondMultiplierActiveAt`'s renamed successor with the bond multiplier).
- **New errors**: `NotGovernance()`, `InvalidFeeShare()`, `InvalidSlashingMultiplier()`, plus the `Delayed*` library errors (`InvalidValue()`, `ValueNotReady()`, analogous to `BondConfig`'s existing `InvalidMultiplier`/`MultiplierNotReady`). **Removed error**: `NotRevealed()` (`:71`), now unused.

### Deploy script and devnet wiring

`contracts/script/DeploySentinelOracle.s.sol` and `scripts/run_devnet.sh`/`scripts/run_sentinel_integration_test.sh` each gain the new constructor args as their own env vars (`SENTINEL_GOVERNANCE`, `SENTINEL_PROTOCOL_FUNDS_RECEIVER`, `SENTINEL_CHARTER_ENS_NODE`, `SENTINEL_ARBITRATION_TIMEOUT`, `SENTINEL_INITIAL_DAO_FEE_SHARE`, `SENTINEL_INITIAL_SLASHING_MULTIPLIER`), updated in the same PR as the constructor change that introduces each — otherwise `forge build`/the devnet script breaks immediately, so this cannot be deferred to a later "docs" phase. `docs/devnet.md`'s references to `SENTINEL_REQUEST_FEE` as a fixed default (`:149`) get a note that the fee is now governed and this is only its *initial* value.

### `crates/sentinel`

- `crates/sentinel/src/service.rs` `handle_resolved` (`:486-520`): drop the `approved == approve` branch that decides whether to claim; always emit `SentinelActionKind::Claim { id: event.requestId }` after a dispute resolves (the contract-side `claim()` already pays `0` extra when the caller's vote lost outright under `slashingMultiplier == bondMultiplier`, so this is safe even at the maximum slashing setting). Update the doc comment at `:482-485` and rename/rewrite the test at `:1300` (`flow_dispute_drops_without_claim_when_arbitration_contradicts_our_vote`) to assert a claim is still submitted, and extend `:1280`'s companion test (`flow_dispute_claims_when_arbitration_matches_our_vote`) or add a new one asserting the *partial* bond return actually reconciles against a non-1.0 slashing multiplier once the integration script exercises one.
- `scripts/run_sentinel_integration_test.sh`: exercise a losing vote under a partial slashing multiplier (i.e. `slashingMultiplier < bondMultiplier`) and assert both sentinels' balances reconcile including the losing sentinel's partial bond return — this is the test coverage that catches a client/contract mismatch here, per the team's expectation that the sentinel-side fix is covered by integration tests rather than needing its own exhaustive unit-level spec in this plan.

### Tests
